# GSoC 2027 Project Ideas
{: .fs-9 }

Seventeen project ideas from the LLM4S Foundation for [Google Summer of Code 2027](https://summerofcode.withgoogle.com/): a large and a medium idea for each of seven projects built on LLM4S, and a large idea each for TermFlow, GraphStore and Forge.
{: .fs-6 .fw-300 }

This page follows the format of our earlier ideas lists ([2025](https://github.com/llm4s/llm4s/blob/main/Google%20Summer%20of%20Code/Project%20Ideas/2025.md), [2026](https://github.com/llm4s/llm4s/blob/main/Google%20Summer%20of%20Code/Project%20Ideas/2026.md)). Every idea builds on a real codebase, names the gap it closes, and has two or three mentors who created or contribute to that project or belong to the LLM4S core team.

{: .note }
> **Draft.** The mentors listed below have been proposed and must confirm before this page is announced. Dates
> follow Google's official GSoC 2027 timeline.

## How to apply

1. **Pick an idea** from the table below and read the project's repository: its README, open issues and roadmap.
2. **Talk to the mentors** on the [LLM4S Discord](https://discord.gg/llm4s), or at the weekly
   [LLM4S Dev Hours](https://luma.com/calendar/cal-Zd9BLb5jbZewxLA), before you write your proposal.
3. **Make a first contribution.** A merged good first issue in the project you apply for (or in
   [LLM4S](https://github.com/llm4s/llm4s/issues?q=is%3Aissue+is%3Aopen+label%3A%22good+first+issue%22)) is the best
   evidence that you can work in the codebase.
4. **Write the proposal** with a week-by-week plan, the deliverables of each idea below, and how you will test them.
   Google's [proposal guide](https://google.github.io/gsocguides/student/writing-a-proposal) explains what a good
   one contains. Read the program [rules](https://summerofcode.withgoogle.com/rules) too.

Our own ideas are welcome: propose them on Discord and find a mentor before you write them up.

### What every project shares

LLM4S is heading for 1.0, and the ideas are designed to follow its rules, so the work lasts beyond the summer:

- **Scala 3** and typed errors: `Result[A]` (`Either[LLMError, A]`) rather than exceptions.
- **Configuration at the edge** through `Llm4sConfig` and named provider sections, never `sys.env` in library code.
- **Providers as modules** (`llm4s-openai`, `llm4s-anthropic`, `llm4s-ollama` and others), chosen by configuration.
- **Tests that need no API key**: `llm4s-testkit`'s scripted client or a recorded fixture, with live calls kept to
  separate smoke tests.
- **Observability** through the LLM4S tracing contract (Langfuse and OpenTelemetry backends).

## Szork

[Szork](https://github.com/llm4s/szork) is a voice-controlled, Zork-style adventure game: an LLM agent acts as the
dungeon master, with speech-to-text, text-to-speech, generated scene images and a Vue web client over WebSockets. It
is LLM4S's showcase of speech, images, tools and agentic gameplay.

### 1. Szork: An MCP-powered game master with NPC agents and durable saves

| | |
|---|---|
| **Project** | [llm4s/szork](https://github.com/llm4s/szork) |
| **Description** | Szork's dungeon master invents everything itself, so lore drifts and puzzles repeat. [Issue #7](https://github.com/llm4s/szork/issues/7) asks for MCP servers that showcase LLM4S's MCP connector. This project builds them in Scala with `llm4s-mcp` (for example a lore server that keeps the world canon-consistent and a puzzle server), connects the game master to them as an MCP client, adds non-player characters as separate agents reached through LLM4S handoffs, and makes saves durable with an LLM4S checkpointer so a game resumes where it stopped. |
| **Expected outcome** | Two or more MCP servers in Scala with tests; the game master using them through `llm4s-mcp`; at least two NPC agents with their own prompts and tools; game state saved through `SqliteCheckpointer` and resumed after a restart; a guardrail for content safety; a short write-up and demo recording. |
| **Skills** | Scala 3, LLM agents and tool calling, MCP, basic web (Vue, WebSockets). |
| **Difficulty** | Hard |
| **Size** | Large, ~350 hours |
| **Mentors** | Kannupriya Kalra ([@kannupriyakalra](https://github.com/kannupriyakalra)), Rory Graves ([@rorygraves](https://github.com/rorygraves)) |

### 2. Szork: Szork on LLM4S 0.5: provider, speech and image modules

| | |
|---|---|
| **Project** | [llm4s/szork](https://github.com/llm4s/szork) |
| **Description** | Szork depends on LLM4S core 0.3.2 and calls its speech, image and model features directly. [Issue #20](https://github.com/llm4s/szork/issues/20) asks for the upgrade to LLM4S 0.5. This project moves Szork onto the 0.5 modules (`llm4s-openai`, `llm4s-anthropic`, `llm4s-speech`, `llm4s-image`), loads providers through `Llm4sConfig` so any configured provider can run the game, covers the game engine with tests that need no API key, and fixes the language-switch bug in [issue #4](https://github.com/llm4s/szork/issues/4). |
| **Expected outcome** | Szork building on published LLM4S 0.5 artifacts; providers chosen by configuration (including a local Ollama model); speech and images through the LLM4S modules; game-engine tests using `llm4s-testkit`; issue #4 fixed with a regression test; an updated README. |
| **Skills** | Scala 3, sbt, LLM APIs; speech and image APIs are a plus. |

| **Size** | Medium, ~175 hours |

## Adk4s

[Adk4s](https://github.com/gruggiero/Adk4s) is an agent development kit for Scala 3 built on LLM4S and
[workflows4s](https://github.com/business4s/workflows4s), with Cats Effect and fs2: ReAct agents, DAG workflows,
structured outputs, durable agent memory, interrupt and resume, and an evaluation harness with LLM judges.

### 3. Adk4s: A DSPy-style program compiler: few-shot bootstrapping and instruction optimisation

| | |
|---|---|
| **Project** | [gruggiero/Adk4s](https://github.com/gruggiero/Adk4s) |
| **Description** | Adk4s is porting the ideas of DSPy, where an LLM program is optimised against a metric instead of hand-tuned. Its [operative plan](https://github.com/gruggiero/Adk4s/blob/main/docs/dspy-port-operative-plan.md) has finished phase 0 (the `Optimizable` predictor surface in `adk4s-optimize`) and phase 1 (the `adk4s-eval` harness). This project delivers phase 2, the compiler MVP: signatures as data, rendering demonstrations into prompts, a `BootstrapFewShot` optimizer and a cache of compiled state; then, as time allows, phase 3's first instruction optimizer. |
| **Expected outcome** | Phase 2 specs implemented with the `OptimizerLaws` checks passing; a compiled program saved and reloaded; an example that measurably improves a task score on a small dataset with `adk4s-eval`; documentation of the optimizer API; a stretch goal of one phase 3 optimizer. |
| **Skills** | Scala 3 (type classes, derivation), Cats Effect, property-based testing; interest in prompt optimisation. |
| **Difficulty** | Hard |
| **Size** | Large, ~350 hours |
| **Mentors** | Giovanni Ruggiero ([@gruggiero](https://github.com/gruggiero)), Iyad M. Issa ([@iyadi](https://github.com/iyadi)), Rory Graves ([@rorygraves](https://github.com/rorygraves)) |

### 4. Adk4s: Adk4s on LLM4S 0.5 with LLM4S tracing

| | |
|---|---|
| **Project** | [gruggiero/Adk4s](https://github.com/gruggiero/Adk4s) |
| **Description** | Adk4s builds on LLM4S 0.3.4. Since then LLM4S has split providers into modules, made its data types growth-safe and defined a tracing contract with Langfuse and OpenTelemetry backends. This project upgrades Adk4s to LLM4S 0.5, loads providers through `Llm4sConfig`, and bridges Adk4s's `AgentEvent` stream to LLM4S tracing, so an Adk4s agent run shows up in Langfuse or an OpenTelemetry collector with its model calls, tool calls and token usage. |
| **Expected outcome** | Adk4s compiling and passing its tests on LLM4S 0.5; provider selection by configuration; an `AgentEvent`-to-tracing bridge with tests; an example traced end to end; a migration note in the Adk4s docs. |
| **Skills** | Scala 3, Cats Effect and fs2, sbt; tracing (OpenTelemetry or Langfuse) is a plus. |
| **Difficulty** | Medium |
| **Size** | Medium, ~175 hours |
| **Mentors** | Giovanni Ruggiero ([@gruggiero](https://github.com/gruggiero)), Kannupriya Kalra ([@kannupriyakalra](https://github.com/kannupriyakalra)) |

## toon4s

[toon4s](https://github.com/com-vitthalmirji/toon4s) is the Scala implementation of
[Token-Oriented Object Notation (TOON)](https://github.com/toon-format/spec), a compact, JSON-compatible format that
cuts the tokens structured data costs in an LLM prompt. It has a pure functional core, a CLI, JMH benchmarks and a
Spark integration.

### 7. toon4s: toon4s on Scala.js and Scala Native: a native CLI and a browser playground

| | |
|---|---|
| **Project** | [com-vitthalmirji/toon4s](https://github.com/com-vitthalmirji/toon4s) |
| **Description** | toon4s runs on the JVM only. Three open issues ask for more: cross-compiling for Scala.js and Scala Native ([#6](https://github.com/com-vitthalmirji/toon4s/issues/6)), a console tool built as a native binary ([#7](https://github.com/com-vitthalmirji/toon4s/issues/7)) and a web playground on Scala.js ([#8](https://github.com/com-vitthalmirji/toon4s/issues/8)). This project cross-builds the dependency-free core, publishes the new platforms, ships a native CLI, and builds a playground that converts JSON to TOON in the browser and shows the token savings. |
| **Expected outcome** | `toon4s-core` published for JVM, Scala.js and Scala Native with the shared test suite passing on each; a native CLI binary built in CI for Linux and macOS; a static playground page deployed with the docs; benchmarks comparing the platforms. |
| **Skills** | Scala 3, sbt cross-building; Scala.js or Scala Native experience is a plus. |
| **Difficulty** | Hard |
| **Size** | Large, ~350 hours |
| **Mentors** | Vitthal Mirji ([@vim89](https://github.com/vim89)), Atul S. Khot ([@atulkhot](https://github.com/atulkhot)), Kannupriya Kalra ([@kannupriyakalra](https://github.com/kannupriyakalra)) |

### 8. toon4s: toon4s-llm4s: TOON tool results and RAG context for LLM4S, with measured savings

| | |
|---|---|
| **Project** | [com-vitthalmirji/toon4s](https://github.com/com-vitthalmirji/toon4s) |
| **Description** | The 2026 ideas list proposed TOON-encoded input and output for LLM4S; it has not been built. This project adds a `toon4s-llm4s` module to the toon4s repository (as the Spark integration is, so LLM4S core gains no dependency): encoders that render tool results and retrieved RAG context as TOON, a tool that converts JSON to TOON, and a benchmark that measures the saving with LLM4S's tokenizer and checks that answers stay correct. |
| **Expected outcome** | A published `toon4s-llm4s` module; round-trip property tests; a benchmark report of tokens saved on realistic tool and RAG payloads, with answer quality compared against JSON; an LLM4S agent sample using it; documentation of when TOON helps and when it does not. |

## LLM4S

[LLM4S](https://github.com/llm4s/llm4s) is the AI framework for Scala: a provider-agnostic client, an agent runtime
with tools, guardrails, handoffs and memory, RAG, and tracing, published as modules on a small core.

### 13. LLM4S: Typed AI services for Scala 3

| | |
|---|---|
| **Project** | [llm4s/llm4s](https://github.com/llm4s/llm4s) |
| **Description** | Calling a model in LLM4S means building a `Conversation`, options and a parser at every call site. Other JVM frameworks let a developer declare a typed interface and get an implementation backed by an LLM. [Issue #1474](https://github.com/llm4s/llm4s/issues/1474) asks for the Scala 3 answer, which need not be a JVM proxy: type classes, `derives` and inline functions are candidates. This project writes the design, compares at least three approaches on classification, extraction and a tool-using task, and builds the recommended one as an experimental module. |
| **Expected outcome** | A design document in `docs/design/` with a maintainer-reviewed recommendation; a prototype of each approach tested against `llm4s-testkit`; an `@Experimental` module with the chosen approach, its tests (meeting the repository's coverage floor) and a user guide. |
| **Skills** | Scala 3 metaprogramming (inline, `derives`, macros), API design, functional programming. |
| **Difficulty** | Hard |
| **Size** | Large, ~350 hours |
| **Mentors** | Rory Graves ([@rorygraves](https://github.com/rorygraves)), Kannupriya Kalra ([@kannupriyakalra](https://github.com/kannupriyakalra)), Vitthal Mirji ([@vim89](https://github.com/vim89)) |

### 14. LLM4S: LLM4S as a GraalVM native image

| | |
|---|---|
| **Project** | [llm4s/llm4s](https://github.com/llm4s/llm4s) |
| **Description** | Platform teams building fast-starting services and serverless functions compile to GraalVM native images; nothing in LLM4S supports or tests that today. [Issue #1463](https://github.com/llm4s/llm4s/issues/1463) lists what a native build must handle: providers and tracing backends found through `ServiceLoader`, `reference.conf` resources merged across jars, and vendor SDKs that use reflection. | **Expected outcome** | Reachability metadata under `META-INF/native-image` for core and the viable provider modules; a sample compiled to a native image in a CI job or documented script; `docs/guide/graalvm-native-image.md` stating what is supported and what is not. |

## TermFlow

[TermFlow](https://github.com/llm4s/termflow) is a functional terminal UI framework for Scala 3, published as
`org.llm4s:termflow`. It uses an Elm-style architecture (a pure `update`, a declarative `view`, `Cmd` and `Sub`) and
ships widgets, a testkit and the LLM4S streaming chat client.

### 15. TermFlow: Accessible, faster terminal UIs for LLM apps

| | |
|---|---|
| **Project** | [llm4s/termflow](https://github.com/llm4s/termflow) |
| **Description** | TermFlow draws a character grid, so a screen reader sees only cells and the renderer repaints more than it needs to when a model streams tokens into a long transcript. Its tracker already names the pieces: a semantic model layer of roles, labels and state ([termflow#136](https://github.com/llm4s/termflow/issues/136)), an opt-in linear renderer for screen readers ([termflow#137](https://github.com/llm4s/termflow/issues/137)), cell-level damage-region rendering ([termflow#128](https://github.com/llm4s/termflow/issues/128)) and configurable frame-rate coalescing ([termflow#129](https://github.com/llm4s/termflow/issues/129)). This project builds them, then proves them on the LLM4S chat client and an agent UI that shows tool calls and approvals as they stream. |
| **Expected outcome** | Widgets that expose roles and labels; a linear renderer selectable at start-up; damage-region rendering with a benchmark of bytes written and frame time on a streamed transcript before and after; frame-rate settings; testkit snapshot tests for each; a performance guide and an accessibility guide on the TermFlow docs site. |
| **Skills** | Scala 3, functional programming, terminal and ANSI rendering, accessibility, benchmarking. |
| **Difficulty** | Hard |
| **Size** | Large, ~350 hours |
| **Mentors** | Iyad M. Issa ([@iyadi](https://github.com/iyadi)), Rory Graves ([@rorygraves](https://github.com/rorygraves)), Kannupriya Kalra ([@kannupriyakalra](https://github.com/kannupriyakalra)) |

## GraphStore

[GraphStore](https://github.com/gruggiero/graphStore) is a temporally-aware knowledge graph for AI agent memory, a Scala
3 take on Graphiti's ideas on the Typelevel stack: episodic ingestion, bi-temporal edges, contradiction-driven
invalidation, and hybrid BM25 and embedding retrieval over Neo4j. It is wired into Adk4s as durable agent memory.

### 16. GraphStore: Temporal knowledge-graph memory for LLM4S agents

| | |
|---|---|
| **Project** | [gruggiero/graphStore](https://github.com/gruggiero/graphStore) |
| **Description** | LLM4S agents remember through `llm4s-memory` and `llm4s-agent-memory`, which store facts but not when they were true or what replaced them. GraphStore keeps exactly that, but today only Adk4s agents can use it and its embeddings come from OpenAI alone. This project brings it to LLM4S: an `Embedder` over any LLM4S embedding provider (Ollama included, for local use), extraction through LLM4S structured completion, and a memory store that LLM4S agents use for recall, including point-in-time questions such as "where did the user work in March?". It ends with a measured comparison against the existing LLM4S memory stores on a temporal memory benchmark. |
| **Expected outcome** | A GraphStore module that runs on LLM4S providers; an LLM4S memory integration with the same contract tests as the existing stores; a sample agent whose answers change correctly as facts are superseded; benchmark results (accuracy and latency) published in the repository; a user guide. |
| **Skills** | Scala 3, Typelevel (cats-effect, fs2, http4s), Neo4j and Cypher, embeddings and retrieval, LLM agents. |
| **Difficulty** | Hard |
| **Size** | Large, ~350 hours |
| **Mentors** | Giovanni Ruggiero ([@gruggiero](https://github.com/gruggiero)), Rory Graves ([@rorygraves](https://github.com/rorygraves)), Kannupriya Kalra ([@kannupriyakalra](https://github.com/kannupriyakalra)) |

## Forge

[Forge](https://github.com/rorygraves/forge) is a Scala meta-orchestrator above the Claude Code and Codex CLIs. It takes
a feature request through design, piece-by-piece implementation, a pull request and merge, with independent review
and a human in the loop, coordinated by a finite-state machine and Git so one person can supervise many features.

### 17. Forge: An LLM4S agent connector and reactive PR review

| | |
|---|---|
| **Project** | [rorygraves/forge](https://github.com/rorygraves/forge) |
| **Description** | Forge drives its coding and reviewing agents through a `Connector` trait with two implementations, one per vendor CLI, so every role needs one of those CLIs and its subscription. An LLM4S-backed connector would let any role run on any LLM4S provider, including a local model through Ollama, with token usage and cost from LLM4S, and make true cross-model review a configuration choice. The project then builds the first capability of Forge's Phase 5 roadmap: reactive PR review, which watches a repository for pull requests Forge did not open and reviews them with that same reviewer role. |
| **Expected outcome** | An LLM4S connector passing Forge's connector test suites, with the streaming, question and resume behaviour the existing connectors have; configuration that assigns a provider and model per role; reactive PR review for GitHub with posted review comments and a cost report; documentation and an end-to-end demonstration on a real repository. |
| **Skills** | Scala 3, cats-effect, LLM agents and tool calling, Git and the GitHub API, state machines. |
| **Difficulty** | Hard |
| **Size** | Large, ~350 hours |
| **Mentors** | Rory Graves ([@rorygraves](https://github.com/rorygraves)), Kannupriya Kalra ([@kannupriyakalra](https://github.com/kannupriyakalra)) |
