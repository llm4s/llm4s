# GSoC 2027 Project Ideas
{: .fs-9 }

Nineteen project ideas from the LLM4S Foundation for [Google Summer of Code 2027](https://summerofcode.withgoogle.com/): four for LLM4S itself, a large and a medium idea for each of six projects built on it, and a large idea each for TermFlow, GraphStore and Forge.
{: .fs-6 .fw-300 }

This page follows the format of our earlier ideas lists ([2025](https://github.com/llm4s/llm4s/blob/main/Google%20Summer%20of%20Code/Project%20Ideas/2025.md), [2026](https://github.com/llm4s/llm4s/blob/main/Google%20Summer%20of%20Code/Project%20Ideas/2026.md)). Every idea builds on a real codebase, names the gap it closes, and has two or three mentors who created or contribute to that project or belong to the LLM4S core team.

{: .note }
> **Draft.** The mentors listed below have been proposed and must confirm before this page is announced. Dates
> follow Google's official GSoC 2027 timeline.

## How to apply

1. **Pick an idea** from the table below and read the project's repository: its README, open issues and roadmap.
2. **Talk to the mentors** on the [LLM4S Discord](https://discord.gg/llm4s), or at the weekly
   [LLM4S Dev Hours](https://luma.com/calendar/cal-Zd9BLb5jbZewxLA), before you write your proposal.
3. **Make a first contribution.** A merged good first issue in the project you apply for (or in
   [LLM4S](https://github.com/llm4s/llm4s/issues?q=is%3Aissue+is%3Aopen+label%3A%22good+first+issue%22)) is the best
   evidence that you can work in the codebase.
4. **Write the proposal** with a week-by-week plan, the deliverables of each idea below, and how you will test them.
   Google's [proposal guide](https://google.github.io/gsocguides/student/writing-a-proposal) explains what a good
   one contains. Read the program [rules](https://summerofcode.withgoogle.com/rules) too.

Our own ideas are welcome: propose them on Discord and find a mentor before you write them up.

### What every project shares

LLM4S is heading for 1.0, and the ideas are designed to follow its rules, so the work lasts beyond the summer:

- **Scala 3** and typed errors: `Result[A]` (`Either[LLMError, A]`) rather than exceptions.
- **Configuration at the edge** through `Llm4sConfig` and named provider sections, never `sys.env` in library code.
- **Providers as modules** (`llm4s-openai`, `llm4s-anthropic`, `llm4s-ollama` and others), chosen by configuration.
- **Tests that need no API key**: `llm4s-testkit`'s scripted client or a recorded fixture, with live calls kept to
  separate smoke tests.
- **Observability** through the LLM4S tracing contract (Langfuse and OpenTelemetry backends).

### AI-assisted development

These projects run in summer 2027, after LLM4S 1.0, and the LLM4S Foundation allows contributors to use AI coding
assistants. The ideas are scoped for that: each asks for more than a 2025 or 2026 idea of the same size would, and
the extra goals at the end of each description are part of the project, not stretch goals.

- **You own every line.** Explain any change you submit, and test it; mentors review design and code as usual.
- **Say how you use AI.** Your proposal describes your workflow and how you check what an assistant produces; a pull
  request notes substantial AI help.
- **Spend the time saved on quality**: tests, documentation, benchmarks and the evaluation each idea asks for.
- Follow each repository's own rules for commits and sign-off, and Google's
  [program rules](https://summerofcode.withgoogle.com/rules).

## LLM4S

[LLM4S](https://github.com/llm4s/llm4s) is the AI framework for Scala: a provider-agnostic client, an agent runtime
with tools, guardrails, handoffs and memory, RAG, and tracing, published as modules on a small core.

### 1. LLM4S: Typed AI services for Scala 3

| | |
|---|---|
| **Project** | [llm4s/llm4s](https://github.com/llm4s/llm4s) |
| **Description** | Calling a model in LLM4S means building a `Conversation`, options and a parser at every call site. Other JVM frameworks let a developer declare a typed interface and get an implementation backed by an LLM. [Issue #1474](https://github.com/llm4s/llm4s/issues/1474) asks for the Scala 3 answer, which need not be a JVM proxy: type classes, `derives` and inline functions are candidates. This project writes the design, compares at least three approaches on classification, extraction and a tool-using task, and builds the recommended one as an experimental module, with streaming, tool calling and structured output, a Java-friendly entry point and the LLM4S samples moved onto it where it makes them simpler. |
| **Expected outcome** | A design document in `docs/design/` with a maintainer-reviewed recommendation; a prototype of each approach tested against `llm4s-testkit`; an `@Experimental` module with the chosen approach covering streaming, tools and structured output, its tests (meeting the repository's coverage floor), a Java entry point, migrated samples and a user guide. |
| **Skills** | Scala 3 metaprogramming (inline, `derives`, macros), API design, functional programming. |
| **Difficulty** | Hard |
| **Size** | Large, ~350 hours |
| **Mentors** | Rory Graves ([@rorygraves](https://github.com/rorygraves)), Kannupriya Kalra ([@kannupriyakalra](https://github.com/kannupriyakalra)), Vitthal Mirji ([@vim89](https://github.com/vim89)) |

### 2. LLM4S: LLM4S as a GraalVM native image

| | |
|---|---|
| **Project** | [llm4s/llm4s](https://github.com/llm4s/llm4s) |
| **Description** | Platform teams building fast-starting services and serverless functions compile to GraalVM native images; nothing in LLM4S supports or tests that today. [Issue #1463](https://github.com/llm4s/llm4s/issues/1463) lists what a native build must handle: providers and tracing backends found through `ServiceLoader`, `reference.conf` resources merged across jars, and vendor SDKs that use reflection. This project builds a minimal LLM4S application as a native image, records what fails, and ships the reachability metadata in each module so users get it for free. It then ships `llm4s-doctor` as a native binary and measures start-up time and memory against the JVM. |
| **Expected outcome** | Reachability metadata under `META-INF/native-image` for core and the viable provider modules; a sample compiled to a native image in a CI job; `llm4s-doctor` released as a native binary; start-up and memory benchmarks; `docs/guide/graalvm-native-image.md` stating what is supported and what is not. |
| **Skills** | Scala 3, JVM internals (class loading, reflection), GraalVM, CI. |
| **Difficulty** | Medium |
| **Size** | Medium, ~175 hours |
| **Mentors** | Rory Graves ([@rorygraves](https://github.com/rorygraves)), Kannupriya Kalra ([@kannupriyakalra](https://github.com/kannupriyakalra)) |

### 3. LLM4S: LLM4S agents on the Agent2Agent (A2A) protocol

| | |
|---|---|
| **Project** | [llm4s/llm4s](https://github.com/llm4s/llm4s) |
| **Description** | Agents built with different frameworks increasingly call each other over [A2A](https://a2a-protocol.org): an agent card says what an agent can do, and tasks run, stream and ask for input over HTTP. LangGraph Platform already serves A2A; LLM4S has none ([issue #2450](https://github.com/llm4s/llm4s/issues/2450)). This project builds an `llm4s-a2a` module that serves any LLM4S agent over A2A, mapping a task to a run, a context to a thread, input-required to a suspended run and cancel to cancellation, with streamed events. It also builds the client side, so a remote A2A agent is a tool or a handoff target inside an LLM4S agent, and covers authentication, multi-tenancy and tracing across agent boundaries. It ends by proving interoperability against agents built with at least two other frameworks. |
| **Expected outcome** | An `@Experimental` `llm4s-a2a` module with server and client, tested against the A2A specification's examples; agent cards generated from an agent's tools and skills; streaming, input-required and cancel round trips; authentication and per-tenant isolation; one trace spanning two agents; an interoperability test suite against two other frameworks in CI; a reference service and a user guide. |
| **Skills** | Scala 3, HTTP and JSON-RPC, streaming (SSE), LLM agents, distributed tracing. |
| **Difficulty** | Hard |
| **Size** | Medium, ~175 hours |
| **Mentors** | Rory Graves ([@rorygraves](https://github.com/rorygraves)), Kannupriya Kalra ([@kannupriyakalra](https://github.com/kannupriyakalra)), Giovanni Ruggiero ([@gruggiero](https://github.com/gruggiero)) |

LLM4S has no batch support ([issue #2337](https://github.com/llm4s/llm4s/issues/2337)), and its Scala 3-only spine cannot run inside the many Spark jobs still on Scala 2.13 ([issue #874](https://github.com/llm4s/llm4s/issues/874), deferred to after 1.0). | **Skills** | Scala 3 and Scala 2.13 cross-building, sbt, Spark or fs2, REST APIs, binary compatibility (MiMa). | <!-- doc-support: ignore -->
| **Difficulty** | Hard |
| **Size** | Medium, ~175 hours |
| **Mentors** | Rory Graves ([@rorygraves](https://github.com/rorygraves)), Kannupriya Kalra ([@kannupriyakalra](https://github.com/kannupriyakalra)), Vitthal Mirji ([@vim89](https://github.com/vim89)) |

## Szork

[Szork](https://github.com/llm4s/szork) is a voice-controlled, Zork-style adventure game: an LLM agent acts as the
dungeon master, with speech-to-text, text-to-speech, generated scene images and a Vue web client over WebSockets. It
is LLM4S's showcase of speech, images, tools and agentic gameplay.

### 5. Szork: An MCP-powered game master with NPC agents and durable saves

| | |
|---|---|
| **Project** | [llm4s/szork](https://github.com/llm4s/szork) |
| **Description** | Szork's dungeon master invents everything itself, so lore drifts and puzzles repeat. [Issue #7](https://github.com/llm4s/szork/issues/7) asks for MCP servers that showcase LLM4S's MCP connector. This project builds them in Scala with `llm4s-mcp` (for example a lore server that keeps the world canon-consistent and a puzzle server), connects the game master to them as an MCP client, adds non-player characters as separate agents reached through LLM4S handoffs, and makes saves durable with an LLM4S checkpointer so a game resumes where it stopped. It then turns Szork into a shared world: several players in one game over WebSockets, and an evaluation suite that replays recorded sessions and scores the game master's consistency with an LLM judge. |
| **Expected outcome** | Two or more MCP servers in Scala with tests; the game master using them through `llm4s-mcp`; at least two NPC agents with their own prompts and tools; game state saved through `SqliteCheckpointer` and resumed after a restart; multiplayer sessions sharing one world; a replay-based consistency evaluation; a guardrail for content safety; a one-command Docker deployment; a write-up and demo recording. |
| **Skills** | Scala 3, LLM agents and tool calling, MCP, basic web (Vue, WebSockets). |
| **Difficulty** | Hard |
| **Size** | Large, ~350 hours |
| **Mentors** | Kannupriya Kalra ([@kannupriyakalra](https://github.com/kannupriyakalra)), Rory Graves ([@rorygraves](https://github.com/rorygraves)) |

### 6. Szork: Szork on LLM4S 1.x: any provider, local-first speech and images, three languages

| | |
|---|---|
| **Project** | [llm4s/szork](https://github.com/llm4s/szork) |
| **Description** | Szork depends on LLM4S core 0.3.2 and calls its speech, image and model features directly. [Issue #20](https://github.com/llm4s/szork/issues/20) asks for the upgrade to current LLM4S. This project moves Szork onto the LLM4S 1.x modules (`llm4s-openai`, `llm4s-anthropic`, `llm4s-speech`, `llm4s-image`), loads providers through `Llm4sConfig` so any configured provider can run the game, covers the game engine with tests that need no API key, and fixes the language-switch bug in [issue #4](https://github.com/llm4s/szork/issues/4). It adds a local-first mode in which the model, speech and images all run without a cloud key, and plays the game in three languages. |
| **Expected outcome** | Szork building on published LLM4S 1.x artifacts; providers chosen by configuration; a documented local-first mode (Ollama plus local speech and images); game-engine tests using `llm4s-testkit` running in CI; issue #4 fixed with a regression test; the game playable in three languages; an updated README. |
| **Skills** | Scala 3, sbt, LLM APIs; speech and image APIs are a plus. |
| **Difficulty** | Medium |
| **Size** | Medium, ~175 hours |
| **Mentors** | Rory Graves ([@rorygraves](https://github.com/rorygraves)), Kannupriya Kalra ([@kannupriyakalra](https://github.com/kannupriyakalra)), Anshuman Awasthi ([@AnshumanAI](https://github.com/AnshumanAI)) |

## Adk4s

[Adk4s](https://github.com/gruggiero/Adk4s) is an agent development kit for Scala 3 built on LLM4S and
[workflows4s](https://github.com/business4s/workflows4s), with Cats Effect and fs2: ReAct agents, DAG workflows,
structured outputs, durable agent memory, interrupt and resume, and an evaluation harness with LLM judges.

### 7. Adk4s: A DSPy-style program compiler: few-shot bootstrapping and instruction optimisation

| | |
|---|---|
| **Project** | [gruggiero/Adk4s](https://github.com/gruggiero/Adk4s) |
| **Description** | Adk4s is porting the ideas of DSPy, where an LLM program is optimised against a metric instead of hand-tuned. Its [operative plan](https://github.com/gruggiero/Adk4s/blob/main/docs/dspy-port-operative-plan.md) has finished phase 0 (the `Optimizable` predictor surface in `adk4s-optimize`) and phase 1 (the `adk4s-eval` harness). This project delivers phase 2, the compiler MVP: signatures as data, rendering demonstrations into prompts, a `BootstrapFewShot` optimizer and a cache of compiled state; then phase 3's instruction optimizers, and applies the compiler to tool-using LLM4S agents, not only single predictors. |
| **Expected outcome** | Phase 2 specs implemented with the `OptimizerLaws` checks passing; a compiled program saved and reloaded; at least one phase 3 instruction optimizer; the compiler applied to a tool-using agent; measured score improvements on two public datasets with `adk4s-eval`; documentation of the optimizer API and a tutorial. |
| **Skills** | Scala 3 (type classes, derivation), Cats Effect, property-based testing; interest in prompt optimisation. |
| **Difficulty** | Hard |
| **Size** | Large, ~350 hours |
| **Mentors** | Giovanni Ruggiero ([@gruggiero](https://github.com/gruggiero)), Iyad M. Issa ([@iyadi](https://github.com/iyadi)), Rory Graves ([@rorygraves](https://github.com/rorygraves)) |

### 8. Adk4s: Adk4s on LLM4S 1.x with tracing and evaluation in Langfuse

| | |
|---|---|
| **Project** | [gruggiero/Adk4s](https://github.com/gruggiero/Adk4s) |
| **Description** | Adk4s builds on LLM4S 0.3.4. Since then LLM4S has split providers into modules, made its data types growth-safe, defined a tracing contract with Langfuse and OpenTelemetry backends and reached 1.0. This project upgrades Adk4s to LLM4S 1.x, loads providers through `Llm4sConfig`, and bridges Adk4s's `AgentEvent` stream to LLM4S tracing, so an Adk4s agent run shows up in Langfuse or an OpenTelemetry collector with its model calls, tool calls and token usage. It also publishes `adk4s-eval` results as Langfuse scores and datasets, so a team can compare agent versions over time. |
| **Expected outcome** | Adk4s compiling and passing its tests on LLM4S 1.x; provider selection by configuration; an `AgentEvent`-to-tracing bridge with tests; evaluation results published as Langfuse scores; every example traced end to end; a migration note in the Adk4s docs. |
| **Skills** | Scala 3, Cats Effect and fs2, sbt; tracing (OpenTelemetry or Langfuse) is a plus. |
| **Difficulty** | Medium |
| **Size** | Medium, ~175 hours |
| **Mentors** | Giovanni Ruggiero ([@gruggiero](https://github.com/gruggiero)), Kannupriya Kalra ([@kannupriyakalra](https://github.com/kannupriyakalra)) |

## RAG in a Box

[RAG in a Box](https://github.com/llm4s/rag_in_a_box) is a turnkey RAG deployment powered by LLM4S: a REST API and
admin UI over PostgreSQL and pgvector, hybrid search, incremental ingestion, built-in connectors, analytics and A/B
experiments for RAG configurations.

### 9. RAG in a Box: On llm4s-rag 1.x: production observability, multi-tenancy and evaluation in CI

| | |
|---|---|
| **Project** | [llm4s/rag_in_a_box](https://github.com/llm4s/rag_in_a_box) |
| **Description** | RAG in a Box depends on LLM4S core 0.2.9; RAG has since moved into its own `llm4s-rag` module with vector stores, reranking and evaluation ([issue #5](https://github.com/llm4s/rag_in_a_box/issues/5)). Its [roadmap](https://github.com/llm4s/rag_in_a_box/blob/main/ROADMAP.md) leaves observability and deployment items open (phase 6): distributed tracing, Grafana dashboards, alerting rules and database migrations. This project moves the server onto `llm4s-rag` 1.x and the provider modules, then delivers those production items with LLM4S's OpenTelemetry tracing and Prometheus metrics. It goes on to what a company needs before a pilot: multi-tenancy with per-tenant access control enforced at retrieval, a RAG evaluation gate in CI that fails a change which lowers answer quality on a golden set, and a Helm chart. |
| **Expected outcome** | The server on LLM4S 1.x with its test suite passing; one trace per query covering retrieval, reranking and generation; Prometheus metrics with a Grafana dashboard and alert rules; schema migrations with Flyway; tenants isolated at retrieval with tests; an evaluation gate in CI; a Helm chart and updated deployment docs. |
| **Skills** | Scala 3, http4s, PostgreSQL; RAG concepts; Docker; observability tooling is a plus. |
| **Difficulty** | Hard |
| **Size** | Large, ~350 hours |
| **Mentors** | Rory Graves ([@rorygraves](https://github.com/rorygraves)), Gopi Trinadh ([@GOPITRINADH3561](https://github.com/GOPITRINADH3561)), Kannupriya Kalra ([@kannupriyakalra](https://github.com/kannupriyakalra)) |

### 10. RAG in a Box: Enterprise connectors: Confluence, Google Drive and a watched directory

| | |

## toon4s

[toon4s](https://github.com/com-vitthalmirji/toon4s) is the Scala implementation of
[Token-Oriented Object Notation (TOON)](https://github.com/toon-format/spec), a compact, JSON-compatible format that
cuts the tokens structured data costs in an LLM prompt. It has a pure functional core, a CLI, JMH benchmarks and a
Spark integration.

### 11. toon4s: toon4s on Scala.js and Scala Native: a native CLI and a browser playground

| | |
|---|---|
| **Project** | [com-vitthalmirji/toon4s](https://github.com/com-vitthalmirji/toon4s) |

## GraphStore

[GraphStore](https://github.com/gruggiero/graphStore) is a temporally-aware knowledge graph for AI agent memory, a Scala
3 take on Graphiti's ideas on the Typelevel stack: episodic ingestion, bi-temporal edges, contradiction-driven
invalidation, and hybrid BM25 and embedding retrieval over Neo4j. It is wired into Adk4s as durable agent memory.

### 18. GraphStore: Temporal knowledge-graph memory for LLM4S agents

| | |
|---|---|
| **Project** | [gruggiero/graphStore](https://github.com/gruggiero/graphStore) |
| **Description** | LLM4S agents remember through `llm4s-memory` and `llm4s-agent-memory`, which store facts but not when they were true or what replaced them. GraphStore keeps exactly that, but today only Adk4s agents can use it and its embeddings come from OpenAI alone. This project brings it to LLM4S: an `Embedder` over any LLM4S embedding provider (Ollama included, for local use), extraction through LLM4S structured completion, and a memory store that LLM4S agents use for recall, including point-in-time questions such as "where did the user work in March?". It also exposes the graph as an MCP server so any MCP client can use it as memory, and ends with a measured comparison against the existing LLM4S memory stores on a public long-term memory benchmark. |
| **Expected outcome** | A GraphStore module that runs on LLM4S providers; an LLM4S memory integration with the same contract tests as the existing stores; an MCP memory server; a sample agent whose answers change correctly as facts are superseded; benchmark results (accuracy and latency) published in the repository; a user guide. |
| **Skills** | Scala 3, Typelevel (cats-effect, fs2, http4s), Neo4j and Cypher, embeddings and retrieval, LLM agents. |
| **Difficulty** | Hard |
| **Size** | Large, ~350 hours |
| **Mentors** | Giovanni Ruggiero ([@gruggiero](https://github.com/gruggiero)), Rory Graves ([@rorygraves](https://github.com/rorygraves)), Kannupriya Kalra ([@kannupriyakalra](https://github.com/kannupriyakalra)) |

## Forge

[Forge](https://github.com/rorygraves/forge) is a Scala meta-orchestrator above the Claude Code and Codex CLIs. It takes
a feature request through design, piece-by-piece implementation, a pull request and merge, with independent review
and a human in the loop, coordinated by a finite-state machine and Git so one person can supervise many features.

### 19. Forge: An LLM4S agent connector and reactive PR review

| | |
|---|---|
| **Project** | [rorygraves/forge](https://github.com/rorygraves/forge) |
| **Description** | Forge drives its coding and reviewing agents through a `Connector` trait with two implementations, one per vendor CLI, so every role needs one of those CLIs and its subscription. An LLM4S-backed connector would let any role run on any LLM4S provider, including a local model through Ollama, with token usage and cost from LLM4S, and make true cross-model review a configuration choice. The project then builds the first two capabilities of Forge's Phase 5 roadmap: reactive PR review, which watches GitHub and GitLab for pull requests Forge did not open and reviews them with that same reviewer role, and workstreams linked to an issue tracker, so a labelled issue becomes a Forge feature run. |
| **Expected outcome** | An LLM4S connector passing Forge's connector test suites, with the streaming, question and resume behaviour the existing connectors have; configuration that assigns a provider and model per role; reactive PR review for GitHub and GitLab with posted review comments and a cost report; issue-tracker workstreams; documentation and an end-to-end demonstration on a real repository. |
| **Skills** | Scala 3, cats-effect, LLM agents and tool calling, Git and the GitHub API, state machines. |
| **Difficulty** | Hard |
| **Size** | Large, ~350 hours |
| **Mentors** | Rory Graves ([@rorygraves](https://github.com/rorygraves)), Kannupriya Kalra ([@kannupriyakalra](https://github.com/kannupriyakalra)) |
