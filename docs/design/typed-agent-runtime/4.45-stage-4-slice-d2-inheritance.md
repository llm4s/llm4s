# 4.45 Stage 4 slice D2: explicit inheritance ([#2049](https://github.com/llm4s/llm4s/issues/2049))

Part of the [Typed Agent Runtime design](../typed-agent-runtime-design.md), §4. Section numbers (§N.N) refer to that document and its [slice records](../typed-agent-runtime-design.md#slice-records). Phase 4 spec: `docs/superpowers/specs/2026-10-19-phase-4-subagents-design.md`, "D2".

Slice D2 of [#2044](https://github.com/llm4s/llm4s/issues/2044). D1 (§4.44) gave a subagent only its own tools and
middleware, the parent's budgets without the timeout, and default completion options. D2 makes everything a child takes
from its parent explicit: a grant of the parent's tools and middleware, a budget each limit of which is capped by the
parent's remainder and holds for the child's whole life, delegation to its own subagents, and permissions that only
narrow. `Agent.delegation` shows the result as a `DelegationPlan`.

Everything is in `llm4s-agent`, package `org.llm4s.agent.delegation`, apart from `RunContext.remainingSteps`
(`org.llm4s.agent.graph`) and the step cap the tool loop reads. The new public types are `@Experimental`. The specs are
`InheritanceSpec` (through a parent's runs, on D1's routing fake client) and `AncestorPermissionsSpec`. The guide is
the "Inheritance" and "Permissions" sections of `docs/guide/agents/delegation.md`.

## API

In `org.llm4s.agent.delegation`:

- `final case class Inheritance private (tools: ToolGrant, middleware: Set[MiddlewareId], budget: TaskBudget,
  delegate: Boolean)`, growth-prone: `apply` defaults `ToolGrant.None`, empty, `TaskBudget()`, `false`; `with*`
  setters (`withMiddleware` takes a set or the ids listed); `Inheritance.none`.
- `enum ToolGrant { None, Only(names), AllExcept(names) }`.
- `final case class TaskBudget private (maxSteps: Option[Int], timeout: Option[FiniteDuration], maxTokens:
  Option[Long], maxConcurrency: Option[Int])`, growth-prone: `apply` defaults every field to `None`; each setter takes
  the value or an `Option`.
- `final case class DelegationPlan(subagents: Vector[SubagentPlan])` with `find(parent, id)` and a `toString` of one
  line per subagent; `SubagentPlan(parent, id, toolName, tools: Vector[PlannedTool], middleware: Vector[MiddlewareId],
  ancestorRules: Vector[AncestorRules], model, modelInherited, budget, delegates, depth, maxDepth, subagents)`;
  `PlannedTool(name, granted)`; `AncestorRules(agent, rules)`. All are output only: their constructors are
  `private[agent]`, so adding a field breaks no caller.
- `TypedAgent.withInheritance(Inheritance)`, `TypedAgent.withSubagents(TypedAgent[?, ?]*)` (the child's own,
  offered only under `delegate`).
- `Agent.delegation: DelegationPlan`.

In `org.llm4s.agent.graph`: `RunContext.remainingSteps: Option[Int]`, the model calls the turn may still make, set for
a tool call of an agent's tool loop.

`private[agent]`: `AncestorPermissions` (middleware id `ancestor-permissions`), `ParentScope` (what a subagent is bound
under), `TaskLimits` (one call's limits), `TypedAgent.bindUnder(scope)`, `AgentBuilder.Inherited` and the state key
`ChildGrant` and the state key `DelegationKeys.grant` (`delegation-grant`, reserved like K2's keys).

## Decisions

### Binding under a parent scope

`AgentBuilder.build()` binds each subagent with `bindUnder(ParentScope)`, where the scope is the delegating agent's
id, client, completion options, runtime, effective tools (its own, its harness's and any it was granted itself),
effective middleware, the permission rules of every ancestor and its own `PermissionMiddleware`s, the child's depth,
and the root's `DelegationConfig`. The child is compiled with an ordinary `AgentBuilder`, given an `Inherited` value
(its depth, the ancestors' rules and its granted tools) that `effective` folds in: `AncestorPermissions` outermost,
the granted tools after its own. So the graph version, the clash check and the ordering checks cover what is inherited
as they cover the child's own, and the plan is read from the same builder (`inventory`) that is built, its middleware in the order the stack resolves (`runsBefore`/`runsAfter` applied).

`TypedAgent.bind(client, runtime)` (D1's standalone path) binds under an empty scope: depth 0, nothing to grant (a
grant naming a tool or middleware is refused), default options, the default `DelegationConfig`.

### Grants

A grant draws only on the delegating agent's tools by name, and its middleware by id, as instances. A name or id the
parent does not have is refused at `build()`, as `ToolSelection` refuses one (§4.37). `delegation` and
`ancestor-permissions` cannot be granted: delegation is `Inheritance.delegate`, and ancestors' permissions always
apply. Nor can any `PermissionMiddleware`, whatever its id: an ancestor's rules reach a child only through
`ancestor-permissions`, so granting one would evaluate one policy twice (tested). The task tools are middleware tools, never in the parent's tool list, so neither `Only` nor `AllExcept` can
reach them. A granted tool clashing with a child tool is refused by the existing clash check. A granted tool, and a granted middleware's tool, keeps the
parent's argument validator: the child checks a granted tool with the validator the parent checks it with,
and every other tool with its own, chosen by tool, never by schema (`ToolSet` keeps a validator per granted tool name,
which the loop's argument check reads), so granting a tool never changes how its own or any other tool's arguments
are validated, even when two tools share a schema (tested). The child's middleware
stack is `ancestor-permissions`, then the granted middleware in the parent's order, its harness's and its own, then
`delegation` when it delegates.

### Delegation by grant

A child is given its own subagents (`TypedAgent.withSubagents`) only when `delegate` is granted and its depth is below
the root's `maxDepth`; otherwise it has no task tools, even if it declares subagents (rule 15). The nested subagents
are bound under the child's scope, so their ancestors' rules include the child's own and the parent's, and use the
root's `DelegationConfig`: one tree, one set of bounds.

### Permissions only narrow

`AncestorPermissions` holds one level per ancestor `PermissionMiddleware` and decides each resource at each level as
`PermissionMiddleware.decide` does (first match wins, unmatched denied). `Deny` at any level gives `Denied: <op>
<target> (by agent '<id>')`; otherwise an `Ask` at any level gives one `NeedsApproval`, and because approval is one flag
per call, the approved call passes every level, the child's own `PermissionMiddleware` included. An ancestor with no
`PermissionMiddleware` adds no level. The guard reads the child's own `PermissionMiddleware` rules too, for their
denials only, so a call the child's own rules deny is denied before an ancestor's `Ask` suspends the parent for a
reviewer (tested); the child's own asks stay with its own middleware, inside. The one approval surfaces through the parent as D3's delegated `Approval`
(§4.46), and approving it there runs the call once, every level passed (tested).

### Budgets at call time

`TaskLimits.at(budget, parentMaxSteps, ctx, now)` computes, from the call's snapshot:

- **deadline**: the parent's `RunContext.deadline` passed fails the call `Fatal` with the parent's own
  `GraphError.DeadlineExceeded(thread, checkpoint)`, so the run fails and `recover` runs the call again;
- **steps**: `budget.maxSteps`, else the delegating agent's `maxSteps`, always capped by the child's own `maxSteps`
  (`TypedAgent.withMaxSteps`) when set, and by `RunContext.remainingSteps`; zero or less is
  `NotStarted(StepLimitReached)`. The child's own limit is in the grant before the whole-life deductions below, so a
  failed attempt's call counts against it too. A child without `withMaxSteps` is compiled under a parent with no step
  limit of its own (not `Agent.DefaultMaxSteps`), so the grant, which every call sets, is the only cap (tested above 50);
- **tokens**: with a parent `maxTokens`, it less the run's tokens (the loop's `runTokens`: the thread's usage since
  admission plus the task's), zero or less being `NotStarted(TokenLimitReached)`; the grant and this remainder go to
  the child runner separately (below);
- **time**: the grant (the runner caps it by the parent's deadline);
- **concurrency**: the grant capped by the parent's `maxConcurrency`.

`NotStarted` is decided before a slot is taken and creates no child thread; its tool message names only the subagent
and the reason. The same snapshot decides the same on replay (rule 1). The child's config carries the token limit and
timeout as `RunBudgets` values, and the step cap goes to the child runner.

`RunContext.remainingSteps` is the active agent's step limit (a child's cap included) less the turn's steps at the
snapshot. The tool loop sets it on the context of every tool call, in `execute` and in a resume.

### Whole-life grants

The child runner treats the call's limits as the child's grant for its whole life. Every effective grant is fixed at
the first admission, from the grant and the parent's remainder then, and stored on the child thread in a runtime-owned
key; every continuation deducts prior usage from the stored values, never from a grant recomputed against a recovered
parent's fresh or larger budget (tested: a child first granted 40 tokens by its parent's remainder never uses more
than 40 after its parent recovers with a far larger budget). The first admission records them
on the child as a `ChildGrant(steps, tokens, deadline, concurrency)` (`DelegationKeys.grant`); each later admission (a recovery,
whose replayed call computes its limits afresh, under a recovered parent run that may have a looser budget or none)
takes the lower of each recorded limit and its own, so a grant can narrow and never widen:

- **tokens**: the first admission records the lower of the budget's grant and the parent run's remainder; each
  admission's `maxTokens` is the recorded limit less the child's roll-up so far (committed usage, prior usage and
  unfolded lost usage, K2), because a run counts tokens from its own admission, and at most the parent's current run's
  remainder. That remainder is one run's allowance, so it caps an admission and is never recorded: a recovery under a
  smaller parent budget lets the child use that allowance rather than settling it, and one under a larger budget never
  widens the recorded limit;
- **steps**: the used steps are the turn's committed model steps plus the agent model steps of failed attempts,
  which called the model but never committed a step. They are counted on their own, never from the lost usage's
  request count, which a middleware's model call (a summariser's) is in too: a task records that it made an agent model
  step (`TaskUsage.step`, from `ModelContext.recordCall` with an attempt number), the runtime puts the failed tasks'
  count on the terminal event (`RunFailed`, `RunCancelled`, `RunTimedOut` gain `steps`), and the child runner folds
  it into `PriorUsage.failedSteps` with the usage. Each admission records the total (`ChildGrant.lostSteps`), and the
  tool loop ends the
  child's turn at the lower of the agent's `maxSteps` and the grant's `steps` less it, compared with the turn's
  committed steps, which a recovered child keeps. A run-level step budget would need a public `RunBudgets` field; the
  state key keeps it internal;
- **time**: the first admission fixes the child's deadline at `min(RunOrigin.startedAt + granted timeout, the
  parent's deadline then)` (by the runtime's clock) and records it; every continuation reuses it and never recomputes it
  from a recovered parent's fresh deadline, which only caps an admission (rule 18). So a child stopped by its parent's
  deadline is, at the parent's recovery, past its own: it is settled `Failed` (below) rather than continued, which
  narrows K2's reattachment after a parent timeout (§4.42);
- **concurrency**: each admission's `maxConcurrency` is the recorded one, narrowed by the call's.

The same rules govern every continuation of a child: a recovery (`recoverChild`) and a resume through its parent (D3's
`ChildRunner.resume`, `resumeChild`, which gains the same `amend` as `recoverChild`, so a resume records the narrowed
grant too), which share one check. A child whose tokens or steps are spent is settled
`TokenLimitReached` or `StepLimitReached`
(`settleChild`) without running, and its refusal returned. One whose own granted time has passed
(its stored deadline `<= now`, whether it came from the grant or from the first parent's cap, and whatever deadline a
recovered parent has now) is settled the same way with
`RunOutcome.Failed` and a `DeadlineExceeded`, the kind a child timing out mid-run records, under either failure policy,
and returned as `TaskRefusal.Failed`; it never reaches `recoverChild` or `resumeChild` with no time left. Otherwise it
continues with the same deducted limits (tested for a recovery, and for a resume past its deadline, with a spent token
grant and with part of one left, and for a failed attempt whose summariser call beside its agent step uses one step,
not two). A parent whose own deadline has
passed keeps the call-time rule: the call fails with the parent's `DeadlineExceeded`. No admission ever carries a
non-positive budget.

### The model

The child uses the parent's client and `CompletionOptions` unless `withModel` sets both (D1 used default options). The
plan records the client by its class name, since an `LLMClient` exposes no model name, and whether it is inherited.

## Where the spec was imprecise

- "the call fails with the parent's own `DeadlineExceeded`, as any step past the deadline does": a tool cannot end the
  run as the runtime's expiry does (`RunTimedOut`). The call is `Fatal` with that error, which the run reports wrapped
  as any tool failure (`NodeFailed(ToolFailed(DeadlineExceeded))`). In practice the runtime's own expiry fires at the
  same moment.
- How a child declares subagents was unspecified (P1 adds them to harness profiles): D2 adds
  `TypedAgent.withSubagents`.
- "middleware ids in order, `AncestorPermissions` included, with the ancestors' rules": the rules are a separate field,
  `ancestorRules`, one entry per ancestor `PermissionMiddleware`.
- "model name": the plan names the client's class.

## Runtime rules

Phase 3's rules 1-13 and Phase 4's 14-19:

1. **One batch, one snapshot.** Limits are computed from the call's snapshot only; parallel children each get the same
   remainder, and the parent's next model call stops at `TokenLimitReached` if together they overshoot (documented).
2. **Total updates.** No parent state key is written; `NotStarted` is a tool error decided when the tool runs.
3. **Visibility.** Unchanged from D1.
4. **At least once.** A replayed call computes the same limits and, for an existing child, continues it with what is
   left of its grant.
5. **Block.** Unchanged; a granted guardrail's Block in a child ends the child `Blocked`.
6. **Full snapshots.** The child's state gains one small key (`delegation-grant`).
7. **Codecs.** No stored format changes; the new key reads as `None` on older child threads.
8. **Tenant.** Never part of a grant; a granted memory middleware is scoped by the parent's tenant, which the child has.
9. **No content in durable events.** No new event. A child settled on a spent grant runs nothing, so, as for any
   settled child D4 reattaches to (§4.47), its settling run is announced with `TaskStarted` and one nested
   `LiveGap(0)`, and the call commits one `TaskEnded` with the refusal's label (tested for tokens and for time).
10. **A failed task commits nothing.** Unchanged; a settled spent child keeps its outcome on its own thread.
11. **Every model call accounted.** The token remainder is read from the parent's usage, which counts each child's
    roll-up once (K2).
12. **Bounded.** Each child's steps, time and tokens are bounded by its grant and the parent's remainder, for its whole
    life (tested for each, and across a recovery).
13. **Types.** Every type named is defined here or in K1-K3 and D1.
14. **The child thread is the journal.** `NotStarted` creates no thread; a spent grant settles the child, whose
    settled outcome later runs read back.
15. **No capability without a grant.** Only granted tools and middleware, task tools only under `delegate` and below
    `maxDepth`; ancestors' permissions only narrow (tested).
16. **Identity inherited.** Tenant, principal, runtime, store and the root's tracing (`ParentScope.tracing`, so a
    child's runs trace where its parent's do) come from the parent and are not grantable (tested for tracing).
17. **Only typed data crosses.** Unchanged; granted tools run against the child's own thread.
18. **Supervision flows down.** A child's deadline is never later than its parent's, its concurrency never above it
    (tested).
19. **Child threads driven only through their parent.** Unchanged.

## Not in this slice

- Task events, nested streams, tracing ids: D4.
- The general-purpose subagent's computed grant in `HarnessProfile.deepAgents`: P1.
