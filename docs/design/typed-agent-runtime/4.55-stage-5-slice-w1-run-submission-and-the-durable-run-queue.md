# 4.55 Stage 5 slice W1: run submission and the durable run queue ([#2134](https://github.com/llm4s/llm4s/issues/2134))

Part of the [Typed Agent Runtime design](../typed-agent-runtime-design.md), §4. Section numbers (§N.N) refer to that document and its [slice records](../typed-agent-runtime-design.md#slice-records). Stage 5 spec: `docs/superpowers/specs/2026-10-20-stage-5-production-design.md`, "W1" and "Rules every slice must satisfy".

Slice W1 of [#2129](https://github.com/llm4s/llm4s/issues/2129), after S3 ([4.52](4.52-stage-5-slice-s3-thread-registry.md)) and
on the critical path to W2 (workers) and W3 (cancel and the busy-thread policy). It adds the durable run queue - the
SPI, its contract, and an implementation in each of the three stores, in the same database as the checkpoints - and
the submission API. It builds no worker loop: W2 takes entries, runs them and closes them with what W1 provides.

## What it adds

In `org.llm4s.agent.service` (`llm4s-agent`), every new type `@Experimental`:

- `RunQueue`: `submit`, `entry`, `awaitClosed`, `openEntries`, `take`, `renew`, `release`, `recordAttempt`, `close`,
  `reclaim`. Its Scaladoc is the contract; `RunQueueContract` (`llm4s-agent-testkit`) is its executable form.
- `Submission` (growth-prone), `Ticket`, `QueuedInput` (`Start(json)`, `Resume(answers)`, `Recover`, with
  `QueuedInput.query` for an `Agent` and `QueuedInput.typed` for a `TypedAgent[I, O]`), `BusyThreadPolicy`
  (`Reject`, `Enqueue`, `Interrupt`), `QueueEntry` (growth-prone), `Attempt`, `EntryOutcome` (`Done`, `Failed`,
  `Cancelled`, `Interrupted`) with `FailureReason` and `CancelReason`, `Lease`, `LeasedEntry`, `TakeRequest`,
  `AttemptStart` (`Recorded`, `Exhausted`, `ThreadDeleted`), `QueueError`, and the ids `EntryId`, `SubmissionKey`,
  `LeaseToken`.
- `AttemptPlan.of(entry, admitted, latest)`: rule 4's classification of an attempt, `Start`, `Recover` or
  `Close(outcome)`, for W2 to act on.
- `RunSubmitter(queue, checkpointer, settings)`: submit, `await` a ticket, `follow` its run's events.
- `RunQueueSettings` (`maxAttempts`, `ticketLifetime`, `lease: LeasePolicy`) and `org.llm4s.config.RunQueueConfigLoader`
  reading `llm4s.agent.queue` (comment 2 on the issue).
- `Checkpointer.latestOfRuns(threadId, runIds): Result[Option[Checkpoint]]`, abstract: the run-id lookup.
- `InMemoryCheckpointer.runQueue`, `SqliteCheckpointer.runQueue`, `PostgresCheckpointer.runQueue`: each store's queue.
  SQLite schema 9 and PostgreSQL schema 3 add `run_id` to every history row, indexed `(thread_id, run_id, position)`,
  and the queue's tables.

## Decisions

**The queue is a separate SPI, reached from its store.** The spec's call (Decisions, 5) holds: no transaction spans an
entry and a commit, and correctness rests on rule 4. Each store exposes its queue as a member (`runQueue`), built over
the store's own connection, pool or lock, so the queue is in the same database and shares the pool. S5's
`CheckpointStore` is where a configured store's queue will be reachable from; until S5 merges it is reached from the
concrete store. A queue is never built apart from its store: the store's `prune` must read the queue's open entries
(below), and the store's `deleteThread` must mark the queue's open entries, and both are only possible in one database.

**The run-id lookup is `latestOfRuns`, by an index on the run.** `latestOfRuns(threadId, runIds)` is the newest
checkpoint, by place in the history, any of the runs committed - never by `createdAt`, which a skewed producer
stamps. Every history row now records its run (`run_id`, backfilled from the checkpoint JSON at migration), indexed
`(thread_id, run_id, position)`: one backwards probe per run, and the set is at most `maxAttempts`. SQLite's planner
prefers the `(thread_id, position)` primary key on a small table, which scans a thread's whole history, so the query
names its index (`INDEXED BY`); PostgreSQL probes each run in a `LATERAL` join over `unnest` of the ids.

**Rule 4 is classified by `AttemptPlan`, from the lookup and the latest checkpoint.** None of the entry's runs
committed: the input was never admitted, so `Start` (a start or a resume runs as submitted). One did: `Recover` when
that run's checkpoint is the thread's latest and `Running`, otherwise `Close` with the outcome the thread's state
gives (`Done` for `Completed` or `Suspended` - a suspended run is at rest, waiting for a resume, which is another
entry - `Failed(RunFailed)` for `Failed`, `Done` with the other run's checkpoint when a direct run took the thread on).
It never reads an attempt count. A worker records the attempt before it reads either, so the attempt's own id is in the
set; it has committed nothing yet, so it changes nothing.

**A queued recover is the owner's explicit transfer of recovery (comment 1 on the issue).** Rule 4 says a worker never
adopts a run started outside the queue; a `Recover` entry is the thread's owner asking the queue to adopt it. Its
attempts recover the thread whatever its recorded runs are until one of them commits (the recovery's claim commit
records its own `RunId`), after which it classifies as any other entry: `Recover` again while that run is the latest
and incomplete, `Close` once it has moved on. A queued recover of a thread with nothing to recover fails as `recover`
does (`NothingToRecover`), and the worker closes it `Failed(RunFailed)`.

**Attempts are recorded before they touch the thread, bounded by `maxAttempts` fixed at submission.**
`recordAttempt(lease, runId)` writes the attempt durably, under the lease, before it answers `Recorded`; a run id the
entry already used is refused, since a reused `RunId` names two runs. `maxAttempts` is copied onto the entry at
submission (from `RunQueueSettings` through `RunSubmitter`), so every worker on every machine agrees on the bound even
while their settings differ during a rollout. Once an entry has made `maxAttempts` attempts, `recordAttempt` records
nothing and answers `Exhausted`, leaving the entry open under the lease: the worker that finds it so settles the
thread if the input was admitted (W3's settle, W2 calls it) and closes the entry `Failed(AttemptsExhausted)` - the
queue cannot settle a thread itself, since that is a fenced commit under the thread's claim. An unadmitted entry is
simply closed. Default: 5 attempts.

**Deletion is caught by the delete itself, not by a marker.** The spec has an entry record the thread's deletion
marker (its tombstone) at submission. A tombstone is kept only for a thread that numbered an event, so a thread with a
claim and nothing else - or one an entry was queued for before it existed - leaves none, and a delete of it would go
unseen. Instead each store's `deleteThread` marks every open entry of the thread (`thread_deleted`) in the delete's own
transaction (under the store's lock in memory), whatever the thread numbered, and `recordAttempt` closes a marked
entry `Cancelled(ThreadDeleted)`, recording nothing. This keeps rule 4's "a direct `deleteThread`, which does not
consult the queue" - the runtime's delete is unchanged; the store, which holds both in one database, does it - and it
leaves S4 free to reclaim tombstones, since nothing reads them for the queue. An entry submitted after a delete is not
marked: the delete is the thread's past. One window is left for W2: a direct delete that lands after `recordAttempt`
and before the attempt's own claim commit lets a `Start` attempt create the thread afresh. Closing it needs the
admission to check, under the thread's claim, that the entry was not marked meanwhile, a `GraphRuntime` hook W2 adds
where it starts queued runs; the service's own delete (W3) closes and cancels the thread's entries first, so only a
delete that bypasses the service can meet it.

**An attempt's run id names no other run on its thread.** `RunId` is reusable (`RunConfig.withRunId`), so the
lookup would take a direct run that had used the same id for the entry's admission (Codex, round 1).
`recordAttempt` therefore refuses a run id that a checkpoint of the thread's history, or an attempt of any entry of the
thread, already has, by the same `(thread_id, run_id)` indexes; a worker gives each attempt `RunId.random()`. What the
store cannot refuse is a direct run started later that reuses an attempt's id - which only the entry's own tenant can
read off the entry - and the lookup trusts that none does, as `GraphRuntime` already documents that a reused `RunId`
names two runs.

**`prune` keeps an open entry's admission evidence, and nothing else.** While an entry is open, `prune` keeps the
newest checkpoint each of its recorded runs committed on its thread, beside what the policy keeps, so the lookup never
loses an admitted run; the event floor is still judged by the policy's own checkpoints, so a long-running entry does
not let the event log grow. Once the entry closes, the checkpoint is pruned as any other. Each store reads its queue's
open attempts in the prune's own transaction (in memory, under the shared lock).

**Leases are claims for entries; only a thread's head is taken.** A lease has a token from a store-wide counter, a
holder and an expiry by the store's clock (rule 1: the database's in PostgreSQL, the clock claims use), and may renew,
record attempts, release and close for as long as no other lease replaced it, expired or not. A thread's open entries
run in one order (rule 5): an entry that has recorded an attempt first - it may have admitted its input and must be
recovered before anything else runs - then `Interrupt` entries, then the rest, each by id. `take` leases only a head,
and only while no other entry of the thread holds a live lease, so two workers never run one thread from the queue;
an `Interrupt` entry can displace a head that was leased but never attempted, so taking the new head also ends the
displaced entry's expired lease, and its old holder can no longer renew it or record an attempt beside the new head's
(Codex, round 3); the claim still decides who runs it (rule 5), and a worker that finds the claim live releases the entry without an
attempt (W2). `take` names the agents its worker can run: an entry whose agent the worker lacks holds its thread back
for that worker rather than letting a later entry jump it.

**Of two `Interrupt` entries the later wins at submission.** Submitting an `Interrupt` entry closes every queued
`Interrupt` entry of the thread that has recorded no attempt `Interrupted(by = the new entry)`. One that has recorded
an attempt is running: it stays, ahead of the new one, for W3 to stop at its next safe point. Stopping a running entry
is W3's; W1 defines the order and the `interrupted` state.

**`Reject` refuses a thread with an open entry.** `Reject` (the default, so a caller sees §5.3's behaviour) refuses a
submission to a thread that has an open entry with `GraphError.ThreadBusy`, naming no holder - the entry may be
another tenant's. A thread busy with a direct run and no entry is W3's to refuse (it owns the busy-thread policy); W1
queues it, and its worker then meets the claim.

**Submission keys are per tenant, looked up or inserted in one step.** A key is unique within its tenant (`None` is
its own scope). A submit with a key the tenant holds for the same submission - thread, agent, tenant, input and policy,
not `maxAttempts`, which a retry may read from changed settings - answers the held entry's ticket (`existing = true`,
with its current position, `None` once closed); a different submission under it is `SubmissionKeyReused`. The store
looks up and inserts in one write transaction (SQLite), under the store's lock (in memory), or under advisory locks on
the key and the thread (PostgreSQL), so two racing retries make one entry. A key lives as long as its entry: once the
entry is reclaimed the key names nothing and a new submit under it makes a new entry.

**Entry ids are issued in order; "ticket expired" is told apart in every store.** An id is a positive `Long` from a
store-wide counter that never goes back (SQLite's meta table and `AUTOINCREMENT`, a PostgreSQL sequence, a counter
in memory), so it is also the entry's place in submission order. A read of an id the store issued but no longer holds
for the caller's tenant answers `TicketExpired`; one past every issued id answers `TicketNotFound`. Another tenant's
live entry answers `TicketExpired` too (rule 9), so the answer never tells another tenant's entry from a reclaimed one.

**Terminal states are four, with typed reasons.** `done`, `failed`, `cancelled`, `interrupted`, as the spec lists. An
entry closes once; a closed entry refuses every lease call with `EntryClosed`, and a lease that is not current gets
`LeaseLost`. A closed entry is kept for the ticket lifetime (default 24 hours, judged by the store's clock against when
it closed) and then reclaimed whole by `reclaim(ticketLifetime, limit)`, which W2's retention sweep calls; an open
entry is never reclaimed.

**Wait and follow are the store's reads.** `awaitClosed` polls `entry` every 100 ms by default; the in-memory queue
wakes on a close. `RunSubmitter.follow` pages the thread's events through `awaitEventsAfter`, so S2's notification
wakes it across machines, keeping those of the entry's attempts' runs and advancing the cursor over every event; the
entry is read again after the events, and since an attempt is recorded before it commits, every event of the entry's
runs is covered by the attempts read. A close records the thread's last event number then (`closedAtSeq`): the
worker closes an entry only after its run has stopped committing, so every event of the entry's runs is at or below it,
and following a closed entry reads no further, `finished` once the cursor reaches it - also on the page during which it
closed - however busy the thread stays
with later runs (Codex, round 2). `release` of a closed entry answers `EntryClosed`, so a worker giving an entry back
learns it is terminal; a lease that is not current still releases nothing, quietly.

**Settings.** `llm4s.agent.queue`: `maxAttempts = 5`, `ticketLifetime = 24 hours`, `lease { ttl = 30 seconds,
renewEvery = 10 seconds }` - the claim's own policy, since W2 renews the lease with the claim. S5 owns the store's
settings; the queue has no store settings of its own.

**What an entry carries.** The input as JSON (`{"kind": "start", "input": ...}`, resume answers keyed by interrupt id),
the agent id, the tenant, the policy, the key, `maxAttempts`, whether its thread was deleted while it was open, and a `trace_parent` column for the
submitter's trace context (O1). The input is the caller's to store (rule 10); no log line or error message carries it.

## Not in this slice

- The worker loop, lease renewal with the claim, deferring to a live claim, the retention sweep (W2).
- Cancel requests, settling a cancelled or exhausted thread, stopping a running entry for an `Interrupt` entry, and a
  `Reject` of a thread busy with a direct run (W3).
- Queue metrics (O2).
- The trace context on `Submission`, and choosing a continuation's trace context at admission (comment 3 on the
  issue): both build on O1's `TraceContext` and `RunConfig.traceContext`, which are not on main yet; the column is in
  the schema.

## Tests

`RunQueueContract` (37 cases) runs against all three stores: `InMemoryRunQueueContractSpec`,
`SqliteRunQueueContractSpec` (with `reopen` and `sibling` on new connections) and `PostgresRunQueueContractSpec`
(`modules/it`, `@Docker`, the database's clock moved per case). `CheckpointerContract` gains two `latestOfRuns` cases.
The schema steps are tested from version-8 (SQLite) and version-2 (PostgreSQL) stores, the SQLite lookup's plan is
checked to use its index, and `RunQueueSpec` covers `AttemptPlan`, a queued start run by a real `Agent`, `follow`,
the settings and the loader.
