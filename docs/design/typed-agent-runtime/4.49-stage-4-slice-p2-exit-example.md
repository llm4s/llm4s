# 4.49 Stage 4 slice P2: the exit example, parallel-specialist deep research ([#2053](https://github.com/llm4s/llm4s/issues/2053))

Part of the [Typed Agent Runtime design](../typed-agent-runtime-design.md), §4. Section numbers (§N.N) refer to that document and its [slice records](../typed-agent-runtime-design.md#slice-records). Phase 4 spec: `docs/superpowers/specs/2026-10-19-phase-4-subagents-design.md`, "P2".

Slice P2 of [#2044](https://github.com/llm4s/llm4s/issues/2044), the last slice of Stage 4. Stage 4's exit criterion
(§6 row 4) is deep research ported to parallel specialists: each child returns a typed final report, the parent
resumes and composes after a child's failure and after a child's approval, and it runs deterministically in CI, as
Stage 3's exit examples do (§4.38). This slice adds that example as a runnable sample, and an acceptance suite that
drives the sample's own agent on `llm4s-testkit`'s `ScriptedLLMClient`, so the suite proves the code a reader runs. It
assembles what K1-K3, D1-D4 and P1 (§4.41-§4.48) built, and needed no library change.

## What it adds

In `modules/samples`, package `org.llm4s.samples.harness`:

- `ParallelDeepResearch`: the lead agent and its two specialists.
  - The lead is on `HarnessProfile.deepAgents` with the general-purpose subagent off
    (`SubagentConfig.deepAgents.withGeneralPurpose(None)`), the specialists on, and
    `DelegationConfig(maxConcurrentChildren = 2)`. It has `fetch_page` (Stage 3's, §4.38), streams, and answers with
    Stage 3's typed `DeepResearch.Brief`. The runtime, and so the checkpointer, is the caller's: SQLite in the example
    and the suite.
  - `researcher: TypedAgent[ResearchQuestion, Findings]`, granted the lead's `fetch_page`
    (`Inheritance().withTools(ToolGrant.Only(Set("fetch_page")))`), streaming.
  - `critic: TypedAgent[Draft, Review]`, with no tools, streaming.
  - The lead's permission rules: reads anywhere, a write to `/report.md`, `write_todos`, both `task` tools, fetches
    from the docs site; a fetch from any other site asks. They bind the children too, since ancestors' rules only
    narrow (§4.45).
- `ParallelDeepResearchExample`: runs it against the configured provider over SQLite, printing the merged stream (the
  lead's text, and each child's start, text and end). The first "process" stops once the first child's report is
  committed to the lead, while the others run; the second `recover`s the lead from the same file, asks the person
  running it about each delegated approval (stdin; no answer rejects), and lists the children. The query names each
  topic's page, so a live model knows what it may fetch.
- `StoppingCheckpointer.reports(commit, agent)`: a commit carrying a completed task of subagent `agent` (its durable
  `TaskEnded`), where the example stops. Any lead tool result would not do: the preset asks the model to plan with
  `write_todos` first, which would stop the process before any child ran.

The suite, `ParallelDeepResearchAcceptanceSpec` in `modules/samples/src/test`, uses `ParallelResearchModel`, a scripted
model for the lead, each researcher and the critic, told apart by their system prompts. Like `ResearchModel`, it
answers from the conversation it is sent (by its last message, and a researcher by the question its first message
carries), so a recovered run that sends a conversation again gets the reply the lost call did.

## The scenarios, and what each asserts

| Scenario | Assertions |
|---|---|
| **Parallel** | Three `task_researcher` calls in one message. Every fetch waits until a second child is live (or the last has arrived), then stays live a little longer, so the children overlap as far as the bound lets them: the peak is exactly 2, below the batch of 3. Each call's tool message is typed `Findings` from its own page; the critic's is a `Review`; the `Brief` lists the three pages; the children are three researchers and a critic, all `Completed`. |
| **Crash and recover** | The first child to fetch finishes. The second fetches once a third has started (so the first has finished and released its slot), and `StoppingCheckpointer` stops before writing that fetch's commit. The third waits until the process has stopped. In a fresh runtime over the same file, `recover`: the finished child makes no model call and fetches nothing; each running child continues from its checkpoint (its one model call in process 2 is sent the fetch's result, so its first step was not made again) and re-fetches once (the lost commit: at least once); the `Brief` lists all three pages. |
| **The example's stop** | Stopping after writing the first commit `reports` matches: at least one researcher is `Completed` at the stop; `recover` composes the `Brief` and makes no model call for a completed child. |
| **Failure** | One researcher's provider fails. The lead sees the call's tool error (`subagent 'researcher' ...`), sends the critic a draft naming the gap, writes it into the report, and its `Brief` lists the other two pages. The failed child's thread stays: `children` lists it `Failed`. |
| **Approval** | A question on a site outside the allowlist: the researcher's fetch asks under the lead's rule. The lead suspends with one delegated approval (`AgentStatus.Suspended.delegated`) for `fetch_page` on that URL, nothing fetched; `Agent.resume` with `approve` runs the fetch once, and the lead composes a `Brief` with both pages. |
| **Cancel** | Cancelling the lead while both live children fetch: each of the two has a durable `RunCancelled`; `recover` finishes with the `Brief`, every child `Completed`. |
| **Streams** | `agent.stream(..., nested = true)`: per child, `TaskStarted` first, then only nested `TextDelta`s, then `TaskEnded` with status `completed`; the deltas spell the child's typed answer. |
| **Cleanup** | `forget` on the lead: neither the lead's thread nor any of its four child threads has a checkpoint left. |

The rules the spec names are checked in these cases: one child per call across the crash (rule 14: the same threads
before and after, three researchers in all), no child message in the lead's thread (rule 17), the lead's usage
counting every model call of the tree exactly once (rule 11, in the parallel and crash cases; the per-child
`TaskEnded` usages sum to the children's calls), and no content in the durable events of the lead or of any child
(rule 9).

## Where the spec was imprecise

- **"Granted `fetch_page`"** is a D2 grant, so the lead holds `fetch_page` itself: a grant names a tool the parent has
  (§4.45). The lead's own rules then decide both its fetches and its children's.
- **"Outside the allowlist asks"** is an `ask` rule on `Network **` after the `allow` of the docs site: first match
  wins, so the allowed site never asks.
- **"At most two children are live at once"** is observed on the children's fetches, not on `TaskStarted` and
  `TaskEnded`: those bracket the child's run and the call's commit, not the concurrency permit, so a third child's
  start may be delivered before an earlier child's `TaskEnded` without the bound being broken. To show the bound is
  what limits them, every fetch holds until a second child is live, so a third live child would raise the peak to 3
  (checked by running the suite with a bound of 3).
- **"Stops after one child completed and while another is mid-run"**: the stop is placed at the second child's fetch
  commit, before writing it, once the third has started. That makes the crash deterministic: the first child's
  terminal checkpoint is written, the second's and third's first model calls are committed and their fetches are not,
  and every model call of process 1 was committed, so rule 11 holds exactly across both processes.
- **Cancel** ends "both children": with a bound of 2 only two are live when the lead is cancelled; the third never
  started, and starts under `recover`.
- **Stage 3's `DeepResearch` stays.** §4.48 expected this example to replace it; it is Stage 3's exit example and
  shows what this one does not (offload, summarisation, memory, an output Block), so both remain, and §4.48 now says
  this one is added beside it.

## Runtime rules

Phase 3's rules 1-13 and Phase 4's 14-19:

1. **One batch, one snapshot.** The three `task_researcher` calls are one message; each child is built from its call's
   arguments only, and the parallel case checks each reports on its own page.
2. **Total updates.** No new state key; a failed child is the call's tool error (failure case).
3. **Visibility.** The scripted lead composes from the tool messages of the next model step; children never see each
   other's findings.
4. **At least once.** The crash case: the lost fetch runs again under `recover`; the committed ones do not.
5. **Block.** Not exercised: the example has no output guardrail (Stage 3's example covers Block, §4.38).
6. **Full snapshots.** The lead's snapshot holds only the bounded reports; each child's state is on its own thread.
7. **Codecs.** No new key or codec; the crash case decodes every thread of the tree from the SQLite file in a fresh
   runtime.
8. **Tenant.** Every run is under one `TenantId`; `children` and `forget` are called with it.
9. **No content in durable events.** Checked on the lead's and every child's log; text is read only from live nested
   deltas.
10. **A failed task commits nothing.** The crash case: what process 2 finds is what process 1 committed.
11. **Every model call accounted.** Checked across the tree, and across both processes of the crash case.
12. **Bounded.** `maxConcurrentChildren = 2` is observed; the other bounds are `DelegationConfig`'s defaults, and each
    child has its own step limit.
13. **Types.** The sample's types are sample code; everything else is §4.37-§4.48's.
14. **The child thread is the journal.** One child per call across the crash; the finished child returns its stored
    report with no model call.
15. **No capability without a grant.** The researcher has only the granted `fetch_page`, the critic nothing; the lead's
    rules bind both, and a fetch they ask about suspends the lead.
16. **Identity inherited.** The children run on the lead's runtime, store and tenant.
17. **Only typed data crosses.** Checked: the lead's thread holds no child conversation, tool call or tool result.
18. **Supervision flows down.** The cancel case: the lead's cancellation reaches both live children.
19. **Child threads driven only through their parent.** The example drives children only through the lead (`recover`,
    `resume`, `forget`), and reads them with `children` and the event log.

## Not in this slice

- Background child tasks with poll, cancel and join (§5.5): out of Stage 4.
- A child on another runtime or checkpointer (spec open question 7).
