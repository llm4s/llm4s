# 4.32 Stage 3 slice F1: filesystem tools ([#1905](https://github.com/llm4s/llm4s/issues/1905))

Part of the [Typed Agent Runtime design](../typed-agent-runtime-design.md), §4. Section numbers (§N.N) refer to that document and its [slice records](../typed-agent-runtime-design.md#slice-records). Phase 3 spec: `docs/superpowers/specs/2026-10-13-phase-3-harness-design.md`, "F1".

Slice F1 of [#1901](https://github.com/llm4s/llm4s/issues/1901), a feature slice on C2 (§4.23: resources, permission rules, batch locks) and C3 (§4.25: `FileBackend`). It gives an agent seven file tools over any `FileBackend`: `ls`, `read_file`, `write_file`, `edit_file`, `delete`, `glob` and `grep`. Everything is in `llm4s-agent`, package `org.llm4s.agent.harness`, `@Experimental`; `FileToolsContract` is in `llm4s-agent-testkit`.

**C3 already owns the hard part.** A backend computes its locks, guards its external effects (C4), enforces its bounds and scopes itself by tenant (§4.25, "The problem, stated once"). The tools only translate: model arguments into backend calls, backend results into bounded text, and the call's declarations - resources, locks, writes, hints - from the arguments. So this slice adds no replay key, no lock key and no stored type of its own; each of those is the backend's, and every tool is generic over the backend. F2 (#1906) runs the same tools over its `WorkspaceFileBackend`, and `FileToolsContract` is how it proves they work there.

The specs are `FileToolsSpec` (each tool on state and composite backends, bounds, permission rules, two edits in a batch, a parallel batch over quota, `recover`, an output Block, a store edit replayed after a crash) in `llm4s-agent`, and in `llm4s-agent-testkit` `FileToolsContract`, run over the state, composite, store-file, resolved-store and resolved-state backends.

## API

```scala
object FileTools:
  val Ls = "ls"; val ReadFile = "read_file"; val WriteFile = "write_file"; val EditFile = "edit_file"
  val Delete = "delete"; val Glob = "glob"; val Grep = "grep"
  val Names: Vector[String]                       // the seven, in that order
  def apply(backend: FileBackend, limits: FileToolLimits = FileToolLimits.default): Vector[AgentTool[?]]

final case class FileToolLimits private (readLimit: Int, maxLineChars: Int, maxResults: Int, maxResultChars: Int)
object FileToolLimits:
  def apply(readLimit = 2000, maxLineChars = 2000, maxResults = 500, maxResultChars = 40000): FileToolLimits
  val default: FileToolLimits
  // withReadLimit, withMaxLineChars, withMaxResults, withMaxResultChars
```

`FileToolLimits` is growth-prone (CLAUDE.md): a private constructor, `apply` with the defaults, `with*` setters. Each limit is at least 1, and `maxResultChars` at least 256, so a result's notes always fit within it. The tools' arguments are private types: callers hold `AgentTool[?]`, and the names are public constants, so F2 and P1 select tools by name.

| Tool | Arguments | Backend call | Resource (C2) | Locks | `writes` | Hints |
|---|---|---|---|---|---|---|
| `ls` | `path` (default `/`) | `ls(path, maxResults)` | `(Read, path)` | none | none | read-only, idempotent |
| `read_file` | `path`, `offset` (1-based, default 1), `limit` (default and most `readLimit`) | `read(path, offset - 1, limit)` | `(Read, path)` | none | none | read-only, idempotent |
| `write_file` | `path`, `content` | `write` | `(Write, path)` | `backend.locks(path)` | `backend.writes` | destructive, idempotent |
| `edit_file` | `path`, `old_string`, `new_string`, `replace_all` (default false) | `edit` | `(Write, path)` | `backend.locks(path)` | `backend.writes` | destructive, not idempotent |
| `delete` | `path` | `delete` | `(Delete, path)` | `backend.locks(path)` | `backend.writes` | destructive, idempotent |
| `glob` | `pattern`, `path` (default `/`) | `glob(Glob(pattern), path, maxResults)` | `(Read, <path>/<pattern>)`, an envelope | none | none | read-only, idempotent |
| `grep` | `pattern` (a regex), `path` (default `/`), `include` (a glob) | `grep(pattern, path, include, maxResults)` | `(Read, <path>/**)`, or `<path>/**/<include>`, or `<path>/<include>` | none | none | read-only, idempotent |

Every hint says `openWorld = false`: a file backend is the agent's own world.

- **Paths are absolute.** Every path argument is a `VPath` (§4.25): it starts with `/`, and `.`, `..` and empty segments are refused, not normalised. A path is parsed in the spec's `validateDecoded`, so an invalid one is an error the model sees before the call is scheduled; under C2's admission rule it takes no lock and no round (§4.23, "Lock function failure"). Locks and resources parse it again from the same string, so all three agree.
- **Argument names.** The spec wrote `old` and `replaceAll`. The tools use `old_string`, `new_string` and `replace_all`: `new` is a Scala keyword, the tools' arguments are snake_case throughout, and these are the names models already use for this tool. `offset` is the 1-based line to start from, the number `read_file` prints beside it, so a model continues a page with the number it was shown.
- **Optional arguments are nullable.** A strict client sends every property, so an optional one is `Schema.nullable`, and `null` means its default, as in `write_todos`.

### Resources: the call's envelope (C2)

A mutation's resource is its concrete path; `ls` and `read_file` too. `glob` and `grep` read files they do not name, so they declare the envelope of every path they may read:

- `glob`'s pattern matches a path relative to `path` (§4.25), so `<path>/<pattern>` matches exactly the composite paths `glob` can return. It is an envelope, not a literal.
- `grep` without `include` may read anything beneath `path`: `<path>/**`. With an `include` that has no `/`, which matches a file's name, `<path>/**/<include>`; with one that has a `/`, which matches the relative path, `<path>/<include>`.
- At the root, `<path>/` is `/`, never `//`.

A permission rule set therefore decides a search for every file it could reach (C2: "An envelope is decided for every target in it"): with `deny(Read, "/secrets/**")`, `grep` over `/` is denied, and `grep` over `/src` is allowed. This is conservative by design; a model narrows `path` or `include` to stay inside what it may read. A literal `*` or `?` in a path is read as a pattern, which is stricter, never looser (§4.25).

`ls` shows the names, sizes and kinds of the entries directly beneath a path, never their contents, and is decided by its one path: denying `Read` on `/secrets/**` also denies `ls /secrets` (`/secrets/**` matches `/secrets`), but `ls /` still shows that `/secrets` exists. The guide says so.

### Locks and the batch snapshot (rule 1)

Mutations declare `backend.locks(path)` (C2's `withLocks`), so two mutations of one path in one model message run one after the other, the second against the first's committed result, and a state backend's backend-wide lock makes its quota exact across a parallel batch (§4.25). Reads take no lock, so **a read issued in the same message as a write is not ordered with it.**

- Over thread state (`StateFileBackend`, or a composite route to one) the read sees the batch's snapshot: the file as it was before the message, as the spec says.
- Over an external backend (a store, F2's workspace) there is no snapshot: the read runs beside the write and sees whichever version the target holds when it runs, the one before or the one after, never a torn one (the store's transaction; F2's atomic replace). The spec's sentence holds only for thread state; `FileToolsContract` caught it on the store backend.

Locking reads would order them, but a state backend's lock is backend-wide, so every read of a batch would then run in its own wave, two supersteps each, even in a batch with no write. So reads stay unlocked, and the tool descriptions and guide say "a read in the same message as a write may not see that write: to read what you wrote, read it in a later message". `FileToolsSpec` checks the snapshot over thread state; the contract checks only that a read sees one whole version.

### Results

Every result is text (`ujson.Str`), bounded before it is built:

- **`read_file`** prints each line as `cat -n` does, its 1-based number right-aligned in six columns, a tab, then the line cut at `maxLineChars` code points, marked `[... line cut at N characters]`. After the lines, when the file has more: `(lines a-b of n; continue with offset=b+1)`. An empty file is `(empty file)`; an offset past the end is an error naming the file's line count.
- **`ls`** prints one entry per line: a directory as `<path>/`, a file as `<path> (<size> bytes)`. **`glob`** prints one path per line. **`grep`** prints `<path>:<line>: <text>`, the text cut at `maxLineChars`. Each asks the backend for at most `maxResults` and, when the listing is `truncated`, ends `(stopped at <maxResults> results; narrow the path or pattern)`. An empty result says so in words, never a blank string, which the loop would send as `""`.
- **Mutations** say what happened: `Created /a.txt (12 bytes)`, `Overwrote ...`, `Edited /a.txt: 2 replacements`, `Deleted /a.txt`.
- **Every result, an error's message included, is at most `maxResultChars` characters.** The text is assembled in a builder that stops before the cap: it reserves room for the notes, and once the next item would not fit it cuts that item on a code point boundary, appends `[output cut at N characters]` and stops reading the listing. So the work and the allocation are bounded by the cap, not by what the backend returned (rule 12), and F4's offload sees a bounded result.
- **Errors.** A backend error goes through `BackendRefused.toolOutcome` (§4.25): a refusal or C4's `EffectReplayRefused` is an `Error` the model sees; anything else is `Fatal`, so the task fails, commits nothing, and `recover` replays it through the backend's guard.

### Not registered with the host file tools

`llm4s-agent-tools`' `ReadFileTool` and `WriteFileTool` are named `read_file` and `write_file`, so a `ToolSet` holding both suites is refused for duplicate names. The guide says to use one or the other: these tools for the agent runtime, the host tools for callers outside it.

## Runtime rules

1. **One batch, one snapshot.** Mutations hold the backend's locks; reads take none, and see the snapshot over thread state or one whole version over an external backend, as documented. Tested: two `edit_file`s of one path in one message both apply; three `write_file`s in one message over a state backend's quota refuse exactly the third; `FileToolsContract` repeats both on every shipped backend.
2. **Update functions are total.** The tools add no update function: a mutation's `Success` carries the backend's `StateUpdate`, whose function is total (§4.25). Every refusal - an invalid path, `old_string` absent or not unique, a quota, a denied permission - is decided when the tool runs. An argument the schema allows but the tool cannot use (a path that is not a `VPath`, a non-positive `offset` or `limit`) is refused in `validateDecoded`.
3. **Visibility.** A write is visible to a later wave of the same batch (when its lock orders it) and to the next superstep, as for any state key. A read in the same wave is unordered with it (above); the tool descriptions and guide say so.
4. **At least once.** The tools perform no effect of their own. Each call builds one `FileContext` from its `ToolContext` and passes it to its one backend call, so the backend's `effectKey` is the call's `IdempotencyKey` (C4), stable across `recover`, retry and approval. Tested: `edit_file` over a store backend whose task fails after the edit applied replays the recorded outcome on `recover`, and the file is edited once; `edit_file` over a state backend in a batch whose other call fails is visible after `recover`, applied once.
5. **Block.** A state backend's files are a state key the tools declare in `writes`, which C1 restores on an output Block (§4.22). Tested: a turn whose answer is blocked leaves the file as the turn before left it. Store effects are not retracted; the guide says so (§4.25).
6. **Full snapshots.** The tools add no key. Their results are messages, which each checkpoint copies, and each is at most `maxResultChars`.
7. **Codecs.** No stored type: arguments are decoded from the model's JSON each call, and results are strings. The tools' key set is the backend's `writes`, so adding them changes the graph exactly as C3 states (`files` and `tool-queue`; old threads at rest continue, §4.29).
8. **Tenant.** Inherited: the backend is scoped by the run's tenant or resolved per tenant (§4.25). `FileToolsContract` checks two tenants' trees stay apart on the tenant-scoped backends.
9. **No content in durable events.** The tools emit no events; the loop's `ToolExecuted` carries no content (§4.14).
10. **A failed task commits nothing.** A `Fatal` from the backend fails the task, so neither its update nor its result commits; a state mutation exists only in a committed result.
11. **Model calls accounted.** Not applicable: no tool calls a model.
12. **Bounded.** Every result is at most `maxResultChars`, assembled in a builder that stops at the cap; every listing asks the backend for at most `maxResults`; `read_file` for at most `readLimit` lines, each cut at `maxLineChars`. Inputs are bounded before use by the backend: a path by `VPath` (1024 bytes), a pattern (and `include`) by 1000 characters in `validateDecoded`, so before the resource built from it reaches a permission rule's glob comparison and before it is compiled (§4.25), content and edits by the backend's byte bound, checked before the result is built.
13. **Every type defined.** `FileTools` and `FileToolLimits` above; the argument types are private and have only the codecs the loop needs to decode them. No new stored type.

## Divergence from the spec

- `old_string`, `new_string` and `replace_all`, not `old` and `replaceAll` (above).
- `read_file`'s `offset` is 1-based, the number printed beside the line; the backend's is 0-based.
- `read_file`'s `limit` defaults to `readLimit` and is also capped at it, so one page is bounded by the configuration whatever the model asks.
- `glob` and `grep` declare an envelope as their resource (C3 said so; the spec did not state the shape).
- A read beside a write sees the batch's snapshot only over thread state; over an external backend, either version (above).

## Limits

- `ls` shows that a denied entry exists (its name, not its content).
- A search's permission is decided for its whole envelope, so a deny rule anywhere beneath `path` denies it, even if no file there would match.
- No `HostFileBackend` yet ([#1964](https://github.com/llm4s/llm4s/issues/1964)); the tools need no change when it lands.
