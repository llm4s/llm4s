# 4.47 Stage 4 slice D4: nested streams, ids in events and tracing, child-task metrics ([#2051](https://github.com/llm4s/llm4s/issues/2051))

Part of the [Typed Agent Runtime design](../typed-agent-runtime-design.md), §4. Section numbers (§N.N) refer to that document and its [slice records](../typed-agent-runtime-design.md#slice-records). Phase 4 spec: `docs/superpowers/specs/2026-10-19-phase-4-subagents-design.md`, "D4".

Slice D4 of [#2044](https://github.com/llm4s/llm4s/issues/2044), a delegation slice on D1 (§4.44). D1's children run
out of sight: the parent's subscribers saw a `task` call start and end, and nothing of the child. D4 lets a parent's
subscribers follow every child, live and in order, lets anyone follow one child by its own log, names a child's
parent in its trace, and commits one durable, content-free event per task: the child-task metric.

Everything is in `llm4s-agent` apart from two `Option` fields on core's `TraceEvent.AgentRunEnded`, the span names in
`llm4s-observability-otel`, the Langfuse metadata in `llm4s-observability`, and `nestedEvents` in `llm4s-effect`,
`llm4s-zio` and `llm4s-pekko`. The new public types are `@Experimental`. The specs are `NestedStreamSpec` (the
merged stream's order, `onChild`, grandchildren, gaps for a held and a settled child, overflow, `subscribeChild`,
`TaskEnded`, the parent ids in `AgentRunEnded`), `OpenTelemetryTracingBackendSpec`, `LangfuseRunMetadataSpec`, and the
adapters' `*NestedEventsSpec`s.

## API

In `org.llm4s.agent.events`:

- `TaskStarted(child: ChildRef)` and `TaskEnded(child, status: String, usage: UsageSummary, duration:
  FiniteDuration)`, with `ReadWriter`s (`duration` in milliseconds, `DurationJson.millisRW`).
- `SubagentEvents.TaskStarted` (`agent.task_started`, live) and `SubagentEvents.TaskEnded` (`agent.task_ended`,
  durable), each an `EventType`.

In `org.llm4s.agent.graph`:

- `StreamEvent.Nested(child: ChildRef, event: StreamEvent)`.
- `nested: Boolean = false` on `GraphRuntime.subscribe`, `RunHandle.subscribe`, `Observer`.
- `EventHandlers.onChild[A](eventType)((ChildRef, A) => R)`, and `EventHandlers.onChild` to start a set.

On the agent:

- `Agent.subscribeChild(ref: ChildRef, afterSeq = 0, config = RunConfig())(listener): Result[Subscription]`.
- `nested: Boolean = false` on `Agent.stream`, `streamResume`, `streamRecover` and `AgentRun.subscribe`.
- `TypedAgent.withStreaming()`; `TypedAgent.bind` takes the parent's `tracing`.
- `AgentIO.nestedEvents`, `AgentZ.nestedEvents`, `AgentPekko.nestedEvents(run, handlers)`.

In core: `TraceEvent.AgentRunEnded.parentThreadId` and `parentRunId`, both `Option[String] = None`, after
`timestamp`.

`private[agent]`: `RunContext.nested`, `NodeEventSink.nested`, `EventHub.nested`, `TaskRefusal.label`, and the
`parent` that `Agent.agentRun`, `AgentRun.apply` and `AgentTracing` take.

## Decisions

### The forwarder is the child run's observer

Live events are never replayed, so a forwarder that started when the parent saw `TaskStarted` would miss a fast
child's first events. The child runner admits the child with an `Observer` whose listener is a `RunScope` of the
child's run. An observer joins the hub during admission, before the claim commits, so it receives every event of the
run from its claim. On the first, the claim, it sends `TaskStarted` (through the calling task's `progress`), so only an
admitted run is announced, and from the forwarder's own thread, so the start is queued ahead of the run's events. A
refused admission abandons the observer, which announces nothing. Each event becomes `StreamEvent.Nested(child, event)`, handed to the parent thread's nested
subscribers by the calling task's sink (`RunContext.nested`, then `EventHub.nested`). The hub offers it like live
progress: in the subscriber's live slots, held during a replay and placed by the parent's handed-over mark, and
fenced by the parent run's claim (`current()` and the token): a parent run that lost its claim, or has released it (a
child that ignored a cancel past the drain outlives its parent's run), forwards nothing into a later run's
subscriptions.

The observer is made with `nested = true`, so a grandchild's events, which reach the child thread's nested
subscribers, reach the child's forwarder and are wrapped again. Recursion needs no code of its own.

The child's `AgentRun` is created with the forwarder's scope and `drain = true`, so the runner's `awaitBlocking`
returns only once the forwarder has passed on the child's terminal event (within `AgentRun.Drain`). The call's result,
and so `TaskEnded`, are committed after it. The order on the parent subscription is `TaskStarted`, the child's events
from its `RunStarted` or `RunRecovered`, its terminal event, then `TaskEnded`.

A forwarder never blocks: `EventHub.nested` only queues. If the forwarder's own subscription fell behind, its
`Disconnected` is passed on as `Nested(child, LiveGap(0))`, never as a nested `Disconnected`.

### Where live events cannot be forwarded: one gap

Only a child this call admits fresh is gap-free. Any other child run this call did not forward has live events this
runtime never sees, or saw in an earlier attempt's subscriptions. The runner sends one `Nested(child, LiveGap(0))` for
each such run, after a `TaskStarted` naming it:

- **Left `Running` or `Suspended` by an earlier attempt** (parent and child crashed and their claims lapsed, a parent
  `recover` after `ChildFailure.Fail`, or a resume through the parent, D3): a gap for the run of the child's latest
  checkpoint, then the run this call drives, announced at its claim and forwarded.
- **Held by another run** (`ThreadBusy`, K2's wait). `child.runId` is the holder when the refusal names it, else the
  configured run id, and a `TaskStarted` naming that run precedes the gap. A later admission by this runtime sends
  `TaskStarted` again and forwards that run.
- **Already settled, or suspended** (a replay after a crash): no run, so `TaskStarted`, the gap, then the call's
  `TaskEnded`. `child.runId` is the run that settled it. A child this call ran to its end has had that run forwarded,
  so it gets no gap; a failed child this call then settled (`settleChild`, under `ChildFailure.Report`) gets one for the
  settlement run, which the call's `TaskEnded` names.

`LiveGap(0)` reads as "an unknown number". Durable child events are never lost: `subscribeChild` replays them.

The same holds for a **subscription that attaches mid-child** (#2074): a `subscribe(..., nested = true)` made while a
child runs has missed that child's earlier live events. The parent's run tells the event hub of each child it
announces (`RunContext.childStarted`, which sends the live `TaskStarted`) and forgets it when the call's runner returns
(`childEnded`, and every child of the thread when the run's claim is released). At attach, under the hub's lock, the
new nested subscription is given, for each child running then, that `TaskStarted` and one `Nested(child, LiveGap(0))`,
in its live slots ahead of anything sent later, so the child's further events follow them (tested). A subscription made
before the child was admitted (`stream`'s) is told nothing extra and stays gap-free (tested). One that attaches after
the runner returned but before the call commits gets the call's `TaskEnded` without a `TaskStarted`.

### `TaskEnded` is emitted where the result is decided

`BoundAgent.delegated` builds the `TaskEnded` beside the outcome: the child (with the run that produced the outcome),
a status label, the runner's roll-up (`ChildEnd.usage`, every attempt and phase), and the time from the child's
`RunOrigin.startedAt` - read from the child's checkpoint, which the runtime stamped at the first admission - to now,
by the runtime's clock. `DelegationMiddleware` emits it only when `toolOutcome` gives a `Success` or an `Error`, the
two results that commit and never run again. A `Fatal` (`ChildFailure.Fail`, a runner failure) fails the task, which
discards the event, and the replay emits the one `TaskEnded`. A call whose child suspended (D3, §4.46) suspends
the parent rather than ending: `delegated` builds no `TaskEnded` for it, and the resumed call that settles the child
commits the one.

The status labels are `completed`, `blocked:<guardrail>`, `step_limit_reached`, `token_limit_reached`,
`output_invalid` and `failed`: a refusal's reason may hold content, so only its kind is stored (rule 9).
A runner refusal before any child of this call existed (`notRun`: an edited call, a thread that is not the call's
child) has no `ChildRef` the parent may name and commits no `TaskEnded`.

### Tracing

A child agent is bound with the parent's `Tracing` (`TypedAgent.bind(client, runtime, tracing)`, passed by
`AgentBuilder.build()` - the root's, for the subagents of every member of a handoff family, since the root's tracing
traces the whole family's runs), so its runs are traced like the parent's (rule 16: a definition cannot set its own). The
runner passes `(parent thread, parent run)` to the child's `AgentRun`, and `AgentTracing` puts them on the child's
`AgentRunEnded`. `TaskEnded` is traced by `AgentTracing` under its own name, `agent.task_ended`, as the other durable
agent events are.

The OpenTelemetry backend names `AgentRunEnded`'s span `invoke_agent <agent>` with `gen_ai.operation.name`,
`gen_ai.agent.name`, `gen_ai.conversation.id` and, for a child, `llm4s.parent.thread_id` / `llm4s.parent.run_id`. It
names both tool spans `execute_tool <tool>` with `gen_ai.operation.name = execute_tool` and `gen_ai.tool.name`: core's
`TraceEvent.ToolExecuted`, and the agent's `agent.tool_executed` custom event, whose payload names the tool, the call
and the agent. Langfuse puts `parent_thread_id` and `parent_run_id` in the trace metadata; `TraceCollector` puts them
on the span's attributes.

## Where the spec was imprecise

- **`graph.task_ended`.** The spec names the metric `graph.task_ended`, "through `TracingSubscriber`". `TaskEnded` is a
  `RunEvent.Custom`, which `TracingSubscriber` traces as `graph.custom` (its payload in the data) and `AgentTracing`
  traces under the event's own name, so it is `agent.task_ended`, beside `agent.tool_executed`.
- **Nested `TextDelta` needs a streaming child.** A child's model step streams only when its agent does, so
  `TypedAgent.withStreaming()` is added (off by default, as `AgentBuilder.withStreaming` is).
- **`TaskStarted` is sent at the claim**, not before the admission, so a refused admission (another runtime started or
  moved the child between the read and the call) announces nothing.
- **`Nested` and run scopes.** A run's own listener (`RunScope`) takes a `Nested` once it has seen its run's claim:
  nested events carry no parent run id, and the hub fences them by the parent's claim.
- **The ToolExecuted span.** The agent traces tool calls as `agent.tool_executed` custom events, not as core's
  `TraceEvent.ToolExecuted`, so the backend renames both.
- **A failed child's run.** D1 named a failed child by the run id the call was configured with, which no admission
  uses. A failed child's `ChildRef` (in `TaskOutcome.Refused` and `TaskEnded`) now names the run of its latest
  checkpoint, the one that recorded the failure, so it matches the child's own log.

## Runtime rules

Phase 3's rules 1-13 and Phase 4's 14-19:

1. **One batch, one snapshot.** Nothing new is read from the snapshot; each call's events name its own child.
2. **Total updates.** The slice writes no state key.
3. **Visibility.** Nested events are live and never reach the parent's state.
4. **At least once.** A replayed call reattaches and sends `TaskStarted` again (with a gap when nothing runs); its
   `TaskEnded` is emitted again only because the failed attempt's was discarded (tested).
5. **Block.** A blocked child is a refusal, `blocked:<guardrail>`; the parent's Block retracts nothing of the child.
6. **Full snapshots.** Nothing is added to a checkpoint.
7. **Codecs.** No stored format changes; `TaskEnded` is a `RunEvent.Custom` with its own versioned codec.
8. **Tenant.** `subscribeChild` is `GraphRuntime.subscribe`, tenant-checked and screened (tested: another tenant is
   `TenantMismatch`); nested events reach only subscriptions of the parent's thread, already screened for its tenant.
9. **No content in durable events.** `TaskEnded` holds ids, a status label, usage and a duration; a test scans both
   threads' logs for the request and the report.
10. **A failed task commits nothing.** `TaskEnded` is emitted only with a committing result; a failed attempt's is
    discarded (tested).
11. **Every model call accounted.** `TaskEnded.usage` is the runner's roll-up, the value added to the parent once.
12. **Bounded.** Nested events take the parent subscription's live slots, so an overflow is a `LiveGap` there (tested);
    the forwarder never blocks and has its own bounded queue.
13. **Types.** Every type named is defined here, in core or in K1-D1.
14. **The child thread is the journal.** A reattached settled child, and a nested subscription attaching mid-child,
    get a gap, never a replay of live events; its durable events are its own log's.
15. **No capability without a grant.** Unchanged.
16. **Identity inherited.** The child's tracing is the parent's (tested through `AgentRunEnded`).
17. **Only typed data crosses.** Nested events reach subscribers only; nothing enters the parent's thread.
18. **Supervision flows down.** Unchanged; the forwarder ends with the child's run.
19. **Child threads driven only through their parent.** `subscribeChild` reads; it drives nothing.

## Not in this slice

- Span nesting (start events and span context): Stage 5 (open question 6).
- A `MetricsCollector` projection of `TaskEnded`: Stage 5.
- Child suspension through the parent: D3.
