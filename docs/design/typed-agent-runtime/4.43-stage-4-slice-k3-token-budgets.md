# 4.43 Stage 4 slice K3: token budgets and the run's deadline ([#2047](https://github.com/llm4s/llm4s/issues/2047))

Part of the [Typed Agent Runtime design](../typed-agent-runtime-design.md), §4. Section numbers (§N.N) refer to that document and its [slice records](../typed-agent-runtime-design.md#slice-records). Phase 4 spec: `docs/superpowers/specs/2026-10-19-phase-4-subagents-design.md`, "K3".

Slice K3 of [#2044](https://github.com/llm4s/llm4s/issues/2044), a kernel slice with no dependency. D2 (§4.45) grants
a child a token budget and a deadline no larger than its parent's remaining ones, and K2 (§4.42) propagates the
deadline to running children. Neither existed as a run limit: `RunBudgets` had `maxSupersteps`, `timeout` and
`maxConcurrency`, and the deadline a timeout implies was private to the runtime, as a `System.nanoTime` value. This
slice adds the token budget, the status a turn ends with at it, and the deadline as a value a task can read.

Everything is in `llm4s-agent`. No new top-level type. The specs are `AgentTokenBudgetSpec` (the budget through the
agent, per accounted call and with usage-less completions), `RunBudgetsSpec` (the deadline), `RunConfigSpec` (the field, validation and the old overload) and
`AgentRunStatusSpec` (the status, its tracing label and the stored outcome's codec); `JAgentResultSpec` covers the
Java mapping.

## API

- **`RunBudgets.maxTokens: Option[Long]`**, the input and output tokens one run may use. `RunBudgets` is a
  growth-prone type, so:
  - `apply` takes `maxTokens: Option[Long] = None` last, and the previous three-field `apply(maxSupersteps,
    timeout, maxConcurrency)` stays as an overload without defaults that forwards with `None`.
  - `withMaxTokens(Long)` and `withMaxTokens(Option[Long])`.
  - `of` takes the same defaulted parameter and refuses a non-positive value as a `ValidationError`, as `apply` and
    the setters throw `IllegalArgumentException` for one ("maxTokens must be positive, was 0").
- **`TurnOutcome.TokenLimitReached`**, stored in `TurnState.outcome` and returned in `TurnOutput`, and
  **`AgentStatus.TokenLimitReached`**, which `AgentRun.status` derives from it. `AgentTracing` labels it
  `token_limit_reached`.
- **`RunContext.deadline: Option[Instant]`**: when the run's `RunBudgets.timeout` expires, by the runtime's `clock`.
- **Java**: `AgentStatusKind.TOKEN_LIMIT_REACHED`, mapped by `FacadeInternals.agentStatus`; it carries nothing and
  has no pending interrupts, like `STEP_LIMIT_REACHED`.

## Decisions

### What a run's tokens are

A run's tokens are `inputTokens + outputTokens` of three parts, read by the model step before it calls the model:

- the thread's usage (`LoopKeys.usage`) in the step's snapshot,
- less the thread's usage in the state the run was admitted with,
- plus what the current task has recorded and not committed (`RunContext.usage`).

The admitted state is a new `private[agent]` field, `RunContext.admitted`, set by `GraphRuntime` from the claimed
execution's state as the claim commits. It is the runtime's only knowledge of it: the graph runtime knows no
usage key, so the subtraction is the tool loop's. Outside a runtime (`CompiledGraph.step`) there is no admission,
and the thread's whole usage counts.

`thinkingTokens` are not added separately: the budget is the input and output tokens the spec names, and a
provider that bills thinking as output reports it in the output count.

### The budget is per run

Each `start`, `recover` and `resume` brings its own `RunBudgets`, so each has its own token budget, counted from
its own admission, as `maxSupersteps` and `timeout` are. A recover after a failure therefore does not count the
failed run's tokens (tested). A budget across the runs of a turn would need a durable counter the spec does not ask
for; D2's child budgets are per child run, which is what this gives.

### The check is before every accounted call

The step limit and the token budget are checked in the same place: at the top of `<id>/model`, before any
`wrapModelCall` runs. At the budget the step commits only the turn's outcome and routes nowhere, so the run
completes and the turn ends `TokenLimitReached`, as `StepLimitReached` does.

The token budget is also checked before every accounted provider call inside the step
([#2084](https://github.com/llm4s/llm4s/issues/2084)): each call a wrapper makes through `next`, and each call a hook (a model wrapper or a prompt-section hook)
makes through `ModelContext.accounted` (a summariser over chunks, an LLM judge). A call at the budget is not made: it
returns `Left` (a `private[agent]` refusal) and marks the task's usage accumulator refused. Whatever the wrappers
then return - the refusal, another error or a response - the model step commits the usage of the calls it made and
ends the turn `TokenLimitReached`, so a wrapper that swallows the refusal cannot carry the step on. Under a budget a
task's model calls run one at a time (a per-task lock held over admission, call and recording), so calls a hook fans
out concurrently are each admitted against the earlier ones' usage (tested); without a budget nothing is serialized.
A call in flight is never interrupted, so a run overshoots by at most the one provider call admitted under the budget.

In `beforeAgent` and `afterAgent` an accounted call is refused the same way, but there is no model step to end: the
hook handles the refusal as it handles any failed call (an LLM guardrail fails closed and blocks). Model calls a tool
makes count towards the run's tokens once committed, and the next model step stops the turn.

### A completion without usage is estimated

A `Completion` with `usage = None` was recorded as zero tokens, so for such a client `maxTokens` (and the child grants
D2 derives from it) never advanced ([#2084](https://github.com/llm4s/llm4s/issues/2084)). Such a call is now charged
an estimate from core's `ConversationTokenCounter` (`cl100k_base`, else four characters a token): the whole request
as input - its messages, every tool definition and a JSON response schema (the agent's output format or one set through its
completion options, from `ModelStep.responseFormat`), which providers count on every call
(tested) - the whole assistant message as output - its text, every tool call's name and arguments (also
those only on `Completion.toolCalls`) and its thinking, so a tool-only answer is not charged nearly nothing (tested) -
at least one token each way. The estimate goes into the
task's usage, and so into `LoopKeys.usage`, `AgentResult.usage` and every budget, and is logged at DEBUG. The
`ModelCallCompleted` event still carries no usage, because the provider reported none: the event records what the
provider said, the accumulator what the run is charged. `UsageSummary` gains no flag.

A retrying client (`ReliableClient`) is one call to the loop: its failed attempts return no completion, so carry no
usage and are not counted. That is a documented limit (Scaladoc of `RunBudgets` and the agents guide): a budget is
set with retries in mind.

### The deadline is fixed with the run's other deadline

`GraphRuntime` already fixed the run's deadline as a monotonic `System.nanoTime` value when the claim commits. It now
also fixes `clock.instant() + timeout` at the same moment, and every task of the run gets it as
`RunContext.deadline`. The monotonic value still decides expiry; the `Instant` is for passing on (to a child's
`RunBudgets.timeout`, K2 and D2), and for a store or service that wants a wall-clock deadline. A runtime whose clock
is stepped can make the two disagree; the runtime's own expiry is unaffected.

## Where the spec was imprecise

- **"From the thread's usage at admission".** Pending writes carried over by a `recover` are applied in the
  recovered run's first superstep, so usage a task of the failed run committed as a pending write counts towards
  the recovered run. That errs towards stopping early, never late.
- **`of`** gets the new parameter with a default rather than an overload: every existing call, named or positional,
  still compiles, and `of` takes untrusted input where the overload rule exists to protect positional `apply`.
- **The outcome on the checkpoint.** K1 (§4.41) added a durable `Checkpoint.outcome: Option[RunOutcome]` with a
  `TokenLimitReached` case that nothing wrote. This slice wires it both ways: `ToolLoop.settled` maps
  `TurnOutcome.TokenLimitReached` to it on the turn's terminal checkpoint, and `AgentRun.settledStatus` rebuilds
  `AgentStatus.TokenLimitReached` from it (tested in `RunOutcomeRebuildSpec`).

## Runtime rules

1. **One batch, one snapshot.** The check reads the model step's snapshot; a model step is one task, so no batch
   shares it. Parallel tool calls that make model calls each count only when committed, which is the "not exact"
   case rule 1 names (the budget is a stopping rule, not a reservation).
2. **Total updates.** No new update function: the step writes `LoopKeys.turn` with a replace, as the step limit does.
3. **Visibility.** The check reads usage committed by earlier supersteps plus the task's own accumulator, so a call
   made earlier in the same task is seen at once.
4. **At least once.** The check is a pure function of the snapshot, the admitted state and the task's accumulator:
   a re-run of the step after `recover` decides again, against the recovered run's own budget (tested).
5. **Block.** Unchanged: a Block keeps the turn's usage, so tokens a blocked turn used still count towards the run.
6. **Full snapshots.** No new key; `TurnState` gains no field.
7. **Codecs.** `TurnOutcome` gains a case; a stored `TurnState` written before it still reads, and one with the new
   case round-trips (tested). `AgentStatus` is not stored.
8. **Tenant.** Unchanged; budgets are per run and read nothing across threads.
9. **No content in durable events.** No new event; the tracing label is a status string.
10. **A failed task commits nothing.** Unchanged. A failed task's usage is on the run's terminal event, not in the
    thread, so it does not count towards a later run's budget.
11. **Every model call accounted.** The budget reads the accounting C1 built and checks it before every accounted
    call; it adds no unaccounted call, and a call without usage is charged an estimate, never zero.
12. **Bounded.** `maxTokens` is a bound on its own: it holds with no other limit set, also for a client that reports
    no usage (estimated; tested). It bounds when calls start, not their size, so the overshoot is one provider call,
    also when a middleware makes several in one step (tested).
13. **Types.** `RunBudgets.maxTokens`, `TurnOutcome.TokenLimitReached`, `AgentStatus.TokenLimitReached`,
    `RunContext.deadline`, `RunContext.admitted` and `AgentStatusKind.TOKEN_LIMIT_REACHED` are defined here.
14. **The child thread is the journal.** Does not apply: no child runs.
15. **No capability without a grant.** Does not apply.
16. **Identity is inherited.** Does not apply.
17. **Only typed data crosses.** Does not apply.
18. **Supervision flows down.** This slice supplies the deadline K2 propagates and D2 narrows; it propagates
    nothing itself.
19. **Child threads are driven only through their parent.** Does not apply.

## Not in this slice

- Granting a child a share of the remaining budget, and a child's deadline from its parent's: D2 (§4.45).
- Propagating cancellation and the deadline to running children: K2 (§4.42).
- A token budget across the runs of a turn, or of a thread.
