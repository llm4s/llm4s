# 4.46 Stage 4 slice D3: child suspension through the parent ([#2050](https://github.com/llm4s/llm4s/issues/2050))

Part of the [Typed Agent Runtime design](../typed-agent-runtime-design.md), §4. Section numbers (§N.N) refer to that document and its [slice records](../typed-agent-runtime-design.md#slice-records). Phase 4 spec: `docs/superpowers/specs/2026-10-19-phase-4-subagents-design.md`, "D3".

Slice D3 of [#2044](https://github.com/llm4s/llm4s/issues/2044). D1 (§4.44) reported a suspended child to the parent
model as a tool error, leaving the child parked behind a committed call. D3 surfaces the child's interrupts through the
parent instead: the parent suspends, lists them under composite ids, and the answers the application gives reach the
child through its `task` call.

Everything is in `llm4s-agent` (`org.llm4s.agent.delegation`, plus `AgentStatus`, `Agent.resume` and `ToolLoop`),
with the delegated interrupts mapped in `java-api`'s `FacadeInternals`. The new public types are `@Experimental`. The
spec is `DelegatedSuspensionSpec`; `DelegationContract`'s `Suspended` row now resumes the child through the parent, on
the in-memory store and SQLite.

## API

In `org.llm4s.agent.delegation`, each with a `ReadWriter`:

- `enum ChildInterrupt` - `Approval`, `Question`, `MiddlewareQuestion`, `Breakpoint`, each `(id, request)` as the
  child's own `AgentStatus.Suspended` gives it, and `Delegated(id, DelegatedRequest)` for the child's own delegated
  interrupts. `ChildInterrupt.of(status)` lists a suspended status's interrupts.
- `final case class DelegatedQuestion(child: ChildRef, pending: Vector[ChildInterrupt])` - what a `task` call asks.
- `final case class DelegatedAnswers(answers: Map[InterruptId, ujson.Value])` - its answer, keyed by the child's ids.
- `final case class DelegatedRequest(child: ChildRef, request: ChildInterrupt)` - one entry of the parent's
  `delegated`.

Elsewhere:

- `AgentStatus.Suspended` gains `delegated: Vector[(InterruptId, DelegatedRequest)]`, defaulted to empty.
- `ToolLoop.delegatedQuestions(suspended)`; `ToolLoop.questions` no longer lists a `task` call's question.
- `Agent.resume`, `startResume` and `streamResume` take composite ids.

## Decisions

### The `task` tools ask

The `task` tools are `AgentTool.Asking[A, DelegatedQuestion, DelegatedAnswers]`. A child that ends `Suspended`
becomes `ToolOutcome.Ask(DelegatedQuestion(child, ChildInterrupt.of(status)))`, so the parent suspends by the
existing tool-question path (§4.1): the batch's other calls finish and commit first. The resume is the tool's
`resume`: the same checks and slot as the first run, then the child runner's resume. A resume that leaves the child
suspended again asks again, as a new phase with its own effect keys, which the loop already supports.

### Flattened under composite ids

The parent lists one entry per child interrupt, `<parent interrupt>~<child interrupt>`, not a nested question, so
one queue holds everything and every answer helper works unchanged (spec decision 8). Interrupt ids are task ids
(`<superstep>.<n>`), so `~` never occurs in one. A child's own delegated interrupts are already flattened in its
status, so a grandchild's entry is `p~c~g` and names the grandchild's `ChildRef` and leaf request: the entry's
`request` is never `Delegated`. A delegated question is not listed in `questions`: `ToolLoop` marks the ask nodes of
tools whose declared question codec is `DelegatedQuestion`'s, which also holds for a wrapped tool, since wrappers keep
the spec.

### Routing the answers

`Agent.resume` groups composite answers by their first segment into the `DelegatedAnswers` of that parent
interrupt, keyed by the rest, and passes the others as they are. The task call's resume groups again before resuming
the child, so `p~c~g` reaches the grandchild one level at a time. Before grouping, `Agent.resume` checks composite ids
against the parent's current `delegated` (one read of the suspended thread): an id that is not pending, an approval
answer that is not an `ApprovalDecision`, and a breakpoint answer that is not `Breakpoint.proceed` are refused with
`GraphError.InvalidResume`, as the runtime refuses the same for its own interrupts. An interrupt answered both directly
and through composite ids is a `ValidationError`.

### Replay (rule 14)

`ChildRunner.resume` reads the child first, as `run` does. A `Suspended` child is resumed (`resumeChild`) only with
the answers it still waits on; when none is (an earlier attempt applied them and the child moved on or suspended
again), it is reattached as `run` reattaches it, with no second resume. One attempt resumes the child at most once,
and the child's own admission refuses an answer to an interrupt that is no longer parked in any case. A `Running`
child (a crash mid-resume) is recovered and a settled one returns its stored outcome, as in K2. Tested: a crash after
the child completed, and after it suspended again on a second approval, before the parent committed; `recover` runs
neither the child's tool nor its model again.

A child that refuses answers the parent-level check could not decode (a middleware question's answer of the wrong
type) is read again and its interrupts asked again, with a WARN: failing the call would leave the child parked behind a
committed call, and failing the run would make every `recover` fail the same way.

### Usage

A call that suspends because its child did adds nothing to the parent (K2): the child's usage stays in the child
thread until the resumed call settles, which adds the child's whole roll-up once. D1's interim count of a suspended
child's usage with its error is removed, since that call no longer commits.

### Edited task arguments (K2's refusal kept)

K2 refuses a task call that runs again with arguments other than those its child started with (`delegation-input`),
and D1 maps that to a tool error; the spec let D3 revisit it. D3 keeps it. Answers to a child's interrupts never edit
the parent's call: they go into `DelegatedAnswers`, and an `edit` of a child approval edits the child's call. An edit
of the `task` call itself happens at the parent's own approval, before the call runs, so its child starts with the
edited arguments and nothing conflicts. The refusal is left for the one case that remains, a child started with other
arguments, where the alternatives - a second child under the same key, or the old child's answer to a question no
longer asked - would break rule 14 or rule 17.

## Where the spec was imprecise

- `ChildInterrupt` "holds the child's interrupt id and its request" in four kinds; a grandchild's interrupt needed a
  fifth, `Delegated`, to cross one level in a `DelegatedQuestion`. The parent's entries never use it.
- The spec does not say how an invalid composite answer is reported. It is refused up front where the parent can
  check it, and re-asked where only the child can (above).
- `ToolLoop.questions` is public; it now excludes delegated questions, so `AgentStatus.questions` and the loop agree.
- Ancestor `Ask` (D2) surfacing as a child approval needs D2's narrowing permissions; it arrives with D2, through the
  same `Approval` entries.

## Runtime rules

Phase 3's rules 1-13 and Phase 4's 14-19:

1. **One batch, one snapshot.** Unchanged: a resume is built from the call's stored arguments and the answers only.
   Two parallel children suspend in one batch and are answered independently (tested).
2. **Total updates.** The `task` tools still write no parent state key; asking writes the question with the call.
3. **Visibility.** The child's report reaches the parent model as the call's tool message in the step after the
   resumed call commits.
4. **At least once.** A resumed task call runs again on `recover`; the child thread decides what it does (rule 14).
5. **Block.** Unchanged: a Block inside a resumed child ends it `Blocked`, a tool error for the parent.
6. **Full snapshots.** The parent's snapshot holds the question (the child's pending interrupt requests), bounded by
   the child's own interrupts, and later only the bounded tool result.
7. **Codecs.** No checkpoint format change: the question is the tool question's existing JSON. The new types'
   codecs are tested by a round trip. `AgentStatus` is not stored.
8. **Tenant.** The child is read and resumed under the parent's tenant (`childAtRest`, `resumeChild`).
9. **No content in durable events.** No new event.
10. **A failed task commits nothing.** A resumed call that fails commits nothing; its replay reattaches (tested).
11. **Every model call accounted.** The roll-up is added once, by the attempt that settles the call (tested: four
    calls after approve, and after a crash and `recover`).
12. **Bounded.** A resume runs under the same `maxConcurrentChildren` slot and checks as a first run; the question
    is bounded by the child's interrupts.
13. **Types.** Every type named is defined here, in D1 or in K1/K2.
14. **The child thread is the journal.** The `Suspended` row now surfaces the child's interrupts again and resumes
    the child through the parent (`DelegationContract`, both stores); a replayed resume never resumes twice (tested).
15. **No capability without a grant.** Unchanged; answers reach only the child the call started.
16. **Identity inherited.** The resumed child runs with its parent's tenant, principal, runtime and store.
17. **Only typed data crosses.** The parent receives the child's interrupt requests and sends back answers; the
    child's messages never enter the parent's thread.
18. **Supervision flows down.** A resumed child is awaited as a started one is: the parent's cancel, deadline, lost
    claim and a timeout on the call reach it (K2's runner, unchanged).
19. **Child threads driven only through their parent.** The child is resumed only by its call (`resumeChild`); a
    direct `resume` of the child thread is still refused.

## Not in this slice

- Ancestor `Ask` through narrowed permissions: D2.
- Nested streams and `TaskStarted` / `TaskEnded`: D4.
