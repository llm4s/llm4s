# 4.42 Stage 4 slice K2: child-run supervision ([#2046](https://github.com/llm4s/llm4s/issues/2046))

Part of the [Typed Agent Runtime design](../typed-agent-runtime-design.md), §4. Section numbers (§N.N) refer to that document and its [slice records](../typed-agent-runtime-design.md#slice-records). Phase 4 spec: `docs/superpowers/specs/2026-10-19-phase-4-subagents-design.md`, "K2".

Slice K2 of [#2044](https://github.com/llm4s/llm4s/issues/2044), the second kernel slice, on K1's child threads
(§4.41). It adds the runner a delegating tool call uses to run a child agent: the child is started at most once,
reattached on every replay of the call, cancelled with its parent, held to its parent's deadline, settled before a
call that reports its failure commits, and its usage is added to the parent once over its whole life. It closes the
§4.9 row "cancelling a run cancels the child runs it started" (#1277).

There is no public API. Everything is `private[agent]`, in `llm4s-agent`: `ChildRunner`, `ChildEnd`, `PriorUsage`
and `DelegationKeys` in the new package `org.llm4s.agent.delegation`, and `GraphRuntime.settleChild` in
`org.llm4s.agent.graph`. D1 (§4.44) builds the `task` tools and `TaskOutcome` on it. The spec is
`ChildSupervisionBehaviours`, run on the in-memory store (`ChildSupervisionSpec`) and on SQLite
(`SqliteChildSupervisionSpec`), through a test-only delegating tool.

## API

All `private[agent]`:

- `ChildRunner.run(agent: Agent, origin: RunOrigin, input: AgentInput, config: RunConfig, ctx: ToolContext,
  settleOnFailure: Boolean = true): Result[ChildEnd]`. `settleOnFailure` is the caller's `ChildFailure.Report`
  (D1's default); `false` is `ChildFailure.Fail`.
- `enum ChildEnd`: `Ended(result: AgentResult, usage: UsageSummary)` and `Failed(error: LLMError, usage:
  UsageSummary)`, `usage` being the child's roll-up.
- `PriorUsage(total: UsageSummary, foldedThrough: Long)` and the state key `DelegationKeys.priorUsage`
  (`delegation-prior-usage`), which every agent graph registers and the loop owns (no tool or middleware may declare
  it); and `DelegationKeys.counted` (`delegation-counted`), the children a turn's committed results counted.
- `GraphRuntime.settleChild(threadId, graph, outcome, message, config, amend)`; `recoverChild` gains `amend`.
  `GraphRuntime.childConfig`, `childAtRest`, `suspendedResult`, `storedEvents`, `claimTtl` and `now` serve the
  runner.
- The child's deadline comes from K3's `RunContext.deadline` (§4.43); `startChild`, `recoverChild` and `resumeChild`
  take `notAfter`, an absolute cap on the deadline their run fixes at its claim.
- `Agent.runtime`, `configured` and `agentRun` become `private[agent]`, and `Agent.awaitBlocking` awaits a begun run as `blocking` does; `AgentRun.result` builds an
  `AgentResult` from a state, for `await` and the runner alike; `TaskUsage.merge`.

## Decisions

### The runner reads the child first, every time

Every run of the call reads the child's latest checkpoint and acts on it (rule 14): none starts it
(`startChild`), `Running` recovers it (`recoverChild`), `Suspended` returns `Ended` with the rebuilt `Suspended`
status (D3 surfaces it), and `Completed` or `Failed` returns the outcome the terminal checkpoint records, through
`AgentRun.settledStatus`, with no run. A thread at the child's id whose checkpoint does not record this call's origin (parent, call and agent) is never
adopted: a top-level thread named like a child, or a child of another origin, is refused with a `ValidationError`,
so a delegation never returns an unrelated thread's answer. The child also records the digest of the input it was started with
(`DelegationKeys.input`, written with its first checkpoint through `startChild`'s `amend`); a call that runs again
with other arguments (an approval that edited them after the child started) derives the same child id and is refused,
rather than handed the report for the input it no longer asks about. Before that refusal, an original child still `Running` or `Suspended`, which no call will reattach, is settled `RunOutcome.Failed("abandoned", ...)` through `settleChild`, under its own claim and fenced by the parent's (#2071), so it never lingers past `childRetention`; a busy one makes the call return that `ThreadBusy` at once, and the next admission of the call settles it. Nested subscribers get a `TaskStarted` and one `LiveGap(0)` for the run found, for the run a `ThreadBusy` names as the holder, and, once the child is read again after the settlement, for the run that settled it (this settlement, or another that got there first), as for any settled child ([#2096](https://github.com/llm4s/llm4s/issues/2096)). A settled checkpoint with no `outcome` is corrupt stored state, a `Left`
(`RestoreRejected`), never a guess from the status. An admission refused because the thread moved between the read
and the call (`ThreadExists`, `NothingToRecover`, `IncompleteRun`, `PendingInterrupts`) reads again; a
`ThreadBusy` waits, with backoff from 10 ms doubling to 500 ms, interruptibly, for `min(2 x ClaimPolicy.ttl,
parent's remaining deadline, the child's stored deadline)` from the first `ThreadBusy`, then returns it as a `Left` for
the call to fail on. The child's stored deadline is D2's (`DelegationKeys.grant`, §4.45), so a recovered parent with a
fresh, long deadline never waits past the child's own ([#2086](https://github.com/llm4s/llm4s/issues/2086)); when that
is what passed and the holder still has the claim, the call returns `ThreadBusy` (`ToolOutcome.Fatal`) at the deadline,
since settling needs the child's claim; the next admission that holds it settles the child `Failed` by D2's
expired-deadline rule.

### A reported failure is settled, then read back

Under `ChildFailure.Report` the call commits the failure as a tool error, so it is never replayed. Before returning,
the runner settles the child with `settleChild`: a `Failed` checkpoint over its latest, with `outcome =
RunOutcome.failed(error)` and a `RunFailed`, under the child's own claim. It then reads the child again and returns
the failure that checkpoint records. So the live failure and the replayed one are the same value, built by the same
code (`AgentRun.settledStatus`), which D1's "a replayed refusal equals the live one" needs. A busy child is waited on
as above. Under `ChildFailure.Fail` the child is not settled: the parent run fails, and its `recover` replays the call,
which recovers the child.

`GraphError.OutputInvalid` is a Block: the child's own run settled it with `RunOutcome.OutputInvalid(errors)`. The
runner reads that checkpoint back, so `Failed(GraphError.OutputInvalid(errors))` carries the whole vector, as replay
does. D1 maps it before the generic branch. A child that ends `OutputInvalid` with no outcome recorded is settled
like any other reported failure, but with `outcome = RunOutcome.OutputInvalid(errors)` (`RunOutcome.failed` would
keep only the message), then read back, so a replay returns the same refusal with no model call (#2079). Under
`ChildFailure.Fail` it stays `Running`.

### A child stopped by its parent's deadline is left for recover

A child whose timeout was capped by the parent's deadline and that ends `DeadlineExceeded` is not settled, even
under `Report`: the parent's run is stopping for the same reason, so the call will not commit, and the parent's
`recover` with a new budget must find the child `Running`, not settled as a failure. The runner returns the error as
a `Left`. A child whose own grant was the shorter has failed on its own, and is a `Failed` like any other.

### Cancellation is `Agent.blocking`'s

The runner awaits the child through `Agent.blocking`: when the calling thread is interrupted (the parent's cancel,
its lost claim, a timeout on the call), it cancels the child, waits up to `AgentRun.Drain` for it to end (a child that
ignores its interrupt longer is logged at WARN by `AgentRun.cancelAndAwaitEnd`), and returns
`Left(CancelledError)` with the flag kept. The child commits `RunCancelled` and stays `Running` for the parent's
`recover`. A child's own children are cancelled the same way, one level at a time, because each level's runner is a
task of the level above.

### The child's deadline and identity come from the parent

The child's `RunBudgets.timeout` is `min(granted, parent's deadline - now)`, by the runtime's clock, computed again at
each admission, so time spent waiting on a busy child never lets the child outlive its parent. The parent's deadline
is also passed to the child's admission as an absolute cap (`notAfter` on `startChild` and `recoverChild`), and the
child's deadline, fixed when its claim commits, is the sooner of the two, so admission latency cannot move it past the
parent's either; a parent with no
deadline passes the grant, and a deadline already passed leaves one millisecond, so the child stops at once. The
child runs with the parent's tenant and principal, whatever its `config` says (rule 16), on the parent's runtime and
its `ClaimPolicy`, with `Durability.Sync` as every child entry point uses.

### Usage: prior usage is folded under the child's claim

A failed, cancelled or timed-out attempt records the usage of its uncommitted tasks only on its terminal event
(`RunFailed`, `RunCancelled`, `RunTimedOut`). The child carries it forward in `DelegationKeys.priorUsage`:

- `recoverChild` and `settleChild` take an `amend` function, given the child's state **under the new claim**; the
  update it returns commits with the claim's checkpoint (or the settled checkpoint), and a child's admission prunes
  only after that commit (below).
  The runner's `amend` folds the lost usage of every terminal event after `foldedThrough` into `total`, and sets
  `foldedThrough` to the last one's sequence.
- A crash before that commit writes nothing, and the next fold finds the same events. A crash after it, before the
  attempt's own terminal event, leaves no newer terminal event, so nothing is folded twice (tested by refusing the
  child's commits after its recover's claim lands).
- The roll-up is the child's `usage` key, plus `priorUsage.total`, plus the lost usage of terminal events after
  `foldedThrough`: the final attempt's own, if it failed.

`settleChild` folds too: its own `RunFailed` carries no usage and becomes the newest terminal event, so the failed
attempt's lost usage must be in `priorUsage` before it lands, or a replay's roll-up would miss it.

The roll-up is added to the calling task's accumulator only by an end the call commits as its result: a completed
report, and under `settleOnFailure` any other settled end. A suspended child (D3), a refusal under `Fail` (which D1
turns into `Fatal`) and a refused `Left` add nothing; the call's later run adds the child's whole life once. A child
cancelled with the calling task is the exception (below).

The roll-up goes into a part of the task's accumulator of its own (`TaskUsage.merge`): it commits with the task's
result like the rest, but a task that fails drops it, where its own model calls become the run's lost usage. The child
thread keeps that usage, and the call's replay, which reattaches the child, adds it then; reported as the failed
attempt's lost usage as well, it would be counted twice. So a tool that runs a child and then fails, or a parent task
cancelled after its child ended, counts the child once (tested). A call that suspends after its child ran (a wrapper asking for
approval after `next()`) commits the roll-up with the suspension, and records the child in a second loop-owned key,
`DelegationKeys.counted` (the child thread ids this turn's committed results counted, cleared as each turn starts).
When the answered call runs again and reattaches the child, the runner sees the child there and adds nothing; a
wrapper that answers without running the call again loses nothing (both tested). `settleChild` checks the tenant, that the thread is a
child, and that it is the runner's child (its origin) both before the claim and again under it. Tool-call tasks
did not commit their accumulator before: the call-tool, approval and ask nodes now add it to `LoopKeys.usage` with
their result (`ToolLoop.withUsage`), which also counts a tool's own model calls.

### A child keeps its newest event

`GraphRuntime.childConfig` raises a child's `RetentionPolicy.maxEvents` to at least 1 at every child admission, so
the previous attempt's terminal event survives until the next fold. A top-level thread may still use `Some(0)`.

### The fold commits before anything is pruned ([#2065](https://github.com/llm4s/llm4s/issues/2065))

`maxEvents >= 1` does not hold off `maxAge`, and the admission used to prune under the store claim but **before** the
claim commit that stores the fold: a commit that then failed (a crash, a refused write) lost a fold computed but never
stored, after its source event was gone, and the child's tokens, requests and cost were undercounted for good. So on a
child thread (`Run.admit`, a run with an origin) the admission's retention pass runs only **after** the claim
checkpoint carrying the folded `priorUsage` has committed, still under the claim and before the run is launched. A
commit that fails prunes nothing; a crash after it leaves the fold stored, and the next fold starts above it.

- The claim's own checkpoint and event now count against a child's limits, so a child keeps one fewer of its earlier
  checkpoints or events than before. That is safe: everything at or below the claim's event is already folded.
- That prune may raise the replay floor above `foldedThrough` (`maxAge` can remove the claim's own event, as can a
  `maxCheckpoints` of 1). The runner's event reads (`terminalsAfter`, for the fold and the roll-up) start again at
  the floor on `ReplayUnavailable` instead of failing: whatever is below it was folded before the prune removed it.
  An explicit `GraphRuntime.prune` of a child thread can still remove an unfolded terminal event; it is the caller's
  choice, and the roll-up then misses that attempt rather than failing.
- Top-level threads keep pruning before the claim commit. They fold nothing, so the ordering protects nothing there,
  and moving the pass would change what a top-level policy keeps: the claim's checkpoint and event would count
  against `maxCheckpoints` and `maxEvents`, and a `maxAge` shorter than the admission could remove the new run's own
  claim event (tested: a top-level `maxEvents = 1` keeps the previous run's last event beside the new run's).
- Tested on the in-memory store and SQLite: a `maxAge` shorter than the gap between attempts (two failed attempts),
  a claim commit refused between the fold and the commit (which failed before the change with the lost call
  uncounted), and a prune that removes the claim's own event (the next fold reads on from the floor).

## Where the spec was imprecise

- **A child cancelled with the calling task** has its usage so far (its `usage` key, `priorUsage`, and the lost usage
  on its terminal events since the fold, the drain's `RunCancelled` included) added to the task's accumulator once it
  has drained, and is not settled. The runner need not tell a timeout on the call from the parent's cancel or lost
  claim. After a timeout (`AgentToolSpec.withTimeout`, which joins the interrupted tool before returning), the call
  commits its timeout error with the accumulator, so the child is counted once there; that call is never replayed,
  and the child, left `Running`, is settled `abandoned` at the parent's next `start` (K1). After a cancel or a lost
  claim, the parent task fails and commits nothing, and the replay that reattaches the child counts it once (its fold
  covers the `RunCancelled`). Both are tested. A child whose provider ignores its interrupt past `AgentRun.Drain` has
  not drained, so only its usage committed so far is added.

- **`ChildRunner.run`** takes `settleOnFailure`, defaulting to `true`: the spec's signature gives the runner no way to
  know the call's `ChildFailure` policy, which decides whether to settle.
- **Every terminal event after `foldedThrough`** is folded, not only the newest. It is the same when one attempt ran
  between folds, and it does not lose an attempt's usage when a lapsed run commits its terminal event between the
  read and the new claim. Folding any of `RunFailed`, `RunCancelled`, `RunTimedOut` moves `foldedThrough`, with or
  without usage.
- **The fold commits before admission's retention prune** on a child thread, which could otherwise remove an event
  whose fold was not yet stored (#2065, above).
- **Usage is added only by an end the call commits**, so a refusal under `Fail` is not counted in the parent's failed
  attempt and again in its replay.
- **A deadline taken from the parent** is not a settled failure (above).

## Runtime rules

Phase 3's rules 1-13 and Phase 4's 14-19:

1. **One batch, one snapshot.** Each call derives its own child id from its key; parallel calls never share a child,
   and a child is built only from its call's arguments and the parent's immutable configuration.
2. **Total updates.** `priorUsage` replaces its value; the runner writes no parent key. A child's failure is a value
   (`ChildEnd.Failed`), decided when the tool runs.
3. **Visibility.** The child's report reaches the parent as the call's result, in the next superstep.
4. **At least once.** The call runs again on `recover`; the child thread is its record, read first every time
   (tested: no child model call after the parent crashed past a completed child, on both stores).
5. **Block.** A Block in the child ends it `Blocked` (or `OutputInvalid`), which the runner returns as such; the
   parent's Block does not touch child threads.
6. **Full snapshots.** The parent's snapshot holds only the tool result; the child's only the child.
7. **Codecs.** No format change; `PriorUsage` has a `ReadWriter`, and a key a snapshot lacks reads as its initial
   value (the graph only gained a key).
8. **Tenant.** The child runs with the parent's tenant and principal; `childAtRest` checks the tenant.
9. **No content in durable events.** No new event.
10. **A failed task commits nothing.** A failed parent attempt adds nothing; the child thread keeps its usage, and
    the replay reads it again (tested).
11. **Every model call accounted.** The roll-up covers committed usage, folded lost usage and the final terminal
    event's, added once (tested, including a failed attempt's tokens and a crash after the fold); no retention limit
    removes a terminal event before its fold has committed (#2065: a `maxAge` shorter than the gap, a refused claim
    commit).
12. **Bounded.** The busy wait by `2 x ttl` and the deadline; the drain by `AgentRun.Drain`; settled children by K1's
    retention, which settling makes apply to every child a committed call made (tested across turns).
13. **Types.** `ChildEnd`, `PriorUsage`, `DelegationKeys` and `settleChild` are defined here.
14. **The child thread is the journal.** The table, row by row: start, recover (and wait while busy), suspended,
    settled (tested, including a lost start race between two runtimes and a child held by another runtime).
15. **No capability without a grant.** Not in this slice (D2).
16. **Identity inherited.** Tenant, principal, runtime, claim policy and durability from the parent.
17. **Only typed data crosses.** Not in this slice (D1); the runner passes an `AgentInput` and returns the child's
    `AgentResult`, not its messages into the parent's thread.
18. **Supervision flows down.** The parent's cancel, its lost claim and a timeout on the call cancel the child
    (tested); the child's deadline is capped by the parent's (tested).
19. **Child threads driven only through their parent.** The runner uses only the `private[agent]` child entry points.

## Not in this slice

- The `task` tools, `TypedAgent`, `TaskOutcome`, `ChildFailure` and `DelegationConfig`: D1.
- Grants and budgets beyond the deadline: D2.
- Surfacing a suspended child's interrupts through the parent: D3.
- Nested streams and tracing ids: D4.
