# 4.38 Stage 3 slice P2: the exit examples ([#1916](https://github.com/llm4s/llm4s/issues/1916))

Part of the [Typed Agent Runtime design](../typed-agent-runtime-design.md), §4. Section numbers (§N.N) refer to that document and its [slice records](../typed-agent-runtime-design.md#slice-records). Phase 3 spec: `docs/superpowers/specs/2026-10-13-phase-3-harness-design.md`, "P2".

Slice P2 of [#1901](https://github.com/llm4s/llm4s/issues/1901), the last integration slice. Stage 3's exit criterion
(§6 row 3) is two examples, a deep-research agent and a coding agent in a workspace, that each show tool policy,
context management, streaming, checkpoint/resume and persisted artifacts, and run deterministically in CI. This slice
adds those two examples as runnable samples, and an acceptance suite for each that drives the sample's own agent on
`llm4s-testkit`'s `ScriptedLLMClient`, so the suite proves the code a reader runs. It assembles what P1 (§4.37) and
the feature slices built. The one library change is the gap the deep-research example found (below).

## What it adds

In `modules/samples`, package `org.llm4s.samples.harness`:

- `DeepResearch`: the deep-research agent. `HarnessProfile.deepAgents` on state files, with todos, summarisation,
  offload, one skill and an `AGENTS.md`, permission rules, a `fetch_page` tool, semantic memory (`llm4s-agent-memory`)
  over a SQLite memory store, an output guardrail, a typed answer (`withOutput`), streaming, and the SQLite
  checkpointer. `DeepResearchExample` runs it against the configured provider, stops its "process" after the first
  committed tool call and recovers the run in a new one.
- `CodingWorkspace`: the coding agent. The harness over a workspace (`WorkspaceFileBackend`,
  `WorkspaceSandboxBackend`, F2) with a state-file scratch mount, rules that allow writes under `/src/**` and ask
  before `execute`, todos, summarisation and offload, `AGENTS.md` from the workspace, semantic memory, an output
  guardrail, streaming, and the SQLite checkpointer. `CodingWorkspaceExample` runs it against the configured provider
  in a workspace container, asking the person running it to approve or reject each command the agent asks to run
  (stdin; no answer rejects), so `Ask` stays a review.
- `StoppingCheckpointer`: a `Checkpointer` wrapper that stops for good at a chosen commit, before or after writing it,
  as a killed process does. The samples use it to show recovery; the suites use it to place each crash.

The suites, in `modules/samples/src/test`, each on `ScriptedLLMClient` with a scripted model that answers from the
conversation it is sent (so a recovered run that sends the same conversation again gets the same reply):

- `DeepResearchAcceptanceSpec`.
- `CodingWorkspaceAcceptanceSpec`, on `llm4s-workspace-client`'s `FakeWorkspace`.
- `CodingWorkspaceIntegrationSpec` in `modules/it`, `@Workspace` tier: the coding scenario against the live
  workspace-runner container. It cannot depend on `modules/samples` (the samples' `application.conf` would reach
  every integration suite's classpath), so it builds the same profile from the workspace backends itself.

`modules/samples` now depends on `llm4s-agent-memory` and `llm4s-workspace-client` (and, in tests, on the workspace
client's tests for `FakeWorkspace` and on `llm4s-agent-testkit` for `ManualClock`). Samples are unpublished, so no
published module gains a dependency.

### The gap the examples found: application files on a state-file agent

`HarnessProfile.deepAgents` reads skills from `/skills` and instructions from `/AGENTS.md` through the profile's
backend (P1). On the default `StateFileBackend` those paths are thread state, and the only writer of thread state is
a tool call. So an agent on state files could not be given a skill or an `AGENTS.md` by its application at all: the
model had to write its own, every thread. The host backend that would serve them from disk is deferred (#1964), and a
`StoreFileBackend` can be filled only from inside a run (its writes need a run's `FileContext`). The class is "files
the application ships, which every thread reads and no tool may change"; skills and instructions are its two
instances. It is fixed once, in `llm4s-agent`:

- `StaticFileBackend(files: Map[VPath, String], maxFiles = 1000, maxBytes = 1 MiB): Result[StaticFileBackend]`,
  `@Experimental`: the files given, fixed when it is built and read-only. `ls`, `read`, `glob` and `grep` see them;
  `write`, `edit` and `delete` are refused (`BackendRefused`), so a file tool reports a tool error. The files are
  validated by the one rule every backend applies (`FileTree.validated`: text, the bounds, no path both a file and a
  directory) when it is built, so a bad bundle fails at the app edge. Mount it in a `CompositeBackend`, for example at
  `/app`, and point `SkillsConfig.withSources` and `InstructionsConfig.withPaths` there. It writes no state key, so it
  adds nothing to a checkpoint (rule 6), and a Block has nothing of it to restore.

## The two examples, and what each asserts

Both suites assert each of the five exit capabilities, and each of the three runtime-rule scenarios the issue lists.

| | Deep research | Coding/workspace |
|---|---|---|
| **Tool policy** | rules allow reads, writes under `/research/**` and `/report.md`, `fetch_page` of one site and `write_todos`; a fetch of another site and a write to `/app/...` are refused, and the model sees why | rules allow reads, writes under `/src/**` and `/notes/**`, `write_todos`, and ask on `execute`; a write to `/README.md` is denied; the run suspends at `execute` |
| **Context management** | the fetched page is offloaded to `/large_tool_results` and read back by path; the conversation is summarised, and later requests carry the summary | the command's long output is offloaded; the conversation is summarised |
| **Streaming** | `agent.stream` and `streamRecover` with `EventHandlers`: `TodosUpdated` and `TextDelta` | `stream` and `streamResume`: `TodosUpdated`, `TextDelta` and `ToolExecuted` |
| **Checkpoint/resume** | the process stops after an intermediate SQLite checkpoint; a fresh runtime over the same file `recover`s (no interrupt is pending, so not `resume`) | the run suspends at `execute`; a fresh runtime over the same file `resume`s it approved, and the command runs exactly once |
| **Persisted artifacts** | `/report.md` and the notes, read back from the SQLite file after recovery; the typed answer | the edited files in the workspace after resume |
| **Parallel batch of edits** | two notes files written by one model message | an edit and a new file under `/src/**` in one message, with a denied write beside them |
| **Crash before a finish commit** | the store stops at the finish task's commit, after memory was recorded; `recover` in a fresh runtime: one copy of the turn in memory, one offloaded page | the same, after the resumed command: one copy in memory, one offloaded output, the command still run once |
| **Output Block** | a turn that writes a file, changes the plan and is summarised, then answers with a secret: no file, plan or summary of it remains, and nothing is recorded in memory | the same through the workspace: no plan, summary or `/notes` file remains; a file it wrote in the workspace stays, because a Block cannot undo an effect outside thread state (rule 5, §4.33) |

## Runtime rules

1. **One batch, one snapshot.** Each example has a batch of file edits from one model message, with a refused call
   beside them, and the suites check every edit of it is kept: state files serialise on the backend's one lock, and
   every workspace mutation and command holds `workspace/<id>` (F1, F2), so each batch applies in call order, each
   call against what the one before it committed.
2. **Total updates.** `StaticFileBackend` writes no state; its refusals are decided when the tool runs.
3. **Visibility.** Unchanged; the suites read what a request needed from that request (the summary, the skill
   listing, the offload preview).
4. **At least once.** The crash cases are the rule's test: the finish task (`afterAgent`) runs again under
   `recover`, and memory is recorded once (C4's transactional guard over the SQLite memory store); the tool calls
   that committed do not run again, so the page and the command are fetched and run once and offloaded once. The
   command replays through F2's `Unverifiable` guard. A stop *before* a tool's commit is the other side of the rule:
   the deep-research suite stops before the fetch's commit, and the fetch runs again under `recover` (at least once)
   with the same idempotency key, so its offload replaces its own and the thread holds one. A command is the case
   that must not run again: the coding suite stops before the approved command's commit, and `recover` refuses the
   ambiguous replay (`Unverifiable`), so the command has still run once and the model is told it may have run. The scripted model
   answers from the conversation, so the replayed model call gets the reply the lost one did.
5. **Block.** The Block case of each suite: files, plan, summary and offloads of the blocked turn are restored (C1),
   memory records nothing (the middleware runs outside the guardrail, P1's placement check); the coding suite shows
   the documented limit, a workspace file the blocked turn wrote.
6. **Full snapshots.** Each example keeps the profile's default retention; `StaticFileBackend` adds no key.
7. **Codecs.** No new key or codec. Every state the suites read back is decoded from the SQLite file by a fresh
   runtime's graph, so a codec that did not round-trip would fail them.
8. **Tenant.** Each example runs under a `TenantId`, and the memory store is resolved per tenant (`MemoryFiles`, one
   SQLite file each). The deep-research suite checks that a new thread of the same tenant recalls the turn and a
   thread of another tenant recalls nothing of it.
9. **No content in durable events.** The suites read `TodosUpdated` (ids and statuses) from the durable log and text
   only from live `TextDelta`s.
10. **A failed task commits nothing.** The crash cases stop before a commit; what recovery finds is only what was
    committed.
11. **Every model call accounted.** Each suite checks the thread's usage counts every scripted model call, across the
    stopped process and the recovering one.
12. **Bounded.** `StaticFileBackend` bounds its files' count and bytes when it is built; every other bound is the
    component's, set by the profile.
13. **Types.** `StaticFileBackend` is defined here; the samples' types are sample code.

## Not in this slice

- Delegation to sub-agents (Stage 4).
- A host-directory backend (#1964). `StaticFileBackend` covers files the application ships; a host backend would
  cover a directory the agent edits.
