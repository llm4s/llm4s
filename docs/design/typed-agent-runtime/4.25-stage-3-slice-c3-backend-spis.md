# 4.25 Stage 3 slice C3: backend SPIs ([#1904](https://github.com/llm4s/llm4s/issues/1904))

Part of the [Typed Agent Runtime design](../typed-agent-runtime-design.md), §4. Section numbers (§N.N) refer to that document and its [slice records](../typed-agent-runtime-design.md#slice-records). Phase 3 spec: `docs/superpowers/specs/2026-10-13-phase-3-harness-design.md`, "C3". Replay is C4's ([4.24](4.24-stage-3-slice-c4-replay-of-external-effects.md)); where the spec and C4's record differ, this slice follows C4.

Implemented. Slice C3 of [#1901](https://github.com/llm4s/llm4s/issues/1901). It fixes the contracts the harness's feature slices build on: where files live (F1, F2, F4, F5, F6), where commands run (F2), and where long-term items are kept (`/memories/`, F7). It uses C2's `LockKey`, `ToolResource` and `Operation` ([4.23](4.23-stage-3-slice-c2-tool-permissions-timeouts-locks.md)) and C4's `EffectKey`, `ReplaySupport`, `ReplayGuard`, `StateCheck` and `AppliedKeys`. It adds no tool: F1 builds the file tools, F2 the `execute` tool. Everything is in `llm4s-agent`, package `org.llm4s.agent.harness`, `@Experimental`; `FileBackendContract` is in `llm4s-agent-testkit`.

The specs are `VPathSpec`, `StateFileBackendSpec`, `CompositeBackendSpec`, `HostFileBackendSpec` and `StoreBackendsSpec` (store, store files, sandbox) in `llm4s-agent`. In `llm4s-agent-testkit`, `FileBackendContract` runs over the state, composite, host, store-file and resolved backends, and C4's `ReplayContract` over the host backend (`Verifiable`), the store-file backend and `LongTermStore.put` (`Transactional`) and `SandboxBackend` (`Unverifiable`), each on a real `GraphRuntime` crashed at every point of C4's table.

## The problem, stated once

Every backend operation that changes something has four obligations, and earlier harness designs met each in a different place:

1. **Order inside a batch** (rule 1). Two mutations of one file in one model message must apply one after the other, the second against the first's result. C2's locks give this, if each mutation declares the right `LockKey`.
2. **Replay** (rule 4). A mutation outside thread state runs at least once. It must go through C4's guard of the class its target supports, under an `EffectKey` that names that one effect.
3. **Bounds** (rule 12). What a backend keeps, and what it returns, has a size and a count limit that holds on its own.
4. **Tenant** (rule 8). A backend shared across threads must never let one tenant's run touch another tenant's data.

**This slice makes each of the four a property of the backend type, not of the tool that calls it.** A backend computes its own locks, keys and guards its own effects, enforces its own limits, and either scopes itself by the run's tenant or is built per tenant by a resolver. F1's tools only translate arguments and results.

## API

All in `org.llm4s.agent.harness`, `@Experimental`.

### Paths: `VPath`

`opaque type VPath = String`: an absolute, `/`-separated path in a backend's own space.

- `VPath(s): Result[VPath]` accepts a string that starts with `/` and whose segments are non-empty, are not `.` or `..`, and contain no NUL, `\` or control character. One trailing `/` is dropped, so `/src/` is `/src`. Nothing is normalised away: `/a/../b` is refused, not rewritten.
- Bounds: at most 1024 UTF-8 bytes, and 255 per segment.
- `VPath.root` is `/`.
- Extensions: `value`, `segments`, `/(name): Result[VPath]`, `parent: Option[VPath]`, `name`, `isWithin(ancestor)` (segment-wise, so `/a/bc` is not within `/a/b`), `relativeTo(ancestor): Option[String]` (no leading `/`; `""` for the ancestor itself).
- A `ReadWriter` as a JSON string that validates on read, and an `Ordering` by value.

### Calls: `FileContext`

`final class FileContext private (run: RunContext, state: ThreadState, ...)` is what a backend operation knows.

- `FileContext(tool: ToolContext)` for a tool call; `FileContext(run, state)` for a hook. `FileContext.withoutState(run)` is `private[agent]`, for `ReplayContract` subjects, which get only a `RunContext`; it needs `ThreadState`'s companion widened from `private[graph]` to `private[agent]`.
- `effectKey(operation, discriminator*)` is the call's key: `ToolContext.effectKey` for a tool call, `RunContext.effectKey` for a hook (C4). A backend never builds a key another way.
- **One key per effect, even two on one path.** A call that writes one path twice performs two effects, so the `n`th request for the same operation and discriminator adds `#n` (from the second on). A call's effects run in the same order on every run, so each keeps its key across replay. This needs one `FileContext` per call, passed to every operation; a second context would count from 0 again. Without the ordinal, the second write would replay the first's outcome and never run.

### Files: `FileBackend`

```scala
trait FileBackend:
  def writes: Set[StateKey[?, ?]]              // the state keys its mutations' updates touch
  def locks(path: VPath): Set[LockKey]         // the locks a mutation of `path` holds

  def ls(path: VPath, limit: Int, ctx: FileContext): Result[Listing[FileInfo]]
  def read(path: VPath, offset: Int, limit: Int, ctx: FileContext): Result[FileLines]
  def write(path: VPath, content: String, ctx: FileContext): Result[(FileWritten, StateUpdate)]
  def edit(path: VPath, old: String, replacement: String, replaceAll: Boolean, ctx: FileContext): Result[(FileEdited, StateUpdate)]
  def delete(path: VPath, ctx: FileContext): Result[(FileDeleted, StateUpdate)]
  def find(under: VPath, accept: VPath => Boolean, limit: Int, ctx: FileContext): Result[Listing[VPath]]
  def search(under: VPath, regex: Pattern, accept: VPath => Boolean, limit: Int, ctx: FileContext): Result[Listing[GrepMatch]]

  final def glob(pattern: Glob, under: VPath, limit: Int, ctx: FileContext): Result[Listing[VPath]]
  final def grep(regex: String, under: VPath, include: Option[Glob], limit: Int, ctx: FileContext): Result[Listing[GrepMatch]]
```

- **`glob` and `grep` are built on `find` and `search`.** `glob`'s pattern (C2's `Glob`) matches a file's path relative to `under`. `grep`'s `include` matches the file's name when the pattern has no `/`, and its relative path otherwise, as ripgrep's `--glob` does. A backend implements only `find` and `search`, which take a predicate over its own paths, so `CompositeBackend` can rebase the predicate for each route. A pattern cannot be rebased.
- **Reads return `Result[A]`; mutations return `Result[(A, StateUpdate)]`.** The spec gave reads a `StateUpdate` too. No read changes state, so the pair would always be empty.
- **`locks(path)` takes the path, not the operation.** Every mutation of a path locks the same keys, and reads take none (F1). A delete of `/a` and a write of `/a/b` conflict through C2's prefix rule, whatever the operation.
- **Locks are a function of the path alone.** C2 schedules a batch once and, before each locked call runs, checks that its current locks are covered by the ones it was scheduled with (`ToolLoop.LocksChanged` otherwise), from the key's stored rendering. Every backend's `locks(path)` depends only on the path and the backend's own configuration (no I/O, no clock, no context), and its segments never contain `/`, so a key survives rendering. `FileBackendContract` checks both.
- **Resources are F1's, and concrete.** C2 treats a resource target containing `*` or `?` as an envelope covering every path it matches. A file tool's resource for a mutation is the concrete path; only `glob` and `grep` declare an envelope. A `VPath` may contain `*` or `?` as a literal character, which a permission rule then checks as an envelope: stricter, never looser.
- `Listing[A](items: Vector[A], truncated: Boolean)`: results sorted by path, at most `limit`, and `truncated` when there were more or a scan bound stopped the walk.
- `FileInfo(path, isDirectory, size, modified: Option[Instant])`, `FileLines(lines, offset, totalLines)` (0-based `offset`), `GrepMatch(path, line, text)` (1-based `line`).
- Outcomes: `FileWritten(created: Boolean, bytes: Long)`, `FileEdited(replacements: Int)`, `FileDeleted(wasDirectory: Boolean)`. Each has a `ReadWriter`, because a guard stores it. All are a few dozen bytes, far under `ReplayGuard.DefaultMaxOutcomeBytes`.
- **Text only.** Content is a `String` of UTF-8 text. A write whose content contains NUL or an unpaired surrogate is refused, and a host file that is not valid UTF-8 cannot be read or edited (a refusal) and is skipped by `search`. Binary content travels as F8b content parts.

**Errors.** `BackendRefused(operation, target, reason)` is a new `LLMError`: a refusal the model should see ("not found", "`old` occurs 3 times", "over quota"). `BackendRefused.toolOutcome(error)` maps it and C4's `GraphError.EffectReplayRefused` to `ToolOutcome.Error`, and any other error to `ToolOutcome.Fatal` (C4: a store failure or an effect whose outcome is unknown fails the task, so `recover` replays it). F1, F2 and F7 use it, so the mapping is in one place.

### `StateFileBackend`

`StateFileBackend(keyId = "files", maxBytes = 1 MiB, maxFiles = 1000, clock = Clock.systemUTC())`.

- **Its own key.** `files: StateKey[Map[VPath, FileEntry], FileUpdate]` with id `keyId`, built by the backend, so two state backends in one agent (under a composite) have two keys. Two with the same id are refused when the graph is built, as any two keys with one id are.
- `FileEntry(content: String, modified: Instant)`, and `FileUpdate` = `Put(path, entry) | Delete(path)`. The update function is total: `Put` replaces, `Delete` of a missing path is a no-op (rule 2).
- **Directories are implicit**: a path is a directory when an entry lies beneath it. A write is refused over a directory, or beneath a path that is a file. `delete` removes a file; it refuses a directory.
- **Lock: `state-files/<keyId>`** for every mutation, so a batch's mutations are applied in order, each against the state the previous one committed.
  - **The lock is needed for correctness; the batch snapshot does not cover it.** Without it, two edits of one file in a batch both read the snapshot and each `Put`s a whole new content, so the later silently drops the earlier (rule 1). The quota check, made against the snapshot, would also let a parallel batch exceed `maxBytes`. An operation-valued update cannot replace the lock: it would have to decide "`old` not found" or "over quota" when it is applied, and an update function may not refuse (rule 2). `StateFileBackendSpec` shows both: two edits in one batch both apply, and a parallel batch over quota refuses exactly one write.
  - **It changes the agent's graph, which old threads survive at rest (§4.29).** Adding file tools over a `StateFileBackend` adds its `files` key and C2's `tool-queue`, and changes the agent's version. Under §4.29 (C5) a thread at rest continues, its files starting empty; a thread in flight (suspended, or `Running` after a crash) is refused with `RestoreRejected` until it is finished or forgotten. Taking the tools out again refuses only a thread whose files hold content: the last file's delete removes the key's entry, so a thread with no files restores (`StateFileBackendSpec`).
  - Under C2's approval edits, which may only narrow locks, an edit to another path keeps the same backend-wide key and is accepted; the other backends lock the path itself, so an edit that moves the target outside the proposed path is refused (`ToolLoop.EditTakesLocks`).
- **Bounds.** The total of paths and contents as JSON strings (what each checkpoint stores, escapes included) is at most `maxBytes`, and the number of entries at most `maxFiles`. Both are checked when the tool runs, against the state the lock guarantees, so they are exact (rules 1, 2).
- No guard: its effect is the committed update. A replay recomputes the same update from the same snapshot (only `modified` differs).

### `CompositeBackend`

`CompositeBackend(default: FileBackend, routes: (VPath, FileBackend)*): Result[CompositeBackend]`.

- Routes by the longest mount that the path is within, segment-wise, and passes the routed backend the path **relative to its mount**, so a backend means the same at any mount (`/memories/notes.md` is `/notes.md` in the store's backend). A path within no mount goes to `default` unchanged.
- Construction refuses the root as a mount, and two routes with one mount.
- `writes` is the union of every backend's. `locks(path)` is the routed backend's locks for the routed path.
- **A strict ancestor of a mount is a directory**, whatever the backend it routes to holds there: it is never read, written, edited or deleted as a file (a refusal), and a file a backend holds at it is never listed. Otherwise `/scratch` could be a file in the default while `/scratch/deep` is a mount.
- `ls` lists the routed backend and adds each mount directly beneath the path as a directory. `find` and `search` span the backend of `under` and every mount beneath `under`, with each backend's predicate rebased onto composite paths, and paths of `default` that a mount shadows dropped. Results are merged in path order and cut at `limit`.

### `HostFileBackend`

`HostFileBackend.open(root: java.nio.file.Path, lockDirectory: java.nio.file.Path, maxFileBytes = 4 MiB, maxScanEntries = 100_000): Result[HostFileBackend]`. Opt-in. `replaySupport = ReplaySupport.Verifiable`.

- **The root** must be an existing directory and is resolved to its real path once, at `open` (so `/tmp` on macOS is `/private/tmp`).
- **One path names one file: a checked precondition.** The backend's locks, stripes and replay all assume it, and no per-alias normalisation can make it true on every file system. So `open` checks it and refuses a root where it does not hold:
  - the `lockDirectory` must be outside the root, both resolved with `toRealPath`, so no path of the backend reaches a lock file;
  - a probe (`HostFileBackend.probeAliases`, injectable) creates a file in the root and looks it up by its 8.3 short name (`Files.isSameFile`), then removes it. Any alias found refuses `open`, naming the behaviour and pointing to F2's workspace file backend or a `StoreFileBackend`. Case and Unicode-normalisation aliases are folded instead (below), and trailing-dot and trailing-space names are refused at resolution;
  - the file system must report hard-link counts (the `unix` attribute view, injectable as `countsLinks`), so a file with another name can be refused. NTFS reports none, so on Windows `open` is refused by default;
  - a root whose identity cannot be checked (it cannot be probed, or it reports no link counts) is refused, unless the caller passes `allowUncheckedIdentity = true`, vouching that one path names one file there.
  - the probe file is named `<prefix>-llm4s-probe-<uuid>.probe`, with a random six-character uppercase alphanumeric prefix, and its short names `<prefix>~1.PRO` to `~4.PRO` are looked up. If another, existing entry holds one of them, the short name cannot be established, and the probe refuses rather than guess;
  - **no two backends may expose one directory, or overlapping directories, under different paths** (bind mounts, symlinked mount points, nested roots), in any process. Within one JVM this is enforced: a registry of open real roots refuses a root that contains or is contained by an open one, the same real root is shared, and `close` releases it. Across processes it is a documented precondition.

  **Supported file systems:** local POSIX file systems, case-insensitive ones included (macOS). NTFS reports no hard-link counts, so a Windows root needs `allowUncheckedIdentity`, and only with 8.3 names off and no hard links. Not supported: SMB/CIFS shares and volumes with 8.3 names on.
- **Resolution.** A `VPath`'s segments are resolved under the root, and every component that exists is checked: **any symbolic link is refused**, not only one that escapes. The spec refused only an escaping link. A link inside the root makes two paths name one file, so their locks would not conflict and two writes in one batch would race. **A regular file with more than one hard link is refused too** (`unix:nlink`, where the file system reports it), for the same reason, and because the other name may be outside the root: a hard link is an escape a symbolic-link check does not see. A segment ending in a dot or a space is refused (Windows reads it as another name). A final lexical check (`normalize().startsWith(root)`) refuses anything else, such as a Windows drive segment. `ls`, `find` and `search` skip links, multiply-linked files, temporary files and names ending in a dot or a space. Resolution runs under the file's lock (below), so a cooperating writer cannot change what was checked before the effect.
- **Lock: `host/<root>/<path>`**, the real root's segments then the path's, both **folded** (Unicode NFC, then case-folded in the root locale). Locks are folded, so `/A` and `/a`, one file on a case-insensitive file system (Windows, most macOS volumes), conflict. The JVM and OS stripes use the same folded identity. On a case-sensitive file system the folding only adds conflicts, which is safe. On Windows, which also resolves 8.3 short names and ignores trailing dots and spaces (aliases no lexical rule folds), the batch lock is the root's one key. **The cross-thread and cross-process stripe is physical**: it is chosen by the real path of the target's nearest existing directory, as the file system resolves it, so any two aliases of one file (case, normalisation, 8.3 names, trailing dots, an SMB share mounted on Linux) share a stripe, and the compare-and-set under it lets only one of them apply. Mutations in one directory are serialised.
- **Every mutation runs through `ReplayGuard.verifiable`** under `effectKey("file.write" | "file.edit" | "file.delete", path.value)`:
  - `probe` digests the path: `StateCheck.of("f" + bytes)` for a file, `StateCheck.of("d")` for a directory, `StateCheck.absent` for nothing. The tag keeps a directory and a file apart.
  - `plan` reads the file once and makes every check inside the plan ("not found", "`old` occurs n times", a directory, over `maxFileBytes`), so a replay whose first attempt landed never re-checks against the edited file. It returns `Plan(before, after, presumed)(effect)`.
  - **The effect is atomic**: it writes a temporary file beside the target (`.llm4s-<uuid>.tmp`, short, so a target name near the file system's limit still has room) and moves it over the target with `ATOMIC_MOVE`. A crash therefore leaves the target either at `before` or at `after`, never torn. A torn file matches neither digest, so it would be refused for ever. This holds for any `Verifiable` file backend: F2's workspace writes must be atomic too.
  - `delete` removes a file or an empty directory, each one atomic. **A non-empty directory is refused.** The spec allowed a directory delete. A recursive delete is not atomic, so a crash part-way leaves a tree that matches neither digest, and its digest is unbounded in size.
- **Concurrent writers, in one process or several: the effect is a compare-and-set (C4).** C2's locks order calls within one batch only, so two threads editing one host file could each plan against `h0`. The effect alone runs under the file's stripe (64, by its real path): first a JVM lock of that stripe, then the OS advisory lock (`FileChannel.lock`) of that stripe's file in the **lock directory** (`lockDirectory`, which the application gives `open`: library code reads no system property, so there is no ambient default), which every backend takes in any process. The lock directory is shared by every root, so backends over overlapping roots in different processes (`/w` and `/w/sub`) lock one file for one target; a lock file inside each root would not be shared, and the two could both pass their compare-and-set. Every backend that may touch the same files, in any process, must be given the same lock directory. Under it the effect resolves the path again (a link swapped in since is refused) and writes only if the digest is still the plan's `before`. Otherwise it writes nothing and is `EffectReplayRefused` ("changed after it was planned"), a tool error the model sees, so an edit is applied or refused, never lost. No lock is held across the guard's intent and outcome commits: a run that lost its claim and stalled between them must not block its successor (`ReplayContract`'s stale-claimant cases). There is one lock file per stripe, and only one thread of a JVM uses it at a time, for two reasons. First, on POSIX, closing any channel of a file can release every lock the JVM holds on it. Second, an interrupt while waiting closes the waiting channel. The OS releases the lock of a process that dies. The cost is one open and lock per mutation.
- **Equal digests.** C4 runs a plan whose `before` equals its `after` again rather than presuming it applied. A host write of the content already there, or an edit whose replacement equals `old`, is such a plan: running it again re-checks and rewrites the same bytes, and reports the same outcome.
- **Bounds.** A file over `maxFileBytes` cannot be read or edited, and `search` skips it; content over it cannot be written. Such a file can still be replaced or deleted: its digest is then streamed (`F` and its SHA-256), so a cleanup never needs to read it into memory. `find` and `search` visit at most `maxScanEntries` entries and then report `truncated`. A directory stream has no order, so each directory is read in full, keeping only its least names (memory bounded by the cap; a huge directory's time by the tool's timeout, as the read stops on interrupt), and entries that are not listed are dropped before they count. A cut-off result is therefore the first entries in name order, whatever the file system.
- **Interruptible regex.** `search` matches over a `CharSequence` that checks the thread's interrupt flag. A catastrophic pattern is then stopped by C2's tool timeout, which interrupts the tool. Java's matcher never checks the flag itself.
- **Tenant.** Not scoped: one root is one tenant's. An application serving tenants builds one per tenant through `FileBackend.resolved` (rule 8).
- Not snapshot-consistent: a host read sees the file as it is, not as the batch's snapshot. F1's guide says so.

### `FileBackend.resolved`

`FileBackend.resolved(id: String, writes: Set[StateKey[?, ?]] = Set.empty)(resolve: FileContext => Result[FileBackend]): FileBackend`.

- Each operation resolves its backend from its context, typically by `ctx.run.config.tenantId` (§9 "Run dependencies": a captured resolver keyed by `RunContext` identity). Caching is the resolver's.
- **Lock: `resolved/<id>`, backend-wide.** Locks are computed from arguments, before any context exists (C2), so they cannot ask the resolved backend for its own. A per-path lock was wrong: a resolver may pick a `StateFileBackend`, whose quota is exact only because every mutation is ordered, and two writes of different paths in one batch would both pass the quota against the snapshot. The backend-wide key covers every resolved backend's locking. Its cost is that a batch's mutations through a resolved backend run one after another.
- `writes` is declared, because a graph registers its keys when it is built. A resolved backend whose `writes` are not within the declared set is an error when it is used (`Fatal`: a wiring bug, not a model error).

### `LongTermStore`

```scala
final case class Namespace(tenant: Option[TenantId], path: Vector[String])
final case class StoreItem(value: ujson.Value, updated: Instant)
final case class StoreEntry(key: String, item: StoreItem)
trait StoreView:                       // what a change sees, in the transaction
  def current: Option[StoreItem]
  def get(key: String): Result[Option[StoreItem]]
  def withPrefix(prefix: String, limit: Int): Result[Vector[StoreEntry]]
final case class StoreLimits private (maxItemBytes: Int, maxItems: Int, maxBytes: Long)   // apply(64 KiB, 1000, 4 MiB)
enum StoreChange[+A]:
  case Put(value: ujson.Value, outcome: A)
  case Remove(outcome: A)
  case Keep(outcome: A)

trait LongTermStore extends AppliedKeys:
  final val replaySupport = ReplaySupport.Transactional
  def limits: StoreLimits
  def get(ns: Namespace, key: String): Result[Option[StoreItem]]
  def list(ns: Namespace, prefix: String, limit: Int): Result[Listing[StoreEntry]]
  def search(ns: Namespace, query: String, limit: Int): Result[Listing[StoreEntry]]
  /** In one transaction: the outcome recorded for `effect`, or `change` applied to the current item, bounds checked, recorded under `effect`. */
  def modify[A: ReadWriter](ns: Namespace, key: String, effect: EffectKey, token: FencingToken)(change: StoreView => Result[StoreChange[A]]): Result[A]
  def forget(key: EffectKey, token: FencingToken): Result[Unit]

  final def put(ns, key, value, ctx: FileContext): Result[Boolean]     // guarded, `store.put`; true when the key was new
  final def delete(ns, key, ctx: FileContext): Result[Boolean]         // guarded, `store.delete`; true when it existed
```

- **`modify` is the one mutation primitive, and it is a read-modify-write in the target's transaction.** The spec had `put` and `delete` only. An edit (`StoreFileBackend.edit`) built from `get` then `put` is wrong twice: another thread can write between them (a lost update), and a replay whose first attempt landed re-reads the edited item and fails with "`old` not found" before it ever reaches the applied-key check. `modify` checks the applied key first, then reads, decides, checks bounds and writes, all in one transaction, serialisable within the namespace. The change decides against a `StoreView` of the namespace, so a check that spans keys is atomic with the write: `StoreFileBackend`'s tree shape (an ancestor that is a file, a descendant that makes the path a directory) is checked there, and two threads writing `/a` and `/a/b` at once cannot both succeed. A `Left` from `change` writes and records nothing (a refusal is not an applied effect).
- **Outcomes are bounded where they are kept.** An applied key outlives a crash before the guard forgets it, so `modify` refuses an outcome whose encoding is over `ReplayGuard.DefaultMaxOutcomeBytes`, before writing anything.
- **Values are copied at the store's boundary.** `ujson.Value` is mutable, so a store copies every value it is given (`put`, `StoreChange.Put`) and every value it hands out (`get`, `list`, `search`, `StoreView`); a caller cannot change stored data outside a transaction.
- **Fenced (C4).** `modify` and `forget` take the guard's claim token. The store keeps the newest token seen per `EffectKey.scope` (one per thread; a small record, kept as long as the thread's data) and, in the same transaction, refuses an older token with a `Left` that changes nothing, so a run that lost its claim can neither apply, nor read back, nor forget after its successor has touched the store. Applied keys are removed only by `forget`.
- **Transactional (C4).** `modify` records `(effect, outcome)` in the store's applied-keys table in the same transaction as the write, and for a key it has applied returns the recorded outcome and writes nothing, even if another thread has since replaced or deleted the item. `forget` removes one applied key. `put` and `delete` wrap `modify` in `ReplayGuard.transactional(ctx.run, key, this)`.
- **Keys.** `put` and `delete` use `ctx.effectKey("store.put" | "store.delete", ns.render, key)`, where `ns.render` is the namespace as a JSON array (tenant or `null`, then the path), so no two namespaces render alike.
- **Bounds (rule 12).** `maxItemBytes` bounds one item (key bytes plus encoded value bytes). `maxItems` and `maxBytes` bound one namespace. All are checked inside `modify`'s transaction, so they hold under any concurrency. An over-limit change is `BackendRefused`, which reaches the model as a tool error. `StoreLimits.apply` refuses `maxItemBytes` over `ReplayGuard.DefaultMaxOutcomeBytes`, so an outcome built from an item always fits a record.
- **Tenant (rule 8).** `Namespace` always carries the tenant, and `None` is its own single-tenant namespace. No operation reaches across namespaces.
- **`InMemoryLongTermStore(limits, clock)`** ships here: one lock for the store, `search` a case-insensitive substring match over keys and string values. Its applied keys live in a map; C4's guard bounds them (in flight plus one per crash leftover). SQLite and Postgres stores are Stage 5.

### `StoreFileBackend`

`StoreFileBackend(store: LongTermStore, path: Vector[String])`, for `/memories/`.

- **Tenant by construction.** Each operation uses `Namespace(ctx.run.config.tenantId, path)`. There is no way to point one run at another tenant's namespace. The spec took a fixed `Namespace`, which a multi-tenant application could misconfigure.
- A file is an item keyed by its `VPath` string, with value `{"content": ..., "modified": ...}`. Directories are implicit, as in `StateFileBackend`.
- **Lock: `store/<path>/<vpath>`.** A namespace is one tenant's, and a batch is one tenant's, so the tenant is not in the key.
- Mutations go through `ReplayGuard.transactional` under `effectKey("file.write" | "file.edit" | "file.delete", path.value)`, each one `store.modify` call, so `edit` decides "`old` not found" inside the transaction.
- Listings read at most `store.limits.maxItems` entries of the namespace, so `ls`, `find` and `search` are bounded by the store's own bound.

### `SandboxBackend`

```scala
final case class ExecResult private (exitCode: Int, stdout: String, stderr: String, truncated: Boolean)   // ReadWriter

trait SandboxRunner:                                   // what F2 implements
  def locks(workdir: VPath): Set[LockKey]
  def run(command: String, workdir: VPath, timeout: FiniteDuration, ctx: FileContext): Result[ExecResult]

final class SandboxBackend:                            // what the execute tool calls
  val replaySupport = ReplaySupport.Unverifiable
  def maxOutputBytes: Int
  def locks(workdir: VPath): Set[LockKey]
  def execute(command: String, workdir: VPath, timeout: FiniteDuration, ctx: FileContext): Result[ExecResult]
object SandboxBackend:
  def apply(runner: SandboxRunner, maxOutputBytes: Int = 32 KiB): SandboxBackend
  def resolved(locks: VPath => Set[LockKey], maxOutputBytes: Int = 32 KiB)(resolve: FileContext => Result[SandboxRunner]): SandboxBackend
```

- **The guard is structural.** The spec says that whatever an implementation does, C4's guard keeps a command from running twice. So the implementer writes a `SandboxRunner`, which only runs, and `SandboxBackend` is a final class that wraps every run in `ReplayGuard.unverifiable(ctx.run, ctx.effectKey("sandbox.execute", command, workdir.value), idempotent = false)`. A runner cannot bypass the guard by mistake, and a resolved runner is never guarded twice under one key.
- **Never idempotent.** C4's list says to pass `ToolHints.idempotent`. The backend passes `false` whatever the tool declares: the hint describes the tool, and an `execute` tool runs arbitrary commands, none of which can be presumed idempotent. So the guard refuses an ambiguous replay (a crash between *begin* and the run's end) and returns a completed command's stored `ExecResult`.
- **Bounds (rule 12).** `execute` cuts `stdout` and `stderr` each, on a character boundary, so that its **JSON encoding** (what the guard records, escapes included: a control character is 6 bytes) is at most `maxOutputBytes`, before the guard records the outcome, and sets `truncated`. So a runner cannot exceed the bound. `maxOutputBytes` is at most 256 KiB, so an `ExecResult` always fits C4's 1 MiB record. A cut by raw UTF-8 bytes would not: output of control characters grows sixfold when encoded, and an omitted outcome cannot be replayed.
- **Not `Transactional`.** The spec allowed a sandbox that records keys transactionally. No sandbox does, and the API would be speculative (CLAUDE.md), so it is not offered. If one does, it can be added with that sandbox.
- **Tenant.** One sandbox is one tenant's. A multi-tenant application uses `resolved` (rule 8).

## Crash windows, concurrency and retention, per backend

C4's crash table applies to each external backend by its class. What each backend adds:

- **State.** There is no window: the effect is the task's own write, which commits with the task or not at all (rule 10). Concurrent runs cannot share a thread (claims).
- **Host.** *Before begin*, *after begin before the move* and *after the move before complete* are the `Verifiable` rows, and the atomic move makes "after the move" a single point. A leftover temporary file (a crash between writing it and moving it) is garbage the backend never lists. Concurrent writers, in one process or several, meet at the effect's compare-and-set: one applies, the other is refused. A run that lost its claim cannot record *begin*, so it never moves a file; one already past *begin* is C4's "effect in flight" limit.
- **Store.** The `Transactional` rows. The applied key is written in the transaction that writes the item, and C4's guard forgets it at *complete*. A crash between them leaves a key the guard never trusts without its *begin* (C4). Two runs on different threads have different keys (the thread is in the key), so neither suppresses the other.
- **Sandbox.** The `Unverifiable` rows: a completed command replays its `ExecResult`, an ambiguous one is refused and never re-run.
- **Retention.** No backend keeps replay evidence of its own: C4's records live in the thread's store and are released by C4's commit rule. A store's applied keys are bounded by C4's protocol.

## Runtime rules

1. **One batch, one snapshot.** Every mutation declares locks: state backends one backend-wide key, so a batch's mutations apply in order against committed state and the quota check is exact; host and store backends their path, so mutations of one path (or of a directory and a path beneath it) are ordered and others run concurrently. A `Verifiable` plan reads the target, not the snapshot. Tested: two edits of one path in a batch both apply; a parallel batch over quota refuses exactly the overflowing write.
2. **Update functions are total.** `FileUpdate`'s function never fails; every refusal (quota, "not found", "`old` not unique", binary content, over a directory) is decided when the tool runs and returned as `BackendRefused`.
3. **Visibility.** Backends return their result to the caller in the same request; a state write is visible to later waves and the next superstep, which F1's guide states.
4. **At least once.** Every external mutation goes through C4's guard of its target's class, under `effectKey(op, path)`, one key per effect. The state backend needs none. No key uses `toolCallId`, `runId`, the checkpoint or the fencing token.
5. **Block.** State files are a state key, which C1 restores on a Block. Host, store and sandbox effects stay; the guide says so.
6. **Full snapshots.** The `files` key is copied into each checkpoint, so `maxBytes` bounds each copy, and the docs pair the backend with a `RetentionPolicy` (P1 sets one).
7. **Codecs.** `files` is a new key at `SchemaVersion.initial`. `VPath`'s reader validates, so a corrupted path fails `restore` with a decode error rather than producing an invalid path. Outcome types have stable codecs; a shape change needs a reader for the old shape (C4).
8. **Tenant.** The store is namespaced by tenant, and `StoreFileBackend` takes the tenant from the run, so it cannot be misdirected. Host and sandbox backends are per tenant through `resolved`. The state backend is the thread's own.
9. **No content in durable events.** Backends emit no events.
10. **A failed task commits nothing.** A state write commits only with a successful task. An external effect outlives a failed task by design, and C4's records make its replay safe.
11. **Model calls accounted.** Not applicable: no backend calls a model.
12. **Bounded.** In the table. Every limit is enforced by the backend itself, under a lock or in a transaction, whatever else is configured.
13. **Every type defined.** Above, with fields, codecs and module. Codecs: `VPath`, `FileEntry`, `FileUpdate`, the three file outcomes, `ExecResult` and `StoreChange`'s outcome (`A`'s). `StoreItem` and `Namespace` are not stored in thread state, so they have none.

## Divergence from the spec and C4

- Reads return `Result[A]`, not `Result[(A, StateUpdate)]`.
- `locks(path)`, not `locks(op)`.
- `glob`/`grep` are final, over `find`/`search`, so a composite can span routes.
- The host backend refuses every symbolic link, not only an escaping one.
- `delete` refuses a non-empty directory.
- A host effect is a compare-and-set under striped JVM and OS locks, across threads and processes; a conflicting change is refused, never lost. Multiply-linked files are refused.
- `LongTermStore.modify` is the transactional primitive; `put` and `delete` are built on it.
- `StoreFileBackend` takes a path, not a namespace, and scopes by the run's tenant.
- `SandboxBackend` is a final class over a `SandboxRunner`; no transactional sandbox.
- `SandboxBackend` never passes `idempotent = true` to the guard, whatever the tool's hints (C4's list says to pass `ToolHints.idempotent`).
- C4's record is followed on every point of replay. One addition: a `Verifiable` target's transition must be atomic (above), which C4 does not state and every `Verifiable` file backend needs.

## Limits

- **Other writers.** The OS lock orders every backend that shares the lock directory, in any process and over any overlapping root. It does not order a writer that does not take it, such as an editor, a version-control checkout, a sandbox command, or a backend given another lock directory. A replay still detects such a change (the digests), but a first run can lose it.
- **`HostFileBackend` is not a security boundary; the workspace sandbox (F2) is.** Resolution checks each component, and the effect checks again under the file's lock, but each then opens by path. So a process that does not take the backend's lock and can write the root can swap a directory for a link in between, and reach files outside the root. Pinned no-follow directory handles (`SecureDirectoryStream`, openat) would close this, but the JDK provides them only on Linux (not on macOS or Windows), and they have no relative mkdir. A Linux-only second code path was considered and declined: the host backend is a convenience for a trusted root, and untrusted execution belongs in F2's sandbox, the isolation boundary. The Scaladoc and the guide say that a host root must never be writable by an untrusted process, a sandboxed command included.
- **Hard links where the file system cannot count them.** Where the `unix` attribute view is missing (Windows), `nlink` cannot be read and a hard link is not detected. A link created after the check and before the open is the race above.
- **ABA.** A host file returned to `before` by another writer between a landed effect and its replay is written again. The final content is the intended one.
- **Temporary files** left by a crash between write and move stay until removed by hand; they are never listed.
