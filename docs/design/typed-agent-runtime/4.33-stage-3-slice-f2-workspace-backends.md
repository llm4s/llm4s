# 4.33 Stage 3 slice F2: workspace sandbox and file backends ([#1906](https://github.com/llm4s/llm4s/issues/1906))

Part of the [Typed Agent Runtime design](../typed-agent-runtime-design.md), §4. Section numbers (§N.N) refer to that document and its [slice records](../typed-agent-runtime-design.md#slice-records). Phase 3 spec: `docs/superpowers/specs/2026-10-13-phase-3-harness-design.md`, "F2".

Slice F2 of [#1901](https://github.com/llm4s/llm4s/issues/1901), a feature slice on C2 (§4.23: resources, locks), C3 (§4.25:
`FileBackend`, `SandboxBackend`, `FileBackendContract`) and C4 (§4.24: `ReplayGuard`, `ReplayContract`). It puts the
containerised workspace behind the harness's two backend SPIs, adds the `execute` tool, and deletes `WorkspaceTools`.

## API

In `llm4s-agent`, package `org.llm4s.agent.harness`, `@Experimental`:

- `ExecuteTool(backend: SandboxBackend, defaultTimeout = 60.seconds, maxTimeout = 10.minutes): AgentTool[ExecuteTool.Args]`,
  the `execute` tool (`ExecuteTool.Name`). It is built only from a `SandboxBackend`, so it knows nothing about workspaces.
  - Arguments: `command` (required), `workdir` (a `VPath`, default `/`), `timeout_seconds` (default `defaultTimeout`, at
    most `maxTimeout`). Seconds on the wire, a `FiniteDuration` inside.
  - Resource `ToolResource(Operation.Execute, <command>)`; hints `destructive` and `openWorld`, not `readOnly`, not
    `idempotent`; locks `backend.locks(workdir)`; tool timeout `maxTimeout` plus one minute, a backstop for a runner that
    does not return.
  - The result is the exit code, `stdout` and `stderr`, and a note when either was cut. A refusal (the command over
    `SandboxBackend.MaxCommandBytes`, a replay refused by C4, a command the runner's policy refuses) is a tool error; a
    failure whose outcome is unknown (the workspace unreachable) is `Fatal` (`BackendRefused.toolOutcome`).

In `llm4s-workspace-client`, package `org.llm4s.agent.harness.workspace` (the harness package, so it reuses C3's
`private[harness]` text rules), `@Experimental`:

- `WorkspaceFileBackend(id: String, workspace: WorkspaceAgentInterface, maxFileBytes: Long = 1 MiB): Result[WorkspaceFileBackend]`,
  a `FileBackend` with `replaySupport = Verifiable`.
- `WorkspaceSandboxRunner(id, workspace)`, a `SandboxRunner`, and `WorkspaceSandboxBackend(id, workspace, maxOutputBytes): Result[SandboxBackend]`,
  the `SandboxBackend` over it. C3 made `SandboxBackend` a final class so a runner cannot bypass the guard, so "the
  sandbox backend implements `SandboxBackend`" is a factory here, not a subclass.
- `WorkspaceLocks`: `workspaceLock(id)`, which every file mutation and command in the workspace holds, and
  `AllWorkspaces`, for resolved backends.

`id` names the workspace in lock keys: 1 to 128 characters of `[A-Za-z0-9._-]`, checked when the backend is built.

## The runner protocol

`WorkspaceAgentInterface` could not support a `Verifiable` backend: it had no delete, no digest and no
compare-and-set, and `readFile` returns lines joined by `\n` (a trailing newline and `\r` are lost), so an edit
could not even read what it replaces. C4's `Plan` requires the effect to be a compare-and-set against `before`,
atomic under a lock every writer of the target takes. The protocol gains, in `llm4s-workspace-shared`:

- `fileSnapshot(path, includeContent, followLinks): FileSnapshotResponse(path, kind, hash, size, content, textError)`;
  with `followLinks = false` a link is described as itself (kind `link`, hash `link:<hex>` of its target), which a
  delete plans and compares, since a delete removes the link, not what it names. A link to nothing is `dangling`.
  `kind` is `absent`, `file` or `directory`; `hash` is `absent`, `directory` or `sha256:<hex>` of the file's bytes,
  the format of C4's `StateCheck.of`, so the runner's digest of a UTF-8 file equals `StateCheck.of(text)`.
  `content` is the file's exact text when asked for, the file is at most `maxFileSize` and it is valid UTF-8;
  otherwise `textError` says why not.
- `writeFile(..., expectedHash: Option[String])`. With `expectedHash`, the runner takes its mutation lock, compares
  the path's current `hash`, refuses a mismatch with `HASH_MISMATCH` writing nothing, and otherwise writes to a
  temporary file beside the target and moves it over the target atomically, so a crash leaves `before` or
  `after`, never a torn file (C3's addition to C4).
- `deleteFile(path, expectedHash): DeleteFileResponse(path, wasDirectory)`: a file, or an empty directory, under
  the same lock and comparison.
- `executeCommand(..., maxOutputChars: Option[Long])`: the runner keeps at most `min(maxOutputChars, maxOutputSize)`
  characters of each stream, reading in chunks, so the bound holds while the output is read, not after a line of any
  length is in memory (C3's `SandboxRunner` contract, rule 12). It used to read whole lines and could keep one line of
  any size.

Every mutating file operation of the runner (`writeFile`, `modifyFile`, `deleteFile`) takes the one mutation lock,
so the comparison is atomic against every file operation. A command the runner executes can also write files, so the
runner has a command gate: a command holds one permit from before its process starts until it exits, and a file
mutation holds every permit, so no mutation runs beside a command from any client (one that waits more than 30 s is
refused as `WORKSPACE_BUSY`, having changed nothing). Every read (`fileSnapshot`, which the backend reads and plans from, and `readFile`, `exploreFiles`, `searchFiles`) takes the gate too, so no command can swap a link it resolved through while it reads; a read issued beside a running command therefore waits for it, within the same bound. A compare-and-set write goes through a link to the file it names
(the link stays), keeps the file's mode, owner, group and ACL, creates a new file as an ordinary write would (umask),
and checks the path again just before its atomic move. A file over `maxFileSize` is never read: its hash is
`oversized`, which nothing can be compared with. What a command leaves running after it exits, and writers outside the
runner (the host, through a bind mount), are outside the fence, as the guide says. Every walk (`exploreFiles`,
`searchFiles`) passes each entry through the same path checks as a requested path, links resolved, before it follows it.

`ContainerisedWorkspace` used to turn every error response into `EXECUTION_FAILED`, losing the runner's code; it now
throws `WorkspaceAgentException(error, code, details)` as `WorkspaceAgentInterfaceRemote` does, which is what lets the
backends tell a refusal from a failure.

### The runner's two invariants

Review of this slice kept finding new ways for the runner to lose a process or to judge a path by the wrong location.
Each was a missing instance of one of two invariants, so the runner now has exactly one place for each.

**1. Every process is tracked from spawn to exit (`ProcessRegistry`).** The registry is the only holder of process
references.

- `spawn` waits at the command gate (bounded). Then, in one step under the registry's lock, it asks once more
  whether the command may still start (not cancelled, connection open, registry not closed), starts the process and
  registers it. A cancellation of a command not yet registered, a disconnect (`killOwner`) and shutdown (`killAll`)
  take the same lock, so each either finds the process or stops it from starting. Only the process's own `onExit`
  removes it and returns its gate permit.
- Cancel, disconnect (`killOwner`), shutdown (`killAll`), a timeout and a failed start announcement all act through
  `kill`. A kill marks the process, kills it, and waits briefly; it never drops it.
- A process that survives its kill stays tracked, findable, cancellable and holding its permit until it has really
  exited. It is reported as `EXECUTION_FAILED` (outcome unknown), never as a completed command or an acknowledged
  cancellation.
- Each process has an owner (its connection, or the direct path), so one client never cancels or kills another's.
- `ProcessRegistrySpec` proves this per entry point (cancel, disconnect, shutdown, start-announcement failure) with
  a process that ignores its kill until the test lets it exit.

**2. One path policy, on the physical location (`checkPolicy`).** Every file operation, every walked entry and every
command working directory goes through one function. It is run on the physical location the operation acts on:

- what the path names with every link resolved, for an operation that follows it;
- the parent resolved through links plus the final name, for an operation on the entry itself (a delete, a snapshot
  of a link as itself).

The policy is:

- the location is inside the workspace (`PATH_ESCAPE_ATTEMPT`);
- with `allowedPaths`, it is inside one (`PATH_NOT_ALLOWED`);
- for a change, it is not inside a `readOnlyPaths` entry (`PATH_READ_ONLY`) and does not name `.git` metadata
  (`PATH_NOT_ALLOWED`).

An allowed or read-only path is matched both as what it names and as the entry itself, so a link the configuration
names exactly is its own entry. No call site checks a path any other way.

**A corollary: every file change commits in one place (`commitStaged`).** A write in any mode (create, append,
overwrite, compare-and-set) and a line edit stage the new content in a temporary file beside the target. Immediately
before an atomic move, the change checks four things: the path still leads to the same target, the target passes
`checkPolicy`, the target is still what the change read (or absent, for a create), and the change is within its commit
deadline. The commit deadline is `gateWait + CommitAfterGate`, and a client waits longer than that for the response, so
a change is never applied after its client gave up. A delete makes the same checks immediately before it removes the
entry. The parent directories a write creates are part of its change, so a write that does not commit removes them.

**The boundary: a file system that answers.** The runner bounds what it controls: sizes, the gate wait and each
change's commit deadline. It does not bound a single file-system call that stalls, such as a read on a hung bind
mount. The JVM cannot interrupt a blocked file read, and a stalled workspace mount stalls the container's commands as
well. Such a stall is an operator fault, as a full disk is. A slow file system is covered (the deadline refuses a late
commit); a stalled one only delays the runner, with nothing applied unseen.

**#870.** The runner now enforces `allowedPaths` (every file operation and a command's working directory; code
`PATH_NOT_ALLOWED`) and `readOnlyPaths` (every mutation; code `PATH_READ_ONLY`), beside the output bound and
`maxFileSize`, so the sandbox's limits hold in the runner whatever tool policy is configured. `networkAllowed` is still
documentation only; #870 stays open for it.

## `WorkspaceFileBackend`

A `VPath` `/src/a.txt` is the workspace path `src/a.txt`; `/` is the workspace root.

| Operation | How | Bound (rule 12) |
|---|---|---|
| `ls` | `exploreFiles(path)`, entries sorted by path | the runner's `maxDirectoryEntries`, then `limit` |
| `read` | `fileSnapshot(path, content)`, split by C3's `Text.lines`, paged | `maxFileSize`, then `limit` |
| `find` | `exploreFiles(under, recursive)`, files only, `accept` then `limit` | `maxDirectoryEntries`, then `limit` |
| `search` | `find`, then each accepted file's text matched line by line with `RegexSafetyManager.safeFind`, lazily, stopping at `limit + 1` matches | as `find` and `read`; a file that is not text or is too large is skipped, and the listing says `truncated` |
| `write` | `Verifiable`: `before` = the snapshot's hash, `after` = `StateCheck.of(content)`, effect = CAS write with parents created | content checked against `maxFileBytes` and for binary before the guard |
| `edit` | `Verifiable`: snapshot with content, C3's `Text.edited` inside the plan, CAS write | `maxFileBytes`, checked before the result is built |
| `delete` | `Verifiable`: `before` = the snapshot's hash (`directory` for a directory), `after` = `absent`, effect = CAS delete | - |

Listings show what the runner's default exclusions (`.git`, `node_modules`, ...) leave. When the runner cut a
listing at `maxDirectoryEntries`, the backend sorts what it got and marks the listing `truncated`: it cannot know
the first entries in path order of a directory it did not see whole.

Refusals the model should see are `BackendRefused`: not found, not a directory, a file where a directory is needed,
binary content, over a bound, a path the sandbox does not allow or makes read-only. `HASH_MISMATCH` is
`GraphError.EffectReplayRefused` (C4: a compare-and-set that lost writes nothing). Anything else, a transport failure
included, is a failure, so the task fails and `recover` probes the target.

## Locks

- A file mutation and `execute` alike lock the whole workspace, `files/workspace/<id>`, so a batch's edits and
  commands apply one after another in call order.
- A per-path key (the spec's `workspace/<id>/<path>`) was used first and dropped: two paths can name one file through
  a link (`/alias -> /real`), and lexical keys would let their edits reach the runner in either order. Reads take no
  lock.
- The spec says `workspace/<id>`. The keys are under C3's `FileBackend.LockRoot` (`files`) instead, because
  `FileBackend.resolved` refuses a resolved backend whose locks are outside it (that is how a resolved backend's
  `files` lock orders it against every route to the same files). Under `files`, a resolved file backend's lock
  also conflicts with every workspace command, as it must.
- A resolved sandbox (`SandboxBackend.resolved`) declares `WorkspaceLocks.AllWorkspaces` (`files/workspace`), which
  covers every runner's `files/workspace/<id>`, as `SandboxBackend` checks.

## Replay (C4)

- **Files: `Verifiable`.** Each mutation runs `ReplayGuard.verifiable` under `ctx.effectKey("file.write" |
  "file.edit" | "file.delete", path)`. `probe` is the snapshot's hash without content. `plan` reads the snapshot once,
  makes every refusal ("`old` not found", over a bound, a directory) and returns `Plan(before, after, presumed)`; the
  effect is the CAS write or delete against `before`. So a replayed edit whose first attempt landed returns its
  original `FileEdited`, not "`old` not found"; one that did not land runs again; one whose file another writer
  changed is refused, naming the conflict. A stale claimant that carries on after its successor wrote finds the hash
  moved and writes nothing.
- **Commands: `Unverifiable`.** `SandboxBackend` already runs every command through `ReplayGuard.unverifiable`, never
  idempotent: a completed command replays its stored `ExecResult`, and one that may have run is refused, never run
  again. `WorkspaceSandboxRunner` only runs. A command the runner's timeout killed is an outcome (exit code -1, as the
  WebSocket path reports it, with a note in `stderr`), recorded like any other, so a replay returns it rather than refusing.
- Both pass `ReplayContract` (`WorkspaceFileBackendReplaySpec` with C3's `FileBackendContract.EditSubject`,
  `WorkspaceSandboxBackendReplaySpec`), and the file backend passes `FileBackendContract`, over a fake
  `WorkspaceAgentInterface` that implements the protocol's comparison and atomicity in memory.

## `WorkspaceTools` and `CodeWorker`

`org.llm4s.toolapi.WorkspaceTools` and `createDefaultWorkspaceTools` are deleted (spec, "Existing tools"). Its tools
were core `ToolFunction`s that called the workspace directly: no locks, no replay guard, no bounds of their own.
`codegen.CodeWorker` moves to F1's file tools over a `WorkspaceFileBackend` and `ExecuteTool` over a
`WorkspaceSandboxBackend` (`FileTools(files) :+ ExecuteTool(sandbox)`, workspace id `codegen`), as do `WorkspaceToolExample` and the `@Workspace` agent suite. `WorkspaceFileBackend` also passes F1's `FileToolsContract`. The migration guide maps each old tool to its
replacement.

## Runtime rules

1. **One batch, one snapshot.** Workspace state is not thread state: every operation reads the workspace as it is,
   not the batch's snapshot. Mutations of one path, and every command against every mutation in its workspace, are
   ordered by their locks, so each plan reads what the previous call left. Reads take no lock, so a read issued
   beside a write may see either. Tested: two edits of one path in a batch both apply; an edit and an `execute` in
   one batch run in call order.
2. **Total updates.** The backends return `StateUpdate.empty`; every refusal is decided when the tool runs.
3. **Visibility.** A workspace effect is visible to the next operation at once, in the same request.
4. **At least once.** Above: one `EffectKey` per effect, from the call's key, the operation and the path (or the
   command and working directory); never `toolCallId`. Tested by `ReplayContract` for both backends.
5. **Block.** A Block cannot undo a workspace effect: a file written or a command run stays, and its evidence goes
   with the turn's `Failed` commit. The guide (`docs/guide/agents/index.md#tool-side-effects`) and the workspace guide
   say so.
6. **Full snapshots.** Nothing of the workspace is in thread state; C4's records are beside the checkpoints.
7. **Codecs.** No new state key. Replay outcomes are C3's `FileWritten`, `FileEdited`, `FileDeleted` and
   `ExecResult`. The protocol's new fields have defaults, so an older client or runner reads the new messages and
   a newer runner reads an older client's.
8. **Tenant.** One workspace is one tenant's: the backends are not tenant-scoped. An application serving tenants
   builds one pair per tenant and picks it with `FileBackend.resolved` and `SandboxBackend.resolved`
   (`WorkspaceLocks.AllWorkspaces`). Tested through the resolved contract.
9. **No content in durable events.** The backends and the tool emit no events; the tool's result is a tool message.
10. **A failed task commits nothing.** A workspace effect outlives a failed task by design; C4's records make its
    replay safe.
11. **Model calls accounted.** Not applicable: nothing here calls a model.
12. **Bounded.** A command is at most `SandboxBackend.MaxCommandBytes` before anything digests it; each stream at most
    `maxOutputBytes` (the runner keeps at most that many characters while reading; `SandboxBackend` cuts the JSON
    encoding again); a written file's content and an edit's result at most `maxFileBytes`, checked before they are
    sent; a read at most the runner's `maxFileSize`; listings at most `maxDirectoryEntries` and `limit`; `search` stops
    at `limit + 1` matches; the timeout at most `maxTimeout`; the tool result is the bounded `ExecResult`. The runner
    enforces its own limits whatever the client sends.
13. **Every type defined.** Above: `ExecuteTool.Args` (`command`, `workdir`, `timeout_seconds`, upickle), the
    protocol's `FileSnapshotCommand`/`Response`, `DeleteFileCommand`/`Response` and the new fields, all `macroRW` with
    defaults; the backends, runner and `WorkspaceLocks` in `llm4s-workspace-client`.

## Divergence from the spec

- Locks are `files/workspace/<id>[/<path>]`, not `workspace/<id>[/<path>]`: C3's resolver requires file locks under
  `files`.
- `WorkspaceSandboxBackend` builds a `SandboxBackend` (a final class) over a `WorkspaceSandboxRunner`.
- The runner protocol grows a snapshot, a compare-and-set write and a delete, without which the file backend cannot
  be `Verifiable`.
