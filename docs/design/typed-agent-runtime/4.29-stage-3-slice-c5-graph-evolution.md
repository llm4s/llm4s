# 4.29 Stage 3 slice C5: restore a checkpoint after the graph gains a key ([#1934](https://github.com/llm4s/llm4s/issues/1934))

Part of the [Typed Agent Runtime design](../typed-agent-runtime-design.md), §4. Section numbers (§N.N) refer to that document and its [slice records](../typed-agent-runtime-design.md#slice-records).

Slice C5 of [#1901](https://github.com/llm4s/llm4s/issues/1901), found while reviewing C2 (#1925). The
[Phase 3 spec](../../superpowers/specs/2026-10-13-phase-3-harness-design.md)'s rule 7 gives a stored *value* a
migration path (codec versions). A change to the graph's *shape* had none: `restore` compared a SHA-256 over every
node, edge, join, resume node and key id, and refused any difference (§4.2). So a key added to a graph - a loop-owned
key such as C2's `tool-queue`, or a harness feature's todos, files or memory - made every thread checkpointed before
the change fail with `RestoreRejected`. F1, F3, F4 and F7 each add keys, and P1's profile adds several at once.

This slice replaces "the fingerprints are equal" with a rule for which shape changes keep a checkpoint restorable,
stated against what the restored run can still observe: its frontier, its pending writes, and (C4) its effect records.

The specs are `GraphEvolutionSpec` (every case below, against `CompiledGraph.restore` and `GraphRuntime`), the
updated `RestoreSpec`, `GraphRuntimeSpec` and `AgentFingerprintSpec`, the "graph that gained a key" case of
`CheckpointerContract`, and `SqliteEvolvingGraphSpec` in `llm4s-agent-checkpoint-sqlite`, which restores threads from
`evolving-graph.db`, a file written by `main` before this slice, and `SqliteLocksEvolutionSpec`, which restores agent
threads from `locks-threads.db` (written by `main` after C2) under an agent that adopted or dropped locks.

## Decisions

### A snapshot records its graph's shape

- **`GraphShape`** (`org.llm4s.agent.graph`, `derives ReadWriter`) is the declared structure of a compiled graph, as
  data: `entry`, `nodes` (sorted), `edges` (each node's static successors, in declaration order), `staticJoins`
  (`GraphShape.StaticJoin(id, sources, target)`, sources sorted, joins in declaration order), `dynamicJoins` (id to target), `resumes` (sorted)
  and `keys` (sorted). `CompiledGraph.shape` returns it.
- **`GraphSnapshot.shape: Option[GraphShape]`**, last, defaulting to `None`. Every snapshot written from this slice on
  carries `Some(shape)`; `None` means the snapshot was written before. The checkpoint format stays 6: a format-6
  checkpoint without the field decodes as `None`, which is exactly what it means.
- `GraphSnapshot.fingerprint` stays, computed as before, for the legacy rule below.

### In flight and at rest

What a restored snapshot can observe of the graph depends on whether it holds unfinished work.

- **In flight**: the snapshot has a pending task, a parked continuation, or a partially arrived static or dynamic join.
  `recover` (a `Running` checkpoint) and `resume` (a `Suspended` one) continue such a run, its pending writes reused.
- **At rest**: none of those. A completed run's checkpoint is at rest. So, for `GraphRuntime.start`, is a `Failed`
  one: `start` keeps only its state and superstep and runs the new input from the entry node, so its frontier is
  never run, and `start` judges it as at rest (`restoreAtRest`, which checks only the header and the state).
  `CompiledGraph.restore` judges a snapshot by its content.
- **The runtime judges a stored checkpoint by its status too** (`restoreStored`, for `recover`, `resume` and
  `updateState`): a `Running` or `Suspended` checkpoint is in flight whatever its snapshot holds. A `Running` checkpoint
  can be quiescent - the run reached an empty frontier, and its closing `Completed` commit never landed - and
  `recover` must finish it with its own version's output projection, not a new one's (found in review). A settled
  checkpoint is judged by its content.

### The rules

Every problem is reported at once, as before (§4.2). A snapshot with a shape:

| Change | At rest | In flight |
|---|---|---|
| Graph id | refused | refused |
| Version | restores | refused: the restored tasks would run other behaviour |
| Key added | restores; the key reads its initial value | restores; the key reads its initial value |
| Key removed, the snapshot holding no value for it | restores | restores, unless a pending write updates or removes it |
| Key removed, the snapshot holding a value for it | refused | refused |
| Node added, with no static edge or static join from a stored node to it | restores | restores |
| Node added, with a static edge or static join from a stored node to it | restores | refused: a stored node's edges or joins changed |
| Node removed | refused | refused |
| Out-edges of a stored node changed | restores | refused |
| Static join over a stored node added, removed or changed | restores | refused |
| Static joins over stored nodes reordered | restores | refused: joins released in one superstep schedule their targets in declaration order |
| Static join over added nodes only | restores | restores |
| Dynamic join removed or retargeted | restores | refused |
| Dynamic join added | restores | restores |
| Entry node changed | restores | restores |
| Resume node a parked continuation or pending write names, no longer one | - | refused |

- **What the restored run depends on, in flight, is every stored node.** Its frontier runs stored nodes, and their
  bodies are the ones that ran before (the version is unchanged), so the routes they return reach any stored node,
  not only those its static edges reach. So every stored node keeps its out-edges, every static join over a stored
  node stays as it was, and every stored dynamic join keeps its target: the part of the graph the run was
  checkpointed in is unchanged. A node added is then reachable only from other added nodes, which nothing of the
  restored run reaches: "a node added that the restored frontier doesn't reach". Its edges back into stored nodes are
  allowed.
- **Values still decode through their codecs** (rule 7), and pending inputs, parked questions and pending writes still
  rebind and decode (§4.2, §4.3): nothing here relaxes that. A pending write still touches only keys its node declares
  (`checkResult`).
- **Why no node is ever removed, even at rest.** The kernel cannot see state that names a node indirectly: an agent's
  `active-agent` names an agent whose nodes a removed handoff takes away (`AgentFingerprintSpec`). A node no longer
  wanted is left declared, unreachable.
- **Why the version is free at rest.** `version` names node behaviour (§4.2). A snapshot at rest runs none of the old
  graph's tasks: the next run starts at the entry node with the new behaviour and the stored state, which decodes
  through the keys' codecs. For an agent this is what makes a harness feature addable at all: the agent's version
  hashes its prompt, tools, middleware and handoffs (§4.13), so adding a middleware changes it.

### Removal, and a loop-owned key holding pending work

A key is removable only while the thread holds no entry for it: an entry is data the new graph cannot read, and for a
loop-owned key such as `tool-queue` it is pending work (calls still waiting) that the new graph could never drain. So
the rule refuses the restore rather than strand the work. The key is judged by its stored entry, not by whether the
value is semantically empty: the codec is gone with the key, so restore cannot decode it to ask. A key that wants to
stay removable `Remove`s its entry when it returns to empty, as `tool-results` and C2's `tool-queue` do when a batch is
collected.

This also settles C2's open finding (a suspended thread with queued calls, rebuilt without lock declarations, strands
the queue). C2 registers `tool-queue` only for a family with a tool that declares locks, and keeps doing so:
- **Adopting locks** adds `tool-queue`. Its initial value is the empty schedule, so every thread checkpointed before
  restores, at rest or in flight, including one written before this slice (the legacy rule: the key is the only
  change, and the version is unchanged, since locks are not part of it). C2's `RestoreRejected` for adopting locks
  is lifted.
- **Dropping every lock** removes `tool-queue`. A thread whose stored schedule holds queued calls is refused, so the
  calls are never stranded; one with no stored schedule (between batches) restores.

Both are tested against `locks-threads.db`, written by `main` after C2 and before this slice
(`SqliteLocksEvolutionSpec`), and in memory in `AgentFingerprintSpec`.

### Snapshots written before this slice

A snapshot with no shape carries only its fingerprint, over its graph's id, version, nodes, edges, joins, resume nodes
and keys. It restores, at rest or in flight, if its version is this graph's and its fingerprint is this graph's
computed over a subset of this graph's keys that drops only keys the snapshot holds no value for: that is, if the graph
only gained keys. The search is bounded: at most 16 such keys (65,536 candidate digests, each hashing only the key
lines over a digest of the rest cloned once). Otherwise it is refused, as before, with a problem saying the snapshot
predates recorded shapes. Once such a thread runs again, its next checkpoint carries a shape and the full rules apply.

### For agents

`AgentBuilder.build` is unchanged: the version still hashes the family's settings (§4.13). So:

- **A thread at rest restores into a changed family** - another prompt, a tool, a middleware or a handoff added -
  as long as no node is removed (a handoff target, an asking tool or an asking middleware) and no key that holds a
  value is (a middleware's key). Its keys start from their initial values.
- **A thread in flight** (suspended for an approval or a question, or `Running` after a crash) needs the same family.
  Finish it - `resume` or `recover` it with the old family - or `forget` it before changing the family. Only a key the
  loop itself adds (C2's `tool-queue`) can be added under an in-flight thread.

### Effect records (C4)

C4 keeps a thread's effect records in the `Checkpointer`, each under an `EffectKey` derived from the thread, the
logical task id (`Task.arrivalId`), the operation and a discriminator, and tagged with that task id. A record holds no
node id, version or key. A commit with a checkpoint releases every record whose task is not live in it
(`GraphSnapshot.liveTasks`: the frontier's tasks and the tasks they and the parked continuations stand in for). So a
record stays valid across a shape change exactly when the restored run's tasks keep their ids and re-run the same
effects. The rules give that:

- **In flight**, the restored frontier and parked continuations are rebuilt with their stored ids, on stored nodes
  that still exist, under the same version, so a re-run task derives the keys its first attempt used and replays its
  records (`EffectReplayRuntimeSpec`: a thread recovered into a graph that gained a key and a node applies its effect
  once). The task ids the run goes on to schedule (`"<superstep>.<ordinal>"`) are the ones the old graph would have
  given: added keys schedule nothing, an added node is unreachable, and every stored node's edges, the stored static
  joins and their order, and the stored dynamic joins are unchanged. So no new task takes an id whose records belong
  to another.
- **At rest** the thread has no records: its settled checkpoint's commit released them (C4, "settled checkpoints").
  The next run starts at the entry node under the new graph, and its tasks' records are new.
- **A refused restore** commits nothing: `restore` runs before the claim commit, so no record is released or written,
  and the thread can still be recovered or resumed under its own graph (tested).


### What this amends

- **§4.2** "restore checks the structural fingerprint": restore now checks the recorded shape by the rules above, and
  the fingerprint only for snapshots without one. The problem "snapshot's graph structure differs from this graph's"
  is gone; each problem names the change.
- **§4.13** "a thread from a changed family is refused rather than misread": still so for a thread in flight. A thread
  at rest restores, since nothing of it runs under the old family. `GraphRuntimeSpec`'s case that refused a completed
  thread at a new version now restores it, and refuses a `Running` one.

## Runtime rules

1. **One batch, one snapshot.** Not affected: restore runs before any task, and a restored batch's tasks keep their ids,
   nodes and inputs.
2. **An update function that fails, fails the run.** Not affected: no update function is added. A shape that cannot be
   restored is refused at `restore`, before any task runs, never by an update.
3. **An update becomes visible from the next superstep.** Not affected: an added key reads its initial value from the
   first superstep after restore, like any key with no entry.
4. **Hooks and tools run at least once.** A task `recover` runs again is in flight, so it runs under the same version,
   in an unchanged stored graph, with the same task id and logical task (`Task.arrivalId`). Its
   `IdempotencyKey` (§4.17) and C4's `taskKey` and `EffectKey`s (thread, logical task, operation, discriminator) are
   therefore the ones its first attempt used, and its effect records still apply. At rest there is no task to re-run,
   and C4 holds no effect record for the thread: a commit with a checkpoint releases every record whose task is not
   live in it, and a snapshot at rest has no live task.
5. **A Block retracts messages only, today** (C1 widened it to every key the turn wrote). An in-flight turn keeps its
   version, so its write sets are unchanged and its recorded prior values cover every key it may write. A key added
   under an in-flight turn can only be loop bookkeeping (C2's `tool-queue`), which is empty whenever a Block can happen.
6. **Every checkpoint is a full snapshot.** Each now also carries its graph's shape: one entry per declared node, edge,
   join, resume node and key, the same for every checkpoint of a graph.
7. **Restore decodes state through each key's codec.** Unchanged, and extended to the shape: an added key has no stored
   value to decode and reads its initial value; a removed key's stored value, which nothing can decode, refuses the
   restore. `GraphSnapshot.shape` is defaulted, so every stored format-6 checkpoint decodes.
8. **Tenant.** Not affected: the tenant is checked before restore, and the shape holds no tenant data.
9. **Durable events carry no message content.** Not affected: no event is added; the shape holds ids only.
10. **A failed task commits nothing.** Not affected.
11. **Every model call is accounted.** Not affected: restore makes no model call.
12. **Bounded.** The shape is bounded by the graph's declarations, and the legacy search by 2^16 digests.
13. **Every named type exists or is defined where it is introduced.** `GraphShape` and `GraphShape.StaticJoin` are
    defined here, with their codecs, in `llm4s-agent`.

## For later slices

- **C2** keeps registering `tool-queue` only in a family with locks, and keeps removing the schedule when the batch is
  collected: adopting locks restores old threads, and dropping them refuses only a thread with queued calls.
- **F1, F3, F4, F7** add their keys with an initial value that means "nothing yet": a thread from before the feature
  reads it. A feature's key that can return to empty removes its entry (`StateOperation.Remove`), so the feature can
  later be taken out of an agent whose threads no longer use it.
- **F3** (merged first): adding `TodoMiddleware` adds `todos` and `tool-queue` and changes the agent's version, so a
  thread at rest restores with an empty plan, a thread in flight is refused, and removing it refuses a thread whose
  plan holds items (`AgentTodosSpec`, `SqliteTodosEvolutionSpec`). A thread last checkpointed before this slice has no
  shape and so is refused by the changed version until it runs once under its own agent; the same holds for every
  feature that adds a middleware or tool.
- **P1** can turn the harness profile on for an existing agent: every thread at rest restores. Threads in flight must
  be finished first; the profile's docs say so.

## Limits

- A snapshot written before this slice survives only added keys at the same version.
- In flight, the version is all or nothing: a new tool in an agent family refuses a suspended thread, even though the
  thread could not observe it. Splitting the agent's version into the parts an in-flight turn depends on is left for a
  later slice, if one needs it.
- The shape does not cover node input types (as before, §4.9): a changed input type is caught when a pending input
  fails to decode.

## Implementation plan

1. `GraphShape` and `GraphShape.StaticJoin`; `GraphBuilder.compile` builds the shape, and the fingerprint keeps its
   formula.
2. `GraphSnapshot.shape`, written by `CompiledGraph.snapshot`.
3. `CompiledGraph.restore`: the header check becomes the rules above (`GraphEvolution`, private to `graph`: the
   shaped rules and the legacy search); `restoreAtRest` for `GraphRuntime.start`. A pending write that touches a key
   the graph no longer has is already refused by `decodeWrite`.
4. Tests first: `GraphEvolutionSpec`, the `CheckpointerContract` case, `SqliteEvolvingGraphSpec` against the fixture
   written on `main`, and `AgentFingerprintSpec` for agents at rest and in flight.
