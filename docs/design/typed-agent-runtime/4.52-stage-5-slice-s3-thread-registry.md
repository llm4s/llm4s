# 4.52 Stage 5 slice S3: the thread registry ([#2132](https://github.com/llm4s/llm4s/issues/2132))

Part of the [Typed Agent Runtime design](../typed-agent-runtime-design.md), §4. Section numbers (§N.N) refer to that document and its [slice records](../typed-agent-runtime-design.md#slice-records). Stage 5 spec: `docs/superpowers/specs/2026-10-20-stage-5-production-design.md`, "S3" and "Rules every slice must satisfy".

Slice S3 of [#2129](https://github.com/llm4s/llm4s/issues/2129), after S1 ([4.50](4.50-stage-5-slice-s1-postgresql-checkpointer.md)) and on the
critical path to W1. The `Checkpointer` SPI gains what an operator, a worker and a server need to find threads: thread
metadata, a tenant-scoped list and search, and an operator's query for incomplete threads. The in-memory, SQLite and
PostgreSQL stores implement it; `CheckpointerContract` gains five cases.

## What it adds

In `org.llm4s.agent.graph` (`llm4s-agent`), every new type `@Experimental`:

- `Checkpointer.threads(query: ThreadQuery): Result[ThreadPage]` and
  `Checkpointer.incompleteThreads(tenantId: Option[TenantId], after: Option[ThreadCursor], limit: Int): Result[ThreadPage]`,
  abstract: every store implements them.
- `Commit.metadata: Option[ThreadMetadata]` (with `withMetadata`; `apply` keeps its earlier forms).
- `ThreadMetadata` - a validated `Map[String, String]` (`apply` throws, `of` returns a `ValidationError`, `empty`,
  `matches`, `toJson`/`fromJson`), at most 32 entries, keys of `[A-Za-z0-9_.:/-]{1,64}`, values up to 256 characters
  with no control character.
- `ThreadStatus` (`Idle`, `Running`, `Suspended`, `Failed`, `Completed`, `Deleted`) with `ThreadStatus.of`.
- `ThreadQuery` (growth-prone: private constructor, `apply` with defaults, `with*`, `matches`, `checkLimit`,
  `MaxLimit = 500`, `DefaultLimit = 50`), `ThreadSummary` (growth-prone), `ThreadCursor(updatedAt, threadId)` and
  `ThreadPage(threads, next)` with `ThreadPage.of`.
- `GraphRuntime.updateMetadata(threadId, metadata, config)`, and `RunConfig.metadata` - present but unused until now -
  set on the thread by a top-level `start`.

## Decisions

**Status is derived when the store is read, from columns the store keeps.** The spec leaves stored-or-derived to the
builder. The store keeps the latest checkpoint's status (or `Deleted` once `Checkpoint.deleting` is set) on the
thread's row, and the claim it already keeps; a read judges the claim by the store's clock (rule 1) and derives:

| | |
|---|---|
| `Deleted` | a cascade delete has begun and not finished (`Checkpoint.deleting`), claimed or not |
| `Running` | a live claim holds the thread - a run, or a change (`updateState`, `fork`, a delete) - on any machine |
| `Idle` | no live claim, and the latest checkpoint is incomplete (`CheckpointStatus.Running`) |
| `Suspended`, `Completed`, `Failed` | no live claim, and the latest checkpoint has that status |

`Running` follows the claim rather than the checkpoint because a server's "running threads" must not include a
thread whose process died hours ago; that thread is `Idle` - stopped, incomplete, recoverable - which is exactly what
the operator's incomplete query lists. A status cannot be stored outright, since a claim lapses by the passage of
time with no write.

**`Deleted` is a delete under way, and a removed thread is not listed.** A tombstone holds nothing of the thread, not
even its tenant (the contract says so), so it cannot be listed tenant-scoped; keeping the tenant in it would be thread
data in the tombstone. The spec's `deleted` status names the state a thread can really be found in: a cascade delete
that stopped part way, which refuses every admission until `deleteThread` finishes it. A thread `deleteThread`
removed is never listed (the caller's instruction for this slice).

**Metadata is set at start and replaced, whole, by a fenced commit.** `Commit.metadata` rides on the commit, so it is
fenced by the thread's claim (and a `Commit.fence`) exactly as every other write (rule 3), and needs no new fencing
path. `Some(m)` replaces the map whole - no merge, so a caller always knows the result - and `None` leaves it. In the
runtime:

- a top-level `start` whose `RunConfig.metadata` is not empty writes it in its claim commit, and refuses metadata
  past the limits with a `ValidationError` before it claims anything; an empty map leaves the thread's as it is, so a
  later turn need not repeat it. `recover`, `resume` and a child's run never touch it;
- `GraphRuntime.updateMetadata` is a change held and fenced as `updateState` is (`holding`), refusing another tenant,
  a child thread, a deleting thread and a thread with no checkpoint (a `ValidationError`: start it first).
- `RunConfig.metadata` stays a `Map[String, String]`, validated at start: the common case stays one call, and the
  type was already there.

A thread that has metadata but no checkpoint (a commit carrying only metadata) keeps it - the row is not dropped as
empty - but is not listed until it has a checkpoint, since its tenant is the latest checkpoint's. The limits keep
metadata small enough to sit on the thread's row and be returned in every page; it is for finding threads, never
content (rule 10), and nothing copies it into events or traces.

**Roots only, children through `children`.** The spec's "root threads by default" is read as "the registry lists root
threads"; there is no flag to include children, which `children` already pages under their parent, and an incomplete
child is its parent's to reattach, so listing it would invite an operator to recover it directly.

**Ordering, paging and the clock.** `updatedAt` is when the store last committed a checkpoint or metadata to the
thread, by the store's clock (rule 1: the database's `clock_timestamp()` in PostgreSQL, the injected `Clock`
elsewhere), never a producer's `createdAt`. Pages are by keyset on `(updatedAt, threadId)`, newest first for
`threads` and oldest first for `incompleteThreads`; a cursor names a position, not a thread, so it survives that thread
changing or being deleted. A thread changed while a caller pages moves to the front: a later page of that pass does
not list it again, and the next pass or `updatedSince` finds it. A store reads one row more than the page so that
`next` is `None` on the last page, never an empty extra page. Pages are 1 to 500 (rule 2): `ThreadQuery` refuses
others on construction, and `incompleteThreads` with a `ValidationError`.

**Tenants (rule 9).** Every query names one tenant, compared as claims are: `None` finds only threads of no tenant.
The thread's tenant is its latest checkpoint's, which admission already guards (`TenantMismatch`).

**Indexes.** Each store answers within its bound however many threads it holds:

- *SQLite, schema 8*: columns `tenant_id`, `graph_id`, `thread_status`, `updated_nanos` (epoch nanoseconds, one
  integer for the keyset) and `metadata_json` on `llm4s_checkpoint_threads`; a table
  `llm4s_checkpoint_thread_metadata (thread_id, key, value)` indexed by `(key, value, thread_id)` for equality search;
  partial indexes `WHERE parent_thread_id IS NULL AND thread_status IS NOT NULL` on `(tenant_id, updated_nanos,
  thread_id)`, with `thread_status`, with `graph_id`, and one restricted to claimed rows for `Running`. A unit test
  checks with `EXPLAIN QUERY PLAN` that every query uses a registry index and needs no temporary sort.
- *PostgreSQL, schema 2*: the same columns (`updated_at timestamptz`, `metadata jsonb`), the same partial indexes,
  thread ids compared `COLLATE "C"` so the order is the database's collation's no more, and a GIN
  (`jsonb_path_ops`) index for metadata containment (`@>`). The indexes lead with `tenant_key`, a generated column
  (`'=' || tenant_id`, or empty for none): PostgreSQL orders an index scan by the columns after one compared by
  equality, but not after one tested with `IS NULL`, so a query for threads of no tenant would otherwise sort. An
  integration test checks the plans over 20,000 threads.
- *In memory*: a scan under the store's lock, which never waits on I/O.

**Backfill.** Opening a SQLite file at version 7 or a PostgreSQL schema at version 1 fills the registry's columns from
each thread's latest checkpoint and its commit time, in the opening transaction. SQLite decodes each checkpoint with
`Checkpoint.fromJson` (a file may hold older formats and older upickle encodings), one row at a time, logging and
skipping one it cannot read, as `ensureHistory` does. PostgreSQL uses `jsonb` operators in one `UPDATE`: every
checkpoint in such a schema was written by this build line, format 8. No metadata is backfilled; there was none.

**The run-id lookup is W1's.** Rule 4's "latest checkpoint committed by any of a set of `RunId`s on a thread" does not
fall out of the registry, which indexes threads, not checkpoints: neither history table has a `run_id` column (the run
id is inside the checkpoint JSON). W1 adds the column and an index on `(thread_id, run_id, position)` with its queue
tables (SQLite schema 9, PostgreSQL schema 3), or scans the history, which `maxAttempts` bounds only per entry.

## Tests

- `CheckpointerContract` (every store), five cases: metadata kept, replaced only by a fenced commit, across a reopen,
  until the thread is deleted, and a metadata-only thread unlisted; root threads of one tenant newest first by commit
  time, paged, never another tenant's, a child or a deleted one, a cursor at a deleted thread still a position; status
  by checkpoint and live claim, by the store's clock, and every status filter; agent, metadata and `updatedSince`
  filters with paging; incomplete threads oldest first, an expired claim's included, paged and bounded. Each case uses
  a tenant of its own, so cases sharing one database do not see each other.
- `ThreadRegistrySpec` (`llm4s-agent`): the types' validation and status precedence; metadata set at start, kept by a
  start without, replaced by one with; a start with bad metadata refused before claiming; `updateMetadata` replacing,
  refused for another tenant, a new thread and a busy one.
- `SqliteCheckpointerSpec`: a version-7 file backfilled; every registry query planned through a registry index.
- `PostgresCheckpointerUnitSpec`: the registry's statements confined to the schema, keyed by tenant, bounded.
- `PostgresCheckpointerSpec` (`modules/it`, `@Docker`): a version-1 schema backfilled to exactly what the store listed
  before; the query plans over 20,000 threads.

## Left for later slices

S4's retention sweep must keep the registry's columns as they are (it prunes history, never the latest checkpoint) and
reclaim a tombstone's row, registry columns already empty. W1 adds the run-id lookup (above) and may page a tenant's
threads through `threads`. P1's example service exposes `threads` and `incompleteThreads` over HTTP.
