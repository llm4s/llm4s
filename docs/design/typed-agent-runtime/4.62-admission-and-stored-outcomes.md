# 4.62 What a guardrail refused stays out of the store ([#2853](https://github.com/llm4s/llm4s/issues/2853), [#2854](https://github.com/llm4s/llm4s/issues/2854))

Part of the [Typed Agent Runtime design](../typed-agent-runtime-design.md), §4. Section numbers (§N.N) refer to that document and its [slice records](../typed-agent-runtime-design.md#slice-records).

Two follow-ups to [#2793](https://github.com/llm4s/llm4s/issues/2793), which took a guardrail's reason out of the
durable event log and traces and left two things stored: the reason, on the blocked run's closing checkpoint, and the
query a guardrail refused, in the run's first checkpoint. The first is the next section; the second, the admission
stage, the one after.

## A blocked run's outcome names the guardrail only (#2853)

### What it changes

- `RunOutcome.Blocked(guardrail)`: the reason is no longer a field. `RunOutcome.blocked(error)` drops it.
- `AgentStatus.Blocked(guardrail, reason: Option[String])` and `TaskRefusal.Blocked(guardrail, reason: Option[String])`:
  `Some` on the result of the run that was blocked, `None` on a status rebuilt from the thread
  (`AgentRun.settledStatus`), which is what a parent reads of a delegated child that had settled before its `task`
  call ran again.
- `TaskRefusal.describe`, the parent model's tool error, names the guardrail and never the reason: the tool message is
  stored in the parent's history, and must be the same live and on a replay.
- Checkpoint format **9**. The step from 8 removes `reason` from a `Blocked` outcome as the checkpoint is read, so a
  format-8 row loads and the reason it held is not returned; a build before this change refuses format 9. No store's
  schema changes: a checkpoint is one JSON document in both SQL stores, and no column or index reads an outcome.
- `EncryptingCheckpointer` seals the error text of an outcome: a `Failed`'s message and an `OutputInvalid`'s errors.
  The text stays in its field - a message is the envelope's JSON, the errors are one element holding the envelope of
  them all - so `Checkpoint`, the stores and their codecs are unchanged. The case, a guardrail's name and a failure's
  kind stay plain: `AttemptPlan` and `AgentWorker` match on a kind, and an operator can still see how runs settle.
  Each is bound to its tenant, checkpoint and field, as a state value is, and a plain one is refused unless plaintext
  reads are on.

### Decisions

**The reason is not stored, rather than stored encrypted.** A reason quotes what the guardrail refused; a store that
keeps it keeps the refused text, whoever can read it. Encryption is optional and covers one of three stores'
deployments, so "encrypted when you remembered to wrap the store" is not a property a guardrail's author can rely on.
The cost is that a status read back from a thread has no reason. The caller of the blocked run has it, and is the one
who can decide where it may be written.

**The absence is in the type.** `Option[String]`, not an empty string and not a placeholder: a caller that prints the
reason has to say what it prints when there is none.

**A live refusal and a replayed one differ only in the reason.** `ChildEnd.Ended` from a child run that just ended has
it; the same end rebuilt from the child's thread has not. What the parent stores - the tool message, the
`TaskEnded` status label - never held it, so a replay commits the same bytes.

**Outcomes keep their shape under encryption.** The alternative was a sealed outcome as one opaque value, which needs
a new field on `Checkpoint` (a format change every store must carry) and hides which way a run settled from the
worker's attempt plan, which reads it. Sealing the text in place needs neither.

### What it does not change

- A failed run's error message is still in its `RunFailed` and `TaskFailed` events, and a queue entry's failure, in
  plain: #2793 left other errors' messages as they are, and `EncryptingCheckpointer` does not seal built-in events.
  Sealing the outcome removes one copy of that text, not the text.
- Rows written at format 8 keep the reason in the store until they are pruned or their thread is deleted. Reading
  them never returns it.

## The admission stage: a query is admitted before its turn is stored (#2854)

### The problem

A turn's first checkpoint holds its input. It has to: the input step runs as a task so that `beforeAgent` can ask a
question, suspend, and be run again by `recover`, and a task's input is what a checkpoint's frontier is (§4.4, §4.13).
So every hook that sees the query sees it after it was written, and an input guardrail's Block retracted a row that
had already been stored. For a store with a write-ahead log, a replica or a backup, written and retracted is
written.

### What it adds

- `AgentMiddleware.admit(query, context: AdmissionContext): Result[String]`, default the query unchanged. It runs in
  stack order before any `beforeAgent`.
- `AdmissionContext`: `threadId`, `agent`, `tenantId`, `principal`, and `accounted(client)` / `recordUsage`. No
  `RunContext`, no `ThreadState`.
- `UsageAccounting`, the supertype of `ModelContext` and `AdmissionContext`: what a guardrail is given to count a
  judge's calls. `Guardrail.validate(value, context)` takes it, in place of a `ModelContext`.
- `GuardrailMiddleware` runs its input guardrails in `admit`; it has no `beforeAgent`. `withInputGuardrails` installs
  one, so both forms are admission stages.
- `AgentInput.admission: Option[Admission]`, the record that travels with the input: which agents' stacks ran, the
  usage and `ModelCallCompleted` events of the stages' own model calls, and - for a refused query - the refusing
  guardrail's name. It holds no text of the query.
- `Agent.admit(threadId, query, config, history): Result[AdmittedQuery]` (`Accepted(input)` or
  `Refused(input, guardrail, reason)`) and `QueuedInput.admitted`, for a caller that stores the turn before the agent
  runs it.
- `GuardrailBlocked.reason: Option[String]`: `None` when the input step raises the block for a query an admission had
  refused.

### How a turn starts now

`Agent.start` (and `run`, `stream`, the worker's start of a queued entry) calls `ToolLoop.admit` before
`GraphRuntime.start`: the root's `admit` stack, then the stack of the agent the thread is with.

- **Admitted.** The run starts with `AgentInput(query = <as the stages left it>, admission = <record>)`. That input is
  what the first checkpoint holds, what a suspended question keeps to run the step again with, and what `recover`
  reads. The query as submitted exists only on the caller's stack.
- **Refused with `block`.** The run starts with `AgentInput(query = "", admission = <record with refusedBy>)`. Its input
  step emits the usual `agent.guardrail_blocked` and returns a Block with `GuardrailBlocked(name, None)`; the run
  closes `Failed` with `RunOutcome.Blocked(name)`. `AgentRun` was given the stage's block, so `await` returns
  `AgentStatus.Blocked(name, Some(reason))`.
- **Any other `Left`, a throw, a question, a blank query.** Nothing starts. `Agent.start` returns the `Left`.

The input step counts the record's usage and announces its events (once: not when it runs again with a middleware's
answers, by when its first run has committed them), blocks if the record says the query was refused, and runs the
`admit` stack of any owner the record does not list before the `beforeAgent` stacks.

### Decisions

**A separate stage, not `beforeAgent` moved.** The three candidates in the issue were a pre-admission hook, a first
checkpoint that holds no query until `beforeAgent` has passed, and overwriting the stored input after a block or
rewrite. The second makes the first checkpoint unrecoverable on its own - a crash before the hooks pass leaves a
thread `Running` with no input, so the caller would have to resubmit, and `recover` would mean something different
for the first step than for every other. The third is the behaviour being fixed, with one more write. The first
keeps the checkpointed input step exactly as it was, and so keeps replay, `recover`, `resume` and middleware
questions unchanged: by the time anything is stored, the question "is this text allowed in the store" is settled.

**A refused query still starts a run.** The alternative was to return `Blocked` with no run at all. That loses the
durable record that a turn was refused - the `guardrail_blocked` event, the `RunFailed`, the trace's `AgentRunEnded`,
a queue entry's close - and gives `Agent.start` a result with no `AgentRun` behind it. Starting a run whose input
holds a name and no query keeps every reader of the event log, the queue and a trace working as before, at the cost
of two checkpoints that hold nothing of the query.

**The stage cannot suspend, and its context cannot be asked to.** A stage that could ask a question would need its
question, and the query it is about, stored while it waits - which is what the stage exists to avoid. So
`AdmissionContext` is not a `ModelContext` with some members unsupported: it has no state, no `emit`, no effect
journal and no answers, and `MiddlewareStack.admit` turns a `MiddlewareAsked` into a `ValidationError`.
`GuardrailReviewMiddleware`, which asks, stays in `beforeAgent`.

**Admission is recorded on the input, not assumed.** A turn can be stored before any agent sees it: a query put on a
queue as submitted, a delegated child's task (the child runner starts the runtime directly), an input stored before
this change. The input step cannot tell those from an admitted one except by the record, so it runs the stages the
record does not list. That makes "every stage runs exactly once per owner per turn" hold on every path, and makes the
read of the thread's active agent, which `Agent` does before the thread is claimed, safe to get wrong: a handoff
target it missed is admitted in the step.

**The stages' model calls are counted by the turn.** There is no run to charge when a judge is called, so the usage
and the events are collected, carried on the input, and committed by the input step, also when it blocks. They are
counted against the run's token budget from then on; the budget cannot refuse them, since they were made before it
existed.

**Input guardrails moved to admission, so they run before `beforeAgent`.** Before, the builder's guardrails ran after
every other middleware's `beforeAgent`, on what those hooks returned. Now they run on the query as submitted. A
middleware that rewrote the query in `beforeAgent` so that a guardrail would pass it - a redaction ahead of a
`PIIDetector` - must rewrite in `admit`; text a `beforeAgent` hook adds is no longer seen by an input guardrail.

**The reason of a refusal is live-only, and tied to the call that admitted.** It is on the `AgentResult` of the
`run` that admitted and started the turn. A turn admitted in one call and blocked in another - a queued entry admitted
by its submitter, a turn held at a breakpoint before its input step and resumed - ends
`AgentStatus.Blocked(name, None)`: `Agent.admit`'s `Refused` carries the reason to the submitter.

### Replay, recover, resume and suspension

- `recover` of a turn whose run stopped after its first checkpoint runs the input step from the stored input: a
  refused one blocks again, a rewritten one runs with the rewrite. No stage runs again.
- `resume` after a `beforeAgent` question runs the input step again with the input the question kept, which is the
  admitted one with every owner recorded.
- A breakpoint before the input step parks the stored input, as above.
- A delegated child and a queued query submitted as it is are admitted by the input step: the same verdicts, with the
  query already stored by whoever stored it (the parent's tool call; the queue entry).

Tested by `GuardedContentContract` (in-memory, SQLite, PostgreSQL): a refused query in no commit a store is given and
nothing it returns, held and resumed, stopped and recovered; a rewritten one stored only as rewritten, across a failed
model call and across a suspension; a queue entry of an admitted query. `AgentAdmissionSpec` covers the stage itself.

### What it does not change

- `beforeAgent`, `afterAgent`, the model and tool wrappers, and the events of a blocked turn.
- An output block: the answer was produced by a model step and stored by it before `afterAgent` ran, and the Block
  retracts the turn as before.
- A child thread's `DelegationKeys.input` still holds a digest of the task it was started with, as submitted.
- No checkpoint format or store schema change: `admission` is an optional field of a node's input, which reads as
  `None` from an input written before it.
