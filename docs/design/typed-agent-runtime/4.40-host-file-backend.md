# 4.40 `HostFileBackend`: a file backend over a host directory ([#1964](https://github.com/llm4s/llm4s/issues/1964))

Part of the [Typed Agent Runtime design](../typed-agent-runtime-design.md), §4. Section numbers (§N.N) refer to that document and its [slice records](../typed-agent-runtime-design.md#slice-records).

Part of [#1901](https://github.com/llm4s/llm4s/issues/1901). Split out of C3 (§4.25), which built a `HostFileBackend` and
took it out before release (§4.25 "Host directories"). It is a `FileBackend` (C3) over a real directory of the host,
with `Verifiable` replay (C4, §4.24), for F1's file tools (§4.32).

## Why a narrower design

The C3 version let any number of backends, in any number of processes, write one directory at once. That needs "one
path names one file" to hold across every writer, and so needed per-file OS locks, a compare-and-set between writers
in different processes, an in-JVM registry of open roots, a mount-table model of where each root physically is, and a
shared lock directory every process had to agree on. About 40 review rounds each found another way a real file system
breaks one of them.

This design takes option (b) of the issue: **one writer per root**. `open` takes an exclusive OS lock on the root,
held until `close()`; any second open of the same or an overlapping root, from this JVM or another process, is refused
with a typed error, `HostRootInUse`. With one writer, the cross-writer machinery has nothing to do and is gone: no
per-file OS locks, no stripes, no registry of open roots, no compare-and-set between backends.

What one writer does not solve stays: aliases a single writer could still be fooled by (links, short names, mounts), a
root replaced under the backend, bounded reads, attributes kept on replace, and what `close()` does to operations
already running.

## API

In `llm4s-agent`, package `org.llm4s.agent.harness`, `@Experimental`:

```scala
final class HostFileBackend extends FileBackend with AutoCloseable:
  val root: Path                 // the real path of the directory given to open
  val maxFileBytes: Long
  val maxScanEntries: Int
  val replaySupport: ReplaySupport // Verifiable
  def close(): Unit

object HostFileBackend:
  def open(
    root: Path,
    lockDirectory: Path,
    maxFileBytes: Long = DefaultMaxFileBytes,     // 4 MiB
    maxScanEntries: Int = DefaultMaxScanEntries,  // 100_000
    allowUncheckedIdentity: Boolean = false
  ): Result[HostFileBackend]

final case class HostRootInUse(root: Path, conflict: HostRootInUse.Conflict) extends LLMError
```

`HostRootInUse.Conflict` is `SameRoot`, `WithinOpenRoot` (an open backend's root contains this one) or
`ContainsOpenRoot` (this root contains an open backend's root). Every other refusal of `open` is a `ValidationError`
naming the field (`root`, `lockDirectory`, `maxFileBytes`, `maxScanEntries`).

## The single-writer lock

### Identity

A directory's **identity** is its file key (device and inode) where the JDK reports one: Linux and macOS. Elsewhere
(Windows) it is its real path, case-folded: `toRealPath` there is the final path the OS resolves, with junctions,
symbolic links and 8.3 short names resolved, and NTFS compares names without case. A path's identity chain is the
identity of its real path and of each of its parents up to the file system's root.

Identity is physical where the file system has file keys, so one directory reached by two paths has one identity: a
symbolic link, a macOS firmlink, or a Linux bind mount (whose mount point has its source directory's device and
inode) all lead to the same lock.

### Lock files and where they live

`lockDirectory` holds one lock file per identity: `<lockDirectory>/<sha-256 of the identity>.lock`. At `open`, the
backend takes, with `tryLock` (never waiting):

- an **exclusive** lock on its root's lock file, and
- a **shared** lock on the lock file of each strict ancestor in its identity chain.

So the same root twice is exclusive against exclusive, an open ancestor's exclusive lock refuses a descendant's shared
one, and an open descendant's shared lock refuses an ancestor's exclusive one. Two siblings share their ancestors'
locks and do not conflict. Each lock is a `FileChannel` lock on the whole file, held until `close()`. The OS releases
the locks of a process that dies, so a crash never leaves a root locked.

Why a lock directory, and not a lock file inside the root: a backend must also refuse an *ancestor* opened after it,
and an ancestor cannot find a lock file somewhere beneath it without walking its whole tree. A descendant can name its
ancestors' locks only if they live somewhere it can write, which the ancestors themselves (`/`, `/home`) may not be.
The lock directory is that place.

The lock directory is the application's choice, as a setting, because only it knows which processes share files. The
library reads no system property for a default; a temporary directory would also be a poor one, since `/tmp` cleaners
delete old files, and a lock file deleted while held lets a second process create a new one and lock it too. The
rules, stated on `open`:

- Every process that may open the same or overlapping roots on one host uses **one** lock directory, on a local file
  system (OS locks over NFS or SMB are not dependable), and nothing prunes it.
- It must not be inside the root: `open` refuses a lock directory whose identity chain contains the root's, which
  also catches one inside through a bind mount. A root inside the lock directory is harmless (the lock files are
  directly in it) and allowed.
- Lock files are never deleted. Deleting one races with another process that has it open and is about to lock it:
  that process would hold a lock on a file no longer reachable, while a third creates and locks a new one. A lock
  file is a few bytes per directory ever opened or passed through, and a directory no backend runs against can be
  emptied by hand.

### One channel per lock file, per JVM

On POSIX, closing *any* channel of a file releases every lock the process holds on it, whichever channel took them
(the `FileChannel` Javadoc warns of it; a test of JDK 21 on macOS confirms it: a second channel opened and closed on a
locked file lets another process take the lock, while the JDK still reports it valid). Siblings in one JVM share their
ancestors' lock files, and a refused open has opened a channel on a file another backend in the JVM holds.

So a JVM-wide table (`RootLocks`) keeps **one** channel per lock file, keyed by the lock file's own identity, with
the exclusive or shared holds this JVM has on it, and closes the channel only when the JVM holds none. It decides
nothing about roots: conflicts between JVMs are the OS lock's, and within the JVM the table applies the same rule
(exclusive against anything, shared against exclusive), because POSIX locks never conflict within one process.

### What the lock does not do

It excludes other **backends** that use the same lock directory, on the same host and in the same mount namespace
(a container sees its own lock directory). A root's ancestors are those of its real path, so a Linux bind mount of a
directory *inside* an open root, mounted somewhere outside it, is a root whose ancestors do not include the open one:
the two are not seen to overlap. Telling would need the mount table's model of where each directory physically is,
which this design dropped; making such a mount needs privilege, and the guide says not to. A writer that takes no lock (an editor, `git`, a
build, a backend given another lock directory) is not excluded. A replay still sees such a change through its digests
and refuses (C4), but a first run can overwrite it.

## The identity model inside the root

One path names one file, so the path the model sees in a listing is the only way to reach that file, a replay record
keyed by path is about one file, and no name leads outside the root. `open` refuses a root where it cannot check
this, and each operation refuses a path where it does not hold:

- **Symbolic links** are refused at every component, wherever they point; listings and walks skip them.
- **Hard links.** A regular file with more than one link (`unix:nlink`) is refused and never listed: its other name
  may be outside the root. A file system that reports no link counts (NTFS: the JDK has no `unix` view on Windows) is
  refused at `open` unless `allowUncheckedIdentity`, the caller vouching that the root holds no hard links.
- **8.3 short names.** `open` probes the root: it creates `<prefix>-llm4s-probe-<uuid>.probe` (a random six-character
  prefix), looks up `<prefix>~1.PRO` to `~4.PRO`, and removes it. A short name that is the probe refuses `open`, and
  `allowUncheckedIdentity` does not waive it. A root that cannot be probed (read-only), or another entry holding the
  probe's prefix, is refused unless `allowUncheckedIdentity`. Probe files a failed cleanup left are hidden and
  reserved.
- **Trailing dots and spaces.** A segment ending in either is refused: Windows drops them, so `a.` is `a`.
- **Mounts beneath the root.** A path component whose file system differs from the root's is never entered (refused,
  and left out of listings and walks). On Linux the mount table (`/proc/self/mountinfo`) is also read, at `open` and
  at each operation, because a bind mount of the root's own file system has the root's device. A mount beneath the
  root refuses `open`, and every operation once one appears. An unreadable mount table on Linux refuses `open` unless
  `allowUncheckedIdentity`.
- **A root replaced after open** (a mount over it, or another directory moved into its place) is refused at every
  operation: the root's file key, file system and creation time are taken at `open` and compared each time.
- **Case and Unicode-normalisation aliases** (`/A` and `/a` on macOS and Windows) are not refused: every mutation of
  one backend takes one lock key, so two names of one file in a batch are ordered anyway, and each effect checks the
  file it reaches.
- **Reserved names.** The backend's temporary files (`.llm4s-<uuid>.tmp`) and probe files, compared case-folded, are
  refused as a path segment and never listed.

## Operations

- **Locks.** Every mutation holds `files/host/<root id>`, one key for the backend. A batch's file mutations through
  one host backend run one after another. This is what makes case and normalisation aliases harmless, and a host
  mutation is a few file operations.
- **Replay.** Each mutation runs through `ReplayGuard.verifiable` under `ctx.effectKey("file.write" | "file.edit" |
  "file.delete", path)`. The probe digests the path (`f` and the bytes for a file, `F` and a streamed SHA-256 for one
  over `maxFileBytes`, `d` for a directory, absent). The plan reads the file once and does every check ("not found",
  "`old` occurs n times", over the limit).
- **Compare-and-set, within the one writer.** C4's `Plan` requires the effect to compare and set against `before`
  under a lock every writer takes. With one writer per root, that lock is the backend's own: the effect takes the
  backend's effect lock, resolves the path again, digests it and writes only if it is still `before`, else returns
  `EffectReplayRefused`. It orders this backend's threads, such as a run that lost its claim and its successor.
- **Atomic.** A write or edit writes a temporary file beside the target, flushes it and moves it over the target
  (`ATOMIC_MOVE`), so a crash leaves `before` or `after`. `delete` removes a file or an empty directory; a non-empty
  directory is refused.
- **Attributes kept on replace.** The temporary file gets the target's POSIX permissions, owner and group, its ACL
  and owner where the file system has an ACL view, and its DOS hidden and system flags, before any byte is written,
  checked to hold. Where they cannot be kept (a setuid, setgid or sticky bit, an owner the process cannot set, a
  read-only DOS file, no permission model the JDK can copy) the write is refused, never widened. Not kept, because the
  JDK cannot see them: POSIX ACLs on Linux and extended attributes.
- **Bounded reads.** Content is read through one no-follow channel, at most `maxFileBytes + 1` bytes, so the bound
  holds for what is read, not a size checked before. `ls`, `find` and `search` visit at most `maxScanEntries` entries,
  in name order, and report a cut-short walk as `truncated`. `search` skips files over the bound and files that are
  not UTF-8; it refuses one it cannot read rather than skip it silently.
- **Tenant.** Not scoped: one root is one tenant's. Use `FileBackend.resolved` to pick one per tenant.

## `close()` and operations in flight

`close()` is idempotent and never blocks:

- Every operation that starts after it is refused (`BackendRefused`, "the backend is closed").
- An operation already admitted runs to its end as it would have, and the root's lock is released when the last of
  them finishes, at once if none is running. So no other backend can open the root while this one is still writing
  to it, and a `close()` called from inside an operation (a `find` predicate, say) cannot deadlock.
- An operation is admitted once, at its entry; its own steps are never checked again.

A caller that must reopen a root right after closing it, while an operation of the old backend may still run, sees
`HostRootInUse` until that operation ends.

## Supported platforms and file systems

| Platform | File systems | `open` |
| --- | --- | --- |
| Linux | local POSIX file systems (ext4, xfs, btrfs, tmpfs, ...) | supported |
| macOS | APFS, HFS+, case-insensitive included | supported |
| Windows | NTFS, ReFS with 8.3 name generation off | only with `allowUncheckedIdentity` (no link counts) |
| any | a volume that generates 8.3 short names (FAT, NTFS with them on, some SMB shares) | refused |
| any | network file systems (NFS, SMB/CIFS) | unsupported: OS locks and file keys are not dependable there; not detected in general |

## Not a security boundary

It is a convenience for a trusted directory. Resolution checks each component, and the effect checks again, but each
then opens by path, so a process that can write the root can swap a directory for a link in between. Never give it a
root an untrusted process can write, a sandboxed command included; run untrusted commands in the workspace sandbox
(F2, §4.33), which is the isolation boundary.

## Testing

- `HostFileBackendSpec` (`llm4s-agent`): operations, the identity checks (symbolic and hard links, temporary and probe
  names, trailing dots, the probe with injected lookups, mounts with injected tables), bounds, attributes, replay,
  the lock (same root, nested either way, siblings, a lock directory inside the root, a refused open leaving others'
  locks held) and `close()` with an operation in flight.
- The cross-process cases start a second JVM (`HoldRoot`) that opens a backend and holds it: this process's open of
  the same, an ancestor or a descendant root is refused, and succeeds once the child exits.
- `HostFileBackendContractSpec` and `HostFileBackendReplaySpec` (`llm4s-agent-testkit`) run C3's `FileBackendContract`
  and C4's `ReplayContract`.
- All three run on Windows (`PlatformTests.suites`); there the backend is opened with `allowUncheckedIdentity`, and an
  injected-probe case checks that it is refused without it. Where the runner's volume makes 8.3 short names,
  `HostFileBackendSpec` stubs the probe so every other case still runs there (the refusal is the injected-probe cases'),
  and the agent-testkit suites are cancelled.
