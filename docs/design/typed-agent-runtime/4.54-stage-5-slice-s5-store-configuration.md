# 4.54 Stage 5 slice S5: store configuration ([#2133](https://github.com/llm4s/llm4s/issues/2133))

Part of the [Typed Agent Runtime design](../typed-agent-runtime-design.md), §4. Section numbers (§N.N) refer to that document and its [slice records](../typed-agent-runtime-design.md#slice-records). Stage 5 spec: `docs/superpowers/specs/2026-10-20-stage-5-production-design.md`, "S5" and "Rules every slice must satisfy".

Slice S5 of [#2129](https://github.com/llm4s/llm4s/issues/2129), after S1 ([#2130](https://github.com/llm4s/llm4s/issues/2130), §4.50). It lets an
application choose and configure its checkpoint store in `application.conf`, as it chooses a tracing backend
(CLAUDE.md, Tracing and metrics), and load a runtime's `ClaimPolicy` and `WatchPolicy` as typed config. P1 (#2139)
builds its three-instance deployment on it.

## What it adds

In `llm4s-agent`, all `@Experimental`:

- `org.llm4s.agent.graph.spi`:
  - `trait CheckpointerBackend { def kind: String; def open(settings: CheckpointerSettings): Result[CheckpointStore] }`;
  - `CheckpointerBackends`: `discover(loader)`, `of(backends*)`, `empty`, `withBackend`, `find(kind)`, `kinds`,
    `failures`, `discovered` - the `TracingBackends` shape;
  - `CheckpointerSettings(kind, extras)`: the selected kind and its block flattened to strings, with `key(name)`,
    `string(name, envVar)`, `optionalString`, `duration(name, default)`, `int`, `boolean`;
  - `CheckpointStore`: `kind`, `checkpointer`, an idempotent `close()`, `isClosed`; built with
    `CheckpointStore(kind, checkpointer, close)`, `CheckpointStore(kind, checkpointer & AutoCloseable)` or
    `CheckpointStore.unmanaged(kind, checkpointer)`.
- `org.llm4s.config.CheckpointerConfigLoader`: `settings()`, `open()`, `open(backends)`.
- `org.llm4s.config.RuntimeConfigLoader`: `claimPolicy()`, `watchPolicy()`, `runtime(checkpointer)`.
- `reference.conf`: `llm4s.agent.checkpointer.kind = "memory"` (`${?LLM4S_CHECKPOINTER}`), and
  `llm4s.agent.runtime.claims` (`ttl`, `renewEvery`, `label = ${?LLM4S_RUNTIME_LABEL}`) and `.watch` (`enabled`,
  `pollInterval`) at the policies' defaults.

In the store modules, each with its `reference.conf` block, its `META-INF/services` entry and a
`<Name>CheckpointerBackendSpec`:

- `SqliteCheckpointerBackend` (`sqlite`): `path` (`${?LLM4S_CHECKPOINTER_SQLITE_PATH}`, required), `busyTimeout`.
- `PostgresCheckpointerBackend` (`postgres`): `url`, `user`, `password` (`${?LLM4S_CHECKPOINTER_POSTGRES_URL}`, `_USER`,
  `_PASSWORD`), `schema`, `callTimeout`, `connectionTimeout`, `maxPoolSize`, opening `PostgresCheckpointer.open` with
  its own pool. A `modules/it` `@Docker` case (`PostgresCheckpointerBackendItSpec`) opens it on a real server from the
  variables.

## The config tree

```
llm4s.agent
  checkpointer            S5: the store
    kind                  memory | sqlite | postgres | another backend's kind
    sqlite { ... }        each store module's own block
    postgres { ... }
  runtime                 S5: GraphRuntime policies
    claims { ttl, renewEvery, label }
    watch  { enabled, pollInterval }
  queue { ... }           W1 (#2134): the run queue's settings (maxAttempts, ticket lifetime, lease)
  worker { ... }          W2 (#2135): concurrency, drain grace, sweep schedule
  harness { ... }         §4.37, unchanged
```

`queue` and `worker` are reserved by this record, not written: W1 and W2 add their blocks and loaders beside
`runtime`, each with its own `reference.conf` keys in `llm4s-agent`. A queue in the store's database is opened from
the same `CheckpointStore` (below), so no store setting is repeated under `queue`.

## Decisions

**The backend returns a `CheckpointStore`, not a `Checkpointer`.** `Checkpointer` has no `close`, and both durable
stores hold a resource (a file connection, a pool) the application must release; adding `close` to the `Checkpointer`
SPI would touch a trait S2, S3 and S4 are changing in parallel, and the in-memory store has nothing to close. A final
class that pairs the checkpointer with its release is the smallest thing that lets the loader return something
closeable. W1's `RunQueue` lives "in the same database as the checkpoints": it can be opened from this handle (a
`runQueue` member, or a second backend method), sharing the pool, without a new configuration path. That is W1's
choice; this slice adds no queue member.

**Settings are strings, as `TracingSettings.extras` are.** A backend sees its block flattened to `Map[String, String]`,
so no Typesafe `Config` appears in a public signature (CLAUDE.md, API rules). `CheckpointerSettings`' typed readers parse
durations with HOCON's own rules (`5 seconds`, `250ms`, a bare number is milliseconds), so a value means the same as
anywhere else in `application.conf`, and every error names the full key. Only the selected kind's block is read (as
tracing reads only the selected mode's), so a half-written block for another store never fails a load.

**`memory` is built in, not a service entry.** `llm4s-agent` owns the in-memory store, so, like `Console` and `NoOp` in
`Tracing.create`, it needs no `META-INF/services` entry and works from a shaded jar. A registered backend that claims
`memory` replaces it, so a test can swap it. `memory` is the default kind: an application that sets nothing behaves as
before, on an `InMemoryCheckpointer` with the system clock.

**A missing module is named.** `CheckpointerBackends.KnownModules` (`private[llm4s]`) maps `sqlite` and `postgres` to
their artifacts, so `kind = postgres` without `llm4s-agent-checkpoint-postgres` fails `open` with "add it as a
dependency", and an unknown kind lists the kinds that are available and any discovery failures. Only `open` fails:
loading the runtime policies, or the settings themselves, does not consult the backends.

**Claims and watch are runtime settings, under `llm4s.agent.runtime`.** They configure a `GraphRuntime`, not a store:
one store is shared by runtimes that may label themselves differently. Keeping them out of
`llm4s.agent.checkpointer` also keeps that block exactly "the store's kind and its stores' blocks". The label binds
`LLM4S_RUNTIME_LABEL`, which a deployment sets from the pod name.

**Variable names.** `LLM4S_CHECKPOINTER*` and `LLM4S_RUNTIME_LABEL`, not `POSTGRES_*` or `PG*`: the store is one of
several Postgres users in an application (`PGVECTOR_*` is the RAG store's), and libpq's `PG*` variables would silently
configure it from an unrelated tool's environment. Each binding is in the module that reads it (`llm4s-agent` for
`kind` and the label, the store modules for their blocks), never core.

**Credentials.** The password is read through `${?LLM4S_CHECKPOINTER_POSTGRES_PASSWORD}` and never logged:
`CheckpointerSettings.toString` lists keys only, its readers' errors name the key and never the value, a block that is
not an object is refused without echoing it, and the loader logs only the kind and the backend's class. The Postgres
backend's own `Connection` value redacts the password from `toString`. The URL is not logged either.

What a backend's dependencies say is not in our hands - a driver may echo the JDBC URL in an exception - so the loader
scrubs every failed open (Codex review, round 1). `CheckpointerSettings.sensitiveValues` are the values of keys that
name a secret or a locator (`password`, `secret`, `token`, `key`, `url`, `uri`, `dsn`) and of `password=`-like
parameters inside any value; an error a backend returns whose message, formatted context or carried exceptions contain
one becomes a `ConfigurationError` with the text redacted and no cause, and an error that contains none is returned
as the backend gave it, so typed errors such as `GraphError.UnsupportedStoreSchema` survive. A thrown exception is
reported by class and redacted message, with no cause; a `LinkageError` (a stale or half-present jar) is caught too,
as discovery catches it. The Postgres backend also refuses a URL that carries a credential (`password=`,
`sslpassword=`, user info before the host), pointing at the `password` key, so the URL is never a secret to begin
with.

**Rule 2 is the store's.** The Postgres backend passes `callTimeout`, `connectionTimeout` and `maxPoolSize` through
to `PostgresCheckpointerConfig`, which already sets the statement, lock and socket timeouts from them (§4.50); the
backend refuses a URL that is not `jdbc:postgresql:` before opening anything, and a value the store refuses is a
`ConfigurationError` naming `llm4s.agent.checkpointer.postgres`. A server that cannot be reached fails within the
connection timeout.

**Not in this slice.** Sharing a caller's `DataSource` (`PostgresCheckpointer.create`) stays code: a pool the
application owns is not configuration. An injected `Clock` stays code too (tests); configured stores use the system
clock, and Postgres judges time by the server's (rule 1).
