# 4.34 Stage 3 slice F4: context management ([#1908](https://github.com/llm4s/llm4s/issues/1908))

Part of the [Typed Agent Runtime design](../typed-agent-runtime-design.md), §4. Section numbers (§N.N) refer to that document and its [slice records](../typed-agent-runtime-design.md#slice-records). Phase 3 spec: `docs/superpowers/specs/2026-10-13-phase-3-harness-design.md`, "F4".

Slice F4 of [#1901](https://github.com/llm4s/llm4s/issues/1901), a feature slice on C1 (§4.22: `ModelContext`,
`ModelContext.accounted`, model wrappers that write state, a Block restoring every key the turn wrote) and C3
(§4.25: `FileBackend`, `CompositeBackend`). It keeps a long thread inside the model's context window in two ways:

- `SummarizationMiddleware` replaces the older part of each request with a summary, kept in the thread and
  extended as the thread grows, without editing the stored history.
- `ToolOutputOffload` keeps a large tool result out of the conversation: the model sees a preview and a path, and
  reads the whole result through an `OffloadBackend` mounted in a `CompositeBackend`.

Both are in `llm4s-agent`, package `org.llm4s.agent.harness`, and opt-in: an agent without them has neither key.
The specs are `SummarizationMiddlewareSpec` (the middleware through the tool loop: trigger, summary in the same
request, extension, the bound, tool pairs, the stored thread, Block, recover, accounting, and the compressors) and
`ToolOutputOffloadSpec` (the wrapper through the tool loop, the bound under a parallel batch, eviction, replay,
content parts, cleanup after a summary, and the backend through a `CompositeBackend`).

## API

In `org.llm4s.agent.harness`, all `@Experimental`:

- `enum SummaryTrigger`: `Tokens(max: Int)` or `Messages(max: Int)`, both at least 1. The trigger fires when the
  outgoing request - as it would be sent with the stored summary applied, system prompt included - is over `max`
  estimated tokens (by the middleware's `tokenCounter`) or holds more than `max` messages.
- `trait SummaryCompressor`, one method:
  `compress(previous: Option[String], messages: Vector[Message], maxTokens: Int, context: ModelContext): Result[String]`,
  a summary of `previous` (the summary so far) followed by `messages`. It may call a model, and must do so through
  `context.accounted`. Two built-ins:
  - `SummaryCompressor.digest(counter: ConversationTokenCounter)`: core's `HistoryCompressor` digest, with no model
    call. An extension appends the new messages' digest to the old one; when that would be over `maxTokens`, it digests
    the old summary and the new messages together, which `HistoryCompressor` consolidates within the cap. Its
    patterns keep no trace of an image or a document, so the summary starts with media lines (`Media: [image
    (url, image/png)], ...`) naming every media part it covers, at most half the bound (beyond that, one `Media: counted` line,
    which later counts add to, counting each kind; only lines in exactly these two formats are read as media, any other line is prose); the digest takes the rest and is what a bound cuts. Media parts are named by kind in the
    text `HistoryCompressor` digests, and a message it returns unchanged joins the summary as its transcript line.
  - `SummaryCompressor.model(client: LLMClient, options: CompletionOptions = CompletionOptions(),
    maxInputTokens: Int = 16000)`: the model writes the summary, given the old one and a transcript of the new
    messages, asked to stay within `maxTokens` (and `options.maxTokens` set to it). Every call goes through
    `context.accounted(client)`. A transcript over `maxInputTokens` (four characters a token) is folded in chunks,
    one call each, each chunk extending the summary the last produced; one message larger than a chunk is cut to
    fit it with a marker that says so (`maxInputTokens` at least 16, so the marker always fits). Media parts appear in the transcript by kind (`[image (url, image/png)]`), never as bytes.
- `final case class ConversationSummary private (text: String, throughMessageId: String)`, with `apply`, `withText`
  and `withThroughMessageId`: a summary of the stored history up to and including the message `throughMessageId` (a
  `StoredMessage.id`).
- `final class SummarizationMiddleware(trigger: SummaryTrigger, keepRecent: Int = 10, compressor: SummaryCompressor,
  maxSummaryTokens: Int = 2000, tokenCounter: Message => Int = <the loop's estimate>, id: MiddlewareId =
  MiddlewareId("summarization"))`. `keepRecent` must be at least 1 and `maxSummaryTokens` at least `SummaryCompressor.MinSummaryTokens` (32), so a counted media line always fits (`require`; the digest compressor refuses a smaller bound too).
  `SummarizationMiddleware.key: StateKey[Option[ConversationSummary], Option[ConversationSummary]]`, a replace key
  with id `summary`, one for every instance (as `TodoMiddleware.key` is).
- `final class ToolOutputOffload(thresholdTokens: Int = 20000, maxResultBytes: Long = 1 MiB, maxTotalBytes: Long =
  4 MiB, id: MiddlewareId = MiddlewareId("tool-output-offload"))`. `thresholdTokens` at least 1000 (so a preview is
  always smaller than what it replaces), `maxResultBytes` at least 1, and `maxTotalBytes` at least `maxResultBytes`
  plus `ToolOutputOffload.MetadataBytes` (128: a key and a tool name of at most 64 bytes each), so every result the
  model is told is stored fits the bound on its own (`require`).
  `ToolOutputOffload.key: StateKey[Offloads, OffloadUpdate]`, id `offloads`, one for every instance;
  `ToolOutputOffload.Mount`, the path `/large_tool_results`.
- `final case class OffloadedResult private (key: String, tool: String, content: String, originalBytes: Long,
  truncated: Boolean)`: one stored result, `key` the call's `IdempotencyKey`.
- `final case class Offloads private (results: Vector[OffloadedResult], evicted: Vector[String])`, oldest first,
  with `Offloads.empty`, `bytes` (what the bound counts) and `get(key)`.
- `enum OffloadUpdate`: `Put(result: OffloadedResult, maxTotalBytes: Long)` and `Drop(keys: Vector[String])`.
- `object OffloadBackend extends FileBackend`: the read-only view of `ToolOutputOffload.key`, for mounting at
  `ToolOutputOffload.Mount` in a `CompositeBackend`.

## Decisions

- **The relationship to `ContextWindowMiddleware`: kept, as the pruning-only option, deliberately distinct.**
  `ContextWindowMiddleware` drops older messages with no model call and no state; `SummarizationMiddleware` replaces
  them with a summary it keeps. They share the loop's token estimate (`ContextPruning.defaultTokenCounter`) and the
  tool-pair rule, and are not meant to be combined: an agent uses one. With both in one stack the outer one decides
  what the inner one sees (summarisation outside pruning summarises before pruning may drop the summary; pruning
  outside summarisation drops messages no summary ever records), so the guide says to pick one. Replacing it was
  rejected: its strategies (`MiddleOut`, `AdaptiveWindowing`, `Custom`) are the zero-cost choice for an agent that
  does not want a summariser's calls, and its users would lose them for no gain.
- **What a request looks like with a summary.** The leading system message stays first. Every request message the
  summary covers is replaced by one `UserMessage` straight after it: a fixed header, then the summary. A user
  message rather than a second system message, because a request may hold one system message
  (`Message.validateConversation`), and a user message keeps a request that starts with the agent's reply valid
  for providers that need a user message first. The kept messages follow unchanged.
- **Finding the covered messages.** A wrapper sees core `Message`s, which carry no id. The middleware aligns the
  request's messages with the stored history (`Messages.key`, read from `context.state`): from the end, each request
  message is matched to the latest stored message at or before the previous match that equals it. The covered
  messages are exactly those matched to a stored message at or before `throughMessageId`. A message that matches
  none (an outer wrapper's note) is never treated as summarised: it is kept, after the summary, and a fold leaves it
  out of what it compresses. The alignment survives what the loop and outer wrappers do to the history - a handoff's view, a
  pruning wrapper, an inserted note - since each of those sends a subsequence of the history plus messages of its
  own. A summary whose `throughMessageId` is no longer in the history, that covers no message of the request, or whose
  removal of what it covers would break the tool-pair rule (`ToolResultRule`), is not sent, and is replaced when
  the trigger next fires.
- **When the trigger fires**, the messages after the summary are split: the last `keepRecent` are kept, moving the
  cut earlier while the first kept message is a `ToolMessage` (so a call is never sent without its results, nor a
  result without its call), the last folded one matches no stored message (so `throughMessageId` names it), or the
  folded stored messages are not exactly the stored messages after the old summary through the new last one. A
  summary therefore always covers a prefix of the stored history, every message of which its compressor saw: a view
  with a gap (a handoff with `preserveContext = false`, a pruning wrapper outside) never folds across the gap. The
  folded messages and the old summary go to the compressor; the new summary, clamped to `maxSummaryTokens`, goes into
  this request (rule 3) and is written to the key with the folded part's last stored id, committed with the model
  step. When no cut is left (everything after the summary is within `keepRecent`, or one tool batch), the request is
  sent as it is.
- **The bound is checked on what is kept and sent.** The summary is at most `maxSummaryTokens` estimated tokens at
  four characters a token (the measure C1's prompt-section budget uses), cut on a code point boundary after the
  compressor returns, whatever the compressor did; a stored summary written another way (`updateState`) is cut the
  same way when sent.
- **The stored thread is never edited.** The middleware writes only its key; the history keeps every message, so
  `history`, `fork` and a later agent without the middleware see the whole thread.
- **Offload replaces a large `Success` with a preview and a path.** A `Success` whose text is over `thresholdTokens`
  estimated tokens (four characters a token) is stored, cut to `maxResultBytes`, and the model sees, instead of the
  text, a header naming the tool, the size, the path `/large_tool_results/<idempotencyKey>` and whether the stored
  copy was cut, then the first 10 lines of the text, each cut to 200 characters. The stored history therefore holds
  only the preview. The path uses the call's `IdempotencyKey` (`ToolContext.idempotencyKey`), the runtime's identity,
  never the provider's `toolCallId` (rule 4).
- **Content parts.** A JSON result's text is a non-blank string as itself, anything else rendered as JSON, as the
  loop sends it. A `ToolContent.Parts` result's text is its text parts joined; when that is over the threshold, the
  text is offloaded and the parts become the preview text followed by every non-text part, in order. Media parts are
  never dropped and never offloaded: they are bounded by the loop's own inline bound
  (`ContentPart.MaxInlineBytes`, §4.27), and a `FileBackend` holds UTF-8 text only.
- **Keys and names.** The path segment is the call's key when it is at most 64 of `[A-Za-z0-9_-]` (the runtime's
  are 64 hex digits); any other key a caller built is hashed (SHA-256, hex). The tool name is stored cut to 64 bytes.
- **The offload bound (rule 12).** `OffloadUpdate.Put` replaces any result with the same key, appends the new one,
  then evicts the oldest results until `bytes` is within the `maxTotalBytes` the update carries. The bound travels
  with the update, so the key is one object for every instance and the update is total. Eviction happens when the
  update is applied, in commit order, so it holds under a parallel batch, whose calls all saw the same snapshot,
  and with or without summarisation. `bytes` is what a checkpoint stores: each result's key, tool name and content
  as JSON strings. Evicted keys are remembered, at most 1024 (oldest dropped), so reading an evicted path says it
  was evicted; an older one reads as not found, saying it may have been evicted.
- **`OffloadBackend` is read-only.** `ls`, `read`, `glob` and `grep` see one file per result, `/<key>`, beneath its
  mount. `write`, `edit` and `delete` are `BackendRefused` ("read-only"), so a tool over the composite turns them into
  tool errors. It writes nothing (`writes` is empty) and has one lock, `files/offloads`, which no mutation takes.
- **Cleanup after a summary.** `ToolOutputOffload`'s `wrapModelCall` reads `SummarizationMiddleware.key` (when the
  graph has it). Results whose path appears in a `ToolMessage` at or before the summary's `throughMessageId` are
  dropped with `OffloadUpdate.Drop`, committed with that model step, one superstep after the summary that advanced
  (rule 3). This is extra: the bound does not depend on it.

## Where the spec was imprecise

- **`LLMCompressor` is not the model compressor.** Core's `LLMCompressor.squeezeDigest` compresses only
  `[HISTORY_SUMMARY]` digests, one call per digest, toward a fixed 50 % with no bound. The model compressor makes its
  own call through the accounted client, with a prompt that extends a summary within a bound; `HistoryCompressor`
  backs the model-free `digest` compressor, as the spec says.
- **"Extended, not recomputed"** is the compressor's contract: it gets the old summary and only the messages after
  it, never the covered ones again.
- **"Offloads older than `throughMessageId`"** is decided by where the result's path appears in the stored history,
  since an offload is made before its `ToolMessage` exists and cannot record its id.
- **The preview.** The spec names a preview without its size; it is fixed (10 lines of 200 characters), and
  `thresholdTokens` has a floor of 1000 so the preview and header are always smaller than the result they replace.

## Runtime rules

1. **One batch, one snapshot.** Offload: each call's `Put` is applied in commit order, eviction inside the update,
   so a batch whose results together exceed the bound keeps it (tested: three results in one batch, room for two).
   Summarisation runs in the model step, one task, outside any batch.
2. **An update function that fails, fails the run.** `summary` is a replace key; `OffloadUpdate` is total (a `Drop`
   of an absent key is a no-op). Nothing is refused when an update is applied.
3. **Visible from the next superstep.** A new summary goes straight into the request that produced it (tested: the
   firing request already holds it); the key serves later requests. The offload preview is the call's result. The
   cleanup reads the summary from the snapshot, so it lags one model step, which is fine for extra cleanup.
4. **At least once.** The compression call reruns when the model step reruns (`recover`, a crash): it costs a call,
   and its result is pure state, committed once with the step (tested: a model failure after compression, then
   `recover`, compresses again and stores one summary). An offload's path is the call's `IdempotencyKey`, stable
   across reruns, and a rerun's `Put` replaces the entry (tested). A provider that reuses a `toolCallId` gets a
   different path (tested). No external effect, so C4's guards are not needed.
5. **A Block restores the keys (C1).** Both keys are in the middleware's `writes`, so an output Block restores them
   to their values before the turn: a blocked turn's summary and offloads are never kept (tested for both).
6. **Full snapshots.** Each checkpoint holds one summary of at most `maxSummaryTokens` and offloads of at most
   `maxTotalBytes` plus 1024 evicted keys (rule 12).
7. **Restore through codecs.** Both keys are new, at `SchemaVersion.initial`, with explicit codecs. They are
   registered only by an agent family with the middleware, so an agent without them keeps its structural fingerprint
   (tested). Adding either to an existing agent changes its version, as for any middleware key (§4.29).
8. **Tenant.** Not applicable: both keys are thread state, never shared across threads.
9. **No content in durable events.** Neither middleware emits an event. The compressor's calls are announced by C1's
   `ModelCallCompleted`, which carries usage only.
10. **A failed task commits nothing.** A model step whose model call fails after compressing commits no summary; the
    compressor's usage reaches the thread through `RunFailed`, as every accounted call does (C1). A tool call that
    fails commits no offload.
11. **Every model call accounted.** The model compressor calls only through `context.accounted(client)` (tested: the
    thread's usage includes the compressor's tokens). A custom compressor is told to do the same; it is handed the
    `ModelContext` for it.
12. **Bounded, measured on what is kept or sent.**
    - **The summary key and the summary sent:** at most `maxSummaryTokens` × 4 characters, cut after the compressor
      returns and again when a stored one is sent (tested with a compressor that ignores the bound and with a stored
      summary written by `updateState`).
    - **The compressor's input:** the old summary (within its bound) and the folded messages, which were part of the
      request the agent was about to send. The model compressor sends each call at most `maxInputTokens` of
      transcript plus the old summary and a fixed prompt (tested: a long fold takes several calls).
    - **The offloads key:** at most `maxTotalBytes` of results, enforced by the total update (tested under a parallel
      batch), each at most `maxResultBytes` of content; at most 1024 evicted keys.
    - **What the model sees of an offloaded result:** the fixed header and at most 10 lines of 200 characters.
13. **Every type is defined.** `SummaryTrigger`, `SummaryCompressor`, `ConversationSummary`,
    `SummarizationMiddleware`, `ToolOutputOffload`, `OffloadedResult`, `Offloads`, `OffloadUpdate` and
    `OffloadBackend`, above, in `org.llm4s.agent.harness`. Stored: `ConversationSummary` (the `summary` key's codec),
    `Offloads`, `OffloadedResult` and `OffloadUpdate` (the `offloads` key's codecs).

## Limits

- A summary is lossy. What the model needs verbatim should stay within `keepRecent`, or in a file.
- The alignment matches messages by value. Two equal messages the outer wrappers reorder could be matched to the
  wrong stored copy; equal messages cover the same content, so the summary still covers what it says it does.
- Several agents of one family share the thread's one summary, as they share its history. A handoff target with
  `preserveContext = false` is sent the summary only where its own view holds a covered message, and does not fold
  across the gap in its view, so it summarises nothing past it until an agent with the whole view has.
- Reading an offloaded result needs a file tool over a `CompositeBackend` that mounts `OffloadBackend` (F1). Without
  one, the model sees the preview only.
