# 4.39 Workspace command confinement ([#1983](https://github.com/llm4s/llm4s/issues/1983))

Part of the [Typed Agent Runtime design](../typed-agent-runtime-design.md), §4. Section numbers (§N.N) refer to that document and its [slice records](../typed-agent-runtime-design.md#slice-records).

A follow-up to slice F2 (§4.33), which finishes [#870](https://github.com/llm4s/llm4s/issues/870). F2 made the
workspace runner enforce `allowedPaths`, `readOnlyPaths` and `maxFileSize` on its own file operations. Two controls
were left: the paths a command started by `execute` touches are checked against the workspace root but not against
`allowedPaths`/`readOnlyPaths`, and `networkAllowed` is accepted but not enforced. This record closes both, with the
kernel doing the enforcement rather than a parse of the command.

## Threat model

The commands are model-issued: an agent asks `execute` to run a program from the allowlist, with arguments it
chooses. The workspace container is the outer boundary; this layer confines each command inside it, so that whatever
the arguments, the program and every process it starts:

- cannot write a path under `readOnlyPaths`;
- cannot read or write a workspace path outside `allowedPaths` (when it is set), or anything outside the workspace
  but the system directories programs need to run;
- cannot open a network connection when `networkAllowed = false`.

`CommandPolicy` (#1715) stays as the layer before this one. It refuses with a clearer message, and it is the only
layer off Linux. It is not a sound boundary on its own: a program's own behaviour (a build tool reading a config, a
symlink created by an earlier command) reaches paths no argument names.

Out of scope: a command that starts a daemon (a new session) escapes the runner's process-group kill. The daemon stays
confined, since the confinement is inherited, but it outlives the command. Only a cgroup per command follows it, and
that needs container privileges a default `docker run` does not give; it is tracked as
[#2008](https://github.com/llm4s/llm4s/issues/2008).

Limits of the confinement, each accepted:

- **Metadata is not protected.** Landlock (through ABI 8) has no rights for metadata, so `chmod`, `chown` and
  timestamp changes (`touch` on an existing file) on a read-only path are not refused; only its content and its
  entries are.
- **`/proc` and `/sys` are readable**, since the JVM and build tools read `/proc/self` and the cgroup files. Landlock's
  ptrace scoping still blocks another process's `environ` and `mem`, but a command can read other processes'
  `cmdline` and `status`, the runner's and concurrent commands' included.
- **A hard link that already exists** into a read-only file, from a writable path, writes that file's content.
- **A read-only entry that is a symlink** protects its target, not the link.
- **Landlock's ABI v6 scopes are not used**: under `--no-net`, abstract `AF_UNIX` sockets in the container's network
  namespace stay reachable, and a command can signal the runner, which runs as the same user.
- **A system or home grant that contains, or lies inside, the workspace root is dropped**, since Landlock grants
  union and such a grant would void `readOnlyPaths` and `allowedPaths`. So a workspace under the home directory gets
  no home grant, and build tools run there cannot write their caches.
- **The runner's own helper programs run unconfined**: the git configuration lister, `getfacl` and `setfacl` (see
  below). On Linux each is taken from `/usr/bin` or `/bin` only, never from `PATH`.
- **`/tmp` is shared by every command**, when it is granted (see Filesystem rules): one command can read, replace or
  delete what another left there. Each command's own `TMPDIR` is still private to it.

## Mechanism

Everything here works in a default `docker run`, with no added capability, cgroup mount or user namespace.

**`llm4s-confine`** is a small C helper with no dependencies, built into the workspace-runner image at
`/usr/local/bin/llm4s-confine`:

```
llm4s-confine --status FILE [--rx P]... [--ro P]... [--rw P]... [--wfile P]... [--no-net] -- program args...
```

It checks the Landlock ABI (v3 or later, kernel 6.2: earlier ABIs cannot refuse `truncate`), builds and installs a
Landlock ruleset from the path options, sets `no_new_privs`, installs the seccomp filter when `--no-net` is given, and
`execve`s the program in its own place, so it keeps the pid, session and process group `setsid` gave it and the
runner's kill works as before. Both restrictions are inherited by every descendant, across `fork`, `exec` and
`setsid`.

When it cannot confine, because the ABI is too old or a call fails, it writes the reason to the `--status` file and to
stderr (`llm4s-confine: unavailable: ...`) and exits with status 125, and the program never starts. The status file is
in a per-command directory of the runner's that no rule grants (under a runner-private, owner-only directory made in
`/var/tmp`, never `/tmp`), so the command cannot write it: the runner reports
`SANDBOX_UNAVAILABLE` when the status is 125 and that file exists, and a program that itself exits 125 is not mistaken
for it. A file rather than stderr, because the WebSocket path streams stderr to the client as it is written.

**`CommandConfinement`** (runner, pure) turns a `WorkspaceSandboxConfig`, the workspace root and the command's temporary
directory into the helper's arguments. `prepareCommand` puts `llm4s-confine <args> --` before the program on Linux
(after `setsid`). Off Linux, it does not, and the runner logs once at startup that commands run unconfined.

The runner's own helper processes (`getfacl`/`setfacl`, the git configuration lister) are not confined. They run
with arguments the runner chooses; only `execute` commands are model-issued. On Linux their programs are resolved from
the system directories `/usr/bin` and `/bin` only, never from `PATH` or a home or temporary directory: a confined
command can write the home directory, which is on the image's `PATH` (sdkman's `bin`), and a `git` it planted there
must never run with the runner's rights. Where one is missing from both, the runner behaves as when it is not
installed: no POSIX ACL is copied, and a git subcommand is refused (`EXECUTION_FAILED`). A command's own program is
still resolved from `PATH` as before, and runs confined. Off Linux, where no command is confined and so none gains by
planting a program, they are resolved as a command's program is (and on macOS `/usr/bin/git` is only a stub).

## Filesystem rules

Landlock is allow-only: what no rule grants is refused. A command is granted:

- read and execute on the system directories (`/usr`, `/bin`, `/sbin`, `/lib`, `/lib32`, `/lib64`, `/libx32`, `/etc`,
  `/opt`) and the JDK (`java.home`; in the image `/opt/java/openjdk`);
- read only on `/proc`, `/sys`, `/dev/urandom`, `/dev/random` and `/dev/zero`;
- read and write on `/dev/null`;
- read, write and execute on the home directory of the user the runner runs as (`user.home`; in the image `/root`,
  which holds the sdkman toolchain), where build tools keep their caches (`~/.sbt`, `~/.cache/coursier`, `~/.m2`). A
  command can leave files there that later commands see; those are confined too, and a build tool already runs the
  workspace's build code. The runner's own files are not under it;
- read and write on a fresh per-command temporary directory, which `TMPDIR` names, removed when the command ends;
- read and write on `/tmp`, only when the runner's own JVM keeps nothing there: it runs with both
  `-XX:+DisableAttachMechanism` and `-XX:+PerfDisableSharedMem`, which it checks at startup
  (`HotSpotDiagnosticMXBean`; the image starts it so). JVM tools write `/tmp` whatever `TMPDIR` says
  (`java.io.tmpdir`; the sbt client's server log), so without it `sbt` fails confined. The condition is because the
  JVM attach mechanism's trigger file (`/tmp/.attach_pid<pid>`) and socket (`/tmp/.java_pid<pid>`) live there:
  Landlock does not govern connecting to a Unix socket, `--no-net` allows `AF_UNIX`, and the command runs as the
  runner's user, so a command that could write `/tmp` could attach to the unconfined runner
  (`jcmd <pid> JVMTI.agent_load`) and run code in it; and the shared perf-data file (`/tmp/hsperfdata_<user>/<pid>`)
  would be there for a command to replace or fill. When either flag cannot be verified, `/tmp` is not granted and the
  runner logs a warning once at startup. Commands then share `/tmp` (see the threat model); like any system grant it
  is dropped when the workspace lies in `/tmp`;
- in the workspace, read and write on the root (or on each `allowedPaths` entry instead, when that is set), and
  read-only on each `readOnlyPaths` entry under it.

The runner's own files never lie in a path a command may write. Its commands' scratch directories are under
`/var/tmp`, and the image starts it with `java.io.tmpdir=/var/tmp/llm4s-runner`, a directory made owner-only in the
image, so the empty directory git runs with (its `HOME`, `XDG_CONFIG_HOME` and `core.hooksPath`) is there, not in a
`/tmp` that commands share, where one could fill or replace it to make every git command fail or race a hook into
it. The runner checks both against the paths commands are granted write on (the workspace, the home directory,
`/tmp` when shared): a scratch parent that would lie inside one refuses every confined command
`SANDBOX_UNAVAILABLE`, and an empty directory that does refuses git `EXECUTION_FAILED`, naming `java.io.tmpdir`.

The workspace and the temporary directory are not executable: a binary built in the workspace, or a wrapper script
such as `./gradlew` run as a program, fails with exit status 126. A build tool run from the system or home
directories, which runs the workspace's code in its own process, is unaffected.

A system or home grant that contains the workspace root, or lies inside it, is dropped (see the threat model). The
runner's directories and every other path are not reachable. `/proc` is readable, but Landlock's ptrace scoping stops
reads of another process's `mem` and `environ`.

**A read-only path inside a writable one.** A Landlock right granted on a directory applies to the whole hierarchy
beneath it, so "the root is writable except `ro/`" cannot be one rule. For each read-only path `R`, `CommandConfinement`
walks from its writable ancestor down to `R` and, at each directory `D` on the way:

- grants read on `D` itself, but no create, delete or rename right, since those would reach `R`;
- grants read and write on every existing entry of `D` that is not on the way to `R`;
- grants write (`--wfile`) on each existing regular file directly in `D`.

`R` gets read only. So **with a read-only path, a command cannot create, delete or rename entries directly in a
directory above it** (with `readOnlyPaths = ["ro"]`, directly in the workspace root). It can still write anywhere in the
other directories and to the existing files in those above `R`. The runner's own file operations are not confined
and create files in the root as before. With no `readOnlyPaths` there is no such limit. The alternatives are a bind
mount or a mount namespace, which need privileges this design does not ask for.

Rules are bound to the paths that exist when the command starts. A path created later under a granted directory is
covered, since the grant applies to the hierarchy. An `allowedPaths` or `readOnlyPaths` entry that does not exist when
the command starts is handled by kind. A missing allowed path is skipped, so it stays unreachable for that command. A
missing read-only path is carved, as above, down to its deepest existing ancestor, which gets read only: a command
cannot create the path, nor any missing directory on the way to it (with `readOnlyPaths = ["ro/new"]` and `ro`
present, nothing can be created or deleted directly in `ro`; its existing entries stay writable). The runner's own path
policy (F2) refuses its own file operations there as before.

## Configuring a container

Until now a container's runner took only a profile name (`WORKSPACE_SANDBOX_PROFILE`: `permissive` or `locked`) and
`WORKSPACE_EXTRA_COMMANDS`, so `allowedPaths`, `readOnlyPaths` and `networkAllowed` could not be set in a container at
all. `ContainerisedWorkspace` takes an optional `sandboxConfig: Option[WorkspaceSandboxConfig]` and passes it as JSON
in `WORKSPACE_SANDBOX_CONFIG`. `RunnerMain` reads, validates and uses it in place of the profile (both set fails fast,
as an invalid one does); `WORKSPACE_EXTRA_COMMANDS` still adds to whichever applies. `CodeGenExample`, whose `sbt`
fetches dependencies, passes `networkAllowed = true`.

## Network

With `networkAllowed = false` the helper installs a seccomp filter that:

- refuses `socket` and `socketpair` with `EACCES` for every address family except `AF_UNIX`, so local tools keep
  working and a program trying the network fails with "permission denied" rather than being killed;
- refuses `io_uring_setup` with `EPERM`, since io_uring can open sockets without calling `socket`;
- kills the process on any system call made under a foreign architecture (i386 `socketcall`, the x32 ABI), which are
  the routes around a filter that checks x86-64 numbers only.

TCP and UDP are both covered, which Landlock's network rules (TCP only, ABI v4) are not, so they are not used. With
`networkAllowed = true` no filter is installed. The default stays `false`, so **commands no longer have network by
default**; nothing on the default allowlists needs it.

## Failure

| Case | Outcome |
|---|---|
| Linux, helper missing, Landlock ABI below v3, or a Landlock or seccomp call fails | the command is refused, `SANDBOX_UNAVAILABLE`, naming the cause (`ExecuteCommandResponse` is not returned); the program never starts |
| A command breaks a rule while running (`rm ro/x`, `curl ...`) | not a runner error: the program fails with "Permission denied", and its exit code and output reach the model as any failing command's do |
| Not Linux (macOS, Windows) | commands run as before, unconfined, `CommandPolicy` only; logged once at startup and documented |

The image is built for amd64 (`Docker / dockerBuildOptions`), which Docker on Apple silicon runs under emulation.
Checked live on Docker Desktop with Rosetta (kernel 7.0.14-linuxkit, 2026-10-17): Landlock's calls return `ENOSYS`
there, so the helper exits 125 and every command is refused `SANDBOX_UNAVAILABLE`, with or without `--no-net`; nothing
runs unconfined and nothing is killed. The same kernel confines a native arm64 build of the image. (`sbt
workspaceRunner/Docker/publishLocal` builds the host's architecture: the `--platform` option is not in the plugin's
`Docker / dockerBuildCommand`.)

## Build

- Source: `modules/workspace/workspaceRunner/src/main/c/llm4s-confine.c`.
- Image: the Docker build adds the source and compiles it statically in one layer (`gcc`, `libc6-dev`; the Landlock
  header comes from noble's `linux-libc-dev`), then removes the compiler.
- The runner takes the helper's path from the system property `llm4s.workspace.confine`, defaulting to
  `/usr/local/bin/llm4s-confine`; tests set it. There is no environment variable.
- On Linux, an sbt task compiles the helper with `cc` into `target/` for `workspaceRunner`'s tests, so the plain `test`
  job exercises the real helper on every PR. A Linux machine without `cc` fails that task with a clear message. Off
  Linux, the task does nothing.

## Tests

1. Unit, every platform: `CommandConfinement` arguments for `allowedPaths`, `readOnlyPaths` (the walk, siblings and files),
   a missing allowed entry skipped and a missing read-only one carved to its deepest existing ancestor, the home
   directory and the temporary directory; `/tmp` only when both JVM flags read on (each alone, or unreadable, is not
   enough), and not when the workspace lies in it; the scratch parent is owner-only, refused inside the workspace or
   another path commands may write, and git's empty directory is refused there too; on Linux `getfacl`/`setfacl` come from
   `/usr/bin` or `/bin` only, never `PATH`, and elsewhere as a command's program;
   `prepareCommand` inserts the helper only
   on Linux; status 125 with the status file becomes `SANDBOX_UNAVAILABLE`, and a program's own 125 without it does
   not; `WORKSPACE_SANDBOX_CONFIG` reaches the container and is parsed and validated.
2. The real helper, Linux runner tests, through `execute`: `cat`, `find` and `grep -r` into a path outside
   `allowedPaths` are refused; `rm`, `mv`, `cp` and creating a file with `touch` into a read-only path are refused,
   also through a symlink in the workspace that leads there (`chmod` is not: Landlock has no metadata rights, see the
   threat model); creating an entry in the root with `readOnlyPaths` set is refused (the
   limitation, pinned); a read-only path that does not exist yet cannot be created; each of these succeeds unconfined,
   so a test cannot pass for the wrong reason. A `git`, `getfacl` and `setfacl` planted first on the runner's `PATH`
   never run unconfined, through `git status` and a compare-and-set write. A JVM program writes its temporary file in
   `/tmp` with the gate on and is refused without it; with the gate on, `git` is refused while the test JVM's
   `java.io.tmpdir` (git's empty directory) is `/tmp`. The helper itself refuses `mknod` of a device node under
   a read-write grant, where a FIFO is still made.
3. Live `@Workspace`, in the image: the issue's acceptance. A write under a read-only path and a read outside
   `allowedPaths` fail; `curl` (an extra command) to the runner's own port on `127.0.0.1` fails with
   `networkAllowed = false` and gets a response with `true`, so the test needs no internet. A JVM (`java T.java`)
   writes its temporary file in `/tmp`, `jcmd 1 VM.version` cannot attach to the runner, and git commands run, their
   empty directory being under the image's `java.io.tmpdir`, `/var/tmp/llm4s-runner`, in a repository owned by uid
   1001 rather than the runner's root, as a Linux host's user owns a bind-mounted workspace: the runner names the
   workspace as git's `safe.directory` ([#2014](https://github.com/llm4s/llm4s/issues/2014)). With #1982 this tier runs
   on the PR.
