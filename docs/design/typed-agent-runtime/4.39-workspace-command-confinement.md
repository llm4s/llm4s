# 4.39 Workspace command confinement ([#1983](https://github.com/llm4s/llm4s/issues/1983))

Part of the [Typed Agent Runtime design](../typed-agent-runtime-design.md), §4. Section numbers (§N.N) refer to that document and its [slice records](../typed-agent-runtime-design.md#slice-records).

A follow-up to slice F2 (§4.33), which finishes [#870](https://github.com/llm4s/llm4s/issues/870). F2 made the
workspace runner enforce `allowedPaths`, `readOnlyPaths` and `maxFileSize` on its own file operations. Two controls
were left: the paths a command started by `execute` touches are checked against the workspace root but not against
`allowedPaths`/`readOnlyPaths`, and `networkAllowed` is accepted but not enforced. This record closes both, with the
kernel doing the enforcement rather than a parse of the command.

## Threat model

The commands are model-issued: an agent asks `execute` to run a program from the allowlist, with arguments it
chooses. The workspace container is the outer boundary; this layer confines each command inside it, so that whatever
the arguments, the program and every process it starts:

- cannot write a path under `readOnlyPaths`;
- cannot read or write a workspace path outside `allowedPaths` (when it is set), or anything outside the workspace
  but the system directories programs need to run;
- cannot open a network connection when `networkAllowed = false`.

`CommandPolicy` (#1715) stays as the layer before this one. It refuses with a clearer message, and it is the only
layer off Linux. It is not a sound boundary on its own: a program's own behaviour (a build tool reading a config, a
symlink created by an earlier command) reaches paths no argument names.

Out of scope: a command that starts a daemon (a new session) escapes the runner's process-group kill. The daemon stays
confined, since the confinement is inherited, but it outlives the command. Only a cgroup per command follows it, and
that needs container privileges a default `docker run` does not give; it is tracked as its own issue.

## Mechanism

Everything here works in a default `docker run`, with no added capability, cgroup mount or user namespace.

**`llm4s-confine`** is a small C helper with no dependencies, built into the workspace-runner image at
`/usr/local/bin/llm4s-confine`:

```
llm4s-confine [--rx P]... [--ro P]... [--rw P]... [--wfile P]... [--no-net] -- program args...
```

It checks the Landlock ABI (v3 or later, kernel 6.2: earlier ABIs cannot refuse `truncate`), builds and installs a
Landlock ruleset from the path options, sets `no_new_privs`, installs the seccomp filter when `--no-net` is given, and
`execve`s the program in its own place, so it keeps the pid, session and process group `setsid` gave it and the
runner's kill works as before. Both restrictions are inherited by every descendant, across `fork`, `exec` and
`setsid`.

When it cannot confine, because the ABI is too old or a call fails, it writes one line beginning
`llm4s-confine: unavailable:` to stderr and exits with status 125, and the program never starts. The runner reads the
marker, not the status alone, so a program that itself exits 125 is not mistaken for it.

**`Confinement`** (runner, pure) turns a `WorkspaceSandboxConfig`, the workspace root and the command's temporary
directory into the helper's arguments. `prepareCommand` puts `llm4s-confine <args> --` before the program on Linux
(after `setsid`). Off Linux, it does not, and the runner logs once at startup that commands run unconfined.

The runner's own helper processes (`getfacl`/`setfacl`, the git configuration lister) are not confined. They run
fixed programs with arguments the runner chooses; only `execute` commands are model-issued.

## Filesystem rules

Landlock is allow-only: what no rule grants is refused. A command is granted:

- read and execute on the system directories (`/usr`, `/bin`, `/sbin`, `/lib`, `/lib64`, `/etc`), the toolchain
  directories the image adds (sdkman under `/root/.sdkman`), and the JDK (`JAVA_HOME`);
- read and write on `/dev/null`;
- read and write on a fresh per-command temporary directory, which `TMPDIR` names, removed when the command ends;
- in the workspace, read and write on the root (or on each `allowedPaths` entry instead, when that is set), and
  read-only on each `readOnlyPaths` entry under it.

The runner's directories, `/root` beyond the toolchain, `/proc` of other processes and every other path are not
reachable.

**A read-only path inside a writable one.** A Landlock right granted on a directory applies to the whole hierarchy
beneath it, so "the root is writable except `ro/`" cannot be one rule. For each read-only path `R`, `Confinement`
walks from its writable ancestor down to `R` and, at each directory `D` on the way:

- grants read on `D` itself, but no create, delete or rename right, since those would reach `R`;
- grants read and write on every existing entry of `D` that is not on the way to `R`;
- grants write (`--wfile`) on each existing regular file directly in `D`.

`R` gets read only. So **with a read-only path, a command cannot create, delete or rename entries directly in a
directory above it** (with `readOnlyPaths = ["ro"]`, directly in the workspace root). It can still write anywhere in the
other directories and to the existing files in those above `R`. The runner's own file operations are not confined
and create files in the root as before. With no `readOnlyPaths` there is no such limit. The alternatives are a bind
mount or a mount namespace, which need privileges this design does not ask for.

Rules are bound to the paths that exist when the command starts. A path created later under a granted directory is
covered, since the grant applies to the hierarchy. An `allowedPaths` or `readOnlyPaths` entry that does not exist when
the command starts is skipped: a missing allowed path stays unreachable for that command, and a missing read-only path
has nothing to protect until something creates it, which the runner's own path policy (F2) refuses.

## Network

With `networkAllowed = false` the helper installs a seccomp filter that:

- refuses `socket` and `socketpair` with `EACCES` for every address family except `AF_UNIX`, so local tools keep
  working and a program trying the network fails with "permission denied" rather than being killed;
- refuses `io_uring_setup` with `EPERM`, since io_uring can open sockets without calling `socket`;
- kills the process on any system call made under a foreign architecture (i386 `socketcall`, the x32 ABI), which are
  the routes around a filter that checks x86-64 numbers only.

TCP and UDP are both covered, which Landlock's network rules (TCP only, ABI v4) are not, so they are not used. With
`networkAllowed = true` no filter is installed. The default stays `false`, so **commands no longer have network by
default**; nothing on the default allowlists needs it.

## Failure

| Case | Outcome |
|---|---|
| Linux, helper missing, Landlock ABI below v3, or a Landlock or seccomp call fails | the command is refused, `SANDBOX_UNAVAILABLE`, naming the cause; the program never starts |
| A command breaks a rule while running (`rm ro/x`, `curl ...`) | not a runner error: the program fails with "Permission denied", and its exit code and output reach the model as any failing command's do |
| Not Linux (macOS, Windows) | commands run as before, unconfined, `CommandPolicy` only; logged once at startup and documented |

The image is amd64. Docker on Apple silicon runs it under emulation, where seccomp may not install; the helper then
refuses rather than runs unconfined. This has to be checked live on such a host before release.

## Build

- Source: `modules/workspace/workspaceRunner/src/main/c/llm4s-confine.c`.
- Image: the Docker build adds the source and compiles it statically in one layer (`gcc`, `libc6-dev`; the Landlock
  header comes from noble's `linux-libc-dev`), then removes the compiler.
- `RunnerMain` takes the helper's path from an environment variable, defaulting to `/usr/local/bin/llm4s-confine`;
  tests pass it directly.
- On Linux, an sbt task compiles the helper with `cc` into `target/` for `workspaceRunner`'s tests, so the plain `test`
  job exercises the real helper on every PR. A Linux machine without `cc` fails that task with a clear message. Off
  Linux, the task does nothing.

## Tests

1. Unit, every platform: `Confinement` arguments for `allowedPaths`, `readOnlyPaths` (the walk, siblings and files),
   skipped missing entries and the temporary directory; `prepareCommand` inserts the helper only on Linux; the
   unavailable marker becomes `SANDBOX_UNAVAILABLE`, and a program's own exit status 125 without it does not.
2. The real helper, Linux runner tests, through `execute`: `cat`, `find` and `grep -r` into a path outside
   `allowedPaths` are refused; `rm`, `mv`, `cp`, `touch` and `chmod` into a read-only path are refused, also through a
   symlink in the workspace that leads there; creating an entry in the root with `readOnlyPaths` set is refused (the
   limitation, pinned); each of these succeeds unconfined, so a test cannot pass for the wrong reason.
3. Live `@Workspace`, in the image: the issue's acceptance. A write under a read-only path and a read outside
   `allowedPaths` fail; `curl` (an extra command) to the runner's own port on `127.0.0.1` fails with
   `networkAllowed = false` and gets a response with `true`, so the test needs no internet. With #1982 this tier runs
   on the PR.
