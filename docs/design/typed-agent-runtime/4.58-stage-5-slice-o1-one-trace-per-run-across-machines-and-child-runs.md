# 4.58 Stage 5 slice O1: one trace per run, across machines and child runs ([#2137](https://github.com/llm4s/llm4s/issues/2137))

Part of the [Typed Agent Runtime design](../typed-agent-runtime-design.md), §4. Stage 5 spec:
`docs/superpowers/specs/2026-10-20-stage-5-production-design.md`, "O1" and "Rules every slice must satisfy".

Slice O1 of [#2129](https://github.com/llm4s/llm4s/issues/2129). Before it, an agent run reached tracing as flat
events: OpenTelemetry made one parentless span, so one trace, per event, and Langfuse made one trace per
`AgentRunEnded` (id = run id), a child's linked to its parent's only by `parent_thread_id` / `parent_run_id`
metadata. O1 makes a run one span tree, a delegated child's run part of its parent's tree, and gives a run a context
it continues, which a queue entry (W1, [#2134](https://github.com/llm4s/llm4s/issues/2134)) will store and pass back.

Placement: core gains two agent-neutral types and an optional field on four events; the span tree is built by
`llm4s-observability-otel` and the Langfuse nesting by `llm4s-observability`; the agent decides the ids. Specs:
`TraceContextSpec` (core), `OpenTelemetrySpanTreeSpec` (otel), `LangfuseSpanTreeSpec` (observability),
`SpanTreeSpec` and `RunOriginTraceSpec` (agent), and the `CheckpointerContract` origin case, now with a trace
context, run against every store.

## API

In `org.llm4s.trace` (core, `@Stable`: the spec makes members added to an existing type take that type's tier, so
the `span` field on the `@Stable` `TraceEvent` cases is `@Stable`, and `stabilityTierCheck` refuses a `@Stable`
signature naming an `@Experimental` type; the two types are a W3C carrier and a placement triple, small enough to
promise):

- `TraceContext(traceId, spanId, sampled)` - the serializable carrier, a W3C Trace Context position. `traceParent`
  writes it as a `traceparent` value; `TraceContext.parse(String): Result[TraceContext]` reads one;
  `TraceContext.of(...)` validates; its JSON form is the `traceparent` string. `spanFor(key)` derives the span `key`
  names in the same trace (SHA-256 of trace id and key); `rootFor(key)` a whole root context from a key;
  `random()` a fresh one.
- `TraceSpan(context, parent: Option[TraceContext], startedAt: Instant)` - where an event sits in a trace; the
  event's own `timestamp` is the span's end. A parent of another trace is refused (`TraceSpan.of` returns a
  `ValidationError`; `apply` and the `with*` setters throw), because OpenTelemetry takes a span's trace from its
  remote parent while Langfuse and the collector take it from `context`: a mismatch would put one span in two traces
  (Codex review, PR #2142). The parent stays a full `TraceContext` (not a bare span id) so its sampled flag reaches
  OpenTelemetry's parent-based sampler.
- `TraceEvent.span: Option[TraceSpan]` (default `None`), carried as a last field `span` by `CustomEvent`,
  `TokenUsageRecorded`, `ErrorOccurred` and `AgentRunEnded`; their `toJson` adds `trace_id`, `span_id` and
  `parent_span_id` when placed.

In `org.llm4s.agent.graph`:

- **`RunConfig.traceContext: Option[TraceContext]`, `withTraceContext(TraceContext | Option[TraceContext])`** -
  the runtime hook by which a run continues a given context. This is what W1 sets: a queue entry stores the
  submitter's `TraceContext` (as its `traceparent` string, or the type's JSON form) and the worker passes it back as
  `RunConfig().withTraceContext(entry.traceContext)` on every attempt - the first `start`, and each `recover` after a
  lease expired. Nothing but tracing reads it.
- **`RunOrigin.trace: Option[TraceContext]`**, `withTrace(...)`, an `apply` parameter defaulting to `None` and the
  previous five-argument `apply` kept as an overload: the span of the parent's tool call that started the child,
  written with the child's first checkpoint and copied onto every later one, like the rest of the origin.

In `org.llm4s.agent.events`: `ToolExecuted.idempotencyKey: Option[String] = None`, the call's key, a last field with
a default (the event stays version 1: an older event reads as `None`, an older reader ignores the field).

## How the ids are chosen

The agent names every span so that each party computes the same id with no coordination (`AgentTraceSpans`,
`private[agent]`). Each key is its kind followed by its parts length-prefixed (`<length>:<part>`), so the encoding is
injective however caller-chosen thread and run ids are spelled (Codex review, PR #2142); the keys below show the
parts:

- **A run's span** is named by the run's incarnation, `llm4s.run/<threadId>/<runId>/<fencingToken>`: a `RunId` may
  be reused (a recovery under the same id, a reused `RunConfig`), a claim's token never is (Codex review, PR #2142).
  Tracing reads the token from the run's first event, its claim; a `task` call from `RunPosition.fencingToken`. It is
  `continues.spanFor(key)` where `continues` is the run's
  `RunConfig.traceContext` (for a child, the context its origin recorded), or `TraceContext.rootFor` of the same key
  when the run continues nothing. Its parent is `continues`.
- **A tool call's span** is `run.spanFor("llm4s.tool/<idempotencyKey>")`, from the call's `IdempotencyKey`, which
  `agent.tool_executed` now records (`ToolExecuted.idempotencyKey`, optional: a digest, no content; an event stored
  before it falls back to `llm4s.tool/<threadId>/<toolCallId>`). `spanFor` derives from the trace id and the key
  only, not from the run's span, so a parent run recovered under a new `RunId` in the same trace names the same span
  for the same call: the child that call started, recorded under it, stays under it. The provider's call id is not
  the key: a later model request may reuse it, and the loop gives that call another idempotency key, so another span
  (Codex review, PR #2142).
- **A suspended phase of a tool call** is a span of its own. A call that suspends - for approval (`NeedsApproval`)
  or with a question (`Asked`, which is how a `task` call whose child suspended ends its phase) - emits a
  `ToolExecuted` in that run, and the run that resumes it emits another, so keying both by the call would place one
  span id twice, under two run spans (Codex review, PR #2142). The call is modelled as one logical span, the
  key's, placed exactly once by the event of the phase that *ended* the call (`Succeeded`, `Errored`, `Denied`,
  `Rejected`), which the store commits once; each suspending phase is `llm4s.tool/<key>/phase/<seq>` under the run
  that suspended. The logical span is the one a child's origin records, so every run of a child - the one started
  in the suspended phase too - is under the call's single span. The cost: that span covers only the final phase's
  duration (the earlier phases' times are in their own spans), so a child's first run can start before it.
  Per-run ids (key + run id) were the other choice, rejected because the child's origin would then name the span of
  the run that started it, which a parent that crashed mid-call never places.
- **Every other durable event** is `run.spanFor("llm4s.event/<threadId>/<seq>")`, a usage record
  `llm4s.usage/<threadId>/<seq>`, the run's error `llm4s.error/<runId>`; all under the run's span.

A `task` call computes its own span the same way, from `ToolContext.idempotencyKey` (`DelegationMiddleware`), and records it as `RunOrigin.trace` at the
child's first admission. `ChildRunner` gives every run of the child - its first, a reattach's recovery, a resume -
the context its *stored* origin recorded, falling back to this call's for a child stored without one; the child's
runs are so under the call that first started it, and its own `task` calls compute grandchildren's spans from it.

Deterministic ids were chosen over ids the backend draws because the tool-call span must be known before it exists:
a child starts, and on another machine may run, while its parent's tool call is still open, and the tool call's span
is only exported when the call ends - possibly by a later run of the parent on another machine. Ids derived from
durable names (run id, thread, call id, sequence number) are the same on every machine and need no storage beyond the
origin. The cost is that a backend must honour given ids: OpenTelemetry's SDK does through its `IdGenerator`
(`PlacedIds`, set per span start on the exporting thread), Langfuse takes client ids anyway.

## Child span, not a link (decided by the spec)

A run continued on another worker, or recovered on another machine, takes the propagated context as its **remote
parent**, so its span keeps the original trace id: the spec (O1, as amended on PR #2141) removed the choice. A span
link alone would split one logical run into several traces, which is what "one trace per run" rules out. Links are
allowed only as supplemental metadata, such as from a recovery attempt to the attempt it replaces; O1 adds none, since
every attempt is already a sibling under the same parent in the same trace, and `RunRecovered.takenOverFrom` names
the replaced run. A later slice may add one through a `links` field on `TraceSpan` without changing the parent rule.

## What each backend builds

**OpenTelemetry** (`OpenTelemetryTracing`): a placed event becomes a span with exactly its placement's trace and span
ids, its parent as a remote `SpanContext` (sampled flag carried; a non-sampled parent is honoured by the SDK's
parent-based sampler), started at `startedAt` and ended at the event's `timestamp`. The tree for a run:
`invoke_agent <agent>` (from `AgentRunEnded`, status `ERROR` when failed, cancelled or timed out) over
`chat <model>` (`agent.model_call_completed`: `CLIENT`, `gen_ai.operation.name = chat`, `gen_ai.request.model`,
`gen_ai.usage.input_tokens` / `output_tokens`, `cost.usd`), `execute_tool <tool>` (`agent.tool_executed`:
`INTERNAL`, as the GenAI conventions ask; status `ERROR` for an errored call), each other `graph.*` / `agent.*` event
and usage record as a point span under the run, and a child's `invoke_agent` under its parent's `execute_tool task`.
An unplaced event becomes its own span, as before.

Model-call spans are points at the call's completion: `ModelCallCompleted` records no start, and adding one is a
durable event change outside this slice. A tool call's span starts at its event's time less its recorded `duration`.

**Langfuse** (`LangfuseTracing`): a placed `AgentRunEnded` of a top-level run creates the trace - id = the placement's
trace id, session = thread, metadata now with `run_id` since the trace id is no longer the run id - and every placed
run, top-level or child, is a span observation `invoke_agent <agent>` with its span id, start and end, a child's
under the `execute_tool task` observation that started it. A **child run creates no trace**: it nests in its
parent's, replacing the metadata link (the `parent_*` fields stay as metadata for search). Model calls are
generations (`chat <model>`, with usage), tool calls spans, every other placed event an event in the trace under its
parent; the turn's message spans are under the run's observation. A top-level run's own parent (a submitter's span)
is not in Langfuse, so its observation has no `parentObservationId`. An unplaced run is traced as before.

**`TraceCollectorTracing`** (`llm4s-observability`) stores a placed event as a span of the placement's trace, with its
span id, parent and start, so each run's tree is in the store under its own trace id, which it first registers as a
`Trace` (root span = the top-level run's) so the trace can be read, queried and deleted like the collector's own; an unplaced event is a span of
the collector's own trace, as before (Codex review, PR #2142). Console tracing prints events as before.

The trace id Langfuse uses is the OpenTelemetry one, so with both backends one run has the same trace id in each.

## Rule 10: no content in attributes

No span attribute an agent run produces carries message content: the agent's durable events carry none, the new
`chat` and `invoke_agent` attributes are names, ids, counts and costs, and `OpenTelemetrySpanTreeSpec` checks that a
run whose messages hold a marker string exports no attribute containing it. Langfuse's run and message observations
keep recording the turn's messages as their input and output, as #1329 made them: that is the conversation record a
Langfuse user asks for, not a span attribute; O1 does not change it. The legacy flat events (`CompletionReceived`,
`ToolExecuted`, `AgentInitialized`) that callers outside the agent trace still map their content as before.

## Checkpoint format

`RunOrigin.trace` and `Checkpoint.trace` are optional, with defaults, so a checkpoint written without them reads as `None`; it belongs to
format 8, which is not released (0.5.1 wrote format 7), as K1's `deleting` field did (§4.41). No format bump, no
SQLite schema step: the store keeps the origin inside the checkpoint JSON, and its `parent_thread_id` column is
unchanged. A build of this format without the field ignores it, losing only the child's trace position.

## For W1 and later slices

- Store the submitter's context on the queue entry as `Option[TraceContext]` (JSON form: the `traceparent` string)
  and run every attempt with `RunConfig.withTraceContext(it)`. The attempts are then siblings under the submitter's
  span in one trace, whatever worker or machine runs them. A submission with no context can record
  `TraceContext.rootFor(entryId)` (or `random()`) so its attempts still share a trace.
- A piece of work is one trace however it is continued. `Checkpoint.trace: Option[TraceContext]` (optional, format
  8, unreleased, so no bump; stores keep it inside the checkpoint JSON) records it: a run that starts work - `start`,
  a first run - writes its own span on every checkpoint it commits; a `recover` or `resume` copies the stored one, as
  do settling and `updateState`. `Agent.resume` / `recover` (and their stream forms) given no `traceContext` continue
  the latest checkpoint's: the continuation's span is a child of the first run's, in its trace, so a `task` call that
  suspended or failed is placed, when it ends, at the span its child's origin recorded (Codex review, PR #2142: a
  default resume used to start a new trace, leaving the child under a span that trace never held). A given
  `traceContext` still wins. A thread with no recorded trace (written before it) continues nothing. A new `start` is a
  new trace. The trace is on the checkpoint, not in the thread's state, because state feeds the replay-stable task
  lineage behind idempotency keys (§4.24), which a run-specific value must never change.
- O2's metrics need nothing from O1; a metric exemplar may name `TraceContext.traceId`.
