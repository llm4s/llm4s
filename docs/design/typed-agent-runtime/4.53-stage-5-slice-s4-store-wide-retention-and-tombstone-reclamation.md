# 4.53 Stage 5 slice S4: store-wide retention and tombstone reclamation ([#2059](https://github.com/llm4s/llm4s/issues/2059))

Part of the [Typed Agent Runtime design](../typed-agent-runtime-design.md), §4. Section numbers (§N.N) refer to that document and its [slice records](../typed-agent-runtime-design.md#slice-records). Stage 5 spec: `docs/superpowers/specs/2026-10-20-stage-5-production-design.md`, "S4" and "Rules every slice must satisfy".

Slice S4 of [#2129](https://github.com/llm4s/llm4s/issues/2129), after S3 ([4.52](4.52-stage-5-slice-s3-thread-registry.md)).
Until now `prune` worked on one thread and a deleted thread's tombstone was kept for good (§4.41, Phase 4 rule 12): a
store whose threads are deleted often - failed one-shot `Agent.run`s, child retention - grew by one record per delete.
This slice adds a store-wide, bounded, claim-free sweep that prunes every thread and reclaims old tombstones, and settles
what a reader of a reclaimed thread id is told. The in-memory, SQLite and PostgreSQL stores implement it;
`CheckpointerContract` gains six cases.

## What it adds

In `org.llm4s.agent.graph` (`llm4s-agent`), every new type `@Experimental`:

- `Checkpointer.sweep(policy: SweepPolicy, after: Option[ThreadId], guard: SweepGuard): Result[SweepPage]`, abstract.
- `SweepPolicy(retention: RetentionPolicy, tombstoneAge: Option[FiniteDuration], batchSize: Int)` - growth-prone
  (private constructor, `apply` with defaults, `of`, `with*`), `DefaultBatchSize = 100`, `MaxBatchSize = 1000`,
  `keepAll`.
- `SweepGuard` - `retained(threads: Vector[ThreadId]): Result[Map[ThreadId, Set[RunId]]]`, with `SweepGuard.none` and
  `SweepGuard.of(map)`.
- `SweepPage(examined: Int, reclaimed: Int, next: Option[ThreadId])` - growth-prone.
- `CheckpointerContract.isolatedCheckpointer(clock)`, a hook for stores whose cases share a database.

SQLite schema 9 and PostgreSQL schema 3: a tombstone's deletion time (`deleted_nanos` / `deleted_at`, the store's
clock) and the store's reclamation mark (`llm4s_checkpoint_meta.reclaimed_first` / `checkpoint_reclaimed.first_seq`).

## Decisions

**The reader contract: a store-wide reclamation mark, not a generation in cursors.** The requirement is that a reader of
a deleted thread's log, or of a new thread reusing the id, is never shown the new thread's events as a continuation of
the old one, before or after reclamation. The spec recommends a per-incarnation generation carried in event cursors and
`RunPosition`. We meet the requirement without one. Event numbers are already per-incarnation ranges: a new thread of a
deleted id numbers from one past the tombstone's skipped number, and `Checkpointer.deleted` refuses any cursor inside
the old range with `ThreadDeleted`. The only thing reclamation loses is the per-id record of where the old range ended.
So the store keeps one number in its place: the highest first number of every tombstone it has reclaimed, which it
raises in the same transaction as each reclamation. A row for an id with no record (a new thread, of a reclaimed id or
any other) starts its numbering at that mark, and a read of an id with no row judges the cursor against it. A cursor
from a reclaimed log is at most the tombstone's first number minus two, so it is below `mark - 1` and refused with
`ThreadDeleted`, before and after a new thread of the id exists, through every store over the storage and across a
restart.

Why not the generation: it would change `eventsAfter`'s and `awaitEventsAfter`'s signatures, every subscription and
event hand-over in `GraphRuntime`, `RunPosition` and every store's event rows, and every caller would carry a pair
where one number already does the job. The mark is one row per store, so reclamation stays bounded, and nothing a
caller holds changes. What the reader is told after reclamation is `ThreadDeleted` - the thread was deleted - rather
than a distinct "reclaimed" refusal; the reader's correct action is the same (read from `afterSeq = 0` to follow
whatever thread is under the id now). The spec's breaking-change list allowed cursors to gain a generation; they do not.

The cost: once a store has reclaimed a tombstone, a new thread of *any* id numbers from the mark, not `1`. A store
that never reclaims behaves exactly as before. Nothing in the runtime assumes a first event of `1` (subscriptions start
from `0` and follow `firstSeq`); the contract's existing cases do, which is why the sweep's cases run on isolated
storage (below). Numbers stay well inside a `Long`.

**A tombstone records when it was deleted, and an empty row is told from a tombstone by that.** The sweep judges age by
the store's clock against `deletedAt` (rule 1), stamped by each delete, a repeated delete of a tombstone included. A
row that numbered no event and was never deleted holds nothing and is dropped as before; with the mark above 1 its
`next_seq` is no longer `1`, so "never deleted" (`deleted_at IS NULL`), not `next_seq = 1`, is what makes it droppable.
On upgrade, rows with `first_seq > 1` - the tombstones a store already holds, and threads created over one - are dated
from the migration (PostgreSQL by the server's clock; SQLite by the system clock, as its migration has no injected
clock), so an upgraded store's old tombstones are reclaimed `tombstoneAge` after the upgrade, never at once.

**What is reclaimable.** A row with no checkpoint, no event since its delete (`next_seq = first_seq`), no metadata,
effect record or pending write, deleted before the cutoff, and no claim but one that expired before the cutoff too. A
lapsed claim counts because its holder may still commit until someone replaces it (the contract allows a commit after
`expiresAt`); one lapsed for `tombstoneAge` has no live holder, and reclaiming its row only makes that holder's
commit `StaleClaim`, which strengthens fencing (rule 3). A tombstone's child place goes with it: `children(after =
reclaimed id)` is then a `ValidationError`, as the `children` Scaladoc anticipated ("as long as its tombstone does").

**The rule-4 hook is a guard asked once per page, outside the store's transactions.** W1's queue is built in
parallel, so the sweep takes a `SweepGuard` rather than reading a queue. For each page the store asks it which of the
page's threads are protected, and with which `RunId`s, before changing anything; a `Left` changes nothing. A protected
thread is pruned as usual (a long-running entry must not grow without bound) except that the newest checkpoint each
named `RunId` committed is kept, and its tombstone is never reclaimed. The events' floor follows the policy alone: the
admission evidence is the checkpoint, not its events. The run id is read from the checkpoint's JSON
(`Checkpoint.runId`) only for a protected thread's history, so no schema column is added for it; W1, which needs a
run-id lookup anyway, may add an indexed column and switch this read to it.

The guard is called outside the transaction because it may read another store (a queue in the same database, on
another connection) and a SQLite store holds the file's write lock inside one. This leaves one window, which W1 must
know: an entry submitted for a thread after the guard answered and before the page's transaction commits. For
checkpoints it is harmless - the entry's attempts have committed nothing yet, or what they commit is the thread's latest
checkpoint, which every policy keeps. For a tombstone old enough to reclaim it is real: the entry may record the
tombstone as its deletion marker (rule 4) and then find it reclaimed. W1 closes it either by treating "the recorded
marker's tombstone is gone and no newer delete happened" as no change, or - in the SQL stores, where the queue shares
the database - by adding an `open entry` condition to the reclamation statement (`Sql.reclaim`, and SQLite's), which
runs in the transaction.

**Paging is by thread id, read one past the page.** Each call reads `batchSize + 1` ids after `after` by the primary
key (a store's own order: byte order in memory and SQLite, the database collation in PostgreSQL), visits `batchSize`,
and returns the last as `next` only if another followed, so the final page says `None`. `after` need not still exist:
pruning cannot remove a row, but reclamation can, and the next page starts from the cursor's place. A thread created
while a caller pages is visited in that pass or the next. Tombstones are threads the store holds, so they are visited
and counted in `examined`.

**Bounded calls.** In memory, a page is one turn at the store's lock. In SQLite, the page's ids are one read and the
page's reclamation and pruning one `BEGIN IMMEDIATE` transaction, bounded as every write is. In PostgreSQL a call makes
up to three transactions, each bounded by the call timeout, so it returns within three times the store's bound: the
page read; the reclamation, under a transaction-scoped advisory lock on the schema (exclusive) with each candidate row
locked in id order, as every call locks rows, then deleted only if still reclaimable; and the pruning, rows locked in
that order. Splitting reclamation from pruning keeps the exclusive lock short.

**Creating a row versus raising the mark, in PostgreSQL.** A claim on an id with no row inserts one numbered from the
mark. Under read committed, an insert that waited on a concurrently deleted row could have read the mark before the
reclaiming transaction raised it. So a claim that finds no row takes the reclamation lock *shared* before inserting
(shared advisory locks cost no row writes and do not block one another), and a reclamation takes it exclusively; a
claim on an existing row - a live thread or a tombstone - takes no advisory lock, and a reclamation that waits for its
row lock re-checks the row and skips it once the claim has landed. A claim takes the shared lock holding no row lock,
and a reclamation takes the exclusive lock before any row lock, so the two cannot deadlock. A concurrency spec races
claims against a sweep reclaiming their ids' tombstones, round after round, and checks every new thread numbers past its
old one. SQLite needs nothing: every write is one `BEGIN IMMEDIATE` transaction.

**The contract's sweep cases run on isolated storage.** A sweep pages through every thread of the store, and a
reclamation moves the mark every later new thread numbers from, so on a database shared by every case the counts would
include other cases' threads and later cases' "numbers from 1" assertions would break. `isolatedCheckpointer(clock)`
defaults to `newCheckpointer` (a new store per case in memory and SQLite); the PostgreSQL contract spec overrides it
with a fresh schema, and its `reopen` and `sibling` now open the schema of the store they are given.

**Scheduling is W2's.** The sweep is a library call; W2's worker runs it on a schedule, one instance at a time (an
advisory lock or a lease row). Two sweeps at once are safe - every change is re-checked under the row's lock - only
wasteful. The sweep reads no tenant (rule 9): it is the operator's, store-wide, and returns counts, never thread data.

## For later slices

- **W1** feeds the guard from open queue entries (thread, each attempt's `RunId`), and handles the guard window above.
  The run-id lookup it adds can serve `RetentionSweep.kept`'s run read. W1 also takes a schema step: whichever of W1 and
  S4 merges second renumbers (S4 is SQLite 9, PostgreSQL 3).
- **W2** loops `sweep` until `next` is `None`, on a schedule, with a `SweepPolicy` from configuration (S5's tree has
  room: `llm4s.agent.worker`), and a guard over its queue. Terminal queue entries' retention (W1) is the same sweep's job.
- **O2** can count `examined` and `reclaimed` per page.
