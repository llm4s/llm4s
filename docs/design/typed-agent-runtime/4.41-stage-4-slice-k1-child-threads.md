# 4.41 Stage 4 slice K1: child threads ([#2045](https://github.com/llm4s/llm4s/issues/2045))

Part of the [Typed Agent Runtime design](../typed-agent-runtime-design.md), §4. Section numbers (§N.N) refer to that document and its [slice records](../typed-agent-runtime-design.md#slice-records). Phase 4 spec: `docs/superpowers/specs/2026-10-19-phase-4-subagents-design.md`, "K1".

Slice K1 of [#2044](https://github.com/llm4s/llm4s/issues/2044), the first kernel slice. Until now a thread had no
parent: `deleteThread` removed one thread, and nothing could list the threads a run created. K1 gives a thread an
origin, so a delegated child can live on a thread of its own that its parent's run alone drives, is listed under the
parent, is deleted with it, and is bounded in number. It also records how every run settled, durably, so a settled
child's result can be read back after a restart (K2 and D1 rely on it). It starts no child itself: K2's child runner
does, through the `private[agent]` entry points added here.

Everything is in `llm4s-agent`, `org.llm4s.agent.graph`, apart from the SQLite schema step
(`llm4s-agent-checkpoint-sqlite`) and the contract cases (`llm4s-agent-testkit`). The new public types are
`@Experimental`. The specs are `ChildThreadSpec` (ids, origin, refusals, cascade, retention, outcomes),
`RunOutcomeRebuildSpec` (a status rebuilt from the thread equals the live one), `FormatSevenCheckpointSpec` (a thread
written by the last format-7 build, resumed), `SqliteSchemaFiveSpec` (a file written by the last schema-5 build,
migrated and continued) and the new `CheckpointerContract` cases.

## API

In `org.llm4s.agent.graph`:

- `final case class RunOrigin private (parent: ThreadId, call: IdempotencyKey, agent: AgentId, startedAt: Instant,
  depth: Int)`, growth-prone (`apply`, `with*`), with a `ReadWriter`. `depth` is 1 for a child of a top-level thread
  and at least 1 (`apply` throws below). `startedAt` is when the child was first admitted: `startChild` stamps it by
  the runtime's clock, whatever the caller passed, and it is copied forward with the origin (D4 measures a task's
  duration from it).
- `final case class ChildThread(threadId, origin, status, latest, updatedAt)`, a plain case class with a
  `ReadWriter`; `ChildThread.of(checkpoint)` builds one from a child's latest checkpoint.
- `enum RunOutcome`: `Answered`, `StepLimitReached`, `TokenLimitReached`, `Blocked(guardrail, reason)`,
  `OutputInvalid(errors)`, `Failed(kind, message)`, with a `ReadWriter`.
- `Checkpoint.origin: Option[RunOrigin]` and `Checkpoint.outcome: Option[RunOutcome]`, with `withOrigin` and
  `withOutcome`; format **8**. The previous ten-argument `Checkpoint.apply` stays as an overload without defaults.
- `ThreadId.child(parent, agent, call)`: `<parent>/~task/<agent>/<digest>`, the digest the first 24 hex characters
  of the SHA-256 of `("llm4s-child-v1", parent, call, agent)`. `ThreadId` gains a `ReadWriter` (a plain string).
- `Checkpointer.children(parent, after, limit): Result[Vector[ChildThread]]`, abstract.
- `GraphRuntime.children(threadId, after = None, limit = 100, config)` and `Agent.children(threadId, config)`, which
  reads every page.
- `GraphError.ChildThread(threadId, parent)`.
- `RunConfig.childRetention` (default `RunConfig.DefaultChildRetention`, 64) and `withChildRetention`. The previous
  eight-argument `RunConfig.apply` stays as an overload without defaults.
- `private[agent]`: `GraphRuntime.startChild`, `recoverChild`, `resumeChild`; `CompiledGraph.withOutcome`;
  `AgentRun.settledStatus(outcome, state)`; `RunOutcome.blocked(error)`.

## Decisions

### A child is decided by its checkpoint, never by its id

`ThreadId.child` gives a hierarchical id so an operator sees the nesting, but the runtime never parses it: a thread is
a child exactly when its latest checkpoint records an origin. A caller who names a top-level thread
`p/~task/a/<hex>` gets a top-level thread (tested). The origin is set by `startChild` on the first claim commit and
copied onto every later checkpoint, as the tenant is. `fork` writes none (a fork is top-level), and `updateState`,
which a child refuses anyway, copies what the latest checkpoint has.

### Refusals come after the tenant check and before any claim

`start`, `recover`, `resume`, `fork` (of a child source), `updateState` and `deleteThread` read the latest
checkpoint, check the tenant, then refuse a child with `ChildThread`, all before claiming the thread, so a refused call
changes nothing and another tenant still learns nothing. Reads (`history`, `checkpoint`, `subscribe`, `children`)
are allowed. `startChild` refuses an existing thread with `ThreadExists`, whatever it is, so K2's runner can loop back
to its read; `recoverChild` and `resumeChild` refuse a top-level thread with a `ValidationError`.

### Paging by place, not by id

`children` pages in creation order. Each store gives a child a place when a checkpoint first names its parent:
`InMemoryCheckpointer` from a counter, kept in a per-parent `TreeMap` index; SQLite one past the file's highest
`child_order`, a column beside `parent_thread_id` (the spec named only the parent column; the order column is what
makes creation order pageable by index). A child keeps its place as it moves on, and a deleted child keeps it in its
tombstone, so a cursor naming a child that retention deleted between two pages still works. An unknown cursor is a
`ValidationError`. A tombstone is never listed, nor a thread whose latest checkpoint names another parent or none.

### Cascade delete holds everything first

`deleteThread` holds the thread, lists every descendant (depth-first, deepest first) under that hold, then holds each
descendant in turn - in this runtime and by a store claim, nested - before deleting any. A descendant with a live
claim anywhere, or a run in this runtime, refuses the whole call with `ThreadBusy` and nothing is removed (tested).
Deletes then run deepest first, each fenced by its own claim; one that fails stops there, leaving the parent and fewer
descendants, and a second delete finishes (tested). Each hold is the existing `holding` (renewed, bounded by a lost
claim), so the cascade inherits its loss handling.

Each child's delete is fenced by its own claim, but the claim that justifies it is the thread's above. So before each
descendant's delete the cascade checks that the root's claim still holds - not found lost, and its token still the
store's current claim, which a renewal proves (`Held.holds`) - and stops with `ThreadBusy` at the first mismatch. A
cascade whose claim was lost while it stalled never deletes a child that a successor run on the parent may reattach
and would then run again (tested: a takeover after the first child's delete leaves the second).

That check and the delete are two store calls, so a takeover between them would still remove the child (#2063). The
store therefore checks the claim above atomically with each delete: `Checkpointer.deleteThread(threadId, token,
fence: Option[(ThreadId, FencingToken)])` deletes only if `token` is the thread's current claim and the fence thread's
current claim is the fence token - one transaction in SQLite, one lock in memory - and otherwise is `StaleClaim` with
nothing removed (the thread's own claim checked first, so a refusal naming the fence thread is a loss of the claim
above). The cascade passes the root's token for every descendant; retention passes the parent's for every thread of
the retained child's tree. The runtime reports a fence refusal as `ThreadBusy` on the thread above, acts on it as a loss of the root's
claim when the root is the fence, and gives the child's claim back as usual, not as lost (tested for both, with the takeover between the check and the delete;
`CheckpointerContract` covers a superseded fence and a matching one). The fence has no default: a store author must
implement it.

Settling an abandoned child at `start` is a commit under the child's own claim, not a delete, and needs no fence
above it. `start` is admitted only on a `Completed` or `Failed` parent (`Running` is `IncompleteRun`, `Suspended` is
refused for its pending interrupts), so the abandoned child belongs to a run that can never be replayed: no
`recover` or `resume` of the parent exists to reattach it. A successor that takes the parent over is another
`start`, whose calls make new keys and so new child ids (a fork's target is another thread, so its children's ids
differ too); it never reads the child as its own, and its own pass would settle it the same way. A stale worker
settling it `Failed` after a takeover therefore changes nothing a successor reads. The same holds when the run's
terminal pass settles a child admission skipped as busy (#2073): the child was listed under that `start`'s claim
before the run's first commit, so it is an earlier run's.

Admission has the mirror race (#2071). A child is listed by `children` only once its first commit - the claim commit
that writes its `origin` - lands, and that commit was fenced only by the child's own claim. A stale task of a parent
taken over or released could therefore register a child after a successor's cascade delete had listed the parent's
children, and the delete would leave it an orphan. The first commit is now fenced by the parent's claim in the store:
`Commit.fence: Option[(ThreadId, FencingToken)]`, the same representation as the delete's, checked after the commit's
own token in the same transaction (SQLite) or under the same lock (in memory), and otherwise `StaleClaim` naming the
parent with nothing written.

So is every other admission or settlement the parent drives on a child, since a stale task whose parent claim expired
just before it reached the child could otherwise take the child's claim and run model calls or side effects after a
successor took the parent: the claim commits of `recoverChild` and `resumeChild`, `settleChild`'s commit, and the
abandon at `start` or at that run's terminal pass (settling an earlier run's child `Failed("abandoned")`, fenced by the starting run's own token). The
child runner passes its parent run's token (`RunContext.position.fencingToken`) as `parentClaim` to `startChild`,
`recoverChild`, `resumeChild` and `settleChild`; the fence thread is the parent the child's origin names. Top-level
threads pass none. A refusal is `ClaimLost` on the parent - the parent run has lost its claim, so the call stops, never
waits as on a busy child - and the child's own claim is given back as usual, not as lost (tested with the takeover
between the parent's last check and each of the five commits, the first also through the child runner on both stores;
`CheckpointerContract` covers a superseded fence and a matching one).

The fence is a field of `Commit`, not a parameter of `Checkpointer.commit` as the delete's is, because it is a
precondition of one write, as `token` is, and `Commit` already carries every other: a store reads it from the
`Commit` it already reads, and every wrapper that forwards the `Commit` whole forwards the fence unchanged. A store
that ignores it still compiles; the two contract cases are what catch it.

Commits inside a child run that is already admitted need no fence, and carry none. The run was admitted under the
parent's claim; it stops when that claim is lost (K2's cancellation), and any later continuation is fenced again at
its admission. Once the first commit has landed the child is listed, so a cascade's preflight finds it and must hold
its claim to delete it (refused with `ThreadBusy` while a run holds it), and a delete clears the claim, so no later
commit under an earlier token lands. Fencing them too would add a read of the parent to every commit of every child
for no case the admission fence leaves open.

### Retention prunes only children whose call has committed

The spec's prunable set is "settled, and its call's result committed in the parent's latest checkpoint, or the parent
is `Completed`". The runtime cannot read a tool call's key out of an agent's state, so it uses the equivalent point in
the run instead: retention runs only where every call of the parent has committed and can never run again.

- **Before the terminal `Completed` checkpoint**, once the last superstep's checkpoint is durable. That checkpoint
  schedules no task (the run is ending because nothing is left), so every call has committed. The pass checks that
  the store's latest checkpoint is that one. Under `Async` or `OnExit`, where it may not be durable yet, the pass runs
  instead once the run's buffered commits have drained (the terminal checkpoint is stored), still under the run's
  claim and before it is released, so a one-shot parent is within `childRetention` once its run ends, whatever its
  durability; a drain that fails leaves the pass to the next `start` (#2067, tested under each mode and with a failed
  drain). Under `Sync` a crash during the pass leaves the parent
  `Running` at that checkpoint; `recover` restores it, has nothing to run, reaches the same point and repeats the
  idempotent pass (tested: a failed delete and a failed terminal commit, then `recover`).
- **At `start` admission**, under the new run's claim, before its first commit, whatever the parent's last status
  (`Completed`, or `Failed` after a Block). `start` is admitted only with no incomplete execution, so no call of an
  earlier run can be replayed and every settled child is prunable. That finishes a pass that was skipped, and removes
  children a Block's retraction left. A child of an earlier run still `Running` or `Suspended` can never be
  reattached, so it is first settled `RunOutcome.Failed("abandoned", ...)` - a `Failed` checkpoint over its latest,
  same snapshot, with a `RunFailed` event - under its own claim, and then counts; one that is busy is skipped
  (tested). The run remembers the children it skipped, and its terminal pass (before the `Completed` checkpoint, or
  after the drain under `Async` or `OnExit`) settles each whose claim is free by then the same way, then prunes, so a
  parent that never starts again is still bounded (#2073, tested under each mode). Only those children: a terminal
  pass never abandons a `Running` or `Suspended` child of the current run (tested). One still busy at the terminal
  pass is left to the next `start` (tested); that needs a stale holder outliving the whole new run, since a holder's
  claim lapses within its TTL. A run admitted by `recover` has no such list, so a crash between admission and the
  terminal pass also leaves them to the next `start`.
- Never at a Block itself, never at `recover` or `resume` admission, and never a child of the current run before its
  call commits (tested).

**Fenced by the parent's claim.** The pass judges by the parent's latest checkpoint (`base`) and holds only while the
caller holds the parent's claim, so it is fenced twice (#2056 review):
- the parent's claim - not found lost, and its token still the store's current claim, proved by a renewal - is checked
  before the listing, after it, and before each child is settled or deleted, and inside each child's cascade; the
  pass stops at the first mismatch, so a stale worker whose claim was lost never deletes a child a successor just
  made (tested: a takeover while the children are listed deletes nothing; one after the first delete stops there);
- the parent is read before and after the listing, and the pass touches nothing unless its latest is `base` both
  times: a successor commits a checkpoint of its own before any of its calls starts a child, and checkpoint ids are
  never reused, so such a listing holds none of a successor's children.

Settled is `Completed` or `Failed`, which in this build always carries an outcome. A failed delete is logged at WARN.

### The outcome is chosen where the run settles

`end` asks the compiled graph how a completed run settled (`CompiledGraph.withOutcome`, default `Answered`); the agent
loop maps `TurnOutcome` to `Answered`, `StepLimitReached` or `TokenLimitReached`. A Block maps its error: `GuardrailBlocked` to `Blocked`,
`GraphError.OutputInvalid` to `OutputInvalid` with every error (its message abbreviates them), anything else to
`Failed(simple class name, message)`. Every other checkpoint records none, so a later run's first checkpoint clears
it; `updateState` keeps the status and so the outcome. `AgentRun.settledStatus` rebuilds the `AgentStatus` (or the
`Left`) from an outcome and the checkpoint's state, and `GraphRuntime.endedBlocked` now reads the outcome; the rebuilt
status equals the live one for each case (tested). K3 (§4.43) writes `TokenLimitReached` and maps it to
`AgentStatus.TokenLimitReached`.

## Where the spec was imprecise

- **Prunable children** are found by the run's position, not by matching keys in the parent's state (above).
- **SQLite** adds `child_order` beside `parent_thread_id`, with the index on both.
- **`Agent.children`** returns every child (bounded by retention) rather than a page; the runtime method pages.
- **`startedAt`** is stamped by the runtime, so a replayed `startChild` cannot move it.

## Runtime rules

Phase 3's rules 1-13 and Phase 4's 14-19:

1. **One batch, one snapshot.** No tool or state key. Two parallel calls derive different child ids from their keys,
   so they never share a thread.
2. **Total updates.** No update function.
3. **Visibility.** No state; a child is visible through `children` once its first checkpoint commits.
4. **At least once.** The child thread is the replay record: `startChild` refuses an existing thread, and retention
   never deletes a child whose call can still run (above). Cascade delete and retention are idempotent.
5. **Block.** A Block retracts the parent's turn and writes `Blocked`, `OutputInvalid` or `Failed`; its children stay
   and are pruned by the next completed turn (tested).
6. **Full snapshots.** A child's checkpoints snapshot only the child; retention bounds the children kept.
7. **Codecs.** Format 8 with a `7 -> 8` step that writes nothing, and SQLite schema 6 with a `5 -> 6` step; both
   tested on a fixture written by the last format-7 / schema-5 build (`format-7-one-approval.json`,
   `schema-5-before-children.db`), restored and continued, and a format-7 checkpoint is a contract case.
8. **Tenant.** `GraphRuntime.children` checks the parent's tenant; the store's `children` needs none. Every refusal
   comes after the tenant check; cascade and retention check each descendant's tenant under the caller's config.
9. **No content in durable events.** No new event. `RunOutcome.Blocked` carries a guardrail's reason and
   `OutputInvalid` the validation problems, as the `Failed` checkpoint and `GraphError.OutputInvalid` already did;
   neither is an event.
10. **A failed task commits nothing.** Unchanged; the outcome is written only with a terminal checkpoint.
11. **Every model call accounted.** No model call.
12. **Bounded.** Settled children per parent by `childRetention`; a run that is never recovered after a crash during
    the pass keeps at most one run's children beyond it. The id grows with depth, which D1's `maxDepth` bounds.
13. **Types.** `RunOrigin`, `ChildThread`, `RunOutcome` and `GraphError.ChildThread` are defined here.
14. **The child thread is the journal.** `ThreadId.child` derives the id from parent, key and agent (tested stable and
    distinct); `startChild` refuses an existing thread; `recoverChild` and `resumeChild` continue one. K2 reads the
    latest checkpoint and picks among them.
15. **No capability without a grant.** Not in this slice (D2).
16. **Identity inherited.** The child runs with the config K2 passes, which carries the parent's tenant; cascade and
    retention use the caller's config.
17. **Only typed data crosses.** Not in this slice (D1).
18. **Supervision flows down.** Not in this slice (K2).
19. **Child threads driven only through their parent.** The refusals above, with the allowed reads (tested).

## Not in this slice

- Starting, reattaching and supervising children: K2, through `startChild` / `recoverChild` / `resumeChild`.
- `settleChild` (a reported child failure settled before its call commits): K2.
- `DelegationConfig`, which sets `childRetention` per agent: D1.
- `AgentStatus.TokenLimitReached` and the `TokenLimitReached` outcome's writer: K3.
