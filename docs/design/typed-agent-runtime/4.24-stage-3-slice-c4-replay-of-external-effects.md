# 4.24 Stage 3 slice C4: replay of external effects ([#1921](https://github.com/llm4s/llm4s/issues/1921))

Part of the [Typed Agent Runtime design](../typed-agent-runtime-design.md), §4. Section numbers (§N.N) refer to that document and its [slice records](../typed-agent-runtime-design.md#slice-records). The Stage 3 spec is `docs/superpowers/specs/2026-10-13-phase-3-harness-design.md` (section C4, and the runtime rules every slice must satisfy).

Slice C4 of [#1901](https://github.com/llm4s/llm4s/issues/1901). It decides how every effect outside thread state behaves when `recover` runs its task again (rule 4). C3's backends, F2's sandbox and F7's memory hooks use it. None of them adds a replay mechanism of its own.

The specs are `ReplayGuardSpec`, `EffectKeySpec` and `EffectReplayRuntimeSpec` in `llm4s-agent`, the effect-record cases of `CheckpointerContract`, and `ReplayContract` in `llm4s-agent-testkit`. `ReplayContract` runs for each support class against `InMemoryCheckpointer` (`{Transactional,Verifiable,Unverifiable,Idempotent}ReplayContractSpec`) and `SqliteCheckpointer` (`Sqlite*ReplayContractSpec`). `ReplayContractSelfCheckSpec` checks that the suite fails each of these: an unguarded target, a target that does not record its key atomically, a transactional target that does not fence by the token, a verifiable target whose effect is not a compare-and-set, effects that share a key, and a store that never releases a record.

## The problem, stated once

At-least-once execution holds three kinds of re-run, and the slice handles all three with one mechanism:

1. **Recovery.** `recover` runs every task of the latest checkpoint's frontier that has no pending write (`GraphRuntime.recover`, `reusableWrites`). Under `Async` and `OnExit` this includes work after the last durable checkpoint, which is planned again and so may differ from the first attempt.
2. **Retry inside a run.** A `RetryPolicy` runs the node again in the same task (`RunContext.discardAttempt`).
3. **Re-run after a suspension.** An approved, edited or answered tool call runs again in a continuation task, under the `IdempotencyKey` it was proposed with (§4.17).

Review kept finding the next gap because each earlier design kept replay evidence somewhere whose lifetime differed from the replay window:

- a marker on a value, which a later write overwrote
- a separate journal released by a hook after the commit, which leaves stale evidence when a crash interrupts the release
- release by age, which is wrong for a run left recoverable for a month
- a key shared by several effects

**This slice keeps replay evidence in the thread's own store, writes it under the run's claim, and releases it inside the commit that ends its window.** The window and the evidence therefore have one owner and one transaction. A crash cannot leave them out of step, and a run that has lost its claim cannot write evidence.

## Decisions

### Keys

- **`RunContext.taskKey: IdempotencyKey`** is the SHA-256, under the tag `llm4s-task-v1`, of the thread id and the id of the *logical* task. For a continuation (a resumed answer, approval or breakpoint), that is the task it stands in for (`Task.arrivalId`), not the continuation's own id. A hook that runs again after a suspension therefore keeps its key, and so do its effect keys and the owner its records are filed under. One identity, the logical task, serves `taskKey`, `RunContext.effectKey`, record tagging and liveness (`GraphSnapshot.liveTasks` keeps origins live). `ToolContext.effectKey` uses the call's `IdempotencyKey`, which is recorded with the call and so is stable too. `EffectReplayRuntimeSpec` tests each across suspend and resume, recovery of a continuation, and fork.
  - **Spec correction:** the spec derived it from `(threadId, superstep, taskId)`, but `position.superstep` is not stable. `updateState` writes its checkpoint one superstep on and keeps the frontier, so after `updateState` and `recover` a task runs at a different superstep with the same task id (`CompiledGraph.edit`: `execution.edited(state, execution.superstep + 1)`).
  - The task id already names the superstep that scheduled the task (`"<superstep>.<ordinal>"`, `CompiledGraph`). It is restored from the checkpoint frontier unchanged, so it is stable across `recover`, retries and `updateState`.
  - Like the tool call's key (§4.17), it identifies a task among the thread's *live* tasks, not for all time. After `deleteThread`, and after an `Async`/`OnExit` replan, a task id can name a different task. C4's own evidence is never confused by this, as the retention rule below shows, but an external system that uses `taskKey` to de-duplicate for longer than the replay window must allow for it.
- **`EffectKey`** is one external effect: the SHA-256, under `llm4s-effect-v1`, of the executing thread, a base key, an operation name and a discriminator, with each part length-prefixed.
  - The **base** is the logical *phase* that performs the effect. For a tool, `ToolContext.effectKey` uses the call's `IdempotencyKey` in `execute`, and every run of `execute` is one phase: a retrying wrapper, `recover`, and the re-run after an approval, which repeats `execute`. An answered `resume` is a different phase of the call and gets its own base, `IdempotencyKey.ofResume`: the call's key, the phase that asked (`ToolQuestionRequest.phase`, `None` for `execute`), and the question and answer as stored JSON. So a resume never replays `execute`'s outcome for the same operation and target. A chain of questions is a chain of phases, distinct even when a question and its answer repeat. A recovered resume derives the same base, and a fork's derives another because the key includes the thread. For a hook, `RunContext.effectKey` uses `taskKey`. A hook that asks runs again from the top with its answers, which repeats the same phase: its pre-question effects replay, and an effect it makes only after the answer gets its own record. If it repeats an operation on the same target after the answer, it names the answer in the discriminator.
  - The **operation** names the kind of effect (`file.edit`, `memory.record`). It stays readable, as `key.operation`, so refusals can name it.
  - The **discriminator** is what the effect touches (`String*`, for example a path, or sorted source memory ids). The parts are length-prefixed, so `("a,b", "c")` and `("a", "b,c")` never collide.
  - Effects in one task therefore have different keys and never suppress each other. Effect keys are built only by `effectKey(operation, discriminator*)` on a `RunContext` or `ToolContext`, and the constructor is private.
  - **The executing thread is part of the key, even when the base is a tool call's key.** A fork keeps the source's `IdempotencyKey`s (§4.19), so without the thread a fork's re-run of a call would share the key of the source's call. With a transactional target it could then remove the source's applied key, or read the source's outcome as its own. **A fork's re-run of a source call is a new effect in the fork.** C4 does not de-duplicate it against the source. The tool still receives the source's `IdempotencyKey`, so an external system that honours that key still de-duplicates, as §4.19 says.

### Support classes and the guard

`ReplaySupport` is `Transactional | Verifiable | Unverifiable`, declared by each external target. `ReplayGuard` is the only way the harness performs an external effect. It has one entry point per class, because each class needs different inputs and the types should force the right ones:

```scala
ReplayGuard.transactional[A: ReadWriter](context, key, applied: AppliedKeys)(effect: FencingToken => Result[A]): Result[A]
ReplayGuard.verifiable[A: ReadWriter](context, key)(probe: => Result[StateCheck])(plan: => Result[ReplayGuard.Plan[A]]): Result[A]
ReplayGuard.unverifiable[A: ReadWriter](context, key, idempotent: Boolean)(effect: => Result[A]): Result[A]
```

Each takes an optional `maxOutcomeBytes` (default `ReplayGuard.DefaultMaxOutcomeBytes`, 1 MiB). `context` is the task's `RunContext`; a tool passes `toolContext.run`.

The guard keeps one **effect record** per key in the thread's store. A record is *begun* (an intent) or *completed* (an outcome). Every `Right` outcome is stored, and a completed record replays its stored outcome, decoded with `A`'s codec.

- **`Transactional`.** The target records `(key, outcome)` in its own applied-keys table, in the same transaction as the effect. Given a key it has applied, it returns the recorded outcome and writes nothing, even if another thread has since replaced or deleted the item.
  - **The target fences itself by the claim token** (`AppliedKeys`). The effect and `forget(key, token)` are given the run's fencing token. For each key `scope` (`EffectKey.scope`, one per thread), the target keeps the newest token any operation on that scope has carried. In one transaction, every operation refuses a token older than that newest (`Left`, nothing changed), and otherwise makes its own token the newest and goes ahead. A thread's tokens only grow, across takeovers and `deleteThread` (§4.16), so once a successor has touched the target, nothing a stale run does there lands: not the applied-key write, not reading back a recorded outcome, not `forget`. The newest token is kept per thread scope, a small record per thread, as the store's own tombstones are.
  - First run: `applied.forget(key, token)` (a stale leftover, see below), then *begin*, then the effect, then *complete*, then `applied.forget(key, token)`.
  - Replay of a completed record: `forget` again, which clears a leftover from a crash between *complete* and `forget`, and return the stored outcome.
  - Replay of a begun record: run the effect again; the target returns its recorded outcome if the first attempt applied. Then *complete* and `forget`.
  - So a target's applied key lives only from the effect to *complete*, and **the guard trusts it only while the journal holds the key's *begin***. A leftover (one per crash between the effect and `forget`, in a task that is never replayed) is garbage, never an answer: the next first run of that key clears it before it begins.
  - The spec trusted the applied key alone and released it after the commit. A crash during that release left a key that a re-created thread, or an `Async` replan reusing a task id, would take for its own and silently skip its write. **The applied key on its own is not evidence.**
- **`Verifiable`.** The target can read a digest of what the effect touches (`StateCheck`: `StateCheck.of(bytes)`, `StateCheck.of(text)`, `StateCheck.absent`).
  - First run: `plan` reads the target once and returns `Plan(before, after, presumed)(effect)`. `before` and `after` are the digests the target has before and after the effect, and `presumed` is the outcome the effect reports when it lands. The guard records the intent `(before, after, presumed)`, runs the effect and records the outcome.
  - Replay of a completed record: the stored outcome.
  - Replay of a begun record: `probe` the target.
    - It matches `before`: the effect did not land, so `plan` and run it again. The new plan must read the recorded `before` too: one that reads anything else saw a change made after the probe, and that is `EffectReplayRefused`, never a compare-and-set over the change. This is checked first: when `before` equals `after` (a write of what is already there), the probe cannot tell whether the effect ran. Running it again is a compare-and-set that changes no digest, so it is safe, whereas presuming would report an effect that may never have run.
    - It matches `after`: the effect landed, so the guard records *complete* with `presumed` and returns it. This is the success "rebuilt from the intent", and `presumed` is how the guard rebuilds it.
    - Anything else: `GraphError.EffectReplayRefused` naming the operation and the three digests.
  - `plan` runs only when the effect must run. A replayed `edit_file` therefore never re-checks "`old` not found" against a file its first attempt already edited.
  - **The effect is a compare-and-set against `before`.** Atomically at the target, under a lock every writer of the target takes (an OS file lock across processes), it checks that the digest is still `before` and only then writes. Otherwise it writes nothing and returns `EffectReplayRefused`. That is the Verifiable class's fence: of a stale run and its successor, whichever writes second finds the digest moved and changes nothing. A target that cannot compare and set atomically is not `Verifiable`; it declares `Unverifiable`. A target that can store a token may also refuse older tokens (`context.position.fencingToken`), but the compare-and-set is what the contract requires.
- **`Unverifiable`.** Nothing can be checked.
  - First run: *begin*, run the effect, *complete*.
  - Replay of a completed record: the stored outcome (for `execute`, the original `ExecResult`).
  - Replay of a begun record: `EffectReplayRefused` ("it may already have run; it is not run again"), unless `idempotent` (the tool's `ToolHints.idempotent`), in which case it runs again.
- **What a `Left` means.** `EffectReplayRefused` is a refusal the model should see, so a tool maps it to `ToolOutcome.Error`. Any other `Left` from the guard means the store failed, or the effect failed and its outcome is unknown or unrecorded. A tool maps that to `ToolOutcome.Fatal` and a hook to `NodeResult.Fail`, so that the task fails, commits nothing, and `recover` replays it from the evidence. The guard never stores a `Left` from `effect`: an effect returns `Left` only when it did not take effect, or cannot tell, and the record stays *begun*, so the class's replay rule decides.
- **Timeouts (C2, §4.23).** A tool past its timeout has its fork interrupted, and the call's result is the error the model sees. If the guard had written its intent, the record stays *begun*. A run of the same call again in the same task (a retrying `wrapToolCall`), or `recover` of a task that never committed, uses the same key and is decided by the target's class:
  - Verifiable: the probe tells whether the effect landed.
  - Unverifiable: refused unless idempotent.
  - Transactional: the target's applied key.

  Once the task commits its timeout error, the record is released with its superstep. A later model call of the tool is a new call with a new key, as C2's guide says. The interrupt is a `CancelledError` or a thrown interrupt inside the effect, both a non-refusal `Left`, so the guard never records an outcome for a timed-out effect. `TimedOutEffectSpec` covers each class.
- **Cancellation.** Between *begin* and the effect, the guard checks the task's interrupt flag. A run that was cancelled, or that lost its claim (which interrupts its tasks), never starts an effect it has only just recorded.
- **Bounds (rule 12).** A record whose encoded intent or outcome is larger than `maxOutcomeBytes` is not stored.
  - An oversized intent (a `presumed` too large) refuses the effect before it runs.
  - An oversized outcome is recorded as *completed, outcome omitted (n bytes)*. Its replay is `EffectReplayRefused` saying so: it never re-runs and never makes up an outcome.
  - Targets keep their outcomes bounded (`ExecResult` by `maxOutputBytes`), so this does not happen with the default cap.
- **No shared mutable values.** `ujson` values are mutable, so every one that crosses the guard or store boundary is copied: the outcome and `presumed` as they are recorded, the stored outcome as it is decoded for a replay, and every value `EffectRecord.toJson` hands out or `fromJson` takes in. A caller that mutates an outcome, a record's JSON or the JSON it read a record from changes nothing stored.
- **Outside a runtime** (`CompiledGraph.step`), the records live with the in-memory `Execution`. They are carried from each execution to the next, so retries and a continuation resumed in memory replay what their task recorded. Each superstep keeps only the records of tasks still live, as a store's commit does. They are not part of a snapshot, so an execution restored from one starts with none, as a process restarted without a durable store would.

### Where the records live: the thread's store

**Spec correction:** the spec put intents and outcomes in an `EffectJournal` of their own (`FileEffectJournal(dir)` and in-memory), released by a kernel hook after the commit. This slice puts them in the `Checkpointer`, for four reasons:

- **Fencing.** A record write must be refused once the run has lost its claim, or a run that has been taken over (a zombie) could record an outcome the new claimant then trusts. The store already fences every write by the claim's token. A separate journal cannot do so atomically.
- **Atomic retention.** The window ends at a commit, and that commit is a store transaction. Releasing in the same transaction leaves no gap for a crash.
- **Durability matches.** Durable evidence for an in-memory thread is useless. In-memory evidence for a durable thread is a bug: after a restart, `recover` would find no record and re-run every `Unverifiable` effect. A file journal next to a SQLite store also isn't shared by the other processes on that file.
- **Tenant and deletion.** A record belongs to its thread's store row, so it goes with the thread's tenant and with `deleteThread`.

`FileEffectJournal` is not built: the SQLite checkpointer is the durable journal. A future PostgreSQL store is too.

The SPI (the source breaks are listed below):

- **`Commit.effects: Vector[EffectRecord]`.** A commit may carry effect records, which are upserted by key and fenced by the commit's token like everything else in it. The guard writes each *begin* and *complete* as an effect-only commit (no checkpoint, no pending writes, no events). It does so synchronously from the task's thread through the committer's fence (`Committer.begun`), whatever the durability mode, because write-ahead must not wait in an `Async` queue. A refusal as stale also stops the run at once (`onStale`), as a refused commit does.
- **`Checkpointer.effect(threadId, key): Result[Option[EffectRecord]]`.** This reads one record. An unknown thread or key is `Right(None)`.
- **`EffectRecord`**: `key`, `taskId` (the task that wrote it) and a guard-defined body. A store persists `EffectRecord.toJson` and reads with `EffectRecord.fromJson`. The JSON is versioned (format 1), and `fromJson` refuses a newer format, as `Checkpoint.fromJson` does. The store also keeps the token of the commit that wrote each record.

### Retention: exactly the replay window

**A commit that carries a checkpoint releases a record exactly when `Commit.releasesEffect(taskId, writer)` is true.** That is when the record's task is not live in the new checkpoint, and either the record was written under another claim or its task was scheduled no later than the new checkpoint's superstep. The store applies this rule inside the commit, before the commit's own records. `GraphSnapshot.liveTasks` is the frontier's task ids, the frontier's origin tasks, and the parked continuations' origin tasks.

Why each part is needed:

- **Not live.** A live task can still run: it is in the frontier, or a parked or resumed continuation stands in for it (a tool call re-run after approval or an answer uses the key its first run used). Its records are kept, however long the thread waits. Nothing is released by age.
- **Written under another claim.** At a claim commit (`start`, `recover`, `resume`, `updateState`), the previous run has ended or been fenced. Any of its records whose task is not live in the claimed checkpoint is an orphan: work after the last durable checkpoint under `Async`/`OnExit`, which will be planned again and may reuse the task id for different work. Dropping orphans then is what makes a reused task id harmless.
- **Scheduled no later than the new checkpoint.** Under `Async`, a run's commits land behind its tasks. The commit of checkpoint *n* can land while tasks of checkpoint *n + 1* are running and recording. Their task ids are scheduled at *n + 1*, after the landing checkpoint, so they are kept. Without this part, a late commit would drop the records of a running task, and a crash then would re-run its effects. Under `Sync` this part never matters: every checkpoint commits before its tasks run.
- **Settled checkpoints.** A `Completed` or `Failed` checkpoint runs nothing, whatever its snapshot lists. A Block can close a superstep in which a sibling parked, but `recover` and `resume` refuse a settled thread, so its commit treats every task as finished.
- **Every other path**:
  - **`deleteThread`** removes every record of the thread in its transaction, so a re-created thread starts with none.
  - **`prune`** removes no record. **Spec correction:** the spec released every key on `prune`, but `prune` never removes the latest checkpoint and needs no claim, so a thread can still be recovered after a prune. Releasing its records would make the next `recover` re-run effects as if they were new. Records never outlive the window anyway, so `prune` has nothing to bound.
  - **`fork`** copies no record, as it copies no pending write: the fork's records start empty, and its keys differ (they include the thread).
  - **A Block's** closing `Failed` checkpoint ends the turn, and its commit releases the turn's records. **C4 cannot undo an external effect, so a Block leaves the effect in place (rule 5).** The guide says so.
- **Bound (rule 12).** A thread holds records only for the effects of its live tasks: under `Sync`, one superstep's tool calls and hooks, plus parked calls. Under `OnExit`, the records of one run, until its exit commit. Each record is capped by `maxOutcomeBytes`. A transactional target holds applied keys only for effects in flight, plus one per crash between its effect and `forget` in a task never replayed.

There is no kernel hook after the commit, and no registry of keys per task. The spec's "each guard registers its key with the running task" is not needed: liveness is a function of the checkpoint, so a task whose result was reused on recovery, and so never registered anything in the new run, still has its records released.

### Crash windows

Each row is a crash, then `recover` by a new runtime over the same store. *Once* means the target shows exactly one application.

| Crash point | Store holds | Transactional | Verifiable | Unverifiable |
|---|---|---|---|---|
| Before *begin* | no record | first run: once, fresh outcome | first run: once | first run: once |
| After *begin*, before the effect | *begun* | effect runs; target has no applied key, so it applies: once | probe = `before`, so it runs: once | refused (cannot tell it did not run), or, if idempotent, runs: once |
| After the effect, before *complete* | *begun* | target returns its recorded outcome, no write: once | probe = `after`, so it returns `presumed`: once | refused: once; or, if idempotent, runs again (twice, which is what idempotent permits) |
| After *complete*, before the task's commit | *completed* | stored outcome; the leftover applied key is forgotten: once | stored outcome: once | stored outcome: once |
| After the task's commit (pending write, then superstep) | released by the superstep commit | the task is not re-run: its pending write is reused | same | same |
| Another thread changed the target, after the effect, before *complete* | *begun* | recorded outcome, interference left in place | `EffectReplayRefused` (state matches neither digest) | refused |
| Another thread changed the target, after *complete* | *completed* | stored outcome | stored outcome | stored outcome |
| Stale claimant read no record, stalled; successor applied, crashed before *complete*; stale run carries on | *begun* (successor's) | stale `forget` refused by the token; recovery gets the recorded outcome: once | stale *begin* refused; recovery: probe = `after`: once | stale *begin* refused; recovery refuses: once |
| Stale claimant wrote *begin*, stalled before the effect; successor replays and completes; stale effect goes ahead | released | stale effect refused by the token: once | stale compare-and-set fails: once | successor refused, stale effect runs: once |

**Concurrent claimants (fencing).** A run that lost its claim (a stale claimant) may keep running its task: it stalled past its lease and has not noticed. Everything it does must be fenced at the place it acts, not only in the journal:

- **In the thread's store.** Its *begin* and *complete* are refused as stale, so it records nothing the successor trusts. A *begin* that landed before the takeover belongs to a task that is still live, so the claim commit keeps it and the successor sees it as *begun*.
- **At a Transactional target.** By the token, as above. That covers its applied-key write, a recorded outcome it reads back, and its `forget`, including a `forget` decided from a lookup it made before the takeover. Codex's case (a stale run reads no record, stalls, then forgets after its successor applied and before the successor recorded *complete*) is refused by the target, so the next recovery still finds the successor's applied key and does not apply twice.
- **At a Verifiable target.** By the compare-and-set: a stale write that lands after its successor's finds the digest moved.
- **At an Unverifiable target there is nothing to fence, and nothing needs it.** A stale run that had not written its *begin* before the takeover is refused at *begin*, so it never starts the effect. One that had written it leaves the record *begun*, so the successor refuses to run the effect again (unless it is idempotent, where running twice is allowed by definition). Either way the effect runs at most once. What a stale run cannot be stopped from doing is finishing an effect it started before the takeover, but then the successor never runs it.

So no interleaving of a stale claimant and its successor applies an effect twice, for any class, provided the target meets its class's contract. Before this revision the in-flight effect was listed as a limit, mitigated only by the lease; Codex review found the same class through `forget`, and the fix is the target-side fence. `ReplayContract` checks both interleavings (below).

**Retention racing a replay.** There is no race to handle:

- Only commits release records, and every commit of a thread is fenced by the one live claim.
- The replaying task is live, so no commit of its run can release its records while it runs.
- `prune` removes none, and `deleteThread` needs the claim, so it is `ThreadBusy` while a run holds the thread.
- A late `Async` commit keeps records of tasks scheduled after it.
- A zombie's late commit is refused as stale.

### `ReplayContract`

`ReplayContract` (`llm4s-agent-testkit`) is the suite every external target passes, once for each support class it offers. It is mixed into a spec that implements `newSubject()`, and optionally `newCheckpointer(clock)` (default `InMemoryCheckpointer`).

A `ReplayContract.Subject` performs effect `slot` (0 or 1) through the target's own guarded code path (`perform(context, slot)`). It exposes the slot's observable state (`observe`, `initial`, `once`) and changes it as another thread would (`interfere`). It also reports its `support`, whether it is `idempotent`, and how many applied keys it still holds (`appliedKeys`).

The suite runs a one-task graph that performs both slots, on a real `GraphRuntime`. It crashes the run at each point of the table: the store goes down at a chosen record write, before or after writing it, or after the task's commit. Every later write fails, as in a dead process. The suite then advances the store's clock past the claim's lease and recovers on a new runtime. For each row and class it checks:

- the target's state
- the outcome the task recorded
- that the two slots never collide
- that no record and no applied key is left once the run has completed

It also checks that a run left recoverable for a year still replays from its records after `prune` with a `maxAge` of a day. Two cases cover stale claimants, on a real takeover: the stale run pauses inside the store (after its first lookup has returned, or after its first *begin* has been written), its claim expires, and a successor recovers the thread and crashes before *complete*, or completes. The stale run then carries on, and a third run recovers if needed. These are the two stale-claimant rows of the table.

C3's file backends, F2's sandbox and F7's memory store each run it. `llm4s-agent-testkit` ships four reference subjects in its tests (`ReplaySubjects`): a transactional counter store, a verifiable text cell, an unverifiable append log and an unverifiable idempotent flag. They run against both stores; `llm4s-agent-checkpoint-sqlite` depends on the testkit's tests for them (`test->test`).

### What C3 (and F2, F7) must do

- **Declare** `replaySupport: ReplaySupport` on every external target: `HostFileBackend` and the workspace file backend `Verifiable`, a `SandboxBackend` `Unverifiable` (or `Transactional` if it records keys itself), `LongTermStore` and F7's `MemoryStore.applyAtomically` `Transactional`. `StateFileBackend` declares nothing and uses no guard: its effect is the committed update.
- **Key** every mutation with `toolContext.effectKey(operation, path)` (or `context.run.effectKey(...)` in a hook). Use one operation name per kind of mutation (`file.write`, `file.edit`, `file.delete`, `store.put`, `store.delete`, `sandbox.execute`). The discriminator is the normalised `VPath` string, or the store `Namespace` and key, or, for `execute`, the command and working directory. Never build a key by hand, and never key by `toolCallId`.
- **Perform** every mutation inside the matching guard:
  - `Verifiable`: `probe` hashes the current content (`StateCheck.absent` for a missing file). `plan` reads the file once and returns `Plan(before, after, presumed)(effect)`, and must do any "`old` not found" or quota check inside `plan`, never before the guard.
  - `Unverifiable`: pass `ToolHints.idempotent`.
  - `Verifiable`: the effect is a compare-and-set against `plan`'s `before`, atomic under a lock every writer takes (for `HostFileBackend`, an OS file lock on the path across processes, plus C2's lock in-process). On a mismatch it writes nothing and returns `EffectReplayRefused`.
  - `Transactional`: implement `AppliedKeys.forget(key, token)`, and give `ReplayGuard.transactional` an effect `token => ...`. In one transaction, every target operation on `key.scope` refuses a token older than the newest the target has kept for that scope, and otherwise stores the token as the newest. Then the effect records `(key, outcome)` with its write, or returns the recorded outcome for a key already applied. `LongTermStore.modify` takes the token and the key from the guard; never forget an applied key outside `forget`.
- **Map** `GraphError.EffectReplayRefused` to `ToolOutcome.Error`, and any other `Left` from a guard to `ToolOutcome.Fatal`.
- **Bound** outcomes under `maxOutcomeBytes`: `ExecResult` by `maxOutputBytes` per stream, and file outcomes are small.
- **Run** `ReplayContract` for each external backend from `FileBackendContract`.

## Runtime rules

1. **One batch, one snapshot.** Each tool call has its own task and `IdempotencyKey`, so the effects of one batch have different keys, and the guard decides each on its own record. `Verifiable` checks the target, not the snapshot. Two calls on one path are ordered by C2's lock (C3's backends lock their paths), so each `plan` reads what the previous call left.
2. **Update functions are total.** The guard runs when the tool runs and returns a `Result` there. A refusal is a tool error decided then, never in an update function, and the guard writes no state key.
3. **Visibility.** Effect records are not thread state. The guard's outcome goes back to its caller in the same request, so nothing waits for the next superstep.
4. **At least once.** This rule is the slice: see the keys, the guard, the retention rule and the crash table. Every effect key is derived from the task id or the call's key, and never from `runId`, `checkpointId`, the fencing token or `position.superstep`.
5. **Block.** Since C1 (§4.22), an output Block restores every state key the turn wrote (`TurnState.priorValues`, `StateOperation.Restore`), messages included. That covers state only. An external effect stays in place, and its records go with the turn's closing `Failed` commit, so the Block neither undoes the effect nor leaves evidence that would replay it. The guide says so (`docs/guide/agents/index.md#tool-side-effects`), as §4.22 rule 5 does. Effect records are not state keys, so `priorValues` never holds or restores them.
6. **Full snapshots.** Records are kept beside the checkpoints, not in them, so no checkpoint copies them and `history` and `fork` never see them. `Checkpoint.CurrentFormat` stays 6.
7. **Codecs.**
   - `EffectRecord` JSON carries a format version (1), and a newer one is refused.
   - SQLite gains `llm4s_checkpoint_effects` in schema step 2 → 3, run in the opening transaction as every step is. A version-2 file opens and migrates.
   - An outcome is stored with `A`'s codec. If that codec changes shape between a crash and its replay, the stored outcome does not decode. The guard then refuses (`EffectReplayRefused`, "the stored outcome does not decode") rather than re-running, and a target that changes an outcome type keeps a reader for the old shape.
8. **Tenant.** Records belong to their thread, in their thread's store, and a thread has one tenant. Effect keys include the executing thread, so a shared transactional target never confuses two threads, whatever their tenants. Namespacing a shared target's *data* by tenant stays the target's job (C3's `Namespace`).
9. **No content in durable events.** The guard writes no events. Records can hold content (an outcome), but they are not events, and they are deleted when the window ends.
10. **A failed task commits nothing.** Effect records are written by their own commits, not with the task's write, precisely so that they outlive a failed task: the failure is what `recover` replays. The commit of a failed task (its `TaskFailed` event) carries no checkpoint, so it releases nothing.
11. **Model calls accounted.** Not applicable: the guard makes no model call.
12. **Bounded.** Per record, `maxOutcomeBytes`. In count, the effects of live tasks only (see Retention). A transactional target's applied keys are bounded by the effects in flight, plus crash leftovers that are never trusted.
13. **Every type defined.** All in `org.llm4s.agent.graph`, `llm4s-agent`, `@Experimental` (Beta):
    - `EffectKey` (`value`, `operation`, `scope`; private constructor)
    - `ReplaySupport` (enum: `Transactional`, `Verifiable`, `Unverifiable`)
    - `StateCheck` (opaque `String`; `of(bytes)`, `of(text)`, `absent`, `ReadWriter`)
    - `ReplayGuard` (object; `Plan[A](before, after, presumed)(effect)`, `DefaultMaxOutcomeBytes`)
    - `AppliedKeys` (trait; `forget(key, token)`, fenced by the claim token per `key.scope`)
    - `EffectRecord` (`key`, `taskId`, `toJson`, `fromJson`)
    - `GraphError.EffectReplayRefused(operation, reason)`

    It also uses `RunContext.taskKey` and `RunContext.effectKey`, `ToolContext.effectKey`, `Commit.effects` and `Commit.releasesEffect`, `Checkpointer.effect`, and `GraphSnapshot.liveTasks`. `llm4s-agent-testkit` adds `ReplayContract` and `ReplayContract.Subject`.

## Source breaks (no shims)

- `Checkpointer` gains the abstract `effect(threadId, key)`. Every store, and every wrapper delegating to one, implements it.
- `Commit` gains `effects` (defaulted in `apply`). A store must upsert a commit's records, apply `releasesEffect` on every commit with a checkpoint, and remove a thread's records on `deleteThread`.
- `GraphError` gains `EffectReplayRefused`.
- The new, unreleased `AppliedKeys.forget` takes the claim token, and `ReplayGuard.transactional`'s effect takes it too (`FencingToken => Result[A]`). This was changed in review before release.
- The SQLite schema moves to version 3, migrated on open. A build that predates it refuses a version-3 file, as it refuses any newer schema.

## Limits

- Fencing at the target is the target's obligation (the token for `Transactional`, compare-and-set for `Verifiable`). The guard cannot impose it on code it only calls. `ReplayContract` is what checks it, so a target that skips the contract is unchecked.
- Compare-and-set compares digests, so a target that returns to an earlier state between a stale run's plan and its write (A → B → A) is not detected. This needs a third writer as well as the takeover, and a target that can store a token closes it.
- `taskKey` and a tool's `IdempotencyKey` are unique among a thread's live tasks, not for all time: after `deleteThread`, or an `Async`/`OnExit` replan, a task id may name new work. C4's own evidence is safe from this. An external system that de-duplicates by these keys beyond the window is not.
- An `Unverifiable` effect whose run crashed between *begin* and the effect is refused on replay even though it never ran. The guard cannot tell the two apart. This is what the class means.
- Under `OnExit`, records accumulate for the whole run, until its exit commit.
