# 4.56 Stage 5 slice W2: workers ([#2135](https://github.com/llm4s/llm4s/issues/2135))

Part of the [Typed Agent Runtime design](../typed-agent-runtime-design.md), §4. Section numbers (§N.N) refer to that document and its [slice records](../typed-agent-runtime-design.md#slice-records). Stage 5 spec: `docs/superpowers/specs/2026-10-20-stage-5-production-design.md`, "W2" and "Rules every slice must satisfy".

Slice W2 of [#2129](https://github.com/llm4s/llm4s/issues/2129), after W1 ([4.55](4.55-stage-5-slice-w1-run-submission-and-the-durable-run-queue.md)).
It adds the worker that runs W1's queue: it takes entries, runs them on the agents it was built with, recovers a dead
worker's entries, runs S4's retention sweep, drains on shutdown and answers health. It lives in `llm4s-agent`
(`org.llm4s.agent.service`), with no JDBC and no HTTP.

## What it adds

Every new type `@Experimental`:

- `AgentWorker(queue, checkpointer, agents, settings, queueSettings)`: `start()`, `shutdown(): DrainReport`, `health():
  WorkerHealth`, `currentState: WorkerState`; `sweepOnce(): Result[SweepReport]` is the sweep's one pass (package-private).
- `QueuedAgent(agent)` and `QueuedAgent.typed(boundAgent)`: what a worker runs, named by agent id. A typed agent's queued
  `I` is decoded and rendered as `BoundAgent.run` renders it (`BoundAgent.queuedQuery`).
- `WorkerSettings` (growth-prone) and `org.llm4s.config.WorkerConfigLoader` reading `llm4s.agent.worker` (comment 1 on
  the issue): `concurrency = 4`, `pollInterval = 1 second`, `unrunnableAfter = 1 hour`, `drain { grace = 30 seconds,
  exitTimeout = 10 seconds }`, `sweep { enabled, every = 5 minutes, batchSize, tombstoneAge?, retention { ... }? }`,
  `label`. The lease, `maxAttempts` and the ticket lifetime stay W1's (`llm4s.agent.queue`).
- `WorkerState`, `WorkerHealth`, `DrainReport`, `SweepReport`.
- On the queue SPI (W1 is unreleased, so these change it in place): `RunQueue.openRuns(threads)`, every tenant's open
  entries' attempt run ids by thread, for the sweep's guard; and `TakeRequest.skip`, entries a take passes over. All
  three stores implement both; `RunQueueContract` gains a case for each (46 cases, 47 on PostgreSQL).
- In the runtime, for W3 to reuse: `GraphRuntime.settleQueued` (a top-level `settleChild`), `Agent.settleQueued`
  (with `SettledTurn.closing`, which gives each unanswered tool call of the last turn a synthetic result),
  and `CompiledGraph.canContinue`.

## Decisions

**One entry, one slot, in the order rule 4 needs.** For each entry it takes the worker (1) starts renewing the lease,
(2) probes the thread's claim, (3) checks its graph can take the thread on, (4) records the attempt with
`RunId.random()`, (5) acts on `AttemptPlan.of(entry, admitted, latest)` read *after* the record, and (6) closes, gives
back or lets the lease lapse from how the run ended. Steps 2 and 3 come before the record, so neither a busy thread nor
an unrunnable one spends an attempt.

**A live claim is found by asking for one.** The `Checkpointer` has no "is this thread claimed" read, and a new abstract
method would touch ~55 wrappers. The worker asks for a short claim (5 seconds) under the entry's tenant and gives it
back at once: `ThreadBusy` means a live claim holds the thread, judged by the store's clock (rule 1), so the entry is
released with no attempt and passed over for `pollInterval` (else the take would hand it straight back). A probe that is
granted over a dead run's expired claim takes it over, so the recovery's `RunRecovered` event no longer names the dead
run in `takenOverFrom`; that field is informational. A direct run that claims the thread between the probe and the
attempt's admission makes the admission `ThreadBusy`: that attempt is spent, the entry released, and the bound still
holds. A probe whose release fails may still hold the thread, so the slot records nothing and lets its lease lapse
(Codex, round 1): the attempt's own admission would otherwise meet the probe as `ThreadBusy` and spend an attempt.

**Another tenant's thread is refused before anything of it is judged (rule 9).** Every read of the thread the worker
makes checks the latest checkpoint's tenant against the entry's first, and another tenant's thread closes the entry
`Failed(RunFailed)` with the runtime's tenant-safe `TenantMismatch` message at once, recording no attempt - never its
graph's restore problems or its checkpoint ids in an outcome the entry's tenant reads (Codex, round 1).

**Graph versions: check before the attempt, pass over, then fail after a bound.** `TakeRequest` names agents only, so
the worker reads the run-id lookup and the thread's latest checkpoint first and asks its agent's graph whether it can
take the latest on (`canContinue`: `restoreAtRest` for a settled thread, `restoreStored` otherwise). A
`RestoreRejected` - another graph's thread, or a run in flight at another graph version during a rolling upgrade - gives
the entry back with no attempt and passes over it for a lease ttl, through the new `TakeRequest.skip`, so it does not
hide every head behind it (`take` answers the oldest head first, and the skipped head still holds its own thread
back). Once it has waited `unrunnableAfter` (default 1 hour) since its submission or its latest attempt, by the store's
clock, the worker closes it `Failed(Unrunnable)`; the thread is not settled, since this graph cannot restore it, and
stays for its owner's `recover`. The store's "now" is the lease's expiry less its ttl, from the take or last renewal,
so no host clock is compared with a stored time. An entry naming an agent no worker has is never taken (W1's `take`
filters by agent) and stays queued, holding its thread: the issue's "left for a worker that can"; failing those too
would need a store-wide scan of stale entries, a later issue if wanted.

**The lease is renewed beside the claim, on the same cadence, and its loss cancels the run.** The runtime renews the
run's claim; the worker renews the entry's lease every `lease.renewEvery` on a virtual thread per slot (the defaults
are the claim's: 30 seconds, every 10). Hooking the runtime's own beat would put a queue concept into the graph
runtime for no gain: both are judged by the store's clock. A renewal refused (`LeaseLost`, `EntryClosed`), or none
landing for a whole ttl, cancels the run (`AgentRun.cancel`), and nothing more is written under that lease.

**How a run's end closes its entry.** The entry is read again after the run (its `admitted` mark may have been set by
the run and its checkpoint retracted by a block) and classified again: `Close` closes it from the thread's state
(completed, suspended, blocked). Otherwise the run failed with work left: the worker lets the lease lapse rather than
giving it back, so the next attempt - which recovers the thread - comes a lease ttl later, a backoff, and
`maxAttempts` bounds the retries. An admission the runtime refuses for good (a resume of a thread that is not
suspended, an input that does not decode, another tenant's thread) closes the entry `Failed(RunFailed)`; a recoverable
store error lets the lease lapse.

**Exhausted entries are settled through a runtime operation W3 can reuse.** On `AttemptStart.Exhausted` the worker
classifies again: `Close` closes from the thread's state; `Recover` with the entry's run committed - its input was
admitted and its run is the thread's incomplete latest - settles the thread with `Agent.settleQueued`, then closes
`Failed(AttemptsExhausted)`; anything else is simply closed. `settleQueued` commits, under the thread's claim and as a
fresh run id, a `Failed` checkpoint with outcome `RunOutcome.Failed("AttemptsExhausted", ...)` over the restored state,
with every tool call of the last assistant message that has no result given `AgentWorker.ExhaustedResult`, so the
thread's next queued entry starts normally. It refuses (`ValidationError`, nothing written) if the latest checkpoint
under the claim is not one of the entry's runs'. W3's cancel settles a cancelled queued run with the same call and a
"cancelled" result string.

**Drain.** `shutdown` stops the take loop (a take in flight lands first), waits `drainGrace` for every slot, cancels
the runs still going and waits `exitTimeout` for them. A run's handle completes only after the run has released its
claim (`DefaultRunHandle`), so when the slot sees its run end, the claim is already free; the slot then closes the entry
if the run reached rest, else releases the lease, so another worker recovers it at once. A run that has not ended by
`exitTimeout` keeps both: the worker stops renewing the lease, and the claim's renewal ends with the process.
`DrainReport` names the entries that finished, were cancelled and exited, or were abandoned.

**Retention: one instance of the fleet at a time, by a store claim.** Every `sweepEvery` the worker claims the
reserved thread id `llm4s-worker-retention-sweep` (no tenant, a lease ttl); `ThreadBusy` means another instance is
sweeping, and the pass is skipped. Holding it, the worker pages `Checkpointer.sweep` with `settings.sweep` and a guard
built from `RunQueue.openRuns`, renewing the claim between pages and stopping if a renewal is refused, then reclaims
closed entries past the ticket lifetime (`RunQueue.reclaim`, `batchSize` at a time). The stores already keep an open
entry's evidence in their own prune (4.55); the guard adds, per the spec's rule 4, that the thread of an open entry
keeps its tombstone, which needs `openRuns` to answer across tenants - it is the operator's, as `reclaim` is. The
default `SweepPolicy.keepAll` prunes nothing, so the default sweep only reclaims expired queue entries.

**Health is a read of the store and the loop.** `health()` is ready when the worker is running, its take loop has beaten
within `2 x pollInterval + lease ttl` and its last take succeeded, and the store answers a checkpoint read and a queue
read at the reserved id `llm4s-worker-health`. The problems name no input.

**Each attempt runs in its submitter's trace.** Every attempt - and an exhausted entry's settle - runs with
`QueueEntry.attemptConfig(runId)` (#2213): the attempt's run id, the entry's tenant and the trace context the submission
carried (`Submission.traceContext`), so all attempts of an entry sit in one trace (O1).

## Not in this slice

- Cancel requests, the busy-thread policy's `Interrupt` stop, and settling a cancelled run (W3; it reuses
  `Agent.settleQueued`).
- Worker and queue metrics (O2), the example service and its probes (P1).
- Failing entries for an agent no worker has.

## Tests

`AgentWorkerSpec` (25 cases, in-memory store, real agents): starts, resumes, recovers and typed starts; concurrency;
deferring to a live claim with no attempt; recovering a dead worker's entry after its lease expires; settling an
exhausted admitted entry and starting the next one with a valid history; an unadmitted exhausted entry; an entry its
graph cannot take on, passed over and then closed `Unrunnable`; a refused renewal cancelling the run; another tenant's thread; a probe that cannot be given back; the three drain
outcomes; health; the sweep's reclaim, its guard and its one-at-a-time lock. `WorkerSettingsSpec` covers the settings
and the loader. `RunQueueContract`'s two new cases run against the in-memory, SQLite and PostgreSQL stores.
