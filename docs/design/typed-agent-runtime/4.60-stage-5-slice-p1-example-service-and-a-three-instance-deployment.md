# 4.60 Stage 5 slice P1: example service and a three-instance deployment ([#2139](https://github.com/llm4s/llm4s/issues/2139))

Part of the [Typed Agent Runtime design](../typed-agent-runtime-design.md), §4. Section numbers (§N.N) refer to that document and its [slice records](../typed-agent-runtime-design.md#slice-records). Stage 5 spec: `docs/superpowers/specs/2026-10-20-stage-5-production-design.md`, "P1" and "Rules every slice must satisfy".

Slice P1 of [#2129](https://github.com/llm4s/llm4s/issues/2129), after W3 ([4.57](4.57-stage-5-slice-w3-cancel-from-any-machine-and-the-busy-thread-policy.md))
and S5 ([4.54](4.54-stage-5-slice-s5-store-configuration.md)). `modules/deploy-service` (unpublished, cask) grows from
`/health` and `/llm-check` into a small example agent service on the Stage 5 kernel, and `deploy/` gains a Postgres
overlay running three of it. P2 ([#2140](https://github.com/llm4s/llm4s/issues/2140)) drives three of these processes
on one Postgres as the stage's exit test.

## What it adds

In `modules/deploy-service` (`org.llm4s.deploy`; unpublished, so no stability tier):

- `AgentServiceConfig`: `llm4s.deploy-service.agent` (`id`, `model` = `demo` | `provider`, `toolDelay`),
  `events` (`wait`, `pageSize`) and `metrics.enabled`, bound to `LLM4S_SERVICE_MODEL`, `LLM4S_SERVICE_TOOL_DELAY` and
  `LLM4S_SERVICE_METRICS`.
- `ExampleAgent` and `DemoModel`: the agent the service runs. `DemoModel` is an `LLMClient` that needs no provider:
  each turn calls a `pause` tool that sleeps `toolDelay` (interruptible), then answers `Echo: <query>`.
  `model = provider` uses `Llm4sConfig.defaultProvider()` instead.
- `ServiceRuntime.open(config)`: the store from `CheckpointerConfigLoader.open()`, its `runQueue`, `RunQueueConfigLoader`,
  `WorkerConfigLoader`, `RuntimeConfigLoader.runtime(...)` over a `MeteredCheckpointer` when metrics are on, the agent,
  an `AgentWorker` and a `RunSubmitter`. `start()`, `drain()` (`AgentWorker.shutdown`) and `close()`.
- `AgentService`: the operations, independent of cask, each answering a `Reply(status, json)`; `AgentRoutes`: them on
  cask.
- `DeployServiceMain`: opens everything from configuration, listens, then starts the worker; a JVM shutdown hook
  (SIGTERM) drains the worker, stops the server and closes the store.

Endpoints: `POST /threads/{threadId}/runs`, `GET /runs/{entryId}`, `GET /runs/{entryId}/events` (SSE),
`POST /runs/{entryId}/cancel`, `GET /threads/{threadId}`, `GET /threads`, `GET /ready`, `GET /metrics`, beside the
unchanged `/health` and `/llm-check`. The table is in `deploy/README.md`.

In `deploy/`: the base Deployment's readiness probe is `/ready`, it labels claims and leases with the pod name
(`LLM4S_RUNTIME_LABEL`, `LLM4S_WORKER_LABEL` from `metadata.name`) and gives the pod 60 seconds to drain;
`deploy/overlays/postgres` runs three replicas with the database settings in a generated ConfigMap, the credentials
from an operator-created Secret, and a PodDisruptionBudget; `deploy/scripts/deploy.sh check` verifies it.

## Decisions

**Small, and no API standard.** The spec puts the HTTP server product in a separate project, so the endpoints are the
fewest that exercise the kernel: submit, follow, cancel, read a thread, list threads. Paths are plain REST nouns
(`threads`, `runs`), not Agent Protocol or LangGraph Platform's API, and the README says the service is an example to
copy. There is no thread delete (the spec's list has none; `RunSubmitter.deleteThread` is one call away for a copier)
and no thread-wide cancel (an entry cancel covers the exit test).

**A run is a queue entry, named by its entry id.** `RunSubmitter`'s ticket is the only handle that exists before a
worker takes the run, survives its attempts (each attempt has its own `RunId`), and answers `follow` and `cancel` from
any machine, so `/runs/{entryId}` uses it rather than a `RunId`. The entry's input is never shown (rule 10), only its
kind, policy, attempts and outcome.

**Events are the entry's, from a thread sequence number.** `GET /runs/{entryId}/events` loops over
`RunSubmitter.follow` (which waits through `awaitEventsAfter`, so a commit by a worker on another machine is streamed
as it lands) and writes each event with its thread `seq` as the SSE `id`. A client resumes with the standard
`Last-Event-ID` header, or `?after=N` for a first connection; the stream ends with an `end` event carrying the closed
entry once `FollowedRun.finished`. Events of other runs on the thread are filtered out, so resuming from the last id
seen repeats nothing. A read that finds nothing writes an SSE comment, which keeps proxies from timing the stream out
and detects a client that has gone (the write fails and the loop ends). Each stream holds one of Undertow's blocking
worker threads for its life; that bounds concurrent streams per instance, which is acceptable for an example and is
named in the README rather than engineered around.

**A read waits for a commit or the close, whichever is first** ([#2396](https://github.com/llm4s/llm4s/issues/2396)).
Closing an entry commits no event, so a read that waited only in `awaitEventsAfter` sent `end` up to `events.wait`
(15 s) after the close. `RunSubmitter.follow` itself now races `awaitEventsAfter` against `RunQueue.awaitClosed`
([#2408](https://github.com/llm4s/llm4s/pull/2408)), so every follower gets the prompt end and `AgentService.follow`
is a plain call to it. (The service first raced the two waits itself, in #2413; that layer went once the library did
it.) `awaitClosed` polls the entry every 100 ms on the database stores, so a waiting stream reads its entry ten times a
second, a primary-key read; the in-memory queue wakes on the close.

**Readiness is the worker's health; liveness stays `/health`.** `AgentWorker.health()` already checks the worker's
loop and that the store answers both the checkpoint and queue reads (W2), so `/ready` reports it and answers `503`
while the worker drains or when the database is unreachable. Liveness stays the process-only `/health`: restarting a
pod because Postgres is down would not help, and would turn a database outage into a crash loop. This applies to the
`dev`, `staging` and `prod` overlays too, which now also run the worker (on the `memory` store by default).

**Drain order on SIGTERM.** The hook drains the worker first (running runs finish within `drain.grace`, the rest are
cancelled and their entries released for another instance), then stops the server, then closes the store, so the
endpoints keep answering from the store during the drain and nothing reads a closed pool. The server is started before
the worker, so a port that cannot be bound exits the process (status 1) before its worker takes a run.
`terminationGracePeriodSeconds: 60` covers `grace` (30 s) plus `exitTimeout` (10 s) with a margin.

**The agent runs in CI with no key.** P2 needs three processes without a provider, and runs long enough to cancel,
interrupt and `kill -9` part-way. `llm4s-testkit`'s `ScriptedLLMClient` records every call forever, which a
long-running service must not, so the service has its own stateless `DemoModel`. Its one tool call per turn gives each
run a superstep boundary (for `Interrupt`) and a configurable stretch of work (for cancel and kill); a recovered run
calls it again with the same history and gets the same answer.

**Configured entirely by environment and system properties.** Everything P2 and a pod need is an existing binding
(`LLM4S_CHECKPOINTER*`, `LLM4S_RUNTIME_LABEL`, `LLM4S_WORKER_LABEL`) or one of the three new `LLM4S_SERVICE_*`
variables; the Postgres schema and pool size are system properties (`JAVA_OPTS` in the overlay), since S5 binds no
variable for them and the service adds none to another module's `reference.conf`.

**Tenant from a header, explicitly not auth.** Every kernel call is tenant-scoped (rule 9), so the service passes an
optional `X-Tenant-Id` through and documents that it authenticates nothing; a real service derives the tenant from
its own authentication.

**`traceparent` in, invalid ignored.** A valid W3C `traceparent` header becomes `Submission.traceContext` (O1), so every
attempt of the run, on any machine, sits in the caller's trace. An invalid header is ignored, as W3C Trace Context
asks of a receiver, rather than refusing the request.

**Metrics on the service's own port.** `GET /metrics` renders a `PrometheusRegistry` that the service owns, fed by
`new PrometheusMetrics(registry)` through a `MeteredCheckpointer` and the worker (O2), with the Prometheus text format
writer, rather than starting `PrometheusEndpoint`'s second HTTP server on another port: one port per pod keeps the
manifests and the probes simple.

**Credentials never in the overlay.** The overlay references a Secret (`llm4s-postgres-credentials`) the operator
creates with `kubectl create secret`, as the README shows; it is not optional, so a pod without it fails to start
rather than falling back to the in-memory store with threads no other pod can see. A placeholder Secret in the
repository would be deployed unchanged by someone.

**The database is external.** The overlay points at a Postgres the operator provides (a managed service, or their
own): running a production database is outside an example's job, and the spec's anti-goal is infrastructure beyond
Postgres, not a bundled one.

## Not in this slice

- The exit test (three processes, `kill -9`, `Interrupt`, cross-machine cancel and trace): P2 (#2140), which starts
  this service as `DeployServiceMain` with the environment variables above.
- An HTTP server product, authentication, Agent Protocol, A2A or AG-UI: a separate project (spec, Decisions 2).

## Tests

- `AgentServiceSpec` (in-memory store, demo agent, real worker): submit, `reject` and `enqueue` on a busy thread,
  submission-key retries, `traceparent` kept and an invalid one ignored, 400s for malformed bodies, resume and recover
  inputs, tenant scoping of entries and threads, cancel of a running and of a queued entry, thread paging with the
  cursor, readiness through the worker's life, error mapping, a drain letting a run finish.
- `AgentRoutesHttpSpec` (real Undertow on an ephemeral port): the SSE stream, ordered and unique ids, an `end` event,
  `Last-Event-ID` and `?after` resumption, the tenant header, `/ready`, `/metrics` on and off, `/health` alongside.
- `EventStreamEndSpec` (in-memory store, the default 15-second wait): the stream sends `end` within 2 seconds of its
  entry's close, for a run that completes, one cancelled while it runs and one an `interrupt` submission stops.
- `AgentServiceConfigSpec`, `ExampleAgentSpec`, `ServiceRuntimeSpec` (opened from `reference.conf`: `memory` store,
  metrics recorded, drain and close idempotent).
- `DeployServiceSmokeSpec` (`modules/it`, `@Docker`): the service as a separate JVM on Postgres, configured only by
  environment variables, ready, a run submitted and streamed to its end, the thread and metrics read, SIGTERM drains and
  exits.
