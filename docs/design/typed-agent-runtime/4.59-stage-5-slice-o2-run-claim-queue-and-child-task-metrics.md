# 4.59 Stage 5 slice O2: run, claim, queue and child-task metrics ([#2138](https://github.com/llm4s/llm4s/issues/2138))

Part of the [Typed Agent Runtime design](../typed-agent-runtime-design.md), §4. Section numbers (§N.N) refer to that document and its [slice records](../typed-agent-runtime-design.md#slice-records). Stage 5 spec: `docs/superpowers/specs/2026-10-20-stage-5-production-design.md`, "O2" and "Rules every slice must satisfy".

Slice O2 of [#2129](https://github.com/llm4s/llm4s/issues/2129), after W2 ([4.56](4.56-stage-5-slice-w2-workers.md)).
Metrics for runs (started, ended by status, duration), claims (acquired, renewed, lost, taken over), commits (latency,
conflicts), the run queue (depth, wait, lease expiries, attempts) and child tasks (started, ended, duration), exported
through `llm4s-observability-prometheus` and `llm4s-observability-micrometer`. It is the `MetricsCollector` projection
of agent events that the Phase 4 spec deferred here (4.47, "Not in this slice").

## What it adds

In core (`org.llm4s.metrics`), agent-neutral:

- `Metric` (`@Experimental`), a sealed trait of `Metric.Counter`, `Metric.Timer` (with its buckets) and
  `Metric.Gauge`: a name (dot-separated lower-case words), help text and label names, built by `Metric.counter`,
  `Metric.timer` and `Metric.gauge`, which throw `IllegalArgumentException` for a bad name, label or bucket.
- On `MetricsCollector` (`@Stable`), three defaulted `@Experimental` members: `increment(counter, labelValues, amount
  = 1.0)`, `observe(timer, labelValues, duration)` and `set(gauge, labelValues, value)`; `compose` forwards them;
  `MetricsCollector.MaxLabelValues = 256`.
- `MetricLabels` (`private[llm4s]`): the label rules every backend applies - a recording with the wrong number of
  values is dropped, a null or blank value is `unknown`, values past 256 distinct per label of a metric are `other`.

In the backends: `PrometheusMetrics` registers a generic metric's family on its first recording (a counter
`llm4s.agent.runs.started` is `llm4s_agent_runs_started_total`, a timer a histogram `<name>_seconds` with the metric's
buckets, a gauge its name); `MicrometerMetrics` records a Micrometer counter, timer (buckets as SLOs) or gauge of the
metric's name. `MicrometerPrometheusSeriesSpec` now feeds generic metrics to both and checks they expose the same
series and values.

In `llm4s-agent`, every new public type `@Experimental`:

- `org.llm4s.agent.metrics.AgentMetrics`: the 24 metric definitions, named `llm4s.agent.*`.
- `MeteredCheckpointer(inner, metrics)`: a `Checkpointer` that forwards every call and records runs, claims, commits
  and child tasks.
- `AgentWorker.apply(..., metrics: MetricsCollector = MetricsCollector.noop)`, and `QueueMetrics` (`private[agent]`),
  the worker's recorder.
- `WorkerSettings.queueDepthEvery` (default 15 seconds; `llm4s.agent.worker.metrics.queueDepthEvery`).
- On the queue SPI (W1 is unreleased, so these change it in place): `RunQueue.depth(agents): Result[Map[AgentId,
  QueueDepth]]` and `QueueDepth(waiting, leased, oldestWaiting)`; `LeasedEntry.expiredLease`. All three stores implement
  both; `RunQueueContract` gains a case for each (48 cases, 49 on PostgreSQL).

## Decisions

**A generic extension of `MetricsCollector`, not an agent-side recorder the backends adapt.** The spec left the
choice open. An agent-side recorder would need each backend to depend on `llm4s-agent` (or a new adapter module per
backend), which the placement rule forbids without a reason. A generic counter, timer and gauge carry no agent
concept, so core stays the contract only (CLAUDE.md, Tracing and metrics) and any later module - the RAG pipeline, the
memory stores - can report metrics the same way. The cost is that a metric's labels are positional strings rather than
typed arguments; the agent side keeps them typed in one place (`MeteredCheckpointer`, `QueueMetrics`), and a backend
refuses a recording whose arity is wrong.

**Metrics are typed definitions, declared once.** A `Metric` carries its kind, help, label names and (for a timer)
buckets, so a Prometheus backend can register a family with the right labels and buckets on first use, with no
registration step. The kind is in the type (`increment` takes only a `Metric.Counter`), so a counter cannot be
observed as a timer. A name is dot-separated Micrometer style; the Prometheus backend derives its name, so the two
backends agree without a table. Names must not end in the suffix the backend adds (`total` for every kind, `seconds`
for a timer); a gauge names its own unit (`llm4s.agent.queue.oldest.seconds`). The constructors throw rather than return
a `Result`: definitions are constants, and a bad one fails at class initialisation where the developer sees it.

**Cardinality is bounded in two places.** The agent's labels take values from fixed sets, except `graph` (a graph's
id) and `agent` (an agent's id), which the code that builds the agents fixes - a bounded case, so they are labels:
per-agent run and queue numbers are what an operator asks for first. Thread, run, entry and tenant ids are never
labels (rule 9 keeps tenants apart; a per-tenant series would also be unbounded). A delegated task's status
`blocked:<guardrail>` is recorded as `blocked`. As a second line, every backend caps each label of each generic metric at
256 distinct values (the Micrometer collector's model cap) and records further values as `other`, logging once.

**Runs, claims, commits and child tasks are read from the store's calls (`MeteredCheckpointer`), not hooked into the
runtime.** Every run's start and end is a commit of a durable event (`RunStarted`/`RunResumed`/`RunRecovered`, then
`RunCompleted`/`RunSuspended`/`RunFailed`/`RunCancelled`/`RunTimedOut`), and every claim and renewal a store call, so a
decorator over the `Checkpointer` sees all of them with no new runtime parameter and no change to `GraphRuntime`, the
`Agent` builder or `TypedAgent`. It counts each run once, in the process whose runtime committed it - never once per
subscriber or per machine, which a projection of a subscription would. The alternatives were a metrics hook in
`GraphRuntime` (a new constructor parameter threaded through the builders, the typed agents and their children) or a
subscription per run (costly, lossy on lag, and per process that follows the thread).

- **Run duration** is from the event that began the run to its terminal event, both stamped by the runtime that ran
  it, so no two hosts' clocks are compared (rule 1's concern). The decorator remembers a begun run's graph and start,
  by thread, run id and claim token, until its end; a cancel's commit writes no checkpoint, so the graph comes from
  there. At most 10,000 runs are remembered (the oldest forgotten first), so runs that never end - their process died -
  cannot grow it; such a run, and one begun before the decorator, ends without a duration.
- **A takeover** is a grant naming `RunClaim.takenOverFrom`. The store names it only within one tenant (rule 9), so a
  takeover of another tenant's expired claim counts as `acquired`; the count is a floor. W2's worker probes a thread's
  claim before each attempt, and a probe that finds a dead run's expired claim is that takeover, so crashed runs show up
  here as they are recovered. The probes and the sweep's lock are claims, so `claims{result="acquired"}` counts them
  too; `busy` counts the worker's deferrals as well as direct runs refused.
- **A lost claim** is `renew` or `commit` refused with `StaleClaim` (`claim_renewals{result="lost"}`,
  `commit_duration{result="claim_lost"}`). The runtime's own judgement that its lease passed (`ClaimLost` with no store
  call) is not a store call and is not counted; its run ends with no terminal event, and its successor's takeover is.
- **A commit conflict** is `CheckpointConflict` (the parent was not the latest); a commit's latency is timed around the
  store call, by result, so the histogram's count is the commit count.
- **A child task starts** at the child thread's `RunStarted` whose checkpoint names an origin - its first admission,
  labelled by the child's agent - and **ends** at the parent's durable `agent.task_ended` (D4's `TaskEnded`), with its
  status and duration from the event. `agent.task_started` is live, never committed, so it is not the source.

The decorator forwards every `Checkpointer` method, the defaulted `awaitEventsAfter` included, so a store's change
notification (S2's `LISTEN`/`NOTIFY`) is kept; a reflection test fails if a new method is not forwarded. A metric that
throws is caught and never changes a call's answer.

**The queue's metrics are the worker's.** The worker sees every take, attempt, plan, deferral, lapse, lost lease and
close, labelled by the entry's agent. Two needed the store:

- **Lease expiries.** A take that replaces an expired lease nobody released is the store's to know (it clears the
  token on release and close), so `take` now answers `LeasedEntry.expiredLease`. It counts a dead worker's lease and
  one a worker let lapse after a failed run (W2's backoff); the worker counts the latter itself
  (`queue.lease.lapses`), so crashes are the difference.
- **Depth.** `RunQueue.depth(agents)` answers, per agent, the open entries waiting and leased and the oldest waiting
  entry's age, all by the store's clock (rule 1), by the stores' existing open-by-agent index. It is store-wide, the
  operator's as `openRuns` is (rule 9 is about answering a tenant's requests; a gauge names no tenant). A worker with a
  collector samples it for its agents every `queueDepthEvery` on a virtual thread of its own, and one without never
  does. Every worker of a fleet reports the same numbers, so dashboards take `max`. Per agent rather than one store-wide
  number so the contract cases can share one database and a dashboard can split by agent.

**Queue wait** is from submission to the entry's first recorded attempt, both store times (`Attempt.startedAt`,
`submittedAt`), recorded once per entry (when the store answers the first `Recorded`), so deferrals and retakes do not
count it twice.

**Dead letters** are `queue.closed{outcome="failed", reason="attempts_exhausted"}`; every close the worker makes, and
the store's `ThreadDeleted` close, is counted by outcome and a bounded reason.

**W3's hook.** W3 (#2136, in parallel) adds cancels and interrupts. The cancel's stopped run is already counted
(`runs.ended{status="cancelled"}`) by the decorator. For entries, `QueueMetrics.closed(agent, outcome)` is the one place a
close is counted, already labelling `cancelled`/`requested` and `interrupted`: W3 calls it wherever it closes an entry
outside `AgentWorker`'s own close (a cancel of a queued entry, an `Interrupt` closing the running one) and has the
worker's `QueueMetrics`. An `Interrupt` submission closing an earlier unstarted one happens inside the store's `submit`
and is not seen by any worker; W3 decides whether to count it at the submitter.

**`WorkerSettings` grows in place.** W2 is unreleased, so `queueDepthEvery` is added to the constructor, `apply` and
`of` with a default, without the forwarding overload a released growth-prone type keeps.

**No breaking change.** The `MetricsCollector` members are defaulted no-ops, so every existing collector compiles;
`RunQueue` and `LeasedEntry` are unreleased (W1). Nothing goes under `### Breaking changes` or into the migration guide.

## Not in this slice

- Cancel-request and interrupt counts beyond the close counter (W3; see the hook above).
- Token and cost metrics per run: the model calls already report them per provider and model through the client's
  `MetricsCollector`.
- Exemplars naming a `TraceContext.traceId` (O1 notes it as possible): neither backend's generic path takes one yet.

## Tests

`MetricSpec` (definitions and `MetricLabels`), `MetricsCollectorComposeSpec` (the new members forwarded),
`PrometheusGenericMetricsSpec`, `MicrometerGenericMetricsSpec` and `MicrometerPrometheusSeriesSpec` (both backends
expose the same generic series). `MeteredCheckpointerSpec` (in-memory store, real agents): claims, renewals, commits by
result, a completed run, a failed run and its recovery, a cancelled run committed without a checkpoint, a child task
started and ended, a throwing collector, and every `Checkpointer` method forwarded. `WorkerMetricsSpec`: an entry's
attempt, plan, wait and close; a dead worker's expired lease; a deferral to a live claim; the depth gauges; no sampling
without a collector; sweep passes; a drain; and the close labels W3 relies on. `RunQueueContract`'s two new cases run
against the in-memory, SQLite and PostgreSQL stores.
