# 4.50 Stage 5 slice S1: the PostgreSQL checkpointer ([#2130](https://github.com/llm4s/llm4s/issues/2130))

Part of the [Typed Agent Runtime design](../typed-agent-runtime-design.md), §4. Section numbers (§N.N) refer to that document and its [slice records](../typed-agent-runtime-design.md#slice-records). Stage 5 spec: `docs/superpowers/specs/2026-10-20-stage-5-production-design.md`, "S1" and "Rules every slice must satisfy".

Slice S1 of [#2129](https://github.com/llm4s/llm4s/issues/2129), the first of Stage 5 and on its critical path: every
later slice runs its contract cases against this store. It adds `llm4s-agent-checkpoint-postgres`
(`modules/agent-checkpoint-postgres`), with `PostgresCheckpointer` passing `CheckpointerContract`, and, from the spec's
rule 1 as revised on 2026-10-21, makes retention judge age by commit time in every store.

## What it adds

In `org.llm4s.agent.graph.postgres`, both `@Experimental`:

- `PostgresCheckpointer`, a `Checkpointer with AutoCloseable`:
  - `open(jdbcUrl, user, password, config = PostgresCheckpointerConfig.default): Result[PostgresCheckpointer]`, over a
    HikariCP pool of its own, closed with the store;
  - `create(dataSource: javax.sql.DataSource, ownsDataSource: Boolean, config = default): Result[PostgresCheckpointer]`,
    over a caller's pool (as `PgVectorStore.create`), closed with the store only if owned;
  - `schema`, `config`, `close()`, `isClosed`.
- `PostgresCheckpointerConfig` (growth-prone: private constructor, `apply` with defaults, `of` returning a
  `ValidationError`, `with*`): `schema` (`llm4s`), `callTimeout` (5 s), `connectionTimeout` (5 s, at least HikariCP's
  250 ms), `maxPoolSize` (10), and `bound = connectionTimeout + callTimeout`.

In `llm4s-agent`: `GraphError.UnsupportedStoreSchema(store, found, supported)`, the typed refusal of a schema a newer
build migrated.

## Decisions

**Locking, not isolation.** Writes run at `READ COMMITTED` and lock the thread's row first (`SELECT ... FOR UPDATE`);
every later statement in the transaction takes a fresh snapshot, so it sees what the previous lock holder committed. A
write that touches two threads (a commit or delete with a `fence`) locks both rows in the order of their ids, one
statement each, so two fenced writes cannot deadlock. `SERIALIZABLE` would also be correct, but its serialization
failures would need a retry loop in every write, and the row lock is the exclusion the contract describes anyway.
Reads run in a `REPEATABLE READ, READ ONLY` transaction: one snapshot per call, never waiting for a writer, never a
serialization failure.

**Rows that come and go.** A claim creates the thread's row with `INSERT ... ON CONFLICT DO NOTHING` and then locks it.
A row a concurrent call deletes (a thread emptied by release or delete, `dropIfEmpty`) while this call waits for its
lock is gone when the lock is granted; the claim then inserts again, a bounded number of times.

**Tokens from a sequence, drawn under the row lock.** `nextval` is not transactional, so two transactions can commit
their values out of order; but a token is drawn only after the thread's row is locked, so the claims of one thread
draw their tokens in the order they commit, which is what "greater than every token issued for the thread before"
needs. Store-wide uniqueness comes from the sequence itself.

**Child places under an advisory lock on the parent.** `children` pages by place, and a page boundary must not be
passed by a commit still in flight. A place drawn from a sequence alone could be taken by one child, committed after
another child's larger place was already paged past. So a commit draws a new place under
`pg_advisory_xact_lock(hashtextextended('llm4s.agent.checkpoint:<schema>:children:<parent>', 0))`, released only after
it commits: one parent's children take places in the order their commits land. It is the last lock a commit takes and
the holder waits for nothing after it, so it adds no deadlock; a hash collision only serialises two parents' child
placements.

**The clock.** `clock_timestamp()`, read once per call after the call holds its row locks, not `now()`: `now()` is the
transaction's start, and a claim that waited for a lock would get an expiry shortened by the wait. Instants are kept
to the microsecond (PostgreSQL's precision), so what a call hands back equals what a later read returns.

**Retention by commit time** (rule 1, revised 2026-10-21). Every checkpoint and event row records `committed_at`, the
store's clock when the commit wrote it, and `prune` compares `maxAge` with that, never the producer's
`Checkpoint.createdAt` or event `timestamp`, which a skewed worker would make too old or too young; those stay in the
JSON as the producer's record. The rule is the contract's, not only Postgres's:
- `RetentionPolicy` and `Checkpointer.prune` say so, and `CheckpointerContract` gains "prune by age by when the store
  committed, never by a skewed producer's own timestamps" (the oldest commit claims to be from next year, the younger
  ones from last year). The existing age case now moves the store's clock between commits instead of stamping
  `createdAt`, which no longer matters.
- `InMemoryCheckpointer` stamps each checkpoint and event with its `clock` at commit.
- `SqliteCheckpointer` stamps them too, in schema 7 (`committed_second`, `committed_nano` on `llm4s_checkpoint_history`
  and `llm4s_checkpoint_events`). A row written before schema 7 has none (NULL) and is judged by its producer's
  timestamp, as it was: nothing better is known and nothing is backfilled. The step creates the history table first on
  a pre-release version-1 file and adds only the columns that are missing.
- With one clock for runtime and store, as every runtime built with `GraphRuntime.inMemory(clock)` has, nothing
  changes for callers.

**Events carry `checkpoint_id` and `committed_at` as columns**, so `prune` decides its floor with two `MIN(seq)`
queries rather than decoding the thread's log as the SQLite store does.

**The schema.** One version table and ordered steps (`PostgresSchema.steps`, version 1 now), applied in one
transaction under `pg_advisory_xact_lock(hashtextextended('llm4s.agent.checkpoint:<schema>', 0))`, so instances
starting together migrate once (the integration suite opens sixteen at once on a new schema). A schema newer than the
build is refused with `GraphError.UnsupportedStoreSchema`, changing nothing, and an owned pool is closed. A schema
already current is only read, so a role with only `USAGE` and DML grants can open it (tested); the schema is created
only if `pg_namespace` lacks it, since `CREATE SCHEMA IF NOT EXISTS` checks the `CREATE` privilege first. Every table
and sequence is qualified by the configured, quoted schema and prefixed `checkpoint_`, so later slices' tables (S3's
registry, W1's queue) can share the schema; the schema name is validated as a lower-case identifier, so nothing
user-supplied reaches SQL unchecked. A missing step is a `ProcessingError` (a build bug, not an upgrade condition).

**Upgrades** follow the 2026-10-21 decision: rolling within one schema and checkpoint format, a full stop otherwise,
an old instance refusing a newer schema with the typed error; expand-then-contract waits for the 1.0 baseline. The
guide's "The PostgreSQL store / Upgrades" and the migration note say so; P2's deployment guide repeats it.

**The bound** (rule 2, the contract's #1919). A call returns within `connectionTimeout + callTimeout`:
- the pool's connection timeout bounds the wait for a connection (a caller's pool brings its own);
- `SET LOCAL statement_timeout`, `lock_timeout` and `idle_in_transaction_session_timeout`, all `callTimeout`, bound
  the transaction on the server, and end with it, never leaking into the pool;
- a client watchdog (one daemon thread per JVM) aborts the connection if the call is still running after
  `callTimeout`, so a stalled network cannot hold a call past the bound either; an owned pool also sets the driver's
  `socketTimeout` past twice the call timeout as a last resort.
A per-statement timeout alone would let a commit of many statements take a multiple of it; the watchdog makes the
bound per call. A call that times out while its `COMMIT` is in flight cannot know whether it landed, like any network
store; fencing keeps that safe. The contract's bounded-store case runs with a 300 ms call timeout and a 250 ms
connection timeout while another connection holds `EXCLUSIVE` on the threads table.

**Connections after a failure.** A connection whose call threw, or that the watchdog aborted, is discarded (evicted
from a HikariCP pool, aborted otherwise) rather than returned: a socket an interrupt closed, or a cancel still in
flight, never reaches another call. On a virtual thread an interrupt closes a blocking socket, so an interrupt flag
already set when a call begins is cleared for the call and set again after it: a flag decides nothing, as in the SQLite
store. An interrupt that lands during a call ends it with `CancelledError` (or the failure itself).

**Change notification stays polling** (the SPI default); S2 replaces it with `LISTEN`/`NOTIFY` ([4.51](4.51-stage-5-slice-s2-cross-machine-change-notification.md)).

**Testing the database clock.** The contract's cases move a `ManualClock`, and its `exactExpiry` / `advanceStoreClock`
hooks exist for a store that reads its own clock. The store takes its clock as an SQL expression
(`private[postgres] createWith(..., clockSql)`), `clock_timestamp()` outside tests. The integration suite mirrors each
case's `ManualClock` into a row of an `it_clocks` table and passes `(SELECT at FROM it_clocks WHERE id = ...)`:
time is still read inside the store's own statements, in the database, and `advanceStoreClock` moves the clock and
writes the row. So `exactExpiry` stays `true`. `PostgresCheckpointerSpec` checks claims and retention on the server's
real clock, and the cross-process case recovers a killed run after its claim expires by it, moving no clock.

## Tests

- `modules/agent-checkpoint-postgres`, `PostgresCheckpointerUnitSpec` (10, no server): configuration, migration plan,
  DDL and every statement confined to the schema (by reflection over `Sql`), the server and driver bounds, SQLSTATE
  naming, a failed open closing an owned pool, a failed call rolled back and its connection discarded.
- `modules/it` (`@Docker`, the pgvector service), package `org.llm4s.agent.graph.postgres`:
  - `PostgresCheckpointerContractSpec`: `CheckpointerContract`, all 82 cases;
  - `PostgresCheckpointerConcurrencySpec`: 64 claimers over 16 stores for 10 rounds, exactly one granted each;
    64 racing event commits numbered 1..128 contiguously, and 32 racing checkpoints over one parent with one winner;
    64 fenced commits on two threads that fence each other, without a deadlock; tokens racing across stores; 48 children
    whose first commits race, paged two at a time, each seen exactly once;
  - `PostgresCheckpointerSpec`: the real clock (claims, retention against skewed producer timestamps), sixteen
    concurrent openers of a new schema, a newer schema refused, a DML-only role, two schemas in one database, the
    store's own pool, interrupts mid-call;
  - `PostgresCrossProcessSpec`: a run in a child JVM, `kill -9`ed, held while it lives, its events reaching a
    subscriber here, recovered here once its claim expires by the database's clock.
- The contract's new skewed-producer case runs on the in-memory and SQLite stores too; `SqliteCheckpointerSpec` adds a
  version-6 file migrated to 7.
