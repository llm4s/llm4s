# 4.26 Stage 3 slice F8a: response format for the agent's answer ([#1912](https://github.com/llm4s/llm4s/issues/1912))

Part of the [Typed Agent Runtime design](../typed-agent-runtime-design.md), §4. Section numbers (§N.N) refer to that document and its [slice records](../typed-agent-runtime-design.md#slice-records). Slice F8a of the Phase 3 plan (`docs/superpowers/specs/2026-10-13-phase-3-harness-design.md`, #1901).

An agent can be given a response format: a JSON schema its final answer must match. The model is asked for it on every call, the answer is checked inside the model step, an invalid answer gets one corrective retry, and a second invalid answer ends the turn as a Block with a typed error. `AgentResult.decodeOutput[O]` reads the answer as `O`. `Agent` stays non-generic; Stage 4's `TypedAgent[I, O]` builds on this.

## API

```scala
// llm4s-agent
Agent.builder("extractor", client)
  .withOutput[Invoice]                    // using SchemaDefinition[Invoice], ReadWriter[Invoice]
  .build()
result.decodeOutput[Invoice]              // Result[Invoice]
GraphError.OutputInvalid(errors)          // the turn's answer failed the format twice

// llm4s-schema-derivation
Agent.builder("extractor", client).withOutputOf[Invoice]   // Invoice derives SchemaOf
```

- **`AgentBuilder.withOutput[O](using SchemaDefinition[O], ReadWriter[O])`** records an `OutputFormat` on the agent. The schema is `definition.toJsonSchema(strict = true)`, as `completeStructured` sends.
- **`OutputFormat`** (`org.llm4s.agent.graph.toolloop`, `@Experimental`) is what `LoopAgent.withOutput` takes: the JSON schema and a check that the answer decodes as `O`. `OutputFormat.of[O]` builds one. It is a class with a private constructor, not a case class: it holds a function, and has nothing to copy.
- **`AgentResult.decodeOutput[O: ReadWriter]: Result[O]`** decodes the answer: `Left(ValidationError("output", ...))` when the turn has no answer (any status but `Completed`), when the answer is not JSON or is JSON `null`, or when it does not read as `O`. It does not need the agent to have a format; it is how a caller reads any JSON answer.
- **`GraphError.OutputInvalid(errors: Vector[String])`**: the caller's `Left` when the corrective answer is invalid too. `errors` are the second answer's problems, JSON-path prefixed as `ToolArgumentValidator` reports them (`$.total: expected number, got string`), at most 20, each at most 300 characters. Its `message` names only the count, never an error, because errors quote the answer and the message goes into the durable `TaskFailed` and `RunFailed` events (rule 9).
- **`withOutputOf[O: SchemaOf: ReadWriter]`** is an extension on `AgentBuilder` in `llm4s-schema-derivation`, which takes `llm4s-agent` as a `Provided` dependency: a user of `completeStructuredOf` does not get the agent runtime on their classpath, and a user of `withOutputOf` already has it. It builds the format with `OutputFormat.deferred` and hands it over with `AgentBuilder.withOutputFormat` (both `private[llm4s]`), so a type that is not an object, and a derived schema that throws when it is built (`SchemaOf.definition`'s run-time recursion guard), are refused with a `Left` at `build()` instead of throwing from the builder call.

## Decisions

- **The format belongs to the agent that sets it.** As with `wrapModelCall`, each agent of a handoff family has its own (or none): a handoff target answers in its own format. A family whose callers decode one type sets the same format on each agent that can answer. The root's format is not imposed on targets, because a target's model calls must carry the format, and a target with tools of its own may be written for a different answer.
- **Every model call of the agent carries `responseFormat = JsonSchema(schema)`**, set by `AgentBuilder` on the options `ModelStep.fromClient` sends; it replaces a `responseFormat` given with `withCompletionOptions`. Tool-calling steps carry it too: providers that enforce a schema still allow tool calls, and the format constrains only the text. A client that cannot honour it drops it inside the client: `OpenAIClient` runs `RequestTransformer` with `dropUnsupported = true`, which drops an unsupported `JsonSchema` with a DEBUG log and no error; the other clients send `responseFormat` or ignore it (`LLMClient.completeStructured`'s Scaladoc lists which). Nothing reaches the agent, so the prompt section below is what such a model follows. A custom `ModelStep` given to `LoopAgent` sends what it likes; the loop validates the answer either way.
- **A prompt section always states the schema.** The agent's system prompt is followed by `Reply with only a JSON value matching this JSON Schema, with no other text, when you give your final answer:` and the compact schema, in the one system message the agent sends (C1's prompt sections will carry it once that slice lands; until then it is appended in `ToolLoop` where the prompt is built). It is never stored.
- **An answer turn is validated inside the model step**, after every `wrapModelCall` returned and before anything is stored. A completion with tool calls (a handoff included) is not an answer and is not checked. The check: the answer's JSON (a surrounding code fence or prose stripped, as `completeStructured` does, with `LLMClient.extractJson`, now `private[llm4s]`), parsed with `BoundedJson`, not `null`, valid against the schema by the agent's `ToolArgumentValidator`, and readable as `O`. A blank answer is invalid, not the step failure it is without a format.
- **A valid answer is stored as its compact JSON**, so the thread, `AgentStatus.Completed`, `afterAgent` and `decodeOutput` all see exactly the value that was validated, never the fence or prose around it. `afterAgent` may still replace it; its replacement is not validated again, and `decodeOutput` reports one that does not decode.
- **An invalid answer is retried once, in the same task.** The model step runs the `wrapModelCall` stack again on the request extended with the invalid answer (as an `AssistantMessage`, at most 16,000 characters) and a `UserMessage` listing its problems (at most 20, each at most 300 characters) and asking again. Neither is stored in the thread. The retry is one more model request, so every wrapper sees it, as it sees any request. If it returns tool calls, those are routed as usual.
- **A second invalid answer ends the turn through the Block path** (rule 10), `NodeResult.Block` from the model node:
  - The update is the output Block's (§4.13): `RemoveTurn` from the turn's user message, `activeAgent` and `transfer` restored to the turn's start, plus `LoopKeys.usage` with both calls. The task's `ModelCallCompleted` events, one per call, commit with it. The runtime closes the thread with a `Failed` checkpoint and retracts the turn's earlier checkpoints (`retractTurn`), so no invalid answer is readable or forkable.
  - The caller gets `Left(GraphError.OutputInvalid(errors))`: `AgentRun.await` reports only a `GuardrailBlocked` Block as `AgentStatus.Blocked`; any other Block error is `Left`, as a non-guardrail `afterAgent` failure is today.
  - `recover` refuses the thread with `NothingToRecover`, as for any Block; the next `start` continues from before the turn.
  - Failing the task instead would lose the usage and events (rule 10), and `recover` would pay for both calls again.
- **The format is part of the graph version.** `AgentBuilder`'s canonical settings gain `output` (the schema) only when a format is set, so the version of every agent without one is unchanged. A thread is continued only by an agent with the same format.
- **Build refuses** a schema whose root `type` is not `"object"` (providers require an object for a JSON-schema response format, as `completeStructuredOf` does), a schema with a keyword the agent's validator cannot check (as `ToolSet` refuses a tool's), and one whose rendering is over 32,768 characters (rule 12).

## Runtime rules

1. **One batch, one snapshot.** Not affected: validation runs in the model task, which is never part of a tool batch, and reads nothing from state but the history it already read.
2. **Total updates.** The slice adds no state key and no update function. The Block's update uses `RemoveTurn`, `Set` and the usage merge the output Block already uses, so it cannot fail at apply time.
3. **Visibility.** The corrective request is built in the same task from the request the first call was sent; nothing goes through state, so nothing waits for the next superstep.
4. **At-least-once.** The model step may run again on `recover` (a crash between the two calls, or a provider error on the second). It then makes both calls again: model calls are not external effects with a replay key, as today. The step stores nothing until it ends, so a re-run cannot leave a half-corrected answer.
5. **Block retraction.** The Block retracts the turn from `messages` and restores `activeAgent` and `transfer`, exactly as an output Block does; the slice writes no other key. When C1 widens retraction to every key, this Block gets it with the output Block, since both go through one helper.
6. **Full-snapshot checkpoints.** No new key, so checkpoints grow only by the answers the agent already stores.
7. **Codec migration.** No stored type changes shape: `Messages.key`, `LoopKeys.usage` and `TurnState` are untouched, so existing threads restore. The graph version changes only for agents that set a format.
8. **Tenant scope.** Nothing is shared across threads: the format is the agent's, fixed at build.
9. **No content in durable events.** `ModelCallCompleted` carries counts and usage only. `OutputInvalid.message`, which `TaskFailed` and `RunFailed` record, gives the problem count, not the problems; the problems are on the error value the caller receives in-process.
10. **Failed tasks commit nothing.** The second invalid answer ends through the Block path, which commits the usage and events. A provider error, a cancellation or a thrown wrapper on either call fails the task as today: it commits nothing, the thread stays `Running`, and `recover` re-runs the step. The usage of a first call made before such a failure is lost with the task, as a retrying wrapper's is; C1's loop-level accounting covers both.
11. **Every model call accounted.** A first invalid answer gets its own `ModelCallCompleted` (its attempts are the first pass's) and its usage is merged into the step's update, whether the second call is valid (stored with it), invalid (in the Block's update) or asks a middleware question (in the suspend's update, as a wrapper's earlier calls are).
12. **Everything bounded.** The prompt section is the schema, at most 32,768 characters, fixed at build. The corrective exchange is sent once and never stored: the echoed answer is cut to 16,000 characters, the problems to 20 of at most 300 characters. `OutputInvalid.errors` has the same bounds. The retry count is fixed at one.
13. **Every type defined.** New: `OutputFormat` (above, `org.llm4s.agent.graph.toolloop`, no codec: it is never stored), `GraphError.OutputInvalid(errors: Vector[String])` (no codec: errors are never stored), `AgentBuilder.withOutput`, `LoopAgent.output`/`withOutput`, `AgentResult.decodeOutput`, and `withOutputOf` in `llm4s-schema-derivation`. Used from the code: `ResponseFormat.JsonSchema` (core), `SchemaDefinition` (core `toolapi`), `ToolArgumentValidator` (`graph.tool`), `BoundedJson` (core `util`), `NodeResult.Block` (`graph`).

## Interactions

- **Output guardrails.** A guardrail sees the validated JSON. Its Block is the ordinary output Block, `AgentStatus.Blocked`, and keeps both calls' usage when the answer needed the retry.
- **Middleware questions.** A wrapper that asks during the corrective call suspends the step with both calls' usage, as it does with any earlier call; once answered, the step runs again from the first call.
- **Streaming.** The invalid answer's text was already streamed as live `TextDelta`s before it was checked; the corrective call's follow, numbered by attempt. Live events are not stored.
- **Checkpoint restore.** Nothing new is stored, so restore is unchanged. A thread whose turn ended `OutputInvalid` restores to the state before that turn.
