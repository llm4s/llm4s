# 4.28 Stage 3 slice F9: typed custom streams ([#1914](https://github.com/llm4s/llm4s/issues/1914))

Part of the [Typed Agent Runtime design](../typed-agent-runtime-design.md), §4. Section numbers (§N.N) refer to that document and its [slice records](../typed-agent-runtime-design.md#slice-records). The Stage 3 slicing, and the thirteen runtime rules cited below as "rule N", are in [`docs/superpowers/specs/2026-10-13-phase-3-harness-design.md`](../../superpowers/specs/2026-10-13-phase-3-harness-design.md) (F9).

Before this slice a listener matched typed events one `case` at a time (`case AgentEvents.TextDelta(d) =>`, `EventType.unapply`, §4.14), and every `case` decoded the payload again until one matched. That works for a hand-written listener, but a selection of event types cannot be built as a value and passed around: `EventType[A]` is invariant, so a `Set[EventType[?]]` loses each `A`, and the fs2, ZIO and Pekko streams offered only the untyped `StreamEvent`. No new event model is needed - `RunEvent.Custom`, `StreamEvent.Live` and `EventType` carry everything (§4.6, §4.14) - only a typed selection and the adapters over it. The specs are `EventHandlersSpec`, `TypedStreamSpec` and the extended `AgentEventBufferSpec` in `llm4s-agent`, `AgentIOEventsSpec` in `llm4s-effect`, `AgentZEventsSpec` in `llm4s-zio` and `AgentPekkoEventsSpec` in `llm4s-pekko`.

Decisions:

- **`EventHandlers[+R]`, in `org.llm4s.agent.graph` beside `EventType`.** A selection is typed handlers packaged with their event types: `EventHandlers.on(Pinged)(p => ...).on(AgentEvents.TextDelta)(d => ...)`. Each `on[A](EventType[A])(A => R)` keeps its own `A`; the handlers are stored by `(name, version)`, so an event is looked up once and its payload decoded once, by the one matching type. `R` is what a handler returns: `Unit` for a listener, a caller's ADT for a heterogeneous stream (`on(Pinged)(MyEvent.Ping(_))`).
  - `dispatch(event): Option[R]` is the result of the handler for the event's name and version; `None` when no handler is registered for it or its payload does not decode (`EventType.decode`, logged at DEBUG), unless `otherwise` is set.
  - `otherwise(StreamEvent => R)` takes every event no handler took: kernel events, `LiveGap`, `Disconnected`, unregistered names, undecodable payloads. Without it they are skipped. It is the one addition to the spec: without it a typed listener could never learn that it lost live events (`LiveGap`) or was disconnected, and an ADT stream could not carry a gap.
  - A second `on` for the same name and version replaces the first, as `Map.updated` does: one handler per event type. `v1` and `v2` of a name are different keys, so a listener over a log written by both registers both.
  - `EventHandlers[R]` is a `StreamEvent => Unit` (it calls `dispatch` and discards the result), so it is passed wherever a listener is: `agent.stream(threadId, query)(handlers)`, `streamResume`, `streamRecover`, `run.subscribe()(handlers)`, `GraphRuntime.subscribe(...)(handlers)`. The spec's `agent.stream(threadId, query, handlers)` and `AgentRun.subscribe(handlers)` overloads are therefore not added: `stream`'s parameter list has defaults, and Scala allows defaults on only one overload, so the listener position is the one that works on every entry point without a new method. A handler that throws is a listener that throws: the subscription ends `Disconnected(ListenerFailed)` (§4.6), as before.
  - No codec: handlers are never stored.
- **Effect adapters are typed per event type, on each wrapper's instance:** `AgentIO[F].events(run, eventType): Stream[F, A]`, `AgentZ.events(run, eventType): ZStream[Any, LLMError, A]`, `AgentPekko.events(run, eventType, bufferSize): Source[A, Future[Done]]`, and for a heterogeneous stream the same three over `events(run, handlers: EventHandlers[R])`, one element per event a handler took. `events(run, eventType)` is `events(run, EventHandlers.on(eventType)(identity))`. Callers merge typed streams with the library's own combinators. The spec writes `AgentIO.events(...)`; instance methods are used because `AgentIO` is `AgentIO[F]` and a companion method would need its effect type spelled at every call (`AgentIO.events[IO, Ping]`), and all three wrappers keep one shape.
  - **It observes a run, it does not own it.** It subscribes with `AgentRun.subscribe`, so it replays the run's durable events from its start and then follows it live, and it misses the live events sent before the stream started (§4.6, `stream*` vs `subscribe`). Ending the stream (`take(n)`, interruption, a downstream failure) cancels its subscription only: the run goes on, and whoever started it awaits or cancels it. For every live event of a turn, use the existing `stream*`, which subscribe before the run starts, and match with `EventType.unapply` or `handlers.dispatch`.
  - It ends after the run's terminal event, or at the run's end-of-run barrier for a run that commits none (§4.6), through the same scope end the `stream*` bridges use (`AgentRun.subscribeEnding`, `private[llm4s]`). A `Disconnected` fails it with the `LLMError` the `stream*` bridges raise.
  - Handlers run on the consumer's side of the bridge's buffer, not on the subscription's dispatcher, so a slow or throwing handler slows or fails the stream, never the run or its subscription.
- **The bridge buffer bounds durable events too** (rule 12). `AgentEventBuffer` - under every fs2, ZIO and Pekko agent stream - dropped live events beyond its capacity but queued durable events without limit, because its listener must never block the dispatcher. A consumer that took nothing while a run (or a tool emitting durable events in a loop) committed millions held them all. It now holds at most `Agent.StreamCapacity` (1024) waiting durable events, the room the kernel gives a listener's durable queue; one more ends the stream, after what is queued, with an error naming the last `seq` the consumer took, as the kernel's own `Disconnected(lastSeq, Lagging)` does. The `seq` is read when the error is reported, after the consumer has taken everything queued before the failure, not when the bound is crossed (up to 1024 events earlier); a kernel `Disconnected` is reported the same way, from the consumer's position rather than the subscription's `lastSeq`, which counts events the run scope filtered out and events a `close` dropped. Resubscribing from it repeats nothing the consumer took. The buffer's listener ignores the rest, so it still never blocks. A run's own events stay far below the bound (a handful per step, `maxSteps` steps), so only a consumer that has stopped draining reaches it. For `events(run, ...)` the run is unaffected; for the `stream*` bridges, as for any failure of those streams, the release cancels the turn. This is a behaviour change to the existing `stream*` bridges (and the Java `AgentStream`, which shares the buffer); the migration note records it.

How the slice meets each runtime rule:

1. **One batch, one snapshot.** Handlers read no state. Tools of one batch emit concurrently; one subscription calls its listener from one dispatcher thread, so handlers never run concurrently for one subscription, and see durable events in `seq` order and live ones in the order they were sent.
2. **Total updates.** The slice writes no state key.
3. **Visibility.** No hook reads anything this slice produces.
4. **At least once.** A durable custom event is committed with its task; a failed or cancelled attempt's are discarded (`RunContext.discardAttempt`, rule 10), so the log holds each committed task's events once, and a tool that `recover` runs again emits them in the recovered run, whose run-scoped stream delivers them once. A live event is at least once: a re-run tool sends it again, to the recovered run's stream, after the first run's subscribers already had it. A handler with an effect outside the stream keys it by something stable across recovery and carried in the payload - for a tool, its `IdempotencyKey` - never by `runId` or `toolCallId`. `TypedStreamSpec` runs a tool that emits both kinds and then fails its first attempt (`ToolOutcome.Fatal`, failing the run), then recovers it: one durable event in the thread's log, the second attempt's, and the live event delivered to both runs' streams.
5. **Block retraction.** Durable events carry no content (rule 9), so a Block has nothing to redact in the log; live events are never stored.
6. **Full snapshots.** No key is added.
7. **Codecs.** A payload's shape is versioned by `EventType`'s `version`; handlers are keyed by `(name, version)`, so a `v1` handler never sees a `v2` payload, and a payload that does not decode goes to `otherwise` (or is skipped), never thrown.
8. **Tenant.** Nothing shared across threads is added; a stream follows one run of its agent's runtime.
9. **No content in durable events.** The slice adds no event. The typed form of a custom event is chosen by the emitter: content belongs in `progress` (live), structure in `emit` (durable), as the streaming guide says; a type cannot enforce it, since a payload is the caller's.
10. **A failed task commits nothing.** Its durable events never reach a handler; the spec's failed first attempt shows it.
11. **Model calls.** None are made.
12. **Bounded.** An `EventHandlers` holds one entry per registered `(name, version)`, sized by the program, not by input. Dispatch inside a listener inherits the kernel's bounds: `capacity` live events then `LiveGap`, `capacity` durable events then `Disconnected(Lagging)`. The effect adapters reuse `AgentEventBuffer`: live events bounded by the stream's buffer size (then one `LiveGap`, which `events(run, eventType)` skips and `otherwise` can carry), durable events now bounded by `Agent.StreamCapacity` (above). The Pekko hand-over is bounded and blocks only the bridge's own pump thread.
13. **Types defined.** `EventHandlers[+R]` (`org.llm4s.agent.graph`, `llm4s-agent`): a map from `(name, version)` to a decoding handler, and an optional `otherwise`; no codec. The adapter methods are on `AgentIO`, `AgentZ` and `AgentPekko`. `EventType`, `StreamEvent`, `RunEvent.Custom` and `AgentEvents` exist (`graph/EventType.scala`, `graph/RunEvent.scala`, `events/AgentEvents.scala`).

Implementation plan:

1. `EventHandlersSpec`, then `EventHandlers`: dispatch of durable and live events, one decode, unmatched and undecodable events, `otherwise`, replacement, versions, use as a listener.
2. `TypedStreamSpec`, then `AgentRun.subscribeEnding`: handlers on `agent.stream` and `subscribe` with a tool's events, a slow handler's `LiveGap` through `otherwise`, the fail-and-recover case of rule 4.
3. `AgentEventBuffer`'s durable bound, with its spec.
4. `AgentIOEventsSpec`, `AgentZEventsSpec`, `AgentPekkoEventsSpec`, then the three adapters: typed per type, heterogeneous through handlers, ending at the run's end, the run unaffected by an early stop, a disconnect raised.
5. The streaming guide, the CHANGELOG, the migration note, and this record's row in the slice table.

Limits:

- `events(run, ...)` misses live events sent before the stream subscribed; it is for observing a run you already hold. `stream*` remain the way to see all of a turn.
- A handler sees the payload only. A caller who needs the envelope (`seq`, `taskId`, the run) matches `StreamEvent` itself, with `EventType.unapply`.
- The Java and Kotlin facades are unchanged; they keep their untyped listeners.
- A single task that emits more durable events than a subscription's capacity (1024 by default) disconnects every subscriber of the run as `Lagging` when it commits, because a commit is handed over whole or not at all (§4.21). That is the kernel's rule, unchanged here; the adapter specs use it to show that a disconnect fails a typed stream and leaves the run alone. A tool that reports many items emits them live, or in batches.
