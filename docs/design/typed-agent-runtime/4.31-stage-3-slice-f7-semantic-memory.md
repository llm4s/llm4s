# 4.31 Stage 3 slice F7: semantic memory ([#1911](https://github.com/llm4s/llm4s/issues/1911))

Part of the [Typed Agent Runtime design](../typed-agent-runtime-design.md), §4. Section numbers (§N.N) refer to that document and its [slice records](../typed-agent-runtime-design.md#slice-records). Phase 3 spec: `docs/superpowers/specs/2026-10-13-phase-3-harness-design.md`, "F7".

Slice F7 of [#1901](https://github.com/llm4s/llm4s/issues/1901), a feature slice on C1 (§4.22: state-writing
boundary hooks, prompt sections, `ModelContext.accounted`, a Block restoring every key the turn wrote) and C4
(§4.24: `EffectKey`, `ReplayGuard`, `AppliedKeys`, `ReplayContract`). It gives an agent long-term semantic memory
that outlives a thread: before a turn it recalls what earlier threads of the same tenant recorded and shows it to
the model; after the turn it records the exchange, and optionally consolidates old memories. It is opt-in: an agent
without `SemanticMemoryMiddleware` has no memory key, section or effect.

The specs are, in the new module `llm4s-agent-memory`: `SemanticMemoryMiddlewareSpec` (through `Agent`: recall
shared by a tenant's threads and never across tenants, the first model call seeing recall, crash and `recover`
after a record and in the middle of a consolidation, a replayed record not resurrecting what another thread
consolidated, record plus two consolidation groups in one `afterAgent`, the bound with consolidation off, a blocked
answer not recorded, accounted manager calls, unsupported stores, failures skipped and cancellations not, the
structural fingerprint, the guide's example), `MemoryInternalsSpec` (the manager's view and the tenant cell) and
`{InMemory,Sqlite,Unverifiable}MemoryReplayContractSpec` (C4's `ReplayContract` over the guarded write path). In
`llm4s-memory`: `TransactionalMemoryStoreContract` (applied keys, fencing, bounds, eviction order, atomic `replace`),
run over `InMemoryStore` and `SQLiteMemoryStore` (`InMemoryTransactionalMemoryStoreSpec`,
`SqliteTransactionalMemoryStoreSpec`, which also opens a version-1 file), `AppliedWriteSpec`, and the changed
`LLMMemoryManagerSpec` (one `replace` per group). In `llm4s-memory-postgres`: `PostgresTransactionalUnitSpec`, the
transactional methods over a fake JDBC connection. In `modules/it` (`@Docker`): `PostgresTransactionalMemoryStoreSpec`,
the contract over a real `PostgresMemoryStore`, plus two stores on one table writing at once within one bound.

## Placement and the C3 decision

- **A new module, `llm4s-agent-memory`** (`modules/agent-memory`), depending on `llm4s-agent` and `llm4s-memory`,
  as the spec's Placement says: `llm4s-memory` depends on core only, and `llm4s-agent` does not depend on it.
  Package `org.llm4s.agent.harness.memory`.
- **The store contract stays in `llm4s-memory`, with no agent type in it.** The spec wrote
  `MemoryStore.applyAtomically(key: EffectKey, ...)`, but `EffectKey` and `FencingToken` are `llm4s-agent` types,
  and `llm4s-memory` must not depend on the agent runtime. So `llm4s-memory` gets its own small vocabulary
  (`AppliedWriteKey(scope, value)`, a `Long` token) and `llm4s-agent-memory` adapts C4's `EffectKey` and
  `FencingToken` to it, one line each (`MemoryEffects.keyOf`). The fencing semantics are C4's, unchanged.
- **F7 stands alone; it does not build on C3's `LongTermStore`.** C3 (#1904, §4.25 in [#1930](https://github.com/llm4s/llm4s/pull/1930), not merged)
  defines `LongTermStore` and `Namespace(tenant, path)` for `/memories/` files: a key-value store of JSON items
  with substring search. The spec's slice map has F7 depend on C1 and C4 only, and puts its writes in
  `MemoryStore.applyAtomically`. A semantic memory needs what `llm4s-memory` already has and `LongTermStore` lacks:
  typed `Memory` values, importance, filters, keyword and embedding search, and the managers (`LLMMemoryManager`'s
  extraction and consolidation). So F7 uses `MemoryStore`, and needs nothing from C3. The two meet in two places,
  both designed so that F7 adopts C3 once it lands without an API change:
  - **Tenant scope.** C3 scopes a namespace by `Namespace(tenant, path)`. F7 scopes by resolving one store per
    tenant (`stores: Option[TenantId] => Result[MemoryStore]`). A `LongTermStore`-backed `MemoryStore`, if one is
    ever wanted, is a resolver `tenant => adapter(store, Namespace(tenant, Vector("memory")))`.
  - **Refusals.** C3's `BackendRefused.toolOutcome` maps refusals for tools. F7 has no tool: its effects run in
    boundary hooks, so it needs no mapping (below, "Failures").

## API

In `llm4s-memory`, package `org.llm4s.agent.memory`, all `@Experimental`:

- `final case class AppliedWriteKey(scope: String, value: String)`: one applied write's identity. `scope` is the
  fencing scope (one per thread), `value` the key itself (which already includes the thread).
- `final case class AppliedWrite(added: Vector[MemoryId], removed: Vector[MemoryId], evicted: Int)`: what one applied
  write did, with `toJson` and `fromJson` (ujson), which the SQL stores persist. Evictions are a count, so an outcome
  is bounded by the write's own size (rule 12), never by the store's.
- `final case class MemoryBounds private (maxMemories: Int, maxBytes: Long)`: `apply(maxMemories = 1000, maxBytes =
  4 MiB)`, `withMaxMemories`, `withMaxBytes`, both at least 1 (`require`). `sizeOf(memory)` is the UTF-8 bytes of its
  content and of its metadata keys and values. `overflow` picks the memories to evict from a store's entries.
- `trait TransactionalMemoryStore extends MemoryStore`, each method one transaction, fenced as C4's `AppliedKeys`:
  - `applyAtomically(key, token, add, remove, bounds): Result[(TransactionalMemoryStore, AppliedWrite)]`: stores
    `add`, deletes `remove`, evicts beyond `bounds`, and records `(key, outcome)`; for a key already applied, returns
    the recorded outcome and writes nothing. A replacement whose `remove` is partly gone already writes nothing
    (it is superseded) and records an empty outcome.
  - `appliedWrite(key, token): Result[(TransactionalMemoryStore, Option[AppliedWrite])]`: the recorded outcome, read
    under the fence.
  - `forgetApplied(key, token): Result[TransactionalMemoryStore]`.
  - `appliedWriteCount: Result[Int]`.

  Each returns the store to use next, because `InMemoryStore` is immutable: its applied writes and fencing tokens are
  part of its value. The SQL stores return themselves.
- `MemoryStore.replace(add, remove): Result[MemoryStore]`, new, with a default that stores then deletes, atomic for a
  store that returns a new value (`InMemoryStore`); `SQLiteMemoryStore` and `PostgresMemoryStore` override it as one
  transaction.
- Implemented by `InMemoryStore`, `SQLiteMemoryStore` and `PostgresMemoryStore`.

In `llm4s-agent-memory`, package `org.llm4s.agent.harness.memory`, all `@Experimental`:

- `final class SemanticMemoryMiddleware(stores, manager, client, recall, record, consolidate, bounds, clock, runsBefore,
  id)`:
  - `stores: Option[TenantId] => Result[MemoryStore]`, resolved once per tenant.
  - `manager: (MemoryStore, LLMClient) => MemoryManager`, built for each hook call.
  - `client: LLMClient`, which the middleware wraps with `context.accounted` before every hook call.
  - `recall: Option[MemoryRecall] = Some(MemoryRecall())`.
  - `record: Option[MemoryRecording] = Some(MemoryRecording())`.
  - `consolidate: Option[MemoryConsolidation] = None`.
  - `bounds: MemoryBounds = MemoryBounds()`.
  - `clock: Clock = Clock.systemUTC()`, which consolidation reads its cut-off from.
  - `runsBefore: Set[MiddlewareId] = Set.empty`.
  - `id: MiddlewareId = MiddlewareId("semantic-memory")`.
  - `withStore(tenant)(f)`: `f` on the tenant's store under the tenant's lock.
- `MemoryRecall private (maxRecallTokens: Int, filter: MemoryFilter)`: `apply(1024, MemoryFilter.All)`, `with*`.
- `MemoryRecording private (maxRecordChars: Int)`: `apply(2000)`, `withMaxRecordChars`.
- `MemoryConsolidation private (olderThan: FiniteDuration, minCount: Int)`: `apply(1.day, 10)`, `with*`.
- `SemanticMemoryMiddleware.RecalledKey: StateKey[String, String]`, a replace key with id `semantic-memory-recalled`
  and initial value `""` ("nothing recalled").
- `object MemoryEvents`: durable `MemoryRecorded(added, evicted)` (`memory.recorded`, v1),
  `MemoryConsolidated(groups, removed, evicted)` (`memory.consolidated`, v1) and `MemorySkipped(operation, error)`
  (`memory.skipped`, v1), where `operation` is `memory.recall`, `memory.record`, `memory.consolidate` or
  `memory.resolve` and `error` the error type's simple name.

The three settings types are growth-prone (CLAUDE.md): private constructors, `apply` with the defaults, `with*`.

## Decisions

### Tenant scope (rule 8)

- **One cell per tenant, not per thread.** The middleware keeps a map from `Option[TenantId]` to a `TenantMemory`
  cell, built on first use by calling `stores(tenant)`. A cell holds the tenant's current store and a lock; every
  access to the store - each write (an applied write, a `forget`) and each read a manager makes through its view -
  runs under the lock, so one tenant's updates are serialised and no read overlaps a write. A store need not be
  thread-safe: `SQLiteMemoryStore` is one JDBC connection. `withStore(tenant)(f)` gives an application the same
  access (tested: concurrent turns over a store that fails any overlapping call). A
  failed resolution is not cached: the next turn resolves again.
- **No two tenants share a store instance.** A resolver that returns, for a new tenant, a store instance a cell of
  another tenant already holds is refused (`ValidationError`). That catches the commonest misconfiguration, one
  store for everyone. A resolver that opens two connections to one file or table is not caught; the guide says a
  resolver must return a store scoped to the tenant. The spec allowed instead "a store filtered by a tenant tag";
  that cannot work with the managers, whose consolidation recalls every old memory of the store, so it is not
  offered.
- **The manager is built for each hook call** from a view of the tenant's cell (below) and
  `context.accounted(client)`. Every call an `LLMMemoryManager` makes - entity extraction while recording, the
  summary of each consolidation group - is therefore counted in the thread's `usage` (rule 11), though the manager's
  API returns no `Completion`.
- **Every thread of a tenant recalls what earlier threads of that tenant recorded**, because they share the cell.
  `recover` and a restarted process resolve the store again; for a durable store (SQLite, Postgres) that is the same
  data.

### The manager's view of the store

The manager is given a `MemoryView` over the cell, not the store itself, so that every write it makes goes
through one of the slice's effects:

- **Reads** go to the cell's current store.
- **`store` and `storeAll`** are buffered in the view, which the manager returns inside its updated manager. The
  middleware applies the buffered memories as one effect (recording).
- **`replace(add, remove)`** is performed at once, as one consolidation effect, and the view goes on over the
  updated store.
- **Every other write** (`delete`, `deleteMatching`, `update`, `clear`) is refused (`ValidationError`), so a manager
  cannot change the store behind the effects. The two managers in `llm4s-memory` use none of them once
  `consolidateGroup` uses `replace`.

### Recall (`beforeAgent`)

- Resolves the tenant's cell, then runs `getRelevantContext(input, maxRecallTokens, filter)` on the turn's input.
- The text is cut at `maxRecallTokens * 4` characters (C1's four characters a token), on a code-point boundary
  (rule 12).
- It is written to `RecalledKey` with the input task's update, so the turn's first model call shows it (rule 3) as the
  prompt section `semantic-memory`, "Relevant memories from earlier conversations:" and the text. The section is cut to
  the same bound again whatever is stored, and is omitted when the text is empty.
- **The recall serves its turn only.** When recall finds nothing, `beforeAgent` removes the key's entry
  (`StateUpdate.remove`) rather than storing `""`; and `afterAgent` removes it as the turn ends. So one turn's recall
  never shows in the next, and **a thread at rest holds no entry for the key** - which is what lets C5 (§4.29) restore
  it whether the middleware is added or removed (rule 7). A turn that ends at the step limit, without `afterAgent`,
  keeps its recall until the next turn's `beforeAgent` replaces it.
- After a crash before the input task commits, the task runs again and recalls again. Nothing has used the result,
  so that is harmless (rule 4). A Block restores the key (C1).
- **A failure to resolve the store, or a configuration the store cannot support, refuses the input**: `beforeAgent`
  returns the `Left`, which the loop treats as an input Block. That happens before any model call, and names the
  problem (a resolver error, a shared store, consolidation on a store that is not transactional). The store is
  resolved in `beforeAgent` even with recall off, so a misconfiguration is found there and not after the answer.
- **A failure of the recall itself** (the store's search failed) is not a Block: the turn goes on with no recall,
  and the middleware emits `MemorySkipped("memory.recall", <error type>)`.

### Record (`afterAgent`)

- **One effect per turn, `Transactional` where the store is.** The key is
  `context.run.effectKey("memory.record", <the turn's user message id>)`. The user message id (`<input task id>/user`)
  names the turn, and the finish task's `taskKey` is stable across `recover`, retries and a resumed question (§4.24).
- **The effect runs the manager.** Inside `ReplayGuard.transactional(context.run, key, cell)`, given the run's token:
  1. `appliedWrite(key, token)`: a key already applied returns its recorded outcome, and nothing else runs;
  2. otherwise the manager records the turn - `recordConversation(Seq(UserMessage(query), AssistantMessage(answer)),
     threadId)` on a view - and the view's buffered memories are each cut to `maxRecordChars` code points;
  3. `applyAtomically(key, token, those memories, Nil, bounds)` writes them, evicts beyond the bounds and records
     the outcome, in one transaction.

  So a replay of a completed record returns the stored outcome without running the manager; a replay of a begun one
  whose first attempt applied returns the store's recorded outcome without running the manager either; only an
  attempt that never applied runs the manager again. A replay **cannot re-insert a memory a later consolidation
  removed**: its key is applied, so it gets the outcome, not the write (tested).
- **The query** is the content of the last user message of the thread (`Messages.key`), the input as `beforeAgent`
  left it.
- **Unsupported stores.** A store that is not a `TransactionalMemoryStore` (`VectorMemoryStore`,
  `EmbeddingMemoryStore`, a store of the application's own) records through `ReplayGuard.unverifiable` (not
  idempotent): a replay of a record that began and never completed is refused rather than run twice. Its bound is
  enforced under the cell lock, by a store, then a recall and a delete of the overflow; that is serialised in the
  process, but not one transaction.

### Consolidation (`afterAgent`, after recording)

- When `consolidate` is set, the manager runs `consolidateMemories(clock.instant() - olderThan, minCount)` on a
  view.
- **`LLMMemoryManager.consolidateGroup` changes** from "store the summary, then delete the originals one by one"
  (`LLMMemoryManager.scala:236-241` before this slice) to one `store.replace(Seq(summary), group ids)`. On the view
  that is **one effect per group**, keyed `context.run.effectKey("memory.consolidate", <the group's source ids,
  sorted>*)`, performed by `ReplayGuard.transactional` with `applyAtomically(key, token, Seq(summary), sourceIds,
  bounds)`.
- So one `afterAgent` that records and consolidates several groups performs distinct effects that never suppress
  each other (tested: a record and two groups in one turn all apply). A replay of a group returns its recorded
  outcome: it cannot consolidate a different set, because a different set has a different key.
- **Two writers consolidating the same memories.** `applyAtomically` treats `remove` as what `add` replaces: if any
  source is no longer in the store, it writes nothing and records an empty outcome. So two threads of a tenant that
  formed the same group at once never both store a summary; the second finds its sources gone (tested in the store
  contract).
- **After a crash in the middle**, `recover` runs the finish task again. Groups that applied are gone from the store,
  so the manager no longer forms them; a group that had not applied has the same sources and so the same key, and
  applies now. The store ends with exactly the consolidated set (tested).
- **Unsupported stores.** Consolidation on a store that is not transactional is refused when the store is resolved
  (above): it would delete originals with no applied key to replay.
- The summary's model call is made before the guard, inside the manager: a replay of a group that already applied
  calls the model again (accounted, rule 11), then gets the recorded outcome and writes nothing.

### Bounds (rule 12), whether or not consolidation is on

- **Each recorded memory** is cut at `maxRecordChars` code points before it is written, and so is each consolidation
  summary (which `LLMMemoryManager` already caps at 2000 characters), with the default when `record` is `None`.
- **Each tenant's store** keeps at most `maxMemories` memories and `maxBytes` bytes (`MemoryBounds.sizeOf`). The
  same `applyAtomically` that adds memories evicts, in the same transaction, the memories of lowest importance
  (a memory with none counts as 0.5), oldest first, until both bounds hold. So the bound needs no consolidation, and
  holds under concurrent threads of the tenant (serialised by the cell lock and, for SQL stores, the transaction;
  `PostgresMemoryStore` also takes a transaction-scoped advisory lock on its table, so processes sharing it are
  serialised too). A store that already holds more than the bound when the middleware first writes is brought within
  it by that first write.
- The in-memory cell holds that bounded store.

### Order

The middleware should run outside guardrail middleware: earlier in stack order, or with `runsBefore =
Set(MiddlewareId("guardrails"))`. `afterAgent` runs in reverse stack order and the first `Left` stops the fold
(`MiddlewareStack.scala:40-43`), so an inner guardrail that blocks the answer stops the fold before this
middleware's `afterAgent` runs: **a blocked answer is never recorded** (tested). `runsBefore` names middleware
that must be registered in the same stack, so it cannot default to the guardrails' id; P1's profile fixes the
order.

### Failures

A boundary hook cannot fail its task: the loop treats a `beforeAgent` or `afterAgent` `Left` other than a
cancellation as a Block (`ToolLoop.boundary`), and a Block on the answer would retract it because memory could not
be written. C4's rule "a hook maps a non-refusal `Left` to `NodeResult.Fail`" therefore has no boundary-hook form
today. So in `afterAgent`:

- A **cancellation** is returned as the `Left`, and fails the task as any cancelled hook does.
- **Anything else** - a store failure, a refusal by the guard (`EffectReplayRefused`), a model failure inside the
  manager, a lost claim - is skipped: the answer is kept, and `MemorySkipped(operation, <error type>)` is emitted.
  The guard has already done what C4 requires: the effect record is *begun* or absent, and the target's applied key
  is the evidence. If the process dies, the finish task has not committed, so `recover` runs it again and the guard
  replays from that evidence (tested: crash after the record's effect, and after its outcome). If the process lives,
  the finish task commits, which ends the replay window: a write that applied stays applied (once); a write that did
  not is lost, never repeated. At most once, as the guard guarantees, and announced.

## Where the spec was imprecise or wrong about the code

- **`applyAtomically` takes no `EffectKey`** (above): `llm4s-memory` cannot see agent types. It also takes the
  fencing token, which C4 added after the spec was written (§4.24, "The target fences itself by the claim token"),
  and the bounds, since eviction is in the same transaction. It is on a sub-trait, `TransactionalMemoryStore`, not
  on `MemoryStore`, so a store that cannot do it is known by its type rather than by a runtime refusal.
- **The resolver returns `Result[MemoryStore]`**, not `MemoryStore`: opening a SQLite file or a Postgres pool can
  fail, and CLAUDE.md asks for `Result` over a throw.
- **`consolidateGroup` uses `replace`, not `applyAtomically`.** The manager is in `llm4s-memory` and knows no effect
  key; `replace` is the atomic operation it can name, and the middleware's view turns each `replace` into one
  `applyAtomically` with the key. A manager used outside the middleware gets an atomic `replace` from the store.
- **The spec's "the store the manager returns is put back in the cell"** holds through the view: the cell is updated
  by the applied writes the view performs, so whatever the manager returns, the cell holds the store those writes
  produced.
- **The bounds are a constructor argument (`MemoryBounds`)**, not part of `record`: consolidation writes too, and the
  bound holds for both.

## Runtime rules

1. **One batch, one snapshot.** Not applicable to the hooks: `beforeAgent` and `afterAgent` run in single-task steps.
   The store is outside thread state, so the snapshot does not matter to it; concurrent threads of one tenant are
   serialised by the cell lock and the store's transaction (tested: two threads recording into one tenant at once,
   bound held).
2. **An update function that fails, fails the run.** `RecalledKey` is a replace key, whose update is total. Every
   refusal is decided while the hook runs.
3. **Visible from the next superstep.** Recall writes `RecalledKey` with the input task; the model step's
   `promptSections` reads it from that committed snapshot, so the turn's first model call shows it (tested on the
   request the model was sent).
4. **At least once.** Recall reruns harmlessly. Each recording and each consolidation group is one C4 effect, keyed by
   `run.effectKey` from the finish task's `taskKey`, the operation and what it touches (the turn's user message id,
   or the sorted source ids), never by run id, checkpoint id or token. The store records `(key, outcome)` with the
   write and fences by the claim token per `key.scope`, keeping the newest token per scope; it removes an applied
   key only in `forgetApplied` (called by the guard through `AppliedKeys.forget`). `ReplayContract` passes over the
   in-memory and SQLite stores, `Transactional`, including both stale-claimant cases, and over a plain store,
   `Unverifiable`. Tested through `Agent`: a crash after the record's effect and after its outcome, then `recover`,
   leaves exactly one copy; a crash in the middle of a consolidation, then `recover`, leaves exactly the
   consolidated set.
5. **Block.** An output Block restores `RecalledKey` (C1). A blocked answer is never recorded when the middleware
   runs outside the guardrails (Order). An effect that applied before a Block - a record, when the middleware runs
   inside a guardrail - stays applied: C4 cannot undo an external effect, and the guide says so.
6. **Full snapshots.** A checkpoint taken during a turn holds one copy of `RecalledKey`, at most
   `maxRecallTokens * 4` characters (rule 12); a settled one holds none, as the key is removed when the turn ends. The
   store is outside checkpoints.
7. **Restore through codecs, and restore compatibility.** `RecalledKey` is a new `String` key at
   `SchemaVersion.initial`. It is registered only by an agent family with a `SemanticMemoryMiddleware`, so an agent
   without one keeps its structural fingerprint and its threads (tested). **Under C5 (§4.29):** adding the
   middleware adds the key, whose initial value means "nothing recalled", so a thread at rest restores into the
   agent that added it (tested through `Agent` and through a reopened SQLite checkpoint, `SqliteMemoryEvolutionSpec`).
   Because a thread at rest holds no entry for the key, it also restores after the middleware is removed (tested).
   As for every change of family, a thread in flight - suspended, or `Running` after a crash - is refused by the
   agent that added the middleware (tested): resume or recover it first. A thread last checkpointed before C5 records
   no shape and restores only into its own version, as C5 says for every feature. The SQLite
   memory store's new tables (`memory_applied_writes`, `memory_fences`) are created with `CREATE TABLE IF NOT
   EXISTS` when the store opens, and its schema version moves to 2, so an existing file opens and gains them; the
   Postgres store creates `<table>_applied` and `<table>_fences` the same way; its table name is now at most 55
  characters, so those names and its index names stay distinct within PostgreSQL's 63-byte identifier limit. `AppliedWrite`'s JSON carries a format
   version (1), and a newer one is refused.
8. **Tenant.** Above: one store per tenant, resolved by `RunContext.config.tenantId`, held in one cell per tenant,
   never shared by two tenants (an identical instance is refused). Tested: two threads of one tenant share recall;
   two tenants do not. C4's effect keys include the thread, so two threads of one tenant never confuse their applied
   keys.
9. **No content in durable events.** `MemoryRecorded`, `MemoryConsolidated` and `MemorySkipped` carry counts, the
   operation name and the error's type name, never memory content or an error message (tested on the stored events).
   Recalled text is in state; memories are in the store.
10. **A failed task commits nothing.** A failed input task commits no `RecalledKey`; its rerun recalls again. A failed
    finish task commits no event; its effects are replayed from C4's records by `recover`. The usage of a manager's
    calls in a failed task goes on `RunFailed` (C1).
11. **Every model call accounted.** The manager gets `context.accounted(client)`, so `LLMMemoryManager`'s
    extraction and consolidation calls are counted (tested: `usage.requestCount` includes them). Embedding calls an
    `EmbeddingMemoryStore` makes are not model calls through an `LLMClient` and are not counted; that is a limit
    below.
12. **Bounded, measured on what is kept or sent.**
    - `RecalledKey` and the section: `maxRecallTokens * 4` characters, cut on a code point, and the section clamps
      a longer stored value. With the default, 4 096 characters, about half of C1's default section budget.
    - Each recorded memory: `maxRecordChars` code points of content.
    - Each tenant's store: `maxMemories` memories and `maxBytes` bytes, enforced in the transaction that adds
      (tested with consolidation off, and under concurrent threads).
    - Each applied write's outcome: ids of what it added and removed (bounded by the write) and an eviction count.
      Applied keys: C4's bound (effects in flight, plus one per crash between effect and `forget` in a task never
      replayed).
    - Each fencing record: one `(scope, token)` per thread that wrote, kept as long as the store keeps data, as C4
      says.
    - In process: one cell per tenant, holding the bounded store. The number of tenants is the application's.
13. **Every type defined.** Above: `AppliedWriteKey`, `AppliedWrite`, `MemoryBounds`, `TransactionalMemoryStore`
    and `MemoryStore.replace` in `llm4s-memory` (`org.llm4s.agent.memory`); `SemanticMemoryMiddleware`,
    `MemoryRecall`, `MemoryRecording`, `MemoryConsolidation`, `MemoryEvents`, `MemoryRecorded`,
    `MemoryConsolidated` and `MemorySkipped` in `llm4s-agent-memory` (`org.llm4s.agent.harness.memory`). Internal:
    `TenantMemory` (the cell, an `AppliedKeys`), `MemoryView`, `MemoryEffects`. Codecs: `RecalledKey` (`String`),
    the three event payloads (`derives ReadWriter`), `AppliedWrite` (its JSON, and a `ReadWriter` over it for the
    guard's outcome).

## Source breaks

- `MemoryStore` gains `replace`, with a default: no implementation breaks.
- `LLMMemoryManager.consolidateGroup` calls `replace`, so a store of the application's own that overrides `store`
  and `delete` but not `replace` gets the default: the same writes as before, in the same order.
- `InMemoryStore` keeps applied writes and fencing tokens in its value; `clear()` keeps them (C4: applied keys are
  removed only by `forget`).
- `SQLiteMemoryStore.SchemaVersion` is 2.

## Limits

- An `EmbeddingMemoryStore`'s embedding calls are not counted in `usage`: they are not `LLMClient` calls, and
  `EmbeddingService` has no accounted form.
- The buffered view does not show the manager its own buffered writes: a manager that reads back what it just
  stored in the same call does not find it. The managers in `llm4s-memory` do not.
- A replay of a consolidation group that already applied repeats the summary's model call before the guard returns
  the recorded outcome.
- A resolver that hands two tenants two handles on one database is not detected.
- A turn that ends at the step limit keeps its recall in the key until the next turn, so a thread left there is
  refused by an agent that removed the middleware.
- With the middleware inside a guardrail, a blocked answer has already been recorded when the guardrail blocks; the
  record is not undone.
