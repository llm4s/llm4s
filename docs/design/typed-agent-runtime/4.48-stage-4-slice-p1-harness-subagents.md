# 4.48 Stage 4 slice P1: subagents in the harness profile ([#2052](https://github.com/llm4s/llm4s/issues/2052))

Part of the [Typed Agent Runtime design](../typed-agent-runtime-design.md), §4. Section numbers (§N.N) refer to that document and its [slice records](../typed-agent-runtime-design.md#slice-records). Phase 4 spec: `docs/superpowers/specs/2026-10-19-phase-4-subagents-design.md`, "P1".

Slice P1 of [#2044](https://github.com/llm4s/llm4s/issues/2044). D1 (§4.44) and D2 (§4.45) let any agent delegate to
`TypedAgent` subagents with `AgentBuilder.withSubagents`. P1 makes subagents part of the harness (§4.37): a
`HarnessProfile` carries a `SubagentConfig`, `HarnessProfile.deepAgents` turns on a general-purpose subagent whose grant
is written in the preset, and `HarnessConfigLoader` reads the bounds from `reference.conf`.

Everything is in `llm4s-agent`: the config types in `org.llm4s.agent.harness` (`SubagentConfig.scala`), the assembly in
`AgentBuilder` and `TypedAgent.bindUnder`, the loader in `org.llm4s.config.HarnessConfigLoader`. The new public types
are `@Experimental`. The specs are `HarnessSubagentsSpec` (through a parent's runs and plans, on D1's routing fake
client) and new cases in `HarnessConfigLoaderSpec`. The guide is "Subagents in a harness" in
`docs/guide/agents/delegation.md`.

## API

In `org.llm4s.agent.harness`:

- `final case class SubagentConfig private (generalPurpose: Option[GeneralPurposeConfig], specialists:
  Vector[TypedAgent[?, ?]], delegation: DelegationConfig)`, growth-prone: `apply` defaults `None`, empty,
  `DelegationConfig.default`; `withGeneralPurpose` (value or `Option`), `withSpecialists(agents*)` (replacing),
  `withDelegation`; `offersAny`. `SubagentConfig.none` (no subagents) and `SubagentConfig.deepAgents` (the
  general-purpose subagent at its defaults).
- `final case class GeneralPurposeConfig private (description: String, systemPrompt: PromptMode, model:
  Option[(LLMClient, CompletionOptions)], inheritance: Inheritance)`, growth-prone: `apply` defaults
  `DefaultDescription`, `PromptMode.Suffix(DefaultPromptSuffix)`, `None`, `DefaultInheritance`; a setter per field.
  `GeneralPurposeConfig.Id` is `general-purpose`.
- `HarnessProfile.subagents: SubagentConfig` and `withSubagents(SubagentConfig)`. `HarnessProfile()` has
  `SubagentConfig.none`; `HarnessProfile.deepAgents` has `SubagentConfig.deepAgents`. `apply` gains the parameter with
  its default, and the previous `apply` stays as an overload without defaults that forwards with `SubagentConfig.none`.

`reference.conf`: `llm4s.agent.harness.subagents { generalPurpose.enabled, maxConcurrentChildren, maxTasksPerTurn,
maxDepth, maxReportBytes, childRetention }`, defaults `true` and `DelegationConfig.default`'s.

## Decisions

- **The general-purpose subagent** is `TypedAgent.text("general-purpose", description)` with a harness of its own, the
  minimal profile (`HarnessProfile()`, so the file tools over a new `StateFileBackend`) with `systemPrompt`, and the
  config's `inheritance` and `model`. It reaches the parent model through the shared `task` tool, in the Deep Agents
  shape `{subagent_type, description}`.
- **Its grant is computed at `build()` from the parent's actual tools.** `DefaultInheritance` is
  `Inheritance(tools = ToolGrant.AllExcept(FileTools.Names + "execute"))`, no middleware, no delegation, the parent's
  limits. When the agent is assembled, an `AllExcept` on the general-purpose subagent is narrowed to the names the
  parent has (`names intersect parentTools`), so D2's refusal of an absent name never fires for it, and a `deepAgents`
  agent builds with or without a sandbox. This applies to any `AllExcept` the application gives it, not only the
  default: withholding a tool the parent lacks is harmless, as `ToolSelection.Except` naming `execute` without a
  sandbox is (§4.37). An `Only` grant is checked as for every subagent. The parent's tools are its harness's, its own
  and those it was granted, the set D2's `ParentScope.tools` grants from; middleware tools (`write_todos`, the task
  tools) are never granted.
- **Why withhold the file tools and `execute`.** Its own harness brings file tools over its own backend; the parent's
  would clash by name, and over a state backend they would see the child's empty files anyway. `execute` is the
  parent's sandbox, a capability the preset does not hand on silently. An application grants it with its own
  `inheritance`.
- **Assembly.** `AgentBuilder.effective` binds the profile's subagents (the general-purpose one, then the specialists)
  before the builder's `withSubagents`, into one `delegation` middleware. With a harness it goes inside the harness's
  `PermissionMiddleware` and outside the harness's other middleware (and the builder's own); without one, innermost as
  before. Every middleware's `wrapToolCall` wraps every tool call whatever its position, so a permission rule decides
  each `task` call by its `(Invoke, task:<id>)` resource either way: with rules, `task` needs an `Invoke` rule, as
  `write_todos` does.
- **One source for the bounds.** With a harness, `SubagentConfig.delegation` bounds every subagent of the agent, and
  `AgentBuilder.withDelegation` beside a harness is refused at `build()`, as `withSystemPrompt` is, so the bounds have
  one source. Without a harness `withDelegation` is unchanged. The profile's bounds are checked by `assembled` and by
  `checkedBeforeSandbox`, so `HarnessConfigLoader` refuses a bad one at the edge (`harness.subagents`).
- **A child's harness subagents follow rule 15.** A `TypedAgent` with a harness that offers subagents (a specialist
  `withHarness(HarnessProfile.deepAgents)`, say) gets them only when its inheritance grants delegation and depth allows;
  otherwise `bindUnder` installs its harness with `SubagentConfig.none`. When it delegates, its harness's bounds are
  replaced by the tree's (`scope.config`), as a child's own subagents are bounded by the root's.
- **Prompt.** `HarnessProfile.defaultPrompt` gains a delegation part when `subagents.offersAny`: delegate independent,
  bounded work; a self-contained description; independent tasks in one message so they run in parallel; only the
  report comes back; verify it before relying on it. The `delegation` middleware's own section still lists each
  subagent's id and description. The preset's prompt stays under its 1,000-token bound (`HarnessProfileSpec`).
- **The general-purpose subagent's prompt** is its harness's default plus `DefaultPromptSuffix`, which tells it that
  its final answer is the whole report and its files are its own.
- **Graph version.** The task tools' specs were already covered (§4.44); two builders of one id compare their harness
  `SubagentConfig`s too (`delegatesAs`), as they compare their own subagents.
- **The Stage 3 deep-research sample** sets `SubagentConfig.none`: it is a one-agent example with permission rules that
  name no `task`, and P2 (§4.49) adds the parallel-specialist version beside it.

## Where the spec was imprecise

- **"That order is declared with `placement`".** `Placement` (§4.37) is for an order a middleware's correctness depends
  on, and the stack refuses every other. The `delegation` middleware has no hook an order changes: only tools and a
  prompt section, like skills, instructions and todos, which §4.37 found free of an order requirement. Declaring one
  would also refuse a supported stack: a builder's `TodoMiddleware` with builder-level subagents, where `delegation`
  is innermost. So the order is fixed by `withHarness`'s assembly and tested (`HarnessSubagentsSpec`), not declared.
- **Config key names.** The spec wrote `general-purpose.enabled, max-concurrent-children, ...`; the harness block uses
  camelCase throughout (`maxTodos`, `keepRecent`), so the keys are `generalPurpose.enabled`, `maxConcurrentChildren`,
  `maxTasksPerTurn`, `maxDepth`, `maxReportBytes`, `childRetention`.
- **`withGeneralPurpose`** is on `SubagentConfig`: `profile.withSubagents(profile.subagents.withGeneralPurpose(...))`.
- **How the profile's and the builder's subagents combine** was unspecified: the profile's first, one `delegation`
  middleware, the profile's bounds. Those bounds are the agent's resolved `DelegationConfig` for the handoff-family
  check (§4.44, #2089): a harness agent always sets bounds, so every other agent of its family must set the same or
  none.

## Runtime rules

Phase 3's rules 1-13 and Phase 4's 14-19:

1. **One batch, one snapshot.** Unchanged from D1/D2: parallel `task` calls to the general-purpose subagent each see the
   parent's snapshot; each child has its own `StateFileBackend` state, so parallel children share no files.
2. **Total updates.** No new state key; the `task` tools write no parent key.
3. **Visibility.** Unchanged: a report reaches the parent model as the call's tool message in the next step.
4. **At least once.** Unchanged: a replayed `task` call reads the child thread first (rule 14).
5. **Block.** Unchanged; the general-purpose child's files are thread state on its own thread, outside the parent's.
6. **Full snapshots.** The parent's snapshot holds only the bounded tool result; the child's files are in the child's
   checkpoints, bounded by its own retention and child retention.
7. **Codecs.** No stored format changes.
8. **Tenant.** Unchanged: the child runs under the parent's tenant and principal, never part of a grant.
9. **No content in durable events.** No new event.
10. **A failed task commits nothing.** Unchanged.
11. **Every model call accounted.** Unchanged: the child's usage rolls up once (K2).
12. **Bounded.** The profile's `DelegationConfig` bounds every limit; `reference.conf` sets them, and a bound that is not
    positive is refused at `build()` and by `HarnessConfigLoader` (tested).
13. **Types.** Every type named is defined here or in §4.37 and §4.41-§4.47.
14. **The child thread is the journal.** Unchanged.
15. **No capability without a grant.** `HarnessProfile()` offers no subagent; the general-purpose subagent's grant is
    written in the preset and shown by `DelegationPlan`; it never delegates; a child's harness subagents need
    `delegate` (tested).
16. **Identity inherited.** Unchanged: runtime, store, tracing, tenant and principal come from the parent.
17. **Only typed data crosses.** The general-purpose child's files stay on its thread; only its text report returns
    (tested).
18. **Supervision flows down.** Unchanged.
19. **Child threads driven only through their parent.** Unchanged.
