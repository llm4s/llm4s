# 4.44 Stage 4 slice D1: `TypedAgent[I, O]` and the `task` tools ([#2048](https://github.com/llm4s/llm4s/issues/2048))

Part of the [Typed Agent Runtime design](../typed-agent-runtime-design.md), §4. Section numbers (§N.N) refer to that document and its [slice records](../typed-agent-runtime-design.md#slice-records). Phase 4 spec: `docs/superpowers/specs/2026-10-19-phase-4-subagents-design.md`, "D1".

Slice D1 of [#2044](https://github.com/llm4s/llm4s/issues/2044), the first delegation slice. K1 (§4.41) gave a thread
an origin, and K2 (§4.42) runs a child on it under its parent's supervision. D1 is what an application writes: a
subagent's definition, `TypedAgent[I, O]`, offered to a parent's model through the `task` tools, with typed data the
only thing that crosses, and the bounds that keep a fan-out finite.

Everything is in `llm4s-agent`, in the new package `org.llm4s.agent.delegation`, apart from `DelegationContract`
(`llm4s-agent-testkit`), which the in-memory store and `SqliteCheckpointer` pass. The new public types are
`@Experimental`. The specs are `DelegationSpec` (the API through a parent's runs, on a routing fake client) and
`InMemoryDelegationContractSpec` / `SqliteDelegationContractSpec` (rule 14's table, row by row). The guide page is
`docs/guide/agents/delegation.md`.

## API

In `org.llm4s.agent.delegation`:

- `final class TypedAgent[I, O] private`, a definition holding clients and functions: `id`, `description`,
  `withSystemPrompt`, `withTools`, `withMiddleware`, `withHarness`, `withModel(client, options)`, `withMaxSteps`,
  `withInputText(I => String)`, `withFailure(ChildFailure)`, `bind(parentClient, runtime): Result[BoundAgent[I, O]]`.
  `TypedAgent(id, description, input: SchemaDefinition[I], output: SchemaDefinition[O])` and
  `TypedAgent.text(id, description): TypedAgent[TaskRequest, String]`.
- `final class BoundAgent[I, O]`: `id`, `definition`, `run(input, config = RunConfig()): Result[TaskOutcome[O]]`.
- `final case class TaskRequest(description: String)`, `enum ChildFailure { Report, Fail }`.
- `final case class ChildRef(threadId, runId, agent, toolCallId, depth)` with a `ReadWriter`.
- `enum TaskOutcome[+O] { Reported(report, child, usage), Refused(child, reason, usage), Suspended(child, status),
  NotStarted(agent, reason) }`: `NotStarted` is a refusal made before any child existed (D2 returns it for an
  exhausted budget); the `task` tools map it as they map `Refused`.
- `enum TaskRefusal { Blocked(guardrail, reason), StepLimitReached, TokenLimitReached, OutputInvalid(errors),
  Failed(message) }` with a `ReadWriter` and `describe`.
- `final case class DelegationConfig private (maxConcurrentChildren, maxTasksPerTurn, maxDepth, maxReportBytes,
  childRetention)`, growth-prone: `apply` defaults 4, 16, 1, 64 KiB, 64, and `with*` setters.

On `AgentBuilder`: `withSubagents(agents: TypedAgent[?, ?]*)` and `withDelegation(config)`.

`private[agent]`: `DelegationMiddleware` (id `delegation`) and `TaskTools`. A call runs its child through K2's
`ChildRunner.run(agent, origin, input, config, ctx, settleOnFailure)` (§4.42), with `settleOnFailure` set exactly under
`ChildFailure.Report`.

## Decisions

### One `task` tool, and one per typed input

As the spec's decision 2 settled: `task` (`{subagent_type: <enum of ids>, description}`) covers every subagent whose
input is a `TaskRequest`, in the Deep Agents shape, and each other subagent gets `task_<id>` with its own input schema,
because one tool with a union of schemas is poorly supported in strict mode. A subagent takes the `task` tool when it
is made with `TypedAgent.text`, or with `TypedAgent.apply` whose input codec is `TaskRequest`'s derived one (compared
by reference: a hand-written `TaskRequest` codec gives it its own tool). Each call's resource is
`(Invoke, task:<id>)`, so a `PermissionMiddleware` decides per subagent, as `write_todos` is decided (§4.37).

### The bounds, each on its own

- **Tasks per turn** are counted from the snapshot: the `task` calls in the current turn's assistant messages (from
  its user message), in message order, up to and including this call (the last call with its id, since a provider may
  reuse ids across steps). A call past `maxTasksPerTurn` is a tool error. The batch's calls are in the committed
  assistant message, so the count is exact and the same on every replay, whichever order the calls run in (rule 1).
- **Concurrency** is a fair semaphore of `maxConcurrentChildren` permits per parent run incarnation
  (`RunContext.incarnation`), held in a weak map so a finished run's goes with it, and acquired interruptibly: a
  cancelled parent stops waiting with `Fatal(CancelledError)`. A call over the bound waits, below the run's
  `maxConcurrency`, which already bounds the batch.
- **Depth** is `depth + 1 <= maxDepth`, where `depth` is how deep the delegating agent runs. An agent built with
  `AgentBuilder` delegates at depth 0. A child never has the `task` tools in D1 (it has only its own tools and
  middleware), so the check first matters when D2 grants delegation, and is tested on the middleware directly.
- **Report size** is the report's rendered JSON in UTF-8 bytes against `maxReportBytes`; a larger report is a tool
  error naming the child thread. Every other `task` tool message is bounded the same way, as the `{"error": ...}`
  message the loop stores: a refusal's or `NotStarted`'s reason is cut to fit, an `OutputInvalid` keeping as many of
  its first errors as fit and saying how many it dropped, a provider message cut on a code point and marked
  `(truncated)`. The full reason stays in the child's `RunOutcome` and in the typed `TaskOutcome`. So the parent's
  checkpoint never holds more than `maxReportBytes` per call (rule 6).
- **Child retention**: `DelegationConfig.childRetention` applies to the agent's runs whose config leaves
  `RunConfig.childRetention` at its default; a run that sets another value keeps it. Every agent of a handoff family
  makes children on the one thread, so the agent keeps the smallest bound any delegating builder of the family sets,
  a handoff target's included.

`build()` refuses a bound that is not positive, naming every one, as well as two subagents with one id and a subagent
that does not bind. A `task` tool name clashing with another tool is refused by the stack's existing clash check.

### The middleware is bound at `build()`

A subagent is compiled with its parent's client and runtime, which the builder resolves only in `build()` (a builder
without `withRuntime` gets a new in-memory runtime per build). So `build()` resolves the runtime once, and each
agent of the family binds its subagents to it in `loopAgent`; `DelegationMiddleware` is appended innermost to the
agent's stack, so the harness's `PermissionMiddleware` wraps every task call. The parent's graph version covers the
task tools' specs, computed from the definitions alone and added to the canonical settings only when the agent has
subagents, so the version of an agent without subagents is what it was. Two builders of one id in a handoff family are one agent
only if they also hold the same subagent definitions (as instances, in order) and the same bounds; otherwise
`build()` refuses them as two different builders, since the version alone cannot tell subagents apart behind equal
task tools.

### The child

A bound subagent is an `Agent` built from the definition: its own prompt, tools, middleware, harness, step limit,
response format (unless it is a text subagent) and the parent's runtime, so the child thread lives in the parent's
store (spec decision 7). It runs with the parent's tenant and principal (rule 16), the parent's budgets without the
timeout (the parent's cancellation and deadline reach the child through the interrupt; K2 caps the child's own
deadline), and the delegation's child retention. The child uses the parent's client with default options unless
`withModel` sets a client and options (D2 makes the inheritance of the parent's options visible in its plan).

### The default input text

A `TaskRequest`'s description, as it is. Any other input: `Task for subagent '<id>', as JSON:` and the input's JSON
with members sorted by key, so the same input renders the same message. `withInputText` replaces it.

### Mapping a child's end

`Completed(answer)` is `Reported` (a typed subagent's answer decoded as `O`), `Blocked`, `StepLimitReached` and
`TokenLimitReached` are refusals, `Suspended` is `TaskOutcome.Suspended`. A failed child is `Refused(Failed(message))`, except
`GraphError.OutputInvalid`, which is `Refused(OutputInvalid(errors))` with the whole vector (and, under `Fail`, that
error itself). A refusal's `usage` is the child thread's, a failed turn's model calls included. Under
`ChildFailure.Report` a refusal is a tool error naming the subagent, the child thread and the reason; under `Fail` it
is `Fatal` with the child's own error (or, for a status refusal, a `ProcessingError` with the same text), so the
parent run fails and `recover` replays the call. The runner is asked to settle a failed child
(`settleOnFailure`) exactly under `Report`, whose call commits; under `Fail` the child stays for the replay to
recover. `NotStarted` maps as `Refused` does, naming no child thread. Until D3, `Suspended` is a tool error and the child stays suspended.

### `BoundAgent.run`

Spec decision 10: it runs the subagent on a new top-level thread with a random id, named by the outcome's
`child.threadId` (depth 0, an empty `toolCallId`), which stays in the runtime until deleted. A typed answer that fails
its schema is `Refused(OutputInvalid)`; any other failure is `Left`.

## Where the spec was imprecise

- `withInheritance` is D2's: the spec lists it with "`Inheritance.none` until then", but a type with one value and no
  reader is speculative, so D1 ships without it and the child has only its own tools and middleware.
- `Refused` under `Fail` was "`Fatal(GraphError...)`". It is `Fatal` with the child's own error, which keeps a
  cancellation a cancellation, and a `ProcessingError` for a status refusal, which has no error.
- `ChildRef.runId` is the run that produced the outcome; a failed child whose runner returned no result names the run
  id the call gave it.
- The rule-14 rows are tested through the public behaviour (a parent's `recover` after its call failed before
  committing): D1 was written against a stand-in with K2's signature, and the same contract now checks K2's runner.
- The runner refuses a call whose child was started with other arguments (an edited call run again) or whose child id
  names a thread that is not its child, with a `ValidationError`. Running the call again cannot change that, so it is
  a tool error (`subagent '<id>' was not run: ...`, bounded by `maxReportBytes`); any other runner failure is `Fatal`.
  D3 may revisit edits.

## Runtime rules

Phase 3's rules 1-13 and Phase 4's 14-19:

1. **One batch, one snapshot.** A child is built from its call's arguments and the parent's configuration only; the
   per-turn count is read from the committed assistant message (tested in one batch and across steps). Parallel
   calls derive distinct child ids from their keys.
2. **Total updates.** The `task` tools write no parent state key; a refusal, an oversized report and a fan-out over
   its bound are tool errors decided when the tool runs.
3. **Visibility.** The report reaches the parent model as the call's tool message in the next model step; nothing a
   child does is visible to its siblings.
4. **At least once.** A task call runs again on `recover`; the child thread is the replay record (rule 14), and no
   `ReplayGuard` record is used.
5. **Block.** A Block in a child ends it `Blocked`, which the parent sees as a tool error (tested); child threads stay
   after a parent Block and are pruned by retention (K1).
6. **Full snapshots.** The parent's snapshot holds only the tool result, bounded by `maxReportBytes` (tested).
7. **Codecs.** No stored format changes. `ChildRef` and `TaskRefusal` have `ReadWriter`s for D3 and D4.
8. **Tenant.** The child runs with the parent's tenant and principal (tested: the child's checkpoints carry it, and
   another tenant cannot read them).
9. **No content in durable events.** No new event (D4 adds `TaskEnded`, without content).
10. **A failed task commits nothing.** A task call that fails commits nothing; the child keeps its own outcome.
11. **Every model call accounted.** A child's model calls are counted in the child's thread, and K2's runner adds
    the child's roll-up to the parent task's accumulator once, as the call commits.
12. **Bounded.** `maxConcurrentChildren`, `maxTasksPerTurn`, `maxDepth`, `maxReportBytes` and `childRetention`, each
    enforced on its own and each tested.
13. **Types.** Every type named is defined here or in K1/K2.
14. **The child thread is the journal.** `DelegationContract` checks every row through the public behaviour, on both
    stores: none starts the child; `Running` continues it from its checkpoint (its tool not run again); `Completed`
    and `Failed` return the stored report or refusal with no child model call; `Suspended` reports it suspended again
    with no child model call.
15. **No capability without a grant.** A child has only its own tools and middleware, never the parent's or the
    `task` tools (tested on the tools sent to the child's model).
16. **Identity inherited.** Tenant, principal, runtime and store come from the parent; tracing is D4's.
17. **Only typed data crosses.** The child's first user message is the rendered input alone, and the parent's thread
    holds only the tool result (tested).
18. **Supervision flows down.** The task call awaits its child; the parent's cancellation interrupts the call, which
    cancels the child (K2 tests this). The child's concurrency is the parent's.
19. **Child threads driven only through their parent.** Unchanged from K1; the `task` tools reach a child only through
    the child runner.

## Not in this slice

- Inheritance, grants, narrowing permissions, budgets and `DelegationPlan`: D2.
- Child suspension through the parent: D3.
- `TaskStarted` / `TaskEnded`, nested streams, parent ids in tracing: D4.
- Subagents in `HarnessProfile`: P1.
