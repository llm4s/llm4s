# 4.30 Stage 3 slice F3: todos ([#1907](https://github.com/llm4s/llm4s/issues/1907))

Part of the [Typed Agent Runtime design](../typed-agent-runtime-design.md), §4. Section numbers (§N.N) refer to that document and its [slice records](../typed-agent-runtime-design.md#slice-records). Phase 3 spec: `docs/superpowers/specs/2026-10-13-phase-3-harness-design.md`, "F3".

Slice F3 of [#1901](https://github.com/llm4s/llm4s/issues/1901), a feature slice on C1 (§4.22: `ModelContext`,
`promptSections`, a Block restoring every key the turn wrote) and C2 (§4.23: batch locks). It gives an agent a plan:
a `write_todos` tool that replaces the thread's todo list, a prompt section that shows the list to the model on
every model step, and events announcing each change. Everything is in `llm4s-agent`, package
`org.llm4s.agent.harness` (the harness package the C3 record settles), and is opt-in: an agent without
`TodoMiddleware` has no todo key, tool or section. The specs are `TodoMiddlewareSpec` (the middleware through the
tool loop: tool, section, bounds, events, Block, recover) and `AgentTodosSpec` (through `Agent`: streaming, the
checkpointed list, permission rules, the structural fingerprint).

## API

In `org.llm4s.agent.harness`, all `@Experimental`:

- `enum TodoStatus`: `Pending | InProgress | Done`, on the wire `"pending" | "in_progress" | "done"`: the strings the
  tool's schema offers and the stored value uses.
- `final case class Todo private (id: String, content: String, status: TodoStatus)`, with `apply`, `withContent` and
  `withStatus`. A growth-prone type (the rule in CLAUDE.md): a todo may gain fields (an active form, an owner).
- `final case class TodoList private (todos: Vector[Todo], nextId: Long)`, with `TodoList.empty`. `nextId` is the
  number the next new todo's id takes, so an id is never reused within a thread (below).
- `final class TodoMiddleware(maxTodos: Int = 50, maxTodoChars: Int = 200, id: MiddlewareId = MiddlewareId("todos"))`.
  Both limits must be at least 1 (`require`, as `AgentToolSpec.withTimeout` does). It contributes:
  - the tool `write_todos` (`TodoMiddleware.ToolName`), writing `TodoMiddleware.key`, locked on `LockKey("todos")`;
  - two prompt sections: `todos-guide`, cacheable, telling the model how to use the tool, and `todos`, the current
    plan, only when the list is non-empty.
- `TodoMiddleware.key: StateKey[TodoList, TodoList]`, a replace key with id `todos`. One key object for every
  instance, so two agents of one family that both plan share the thread's one plan, and a graph never sees two
  distinct keys with one id.
- `object HarnessEvents` with two event types:
  - `TodosUpdated` (`harness.todos_updated`, v1), durable: `TodosUpdated(todos: Vector[TodoMark])`, where
    `TodoMark(id: String, status: TodoStatus)`. Ids and statuses only (rule 9).
  - `TodosProgress` (`harness.todos_progress`, v1), live: `TodosProgress(todos: Vector[Todo])`, the whole list,
    content included.

Later harness slices add their events to `HarnessEvents`.

## Decisions

- **The tool replaces the whole list.** Its arguments are `{"todos": [{"id"?, "content", "status"}, ...]}`. The
  result is the new list: each item in the order given, every todo of the old list not named again is dropped.
  The model can therefore reorder, edit, add and remove in one call, and the stored list is always exactly what
  the last call said.
- **The tool assigns ids.** An item with an `id` keeps that todo's id; the id must name a todo of the current list,
  or the call is refused (an unknown id is a model mistake, not a new todo). An item without one keeps the id of the
  first todo of the current list with exactly the same content that no other item claimed, and otherwise takes a
  fresh id, `nextId` in decimal, after which `nextId` grows. So a model that re-sends its list without ids, changing
  only statuses, keeps every id; and an id, once dropped, is never given to another todo of the thread. Events and
  streaming consumers can follow a todo by id. A Block restores `nextId` with the list, so ids of a retracted turn
  can be issued again; the turn's `GuardrailBlocked` event tells a consumer that read its `TodosUpdated`.
- **Refusals are tool errors, decided when the tool runs (rule 2).** Three checks, all before any state is read,
  in `validateDecoded`: more than `maxTodos` items; an item whose content is empty (after trimming) or over
  `maxTodoChars` Unicode code points (the measure the argument validator uses for `maxLength`); an id given twice. The
  schema also advertises `maxItems` and `maxLength`, so the argument validator refuses most over-long calls first, with
  its own message. Because they are argument checks, a refused call takes no lock round (§4.23, "Lock function
  failure"). One check needs the state, an unknown id; it is made in `execute`, against the committed snapshot,
  under the lock. Every refusal is `ToolOutcome.Error`, which the model sees; the run continues.
- **Two calls in one batch apply in order.** `write_todos` locks `todos`, so C2 runs a second call of one batch in
  the next wave, after the first committed: the second call sees the first's list and ids, and the stored list is
  the last call's - nothing is lost silently.
- **The plan guides the model only (§8).** The section is text for the model; the middleware has no `wrapModelCall`
  or `wrapToolCall`, never filters tools, and never routes. `write_todos` is a tool like any other: its resource is
  the default `(Invoke, write_todos)`, so a `PermissionMiddleware` with no rule for it denies it.
- **The prompt sections.** `todos-guide` is a fixed text naming the limits. `todos` renders the stored list, one
  line per todo, `- [status] (id) content`, with line breaks and other control characters in the content replaced
  by spaces, so stored content cannot break the section's structure. The tool's result is the same rendering of the
  new list, so the model learns the ids it was given.
- **Events.** Each call that changes the list emits `TodosUpdated` with the new list's ids and statuses, committed
  with the call's task, and `TodosProgress` with the whole list, live. A call whose list equals the stored one
  emits neither. The tool emits them as it returns its `Success`.

## Where the spec was imprecise

- **The key holds a `TodoList`, not a bare `Vector[Todo]`.** It carries `nextId` beside the todos, so ids are not
  reused (above). `TodoList.todos` is the spec's vector.
- **Who assigns ids.** The spec names `Todo(id, ...)` without saying; the tool does, as above.
- **Two sections, not one.** The spec names "a prompt section showing the current plan". The guide is split from
  the plan so the stable text is `cacheable` and comes first in the system prompt (C1 places cacheable sections
  first), while the plan, which changes, follows it.

## Runtime rules

1. **One batch, one snapshot.** Met by the `todos` lock: conflicting calls run in successive waves, each reading
   the list the previous one committed. The id check is made in that wave, against that snapshot. Tested: two calls
   in one batch, the second naming an id the first created.
2. **An update function that fails, fails the run.** The key is a replace key, whose update is total. Every refusal
   is a `ToolOutcome.Error` decided when the tool runs.
3. **Visible from the next superstep.** The plan section is built from the snapshot of each model step, so the step
   after a `write_todos` call shows the new list. Nothing needs the list in the request that wrote it. Tested.
4. **At least once.** The tool is a pure function of its arguments and the committed snapshot, so a rerun after a
   failure (`recover`) produces the same list and ids. It performs no effect outside state: its durable event is
   committed with the task, so a rerun announces the change once. Tested: a wrapper failing the call after the
   tool returned, then `recover`, gives one `TodosUpdated` and the same ids. C4's guards are not needed.
5. **A Block restores the list (C1).** The tool's `writes` are in the agent's harness writes, so an output Block
   restores the key, `nextId` included, to its value before the turn. Tested. The turn's `TodosUpdated` events stay
   in the log, as every durable event of a blocked turn does; the turn's `GuardrailBlocked` follows them.
6. **Full snapshots.** Each checkpoint holds one copy of the list, at most `maxTodos` todos (rule 12).
7. **Restore through codecs.** The key is new, at `SchemaVersion.initial`, with explicit codecs (status strings fixed
   by name). **Structure:** the key, and C2's `tool-queue` (the tool takes a lock), are registered only by an agent
   family with a `TodoMiddleware`, so an agent without one keeps its structural fingerprint and its old threads
   (tested). Adding `TodoMiddleware` to an existing agent adds both keys, which changes the fingerprint, so today its
   threads checkpointed before are refused (`RestoreRejected`): finish or `forget` them first. C5
   ([#1934](https://github.com/llm4s/llm4s/issues/1934), in review) restores a thread at rest into a graph that only
   gained keys; once it lands, adding todos to an agent no longer orphans its completed threads, and this note and
   the migration note are updated.
8. **Tenant.** Not applicable: the list is thread state, never shared across threads.
9. **No content in durable events.** `TodosUpdated` carries ids and statuses; the content is in state and in the
   live `TodosProgress`. Tested on the stored event.
10. **A failed task commits nothing.** A failed call's list and durable event are discarded with the task. Its live
    `TodosProgress` was already delivered, as every live event of a failed task is (live events are not
    transactional; a consumer that needs the committed plan reads `TodosUpdated` or the state).
11. **Every model call accounted.** Not applicable: no model call is made.
12. **Bounded, measured on what is kept or sent.**
    - **The key:** a list the tool accepts has at most `maxTodos` todos, each at most `maxTodoChars` code points, and
      ids of at most 19 digits (a `Long`). A list written another way - `updateState`, or an agent rebuilt with
      lower limits - is not refused by the key, but it is clamped wherever it is sent.
    - **The plan section, the tool result and the events:** each renders at most `maxTodos` todos of the stored list,
      each content cut to `maxTodoChars` code points and each id to 20, and says how many it left out. So a section
      holds at most `maxTodos` lines of `maxTodoChars` code points plus a fixed overhead, whatever is stored. With the
      defaults it is about 12 000 characters, some 3 000 of C1's default 8 192-token budget. `TodosUpdated` and
      `TodosProgress` carry the same at most `maxTodos` items.
    - **The guide:** fixed text, under 1 000 characters.
13. **Every type is defined.** `TodoStatus`, `Todo`, `TodoList`, `TodoMark`, `TodosUpdated`, `TodosProgress`,
    `TodoMiddleware` and `HarnessEvents`, above, in `org.llm4s.agent.harness`. Stored: `TodoList`, `Todo` and
    `TodoStatus` (the key's codec), and the two event payloads (their event types' codecs).

## Limits

- A wrapper outside `write_todos` that turns its `Success` into an error still commits the event the tool emitted,
  and not the list. Wrappers that rewrite a successful outcome are rare; the state is authoritative.
- The middleware does not check that at most one todo is `InProgress`; the guide asks the model to keep it so.

## Implementation plan

1. Tests first: `TodoMiddlewareSpec` through `ToolLoop` with a scripted model (write and replace, ids kept and
   fresh, unknown and duplicate ids, limits, two calls in one batch, the section from the next step, clamped
   rendering of an oversized stored list, events, an output Block, a failed call recovered) and `AgentTodosSpec`
   through `Agent` (streamed events, a checkpointed list, a permission rule denying the tool, the fingerprint of
   an agent without todos unchanged).
2. `TodoStatus`, `Todo`, `TodoList` and their codecs; `HarnessEvents`, `TodoMark`, `TodosUpdated`,
   `TodosProgress`.
3. `TodoMiddleware`: the key, the tool (schema, `validateDecoded`, id resolution, events), the two sections.
4. Guide (`docs/guide/agents/index.md`, "Todos"), CHANGELOG, migration note (Stage 3), the slice table of the
   design document.
