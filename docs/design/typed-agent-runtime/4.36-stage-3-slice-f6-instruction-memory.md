# 4.36 Stage 3 slice F6: instruction memory ([#1910](https://github.com/llm4s/llm4s/issues/1910))

Part of the [Typed Agent Runtime design](../typed-agent-runtime-design.md), §4. Section numbers (§N.N) refer to that document and its [slice records](../typed-agent-runtime-design.md#slice-records). Phase 3 spec: `docs/superpowers/specs/2026-10-13-phase-3-harness-design.md`, "F6".

Slice F6 of [#1901](https://github.com/llm4s/llm4s/issues/1901), a feature slice on C1 (§4.22: `ModelContext`,
`promptSections`) and C3 (§4.25: `FileBackend`). It gives an agent **instruction memory** (§9 "Skills and memory
distinction"): standing instructions kept in `AGENTS.md` files, read through a `FileBackend` and shown to the model as
one prompt section. Unlike semantic memory (F7, §4.31: facts and embeddings recalled per query), instruction memory is
a few whole files the agent always sees, and - where the backend and the permission rules allow it - edits like any
other file. Everything is in `llm4s-agent`, package `org.llm4s.agent.harness`, `@Experimental`, opt-in.

It is built on the mechanism F5 introduced for skills (§4.35, "The shared piece"): `RunDocuments` reads once per run
incarnation into a bounded LRU and reports in the computing task; `DocumentText.read` reads a file within a bound;
`SectionText` builds the section within its bound; `Report` and `HarnessEvents.DocumentsReported` name what was cut or
left out. This slice adds no second copy of any of them. The spec is `InstructionMemoryMiddlewareSpec`.

## API

- `final class InstructionMemoryMiddleware(paths: Vector[VPath], backend: FileBackend, maxFileTokens = 2000,
  maxTotalTokens = 4000, maxCachedRuns = 64, id = MiddlewareId("instructions"))`. Every limit must be at least 1, and
  `maxFileTokens` at most `maxTotalTokens` (`require`).
- `instructions(context: ModelContext): Result[Vector[Instructions]]`: the files the run shows, through its cache.
- `final case class Instructions private (path: VPath, text: String, cut: Boolean)` with `apply` and `with*`: one
  file as shown, `cut` when it was cut at a limit.

No new event: an over-limit or unreadable file is a `DocumentIssue` in F5's `DocumentsReported`.

## Decisions

- **Order and scope.** The files are read in the order given - for example the user's `AGENTS.md`, then the
  project's - and shown in that order, each under a `## <path>` heading, after a guide line saying that a later file
  refines an earlier one. One section, id the middleware's id, `cacheable`: it is the same for every request of a run.
  With no file, or only empty ones, there is no section.
- **A missing file is skipped**, silently: a user-scope file need not exist. A refusal (binary content, a path that is
  a directory) is reported `Unreadable`, by the refusal's kind only. Any other backend error fails the model step,
  which `recover` runs again (as for skills).
- **Bounds (rule 12).** Each file is read at most `maxFileTokens` estimated tokens (`PromptSection.estimatedTokens`,
  C1's estimate): reading stops at the bound, so no more is kept. A file over it is shown cut, with a marker saying
  so, and reported `Cut`. The whole section - guide, headings and markers included - is at most `maxTotalTokens`: a
  file that does not fit whole is cut to the room left (`Cut`) and the files after it are left out (`NotListed`); one
  whose room cannot hold even the cut marker is left out alone, and a later, shorter file is still shown if it fits.
  So the section's size is bounded on its own, and the cache's memory by `maxCachedRuns × maxTotalTokens`. Each file
  is added to the section as it is read, so at most one file is held beside it; a file is read only when its heading
  and one character fit in the room left - otherwise it is named `NotListed` unread - and none once the section is cut.
- **When.** Read on a run's first model call, from that step's snapshot, cached for the run; a recovered or resumed
  run reads again (F5's `RunDocuments`). A file edited during a run shows from the next run, never in the run that
  edited it, so a run's instructions do not change under it.
- **Editing.** No tool is added. The agent edits an instruction file with F1's `edit_file` (`FileTools(backend)`,
  §4.32) over the same backend, when
  the backend accepts the write (a `StateFileBackend` or a writable store mount) and the `PermissionMiddleware` rules
  allow `Write` on its path. A read-only scope is made read-only by a deny rule, or by mounting it on a backend that
  refuses writes. The middleware's `writes` are the backend's, so a state backend's key is registered with the graph
  even with no file tool; the middleware itself never writes. Tested through `FileTools`: an edit shows from the next
  run, and a `PermissionMiddleware` deny rule on one scope leaves that file unchanged while the other is edited.
- **Content.** A file is instructions the application chose to give the model: it is shown as it is (only a cut
  marks it). Its text is never put in an event (rule 9).

## Where the spec was imprecise

- **"Cached by run id"** is cached by run incarnation (§4.35): a run id can be reused, the claim's token cannot.
- **`maxFileTokens` is at most `maxTotalTokens`**: a file bound larger than the section's could never be reached.

## Runtime rules

1. **One batch, one snapshot.** The files are read from the snapshot of the run's first model step, once; nothing is
   checked against it. An edit in the run shows from the next run (tested).
2. **Total updates.** No update function: the middleware writes no key.
3. **Visibility.** The section is built in the request it is for, so the first model call sees the files (tested).
4. **At least once.** Reading is idempotent, with no external effect; the report is committed at least once per run
   (F5's mechanism; tested here through a failed first step and recover).
5. **Block.** Nothing to retract; an edit made through the file tools is restored by C1 as theirs.
6. **Full snapshots.** Nothing is added to a checkpoint.
7. **Codecs and structure.** No key beyond the backend's; adding the middleware changes the agent's version by its
   middleware id (§4.29). No new event.
8. **Tenant.** The backend is the tenant boundary (a resolved backend per run); the cache is keyed by run
   incarnation, which has one tenant.
9. **No content in durable events.** `DocumentsReported` names paths and limits only (tested on the stored event).
10. **A failed task commits nothing.** The failed step's report is discarded, and the recovered run reports again
    (tested).
11. **Every model call accounted.** Not applicable.
12. **Bounded.** Each file at most `maxFileTokens`, the section at most `maxTotalTokens` (tested on what is sent), the
    event at most 32 issues, the cache at most `maxCachedRuns` entries of at most one section each.
13. **Types.** `InstructionMemoryMiddleware` and `Instructions` are defined here, in `llm4s-agent`.

## Not in this slice

- A host-directory backend (#1964). With one, an `AGENTS.md` on disk may change between a run and its recovery, and
  the recovered run reads it as it is then.
- Discovering `AGENTS.md` files by walking up from a working directory: the application lists the paths.
