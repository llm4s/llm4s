# 4.37 Stage 3 slice P1: the harness profile ([#1915](https://github.com/llm4s/llm4s/issues/1915))

Part of the [Typed Agent Runtime design](../typed-agent-runtime-design.md), §4. Section numbers (§N.N) refer to that document and its [slice records](../typed-agent-runtime-design.md#slice-records). Phase 3 spec: `docs/superpowers/specs/2026-10-13-phase-3-harness-design.md`, "P1".

Slice P1 of [#1901](https://github.com/llm4s/llm4s/issues/1901), the first integration slice. It assembles what the
feature slices built - F1's file tools (§4.32), F2's `execute` tool (§4.33), F3's todos (§4.30), F4's summarisation
and offload (§4.34), F5's skills (§4.35), F6's instruction memory (§4.36) and C2's permissions (§4.23) - into one
value, `HarnessProfile`, installed on an agent with `AgentBuilder.withHarness`. It adds no new behaviour to any of
them. It also turns the order those middleware need from documentation into a check: a middleware declares where it
must run relative to another, and `build()` refuses a stack that breaks it.

Everything is in `llm4s-agent`: the profile in `org.llm4s.agent.harness`, the ordering check in
`org.llm4s.agent.graph.middleware`. All new types are `@Experimental`. The specs are `HarnessProfileSpec` (assembly,
order, tool selection, prompt, timeouts, retention, the bounds), `HarnessConfigLoaderSpec` (the `reference.conf`
defaults and overrides), `MiddlewarePlacementSpec` (the ordering check, in a stack and across a family) and, in
`llm4s-agent-memory`, a placement case in `SemanticMemoryMiddlewareSpec`.

## API

In `org.llm4s.agent.harness`:

- `final case class HarnessProfile private (backend: FileBackend, sandbox: Option[SandboxBackend], tools:
  ToolSelection, todos: Option[TodoConfig], summarization: Option[SummarizationConfig], offload: Option[OffloadConfig],
  skills: Option[SkillsConfig], instructions: Option[InstructionsConfig], systemPrompt: PromptMode, permissions:
  Vector[PermissionRule], toolTimeout: Option[FiniteDuration], retention: RetentionPolicy)`, growth-prone: `apply`
  carries the defaults, each field has a `with*` setter (an `Option` field's takes the value or an `Option`), `.copy`
  is private. `HarnessProfile()` is the minimal profile: the file tools over a fresh `StateFileBackend`, nothing else
  on, the default prompt, no permission rules, the default retention.
- `HarnessProfile.deepAgents`: the opinionated preset - the minimal profile with todos, summarisation, offload, skills
  (`/skills`) and instructions (`/AGENTS.md`) on, each at its component's defaults. A `def`: each call has its own
  `StateFileBackend`.
- `enum ToolSelection`: `All`, `Only(names: Set[String])`, `Except(names: Set[String])`, over the profile's tools: the
  seven file tools (`FileTools.Names`) and `execute`.
- `enum PromptMode`: `Default` (the profile's prompt), `Replace(text)` (`text` instead), `Suffix(text)` (the profile's
  prompt, then `text`).
- `TodoConfig`, `SummarizationConfig`, `OffloadConfig`, `SkillsConfig`, `InstructionsConfig`: each a growth-prone
  `final case class X private (...)` holding its middleware's settings, with `apply` defaults equal to the
  middleware's own defaults and `with*` setters. `SummarizationConfig.compressor: Option[SummaryCompressor]`: `None`
  is `SummaryCompressor.digest` over core's `cl100k_base` counter, built when the profile is assembled, so the
  default makes no model call; a model compressor is given here with its client.
- `object HarnessConfigLoader`, in `org.llm4s.config` (the one package that reads configuration, as
  `ToolsConfigLoader` in `llm4s-agent-tools`): `load(): Result[HarnessProfile]`, the preset with `llm4s.agent.harness.*` applied
  from the application's configuration (system properties, `application.conf`, `llm4s-agent`'s `reference.conf`).
  The loaded profile is checked as `build()` would check it, so a bad value fails at the app edge. Backends, the
  sandbox, permission rules and a model compressor are code, set on the loaded profile with `with*`.

On `AgentBuilder`: `withHarness(profile: HarnessProfile)`, replacing any set before.

In `org.llm4s.agent.graph.middleware`:

- `AgentMiddleware.placement(other: AgentMiddleware): Option[Placement]`, `None` by default: where this middleware
  must run relative to `other`, when both are present.
- `enum Placement`: `Outside(reason)`, this middleware must wrap `other` in one agent's stack;
  `OutsideAtBoundary(reason)`, the same, and also across an agent family, where only the boundary hooks matter.

## Decisions

- **What `withHarness` installs.** At `build()`, the profile is assembled into tools, middleware, a system prompt
  and a retention policy:
  - **Middleware**, outermost first, before the builder's own (`withMiddleware`): `PermissionMiddleware` (only when
    `permissions` is non-empty), `SummarizationMiddleware`, `ToolOutputOffload`, `SkillsMiddleware`,
    `InstructionMemoryMiddleware`, `TodoMiddleware`, each only when its config is set. The builder's own middleware
    run inside them, in their order; `runsBefore` and `runsAfter` still apply across both.
  - **Tools**: the selected file tools over the profile's backend - over a `CompositeBackend` that also mounts
    `OffloadBackend` at `/large_tool_results` when `offload` is set, so the model can read an offloaded result with
    `read_file` - and `execute` over `sandbox` (F2's `ExecuteTool`), only when `sandbox` is set and selected. They
    join the builder's tools; a name clash is refused as any other is. Skills and instructions read through the same
    backend, so the paths their sections show are the paths `read_file` and `edit_file` take.
  - **Prompt**: by `systemPrompt`. With a harness, `withSystemPrompt` is refused at `build()`: the prompt is set
    through `PromptMode.Replace` or `Suffix`, so there is one place it comes from.
  - **Retention**: below.
- **Empty `permissions` installs no `PermissionMiddleware`.** A `PermissionMiddleware` denies what no rule matches,
  so an empty rule list would deny every call. With rules, the rules are the whole policy: everything the agent may
  call needs a rule, `write_todos` included (F3's decision: the plan grants no permission).
- **Tool selection is checked.** A name in `Only` or `Except` that is not one of the profile's tools is refused (a
  typo would otherwise silently select everything or nothing), and so is `execute` without a sandbox. Selection
  applies to the profile's tools only: `write_todos` comes with `todos`, and the builder's tools are the builder's.
- **`toolTimeout`** bounds each run of the profile's tools that declares no timeout of its own (C2's
  `AgentToolSpec.withTimeout`). The builder's tools and middleware tools keep their own.
- **Retention (rule 6).** Every checkpoint is a full snapshot of the thread, files, plan, summary and offloads
  included, so the profile bounds how many are kept: by default the latest
  `HarnessProfile.DefaultRetainedCheckpoints` (20). The root agent's profile applies: after a turn ends, when its
  `AgentRun.await` first returns the outcome - every `Agent.run`, `recover` and `resume` does - the thread is pruned
  with `GraphRuntime.prune` under the run's tenant. Pruning never removes the latest checkpoint or its pending
  writes, so it never changes what `recover` or `resume` does next. A prune that fails is logged at WARN and the
  turn's outcome is returned: retention is housekeeping, and the next turn prunes again. A turn started with `start`
  and never awaited is pruned by the thread's next awaited turn. `RetentionPolicy.keepAll` turns it off.
- **The default prompt** teaches plan, act and verify; context management; and tool safety. It is built from fixed
  parts, each only when the feature it describes is on: the file tools, the plan (`write_todos`), summarisation and
  offloaded results, and `execute`. Delegation is added in Stage 4. It is the system prompt, so it is not one of the
  middleware's prompt sections and does not count against `maxPromptSectionTokens`; its size is fixed by its parts
  (tested: the whole preset's prompt is under 1,000 estimated tokens).
- **The preset's sections fit the budget together.** F6's spec shows that todos, skills, instructions and recalled
  memory at their defaults, each full, fit `LoopAgent.DefaultMaxPromptSectionTokens`. The preset's configs are those
  defaults, and `HarnessProfileSpec` runs the same computation on the preset's own configs, so a change to the
  preset that breaks the budget fails a test.

### Ordering between middleware is checked, not documented

F4 documented that `SummarizationMiddleware` must run outside `ToolOutputOffload`, and F7 that a
`SemanticMemoryMiddleware` must run outside guardrail middleware. Each was a sentence in Scaladoc, and a wrong order
ran silently wrong. They are one class - a middleware whose correctness depends on its position relative to another - so the fix is one mechanism:

- A middleware states the requirement itself, as `placement(other)`. It names the other by type, since ids are
  configurable. The requirement is a check, never an arrangement: `MiddlewareStack.of` (so `ToolLoop.build` and
  `AgentBuilder.build()`) refuses a stack where `m.placement(o)` is defined and `m` is not outside `o`, as one
  `ValidationError` naming both, the reason, and the fix (register it earlier, or name it in `runsBefore`).
  `runsBefore` and `runsAfter` still arrange; this is what checks the arrangement.
- **Across a family**, only boundary hooks interleave: the root's `beforeAgent` runs before the active agent's and
  its `afterAgent` after. So a `Placement.OutsideAtBoundary` middleware on a handoff target is refused when the root
  has the middleware it must wrap (`ToolLoop.build`): the root's runs outside it whatever the order. A
  `Placement.Outside` is not checked across a family, since the root's model and tool wrappers do not wrap a
  target's calls.

The requirements, found by reading every harness middleware's Scaladoc and design record for order:

| Middleware | Must run outside | Kind | Why |
|---|---|---|---|
| `SummarizationMiddleware` | `ToolOutputOffload` | `Outside` | it aligns the request with the stored history; offload's `wrapModelCall` cuts tool results first otherwise, and the cut messages match nothing stored (§4.34) |
| `SemanticMemoryMiddleware` | `GuardrailMiddleware`, `GuardrailReviewMiddleware` | `OutsideAtBoundary` | `afterAgent` runs in reverse order, and inside a guardrail it records an answer the guardrail then blocks (§4.31) |

Checked and found free of an order requirement: `SkillsMiddleware`, `InstructionMemoryMiddleware` and
`TodoMiddleware` (prompt sections and a tool only: stack order sets section order, and the cacheable ones come first
whatever it is); `PermissionMiddleware` against `ApprovalMiddleware` (C2 says to register permissions first, so a
denied call is refused before a reviewer is asked; the other order asks a question whose approval the rules then
override with a denial, which is a wasted question, not a wrong outcome - and approval being one flag per call, an
`ApprovalMiddleware` outside permissions is a supported combination, `ToolPermissionsSpec`); `ToolOutputOffload`
against `PermissionMiddleware` (a denial is short, and offload caps every
`ToolMessage` in the request either way); `SemanticMemoryMiddleware` against the harness middleware (boundary hooks
only, which they do not use).

## Where the spec was imprecise

- **The order "permissions, then offload, summarisation".** F4 (§4.34) requires summarisation outside offload, and
  the integration review confirmed it; the profile installs permissions, summarisation, offload, skills,
  instructions, todos, and `Placement` makes the F4 order a check.
- **`SemanticMemoryMiddleware` is not a profile field.** It is in `llm4s-agent-memory`, which depends on
  `llm4s-agent`, so the profile cannot name it. It is added with `withMiddleware`, inside the harness middleware, and
  its `Placement` keeps it outside guardrail middleware.
- **The config types** (`TodoConfig`, `SummarizationConfig`, `OffloadConfig`, `SkillsConfig`, `InstructionsConfig`)
  are named by the spec and defined here (rule 13).
- **"Keep the latest N checkpoints"** is N = 20, and applied by the agent after each turn, since a
  `RetentionPolicy` is otherwise only applied by an explicit `prune`.

## Runtime rules

1. **One batch, one snapshot.** No new tool or state key: every batch rule is the component's (F1's locks, F3's
   tool lock, F4's total offload update), unchanged by assembly (tested: a parallel batch of file writes through a
   harness agent keeps both files).
2. **Total updates.** No new update function.
3. **Visibility.** Unchanged; each component puts what the current request needs into it.
4. **At least once.** No new effect. `execute` replays through F2's `Unverifiable` guard; pruning is idempotent and
   never removes the latest checkpoint, so a crash between a turn and its prune loses nothing.
5. **Block.** The profile's keys are its middleware's and backend's `writes`, so C1 restores them on an output Block
   (tested: a blocked turn through a harness agent leaves no file and no plan).
6. **Full snapshots.** The profile's `retention` bounds the checkpoints a thread keeps (tested: a thread run past
   the bound keeps it).
7. **Codecs and structure.** No new key or codec. A harness changes the agent's version through its middleware ids,
   tools and prompt, which the fingerprint already covers; the same profile gives the same version (tested).
8. **Tenant.** The backends are the tenant boundary (§4.25); pruning runs under the run's `RunConfig`, so another
   tenant's thread is refused.
9. **No content in durable events.** No new event.
10. **A failed task commits nothing.** Unchanged.
11. **Every model call accounted.** The default compressor makes no model call; a model compressor calls through
    `context.accounted` (F4).
12. **Bounded.** Every component keeps its bound, and the profile sets each from its config; the prompt is a fixed
    size; the preset's sections fit the section budget together (tested); the checkpoint count is bounded by
    `retention`.
13. **Types.** `HarnessProfile`, `ToolSelection`, `PromptMode`, the five config types, `HarnessConfigLoader` and
    `Placement` are defined here.

## Not in this slice

- Delegation (sub-agents) and its prompt part: Stage 4.
- `SemanticMemoryMiddleware` as a profile field: it would need the profile in `llm4s-agent-memory`.
- A host-directory backend (#1964): the profile takes any `FileBackend`, so it needs no change when one exists.
