# 4.23 Stage 3 slice C2: tool permissions, timeouts and batch locks ([#1903](https://github.com/llm4s/llm4s/issues/1903))

Part of the [Typed Agent Runtime design](../typed-agent-runtime-design.md), §4. Section numbers (§N.N) refer to that document and its [slice records](../typed-agent-runtime-design.md#slice-records). Phase 3 spec: `docs/superpowers/specs/2026-10-13-phase-3-harness-design.md`, "C2".

Implemented. Slice C2 of [#1901](https://github.com/llm4s/llm4s/issues/1901), a core slice with no dependency. It closes the §4.9 carry-forward "tool permissions and timeouts on `AgentToolSpec`, with the ordered deny-if-unmatched permission rules of §5.6", and adds the batch locks C3's backends take. Everything is in `llm4s-agent`; core is unchanged. The specs are `ToolPermissionsSpec`, `ToolTimeoutSpec`, `ToolBatchLockSpec` (agent), `GlobSpec`, `LockKeySpec` and `PermissionMiddlewareSpec`.

## API

In `org.llm4s.agent.graph.tool`, all `@Experimental`:

- `AgentToolSpec` gains three fields, each with a setter:
  - `timeout: Option[FiniteDuration]`, `withTimeout(d)`; `d` must be positive (`require`, as the name check is).
  - `resourcesOf: A => Vector[ToolResource]`, `withResources(f)`. The default is `Vector(ToolResource(Operation.Invoke, name))`; a call whose function returns an empty vector is checked as that default, so a resource function cannot opt a call out of the rules.
  - `locksOf: A => Set[LockKey]`, `withLocks(f)`. The default is no lock.
- `enum Operation`: `Read | Write | Delete | Execute | Network | Invoke`. Its `label` is the lower-case name used in messages.
- `final case class ToolResource(operation: Operation, target: String)`: what one call touches. The target is a tool name, a path or a URL, matched by a `Glob`.
- `opaque type LockKey` over its segments (below).
- `final class Glob`: `Glob(pattern)`, `matches(target)`, `pattern`. Equal by pattern.

In `org.llm4s.agent.graph.middleware`:

- `enum PermissionDecision`: `Allow | Deny | Ask`.
- `final case class PermissionRule(operation, target: Glob, decision)`, with `PermissionRule.allow/deny/ask(operation, pattern)`.
- `final class PermissionMiddleware(rules: Seq[PermissionRule], id = "permissions")`.
- `ToolCallRequest` gains `resources: Vector[ToolResource]` and `withResources`, so a tool wrapper sees what the call touches. `ToolCallRequest(spec, call)` stays, as the growth-prone rule asks, and forwards with the tool's default resource; the loop always passes the decoded call's own.

`LockKey`, exactly:

```scala
opaque type LockKey = Vector[String]
object LockKey:
  def apply(path: String, more: String*): LockKey   // each part split on '/', empty segments dropped
  extension (key: LockKey)
    def segments: Vector[String]
    def /(path: String): LockKey                    // appends path's segments
    def conflictsWith(other: LockKey): Boolean      // one is a prefix of the other, segment by segment
    def render: String                              // segments joined with '/'
```

`LockKey("workspace", id, "src/a.scala")` and `LockKey(s"workspace/$id/src/a.scala")` are the same key. Prefixes are by segment: `a/b` conflicts with `a/b/c` and `a`, not with `a/bc`. `LockKey("")` (no segments) is the root and conflicts with every key. The key is never stored, so it has no codec.

## Decisions

### Permissions

- **Rules see decoded arguments.** The resources are computed in the call pipeline after the schema check, decoding and `validateDecoded` (steps 2-4 of §4.7), and handed to every wrapper on `ToolCallRequest.resources`. A resource function that throws refuses the call as invalid arguments, as a throwing `validateDecoded` does; a cancellation cancels the task.
- **First match wins; unmatched is denied.** For each resource the first rule with the same operation whose glob matches the target decides; no match is `Deny`. A call runs only if every resource is allowed: any `Deny` gives `Error("Denied: <op> <target>")` (the first denied resource, in resource order), recorded as `ToolExecutionOutcome.Denied`; otherwise any `Ask` gives `NeedsApproval("Permission required: <op> <target>, ...")` unless `context.approved`.
- **Approval is one flag per call.** `ToolContext.approved` is set once a reviewer approves the call, whichever wrapper or tool asked. So an approval satisfies every `Ask` of the call, including one a `PermissionMiddleware` would have raised after another middleware's approval. This is the existing semantics (§4.8), unchanged.
- **Edits are checked again.** An `Edit` answer runs the whole chain again on the edited arguments with `approved = true` (`ToolLoop.scala`, the approval node's `ApprovalDecision.Edit` case, through `Pipeline.approved` and `rerun`). So the resources are recomputed: `Deny` still denies, `Ask` passes. A reviewer cannot widen a call past a deny rule.
- **Order in the stack.** `PermissionMiddleware` should be registered first (outermost), so a denied call is refused before any other wrapper asks for approval of it. The docs say so; the stack does not enforce it.
- **Sandbox `execute` is limited by the sandbox too.** An `Execute` rule constrains which commands the agent may ask to run, not what a command does once running. The guide states this (§5.6).
- **`Glob` is agent-local.** `*` matches within a segment (not `/`), `?` one character other than `/`, `**` any run of characters including `/`; `**` as a whole segment also matches zero segments (`src/**/a.scala` matches `src/a.scala`, `src/**` matches `src`). Every other character is literal: no escapes, classes or braces. Every string is a valid pattern, so `Glob(pattern)` is total. F1's `glob` tool uses the same class.

### Timeouts

- **The timeout bounds each run of the tool, not the task.** The pipeline's innermost function (the tool's `execute` or `resume`, guarded) runs the tool in a forked virtual thread under `ox.timeoutOption`. On expiry Ox interrupts the fork and joins it, and the innermost function returns `ToolOutcome.Error("Tool '<name>' timed out after <n> ms")`: a tool-level error the model sees, recorded as `Errored`, so the run continues. Each wrapper sees that `Error` from `next` and may retry; a retry is bounded again. The spec says "the loop interrupts a task"; interrupting the task would cancel it and record nothing (§4.4), so it is the tool's fork that is interrupted, and the task records the error.
- **A timed-out tool commits nothing of its own.** Its outcome, if it ever produces one, is discarded with the fork, so a `Success` update it would have made is never applied (rule 10 holds trivially: the task commits only the error result).
- **The structured scope waits.** A tool that ignores its interrupt keeps the scope, and so the batch, waiting past the timeout. The tool-author rule, in the guide: block interruptibly.
- **Cancellation is not a timeout.** A cancel or deadline interrupts the task thread while it waits; Ox interrupts and joins the fork and rethrows, and the pipeline returns `Fatal(CancelledError)` with the flag restored, so the task records nothing and `recover` runs the call again, as for an untimed tool.
- **The key is unchanged.** Every run of a call, timed out or not, sees the call's `IdempotencyKey`, so an effect a timed-out run started replays through its C4 guard when the call runs again (a retrying wrapper, `recover`). A model that calls the tool again after a timeout issues a new call with a new key: the timeout tells it the outcome is unknown, not that nothing happened.
- **Thread-locals.** A timed tool runs on another thread than the task, so a thread-local the caller set (an MDC entry) is not visible to it. Only a tool with a timeout is affected.

### Batch locks

- **Waves, in call order.** When a model message has several calls, each call's locks are computed from its decoded arguments. A call is ready when no earlier call of the batch that has not finished holds a lock conflicting with one of its own. The model step fans out the ready calls and records the others, in call order, in a loop-owned key, `tool-queue` (`ToolLoop.queue`). When the barrier releases, `collect` takes the queue: if it is not empty, it fans out the queued calls now ready and keeps the rest; once it is empty, it appends every result in call order and routes to the model, as before. Calls without locks never wait.
- **No deadlock, bounded waves.** Conflicts are ordered by call index, so the first queued call is always ready, every wave runs at least one call, and a batch of `n` calls takes at most `n` waves.
- **A later call sees the earlier one's committed state.** Each wave runs in its own superstep, after the previous wave's pending writes committed. A snapshot check (a quota, a file's content) is therefore exact across conflicting calls, and two whole-value writes to one key no longer lose one (rule 1).
- **The queue holds `ToolTask`s, keys included.** A queued call's `IdempotencyKey` is derived by the model step from its position (§4.17) and stored with the task, so a call run in a later wave, and on `recover`, has the same key as it would have had in the first. The spec does not name this key; it is needed because `collect` runs at another position than the model call.
- **Recover resumes mid-sequence.** Each call commits its own result as it finishes; `recover` re-runs only tasks with no committed pending write, so a finished earlier wave is never run again, and the queue says which calls are still to run.
- **Budgets.** Each further wave costs two supersteps, its calls and the `collect` that schedules them, and `RunBudgets.maxSupersteps` counts both. The spec says "counts these supersteps"; it is two per wave.
- **Lock function failure.** A call whose arguments do not decode has no locks (it will be refused without touching anything). A lock function that throws gives the call the root lock, so it waits for every earlier locked call and every later locked call waits for it; the call is then refused or run as usual. This keeps scheduling total (rule 2: `collect` and the model step never fail on caller code).
- **Approvals and questions.** A call that suspends holds back every later call that conflicts with it, as it already holds back the model. A later wave's approvals are asked only once the earlier wave has settled, so a reviewer may see a batch's approvals in more than one round. An edit changes only the call being run: queued calls keep their arguments, so their locks are those they were scheduled with.

## Runtime rules (spec §"Runtime rules every slice must satisfy")

1. **One batch, one snapshot.** Met, and the reason for locks: calls with conflicting locks run in successive supersteps. Calls without locks still share the snapshot, as before; C3's backends take locks for every mutation. Tested: two locked calls each reading and incrementing one replace-key end at 2; unlocked, they end at 1.
2. **A failing update fails the run.** Met. Denial, timeout and refusal are decided when the tool runs and are tool results; `tool-queue` is a replace-key, and scheduling is total (a throwing lock function gives the root lock).
3. **Visible from the next superstep.** Met by waves: a later wave runs in a later superstep.
4. **At least once.** Met. A queued call keeps the key the model step derived; a timed-out run's effect replays through its C4 guard under the same key. Tested: a crash (`Fatal`, and a cancel) in the second locked call, then `recover`, runs only the second; a timed-out run and its retry see one key.
5. **A Block retracts messages only.** Not affected: a batch ends before `finish`, so `tool-queue` is empty when a Block can happen. C1's key-generic restore will treat it as loop bookkeeping.
6. **Full snapshots.** `tool-queue` holds at most the unrun calls of one batch and is empty between batches.
7. **Restore through codecs.** `tool-queue` is a new key at `SchemaVersion.initial`; a checkpoint written before it has no value and restores with the empty initial, which is what an old batch (every call fanned out) needs. `ToolTask`'s shape is unchanged. No stored type changes.
8. **Tenant.** Not applicable: rules, locks and timeouts are per agent, not shared across threads. A `PermissionMiddleware` per tenant is built per agent.
9. **No content in durable events.** Met: denials and timeouts are announced as before, `ToolExecuted` with an outcome (`Denied`, `Errored`), never the message or arguments.
10. **A failed task commits nothing.** Met: a timeout is a successful task with an error result; a cancelled timed tool records nothing. Tested.
11. **Every model call accounted.** Not applicable: no model call is added.
12. **Bounded.** `tool-queue` is bounded by the calls of one message and cleared with the batch; waves by the number of calls; a timed tool's fork by its scope. Rule lists and resource vectors are the caller's.
13. **Every type defined.** Defined above, with their module and package. None is stored, so none has a codec; `ToolTask` keeps its own.

## Source breaks

- `tool-queue` is a key the loop owns: a tool or middleware declaring a key with that id is refused at build, as `tool-results` is.
- `ToolCallRequest` has a new field; `ToolCallRequest(spec, call)` still compiles.

## Limits

- Timeouts rely on interruption: a tool that blocks uninterruptibly delays its batch past the timeout.
- Locks order calls only within one batch. Two batches never overlap in one thread; two threads sharing an external resource are not ordered by these locks (a backend that needs that orders them itself).
- `ToolRegistry` tools (`AgentTool.fromToolFunction`: built-in, MCP, Java and Kotlin tools) take the default resource `(Invoke, name)` and no locks or timeout. A caller who needs more wraps one in an `AgentTool` over `tool.spec.withResources(...)`; the adapters do not take them yet.
