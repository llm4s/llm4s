# 4.57 Stage 5 slice W3: cancel from any machine, and the busy-thread policy ([#2136](https://github.com/llm4s/llm4s/issues/2136))

Part of the [Typed Agent Runtime design](../typed-agent-runtime-design.md), §4. Section numbers (§N.N) refer to that document and its [slice records](../typed-agent-runtime-design.md#slice-records). Stage 5 spec: `docs/superpowers/specs/2026-10-20-stage-5-production-design.md`, "W3" and "Rules every slice must satisfy".

Slice W3 of [#2129](https://github.com/llm4s/llm4s/issues/2129), after W2 ([4.56](4.56-stage-5-slice-w2-workers.md)). It
lets a caller on any machine cancel a queued run or a thread's runs, and gives each submission's `BusyThreadPolicy` its
full behaviour: `Reject`, `Enqueue` and `Interrupt`. It reverses §5.3's "do not queue" for the run queue (§5.3 and the §9
decision log are rewritten). It lives in `llm4s-agent` (`org.llm4s.agent.service`, and the runtime's stop in
`org.llm4s.agent.graph`), with store support in all three stores.

## What it adds

- `RunQueue.cancel(tenantId, target: CancelTarget, reason: CancelReason): Result[Vector[QueueEntry]]`, with
  `CancelTarget.Entry(entryId)` and `CancelTarget.Thread(threadId)`; `RunSubmitter.cancel(tenantId, target, note)`.
- `StopRequest` (`Cancel(reason)`, `Interrupt(by)`, with `outcome`), held on the entry as `QueueEntry.stopRequest` and
  answered with every lease the store grants or renews as `Lease.stop`.
- `RunSubmitter.deleteThread(runtime, tenantId, threadId, timeout)`: the service's delete.
- In the runtime: `RunHandle.stopSettling(settlement, atBoundary)` (package-private), `StopSettlement`, and
  `AgentRun.stopSettling(result, outcome, atBoundary)`; `ToolLoop.cuttable`.
- `AgentWorker.CancelledResult`, `InterruptedResult`, `CancelledKind`, `InterruptedKind`.
- SQLite schema 11 and PostgreSQL schema 5: `stop_json` on each queue entry.
- `RunQueueContract` gains eight cases (54, 55 on PostgreSQL); `AgentWorkerStopSpec` (21 cases) and
  `SqliteWorkerStopSpec` (2, two connections to one file) run the worker.

## Decisions

**A cancel is a stop request on the entry, seen with the lease's renewal.** The spec leaves the channel to the builder:
S2's notifications or the claim renewal. A worker already renews each entry's lease every `lease.renewEvery` (10 seconds
by default) beside the run's claim (W2), in the same database as the request, and `renew` reads the entry's row under its
lock anyway, so the request rides on it: `renew` answers the lease with the entry's stop request (`Lease.stop`), and so
does `take`, for the worker that takes an entry whose worker died. No notification channel, no extra read, and the worst
latency is one renewal interval, which an operator who wants faster cancels shortens. S2's `LISTEN/NOTIFY` wakes event
followers; making it wake a worker for a cancel would add a second channel the in-memory and SQLite stores would poll
anyway.

**What a cancel does depends on whether the entry has started.** An open entry that has recorded no attempt has run
nothing, so the store closes it `Cancelled(reason)` in the cancel's own transaction ("a cancel of a queued entry closes
it before it runs"), and a worker that had leased it meanwhile meets `EntryClosed` at `recordAttempt`. One that has
recorded an attempt may have admitted its input and may hold the thread's claim, so only the worker running it can stop
it: the store sets `StopRequest.Cancel(reason)` and the entry stays open until that worker - or, if it died, the next one
to take the entry - closes it. A cancel replaces an interrupt request; a second cancel keeps the first's reason. A
thread target cancels every open entry of the caller's tenant on the thread; an entry target answers `entry`'s errors
for another tenant's entry (rule 9). PostgreSQL decides under the thread's advisory lock, which `recordAttempt` takes too,
so an entry is never closed as unstarted while its first attempt is being recorded.

**The stopped run settles itself, under its own claim.** The spec has a queued run stopped by cancellation settled - a
synthetic "cancelled" result for every tool call left without one and a terminal `Failed` checkpoint with a cancelled
outcome - "under the same claim before it is released". W2's `Agent.settleQueued` takes a claim of its own after the run
has released its, which leaves a gap another run could take the thread in. So the runtime gains a settling stop:
`RunHandle.stopSettling(settlement, atBoundary)` records the `StopSettlement` (the outcome, and the state update that
closes the turn - `SettledTurn.closing` with the synthetic result) and stops the run; when the stopped run closes
(`cancelled()`), instead of committing `RunCancelled` against its last checkpoint and leaving it `Running`, it commits a
`Failed` checkpoint over that one, with the settlement's update and outcome and the run's `RunCancelled` event, as its own
closing commit, under its claim, before it releases it. The worker waits for the run to exit (`AgentRun.await`) and then
closes the entry. W2's `settleQueued` stays the fallback: a run that could not commit its settlement (its claim was lost,
the store refused the commit, or its worker died and the next worker found the stop request) leaves the thread `Running`,
and the worker that acts on the request settles it with `Agent.settleQueued` - the same synthetic results and outcome -
under a claim of its own, if the entry's run is still the thread's incomplete latest. A plain `AgentRun.cancel` of a
direct run is unchanged: no settlement is recorded, so the run closes as before and its thread stays `Running` for its
owner's `recover`. The settlement belongs to the stop that recorded it: a plain `cancel` that comes while a boundary
stop is still waiting for its tool superstep - a drain's, or a lost lease's - withdraws it first, so the run closes as a
cancelled run and the thread stays `Running` for the next attempt, rather than cutting the tool call and committing the
interrupt's settlement (Codex, round 1). The cause and the settlement are recorded in one step under the handle's
lock, so whichever stop records the cause first decides how the run closes: a settling stop that comes after a plain
cancel won installs nothing (round 2). A later interrupt request refreshes a settlement still pending, and once the run
has settled, the worker applies stop requests one at a time, each reading the current one (round 3), and closes the entry with the stop the checkpoint records - an interrupt's outcome names its entry -
never a request that replaced it afterwards (round 2). A settling stop's cause is a compare-and-set, so it never overwrites the run's own
`Finishing`, expiry or lost claim (round 4). The settled checkpoint is found as the entry's own newest checkpoint too,
so a direct run that took the thread on before the worker closed the entry does not hide it (round 4). And a run the
drain cancelled - a plain cancel, which withdrew the stop's settlement and may have cut a tool call - is given back for
recovery rather than settled by the fallback; the next worker acts on the still-durable request (round 4). An `Interrupt` submission marks, and closes, only its own tenant's entries of the thread
(rule 9), as a cancel does (round 5). The fallback settle commits as the run it settles - the run id of the entry's own
newest checkpoint - so the run-id lookup still finds the settlement once a direct run has moved the thread on (round 5). And `recordAttempt` refuses an entry that is no longer its thread's head - an
`Interrupt` entry displaced it between its take and its attempt - ending its lease (`LeaseLost`, committed) so the
interrupting entry is taken next, rather than letting the displaced entry record an attempt and jump ahead again
(round 6).

**The entry closes from how the run ended.** After the run exits, the worker reads the entry again (for the latest
request) and the thread, and closes it: `Cancelled(reason)` or `Interrupted(by)` when the latest checkpoint is the stop's
settlement (`Failed`, outcome kind `Cancelled` or `Interrupted`, committed by one of the entry's runs or over its run's
checkpoint by the fallback settle); otherwise with the outcome `AttemptPlan` gives the thread's state - a cancel that
arrived while the run was committing a completed, suspended or failed result was a no-op (the runtime ignores a stop once
the run is `Finishing`), and the ticket reports that result; a run that failed on its own with work left is settled by
the fallback and closed as the request says, rather than retried; and an entry whose input was never admitted closes as
the request says with the thread untouched. Either way the entry is closed, so no worker runs it again. Outcome kinds:
`AgentWorker.CancelledKind` (`"Cancelled"`) and `InterruptedKind` (`"Interrupted"`), each a `RunOutcome.Failed` whose
message names the reason - the requester's note, the thread's delete, or the interrupting entry.

**`Interrupt` stops at the next superstep boundary.** The runtime's `stopSettling` with `atBoundary = Some(cuttable)`
sets a boundary flag on the run's stop signal. The run publishes the nodes of the superstep it is about to execute
before it checks the flag (`atBoundary`), and the stop reads them after setting it, so one of the two always sees the
other: a stop that finds the superstep in flight made only of `cuttable` tasks cuts it as a cancel does, and otherwise
the superstep runs to its end and commits, and the run stops at the next superstep's start. For an agent `cuttable` is
its model nodes (`ToolLoop.cuttable`): an in-flight model call is cut, a tool call is never cut mid-flight, and so no side
effect is half-recorded. A tool superstep's calls all finish - including ones waiting for a slot of the superstep's
concurrency bound, `RunBudgets.maxConcurrency` (16 by default), which belong to the same superstep - and calls of later
supersteps (a lock-scheduled batch's later rounds, `AgentToolSpec.withLocks`) do not start. The cost the spec names
holds: a long tool call delays the interrupt.

**The interrupted turn keeps its finished calls' results.** A tool call's result is recorded in the batch's results key
(`ToolLoop.results`) and only appended to the history when the batch is collected, a superstep later; a run stopped at
the boundary after its tool superstep has results that were never collected. `SettledTurn.closing` therefore appends,
for each unanswered call of the last assistant message, the result the batch recorded for it - as collection would - and
the synthetic result only for a call that has none, then clears the batch's results and lock schedule so the next turn's
batch starts empty. This also corrects W2's exhausted settle, which gave a finished call the synthetic result and left
the batch's keys behind (unreleased, so changed in place). A cancel cuts its superstep, so a call that finished in it
recorded only a pending write the superstep's commit would have applied: it gets the synthetic "cancelled" result, as
the spec says of every call left without one.

**`Interrupt` asks the running entry to stop; the queue orders the rest.** Submitting an `Interrupt` entry sets
`StopRequest.Interrupt(by = the new entry)` on every open entry of the thread that has recorded an attempt and was not
asked to cancel, in the submission's transaction (under PostgreSQL's thread lock); a later `Interrupt` replaces `by`, so
the running entry closes `Interrupted(by = the latest)` - W1 has already closed the earlier, unstarted `Interrupt` entry
`Interrupted(by = the later)`. W1's run order does the rest (rule 5): the running entry, having recorded an attempt, stays
the thread's head until it closes; then the `Interrupt` entry, ahead of the queued ones, which keep their order. The
interrupted entry closes `interrupted` and is not retried. An entry whose worker died while it was asked to stop is
acted on by the next worker that takes it, recording no attempt (so a stop never spends `maxAttempts`): its run is no
longer in flight, so there is no superstep to finish, and the thread is settled as it stands.

**`Reject` refuses a direct run's thread too.** W1 left a thread busy with a direct run, and no entry, to W3. Each
store's `submit` refuses a `Reject` submission while a live claim holds the thread, by the store's clock (the database's
in PostgreSQL), in the submission's own transaction: SQLite and PostgreSQL read the thread row's claim, the in-memory
queue the checkpointer's under the shared lock. Only a claim of the submitter's own tenant counts (rule 9, Codex round
7): another tenant's direct run is never reported, so a submission naming another tenant's thread learns nothing of it -
it is queued, as on an idle thread, and the worker that takes it refuses it before probing the claim, closing it
`Failed(RunFailed)` with the tenant-safe `TenantMismatch` message (W2), exactly as if no run were there. A claim that
recorded no tenant (SQLite, made before claims carried one) is not counted either. `Enqueue` and `Interrupt` are accepted on such a thread; the worker that
takes the entry meets the live claim and defers to it (W2). A direct run is never interrupted - it is its owner's, with
no queue entry to carry a request - so an `Interrupt` entry waits for it as an `Enqueue` entry does, ahead of the queued
entries.

**A pending interrupt is not a busy thread.** A suspended thread holds no claim and its entry is closed `Done`, so every
policy accepts a submission to it, and the runtime refuses a queued start while interrupts are pending (§5.3,
`PendingInterrupts`), which the worker closes `Failed(RunFailed)`. A resume is what answers the interrupts. W3 adds
nothing for this; `AgentWorkerStopSpec` checks it for all three policies.

**The service's delete waits for the entries to close.** `RunSubmitter.deleteThread(runtime, tenantId, threadId,
timeout)` cancels the thread (`CancelTarget.Thread`, reason `CancelReason.ThreadDeleted`): the queued entries close at
once, the running one is stopped and settled by its worker. It waits for each to close within `timeout` - a running
entry closes only once its run has exited - and then deletes the thread with `GraphRuntime.deleteThread`, which claims it
and deletes its children first. An entry still open at the timeout leaves the thread undeleted (`ThreadBusy`); calling
again finishes the delete. An entry submitted between the cancel and the delete is marked by the delete itself and closes
`Cancelled(ThreadDeleted)` without running (W1). The runtime is a parameter because the submission API holds only a
`Checkpointer`: the delete is the runtime's.

**Closes outside the worker are counted where they happen, at the submitter (O2, design 4.59).** The worker counts
every close it makes, the stopped entries' `cancelled`/`interrupted` closes included, through `QueueMetrics.closed`.
The entries W3 closes without a worker - a cancel of an entry not yet started (and so the service's delete), and the
earlier unstarted `Interrupt` entry a new `Interrupt` submission closes inside the store's `submit` - are counted by
`RunSubmitter`, given a `MetricsCollector` (`new RunSubmitter(queue, checkpointer, settings, metrics)`): it reads the
targeted entries before the call and counts each that was open then and is closed after. The store does not count
them: the queue SPI holds no collector, and a store is shared by processes that each have their own. So a caller that
uses `RunQueue.submit` or `RunQueue.cancel` directly, past `RunSubmitter`, is not counted, and the reads are made only
when a collector is given.

**#1750 is built on, not closed.** [#1750](https://github.com/llm4s/llm4s/issues/1750) asks for a frontier edit that
records a result for each unfinished call of an abandoned batch and moves the thread on. W3 builds that edit - a run
settled as it stops, its finished calls' results kept, a synthetic result for each other call, the batch's keys cleared,
the thread at rest - and uses it for queued runs. What #1750 also asks for, a public API a direct run's owner calls after
a local cancel, and its OpenAI and Anthropic one-result-per-call contract tests, stay with #1750: `stopSettling` and
`settleQueued` are package-private, and a direct cancel still leaves the thread for `recover`, as the spec requires.

**Schemas.** SQLite schema 11 and PostgreSQL schema 5 add `stop_json`, the stop request as `StopRequest.toJson` writes it
(its outcome's JSON), `NULL` for none; an older entry has none. Both steps follow W1's (10 / 4).

## Not in this slice

- A public frontier edit for direct runs (#1750, above).
- `wrapModelCall` continuation nodes in `ToolLoop.cuttable`, so an interrupt cuts a resumed middleware model call too (follow-up [#2364](https://github.com/llm4s/llm4s/issues/2364)).
- Queue and worker metrics (O2), the example service (P1).

## Tests

`RunQueueContract` gains eight cases on all three stores: another tenant's direct run never reported to a `Reject` submission; an attempt refused at a head an `Interrupt` entry displaced; an `Interrupt` entry reaching only its own tenant's entries; `Reject` refused while a live claim holds the thread, until it
is released or expires, and the other policies accepted; a cancel of an unstarted entry closing it at once, leased or
not; a started entry asked to stop durably, the request answered with its renewals and takes, through a reopen; a thread
cancel scoped to the caller's tenant; and an interrupt request for the latest `Interrupt` entry, never over a cancel.
`AgentWorkerStopSpec` runs real agents on the in-memory store: a cancel stopping, settling and closing a running entry
with the next entry starting normally; a tool call cut off answered `cancelled`; a cancel arriving after the run reached
rest closing with its outcome; a queued entry cancelled before it runs; a dead worker's entry cancelled and settled with
no new attempt; a local cancel unchanged; an interrupt cutting a model call and running ahead of queued entries; an
interrupt during a tool call keeping its result and starting no later call; two interrupts; a direct run not interrupted
and refusing `Reject`; a suspended thread refusing a start under every policy; the service's delete, finished and timed
out; and tenant-scoped cancels. `SqliteWorkerStopSpec` cancels and interrupts through a second connection to the file.
The schema steps are tested from version-10 (SQLite) and version-4 (PostgreSQL) stores, and `PostgresRunQueueUnitSpec`
checks the new statements and their locks.
