# 4.22 Stage 3 slice C1: kernel hooks for the harness ([#1902](https://github.com/llm4s/llm4s/issues/1902))

Part of the [Typed Agent Runtime design](../typed-agent-runtime-design.md), §4. Section numbers (§N.N) refer to that document and its [slice records](../typed-agent-runtime-design.md#slice-records).

Slice C1 of [#1901](https://github.com/llm4s/llm4s/issues/1901), refining the C1 section of the
[Phase 3 spec](../../superpowers/specs/2026-10-13-phase-3-harness-design.md). Stage 3's harness features (todos,
summarisation, skills, instruction and semantic memory, the profile) are middleware. Today a middleware cannot do
what they need: `wrapModelCall` sees only the request and returns a `Completion`, `beforeAgent` and `afterAgent`
return only text, no hook reads thread state or writes a key, there is no way to add prompt content without storing
it, a retrying wrapper's discarded calls drop out of `usage`, and an output Block retracts the turn's messages but
keeps every other key the turn wrote. This slice gives the hooks state, writes, prompt sections and accounted model
calls, and makes a Block restore the whole turn. The specs are `KernelHooksSpec` (loop and runtime, `RunFailed`
usage included), the updated `MiddlewareStackSpec`, `AgentKernelHooksSpec` (traced usage of a failed run, the
builder's budget), and `SqliteKernelHooksSpec` in `llm4s-agent-checkpoint-sqlite` (updates and prior values through a
SQLite checkpoint and `recover`).

## Decisions

- **One context for the non-tool hooks: `ModelContext`.** It carries `run: RunContext` and `state: ThreadState`, the
  committed snapshot the hook's task read. It is a class, not a data type: it also holds the task's usage
  accumulator, reached through `accounted` and `recordUsage`. Tool wrappers keep `ToolContext`, which already has
  `run` and `state`.
- **`wrapModelCall(request, context: ModelContext)(next: ModelRequest => Result[ModelResponse]): Result[ModelResponse]`.**
  `ModelResponse` carries `completion` and `update`. A wrapper adds its writes with `addUpdate`, which keeps those of
  the wrappers inside it, and changes the completion with `withCompletion`, which keeps the update. The combined
  update applies innermost first. When a wrapper calls `next` more than once, only the response it returns counts:
  the updates of a response it discarded are never committed. A wrapper that answers without `next` (a cache) builds
  `ModelResponse(completion)`. The update commits with the model step's task, on every route the step takes
  (finish, tool batch, handoff, refused handoff batch).
- **`beforeAgent(input, context): Result[BoundaryResult]` and `afterAgent(answer, context): Result[BoundaryResult]`.**
  `BoundaryResult` carries `text` and `update`. Each middleware's update is its own: the text is threaded through the
  stack as before, and the updates are combined in the order the hooks ran. `beforeAgent`'s commits with the input
  task, so the turn's first model call sees it (rule 3); `afterAgent`'s with the finish task. A Block discards the
  updates of the blocking hook run, and a middleware question discards those of the run that asked, which runs again
  once answered.
- **Writes are checked per middleware.** Every hook's update may touch only *that* middleware's `writes`; the loop's
  keys stay forbidden, as `ToolLoop.build` already refuses a middleware declaring one. The stack attributes each
  update to the middleware that produced it - a `ModelResponse` records which wrapper added each part - and the loop
  checks each part as its hook returns - so a later hook's `Left`, a question, or a wrapper that discards the response cannot hide it - before it commits anything. An undeclared write fails the run with a `ValidationError`
  (`NodeResult.Fail`, the checkpoint `Running`), as a tool's undeclared update does; it is a bug, not a Block.
  Tool updates keep their existing rule (`tool.writes ++ stack.writes`).
- **`promptSections(context): Result[Vector[PromptSection]]`.** `PromptSection(id, text, cacheable)` is a
  growth-prone type (private constructor, `apply`, `with*`). Before each model step the loop collects every
  middleware's sections, in stack order, and appends them to the agent's system prompt - cacheable ones first, so a
  provider's prompt cache sees a stable prefix - in one system message, built for the request and never stored. The
  hook reads the snapshot only (rule 3). The sections are collected once per model step: every call a retrying
  wrapper makes sends the same ones. A duplicate id within one request fails the run, naming the id and its
  middleware. The bound is measured on what is sent: what the sections add to the rendered system prompt, the
  separators between them included, is capped by the agent's `maxPromptSectionTokens`
  (`AgentBuilder.withMaxPromptSectionTokens`, default 8192), estimated at four characters a token - a bound on size
  whatever the model's tokenizer, and whatever else is configured - and one request carries at most
  `LoopAgent.MaxPromptSections` (64) sections, so many empty sections cannot grow the prompt either. A request over
  either fails the run with a `ValidationError` naming every section's middleware, id and size: a configuration
  error, never truncated silently. Each middleware still caps its own.
- **An output Block restores the whole turn.** Every key the turn wrote - middleware keys and tool keys as well as
  messages, the active agent and the transfer - returns to its value before the turn's input. Only `usage` is kept.
  How: the turn's `TurnState` records, for each key the turn may write, a `PriorValue`: its value before the turn
  first wrote it, encoded with the key's codec, and the fingerprint (SHA-256 of the encoded value) of what the
  turn's own writes last left there (`priorValues`, one entry per key). The single-task steps record it from the snapshot they
  read: the input step for `beforeAgent`'s keys, the model step for its wrappers' keys and, when it fans out a batch,
  for every key the batch's tools and the stack's tool wrappers may write - so concurrent tool tasks never write
  the record (rule 1) and an approved or answered call later in the batch is covered. The finish step's Block
  update restores each recorded key that still holds what the turn left there (a key with no stored entry before
  the turn is removed), then removes the turn's messages and restores the agent and transfer as before. A key
  someone else wrote since - `updateState` while the turn waited for review - keeps that newer value: a Block undoes
  the turn's own writes, never another's. The fingerprint is taken where the turn's writes are known: the input and
  model steps from the state their own update produces, and `collect` - the batch's single join task - from the
  snapshot after the batch's tools committed, for the keys those tools and tool wrappers may write. A completed turn clears the record, so settled
  checkpoints do not carry it. The restore is a kernel operation, `StateOperation.Restore` (`private[graph]`): it
  sets a key's stored value without its update function, which has no update for "go back". Only a Block update
  uses it, and a Block update is never a pending write. A prior value that no longer decodes fails the run rather
  than leave the blocked turn's value in place.
- **Usage is counted by the loop (rule 11).** The `next` the loop hands to the innermost wrapper records every
  provider call that returns a completion in the task's accumulator, and announces it with a durable
  `ModelCallCompleted` whose `attempts` is that call's attempt number - so a retrying wrapper cannot lose a
  discarded call's cost. `context.accounted(client)` wraps a client so every `complete` and `streamComplete` through
  it, and `completeStructured`, which goes through `complete`, records its usage the same way (`attempts` 0); a hook
  hands it to a library that calls a model internally. `context.recordUsage(model, usage, cost)` records usage that
  arrives without a client call. A succeeding, suspending or blocking task adds the accumulator to `usage` with its
  own update. A task that commits nothing - one that fails, or one a cancel or a deadline cuts short (rule 10) - has
  its accumulator collected by the runtime, and the total goes on the run's terminal event:
  `RunFailed(message, usage)`, `RunCancelled(usage)` or `RunTimedOut(usage)`; `AgentTracing` adds it to the run's
  traced usage. A wrapper that calls `next` several times and then fails therefore loses none of its calls.
- **Guardrails call a model through the hook's accounted client.** `Guardrail.validate(value, context: ModelContext)`
  defaults to `validate(value)`; `LLMGuardrail` and `TopicBoundaryGuardrail` override it to make their judge call
  through `context.accounted(llmClient)`, and `CompositeGuardrail` passes the context to each guardrail.
  `GuardrailMiddleware` and `GuardrailReviewMiddleware` call that form, so every judge call is counted.
- **The completion a wrapper returns is not counted; the calls are.** Before this slice the loop counted the
  completion the stack returned and, for a question, the ones `next` returned. A wrapper answering from a cache, or
  returning a reviewed completion, made `usage.requestCount` count a request nobody sent. Now `usage` is exactly the
  provider calls made, through `next` or an accounted client.
- **No `beforeModel` / `afterModel`.** A model wrapper covers both. §5.6 is amended.

## Where the spec was wrong about the code

- **`AgentInput` already exists**: it is the turn's input (`query`, `history`), the graph's input type and stored in
  `MiddlewareQuestionRequest`. The hook result for both boundary hooks is `BoundaryResult(text, update)`; one type,
  since the two hooks return the same thing. §5.6's amendment text named `HookResult[A]`; it is corrected.
- **`context.recordUsage(TokenUsage)` "is kept" - there is no such method.** It is added, taking the model name and
  cost too, since `usage` is per model (`UsageSummary.byModel`) and a bare `TokenUsage` cannot be attributed.
- **`MiddlewareFailed` carries the `Throwable` of a throwing hook.** An over-budget or duplicate section set, and an
  undeclared hook write, are configuration errors of no one hook's throw; they fail the run with a `ValidationError`
  instead.
- **"Restore to the turn's settled checkpoint" cannot be read from the store.** `prune` with `maxCheckpoints = 1`
  may remove the settled checkpoint while a turn is suspended, and on a new thread there is none - restoring from it
  would then reset the thread, imported history included. So the restore point lives in the thread state
  (`TurnState.priorValues`), as `startAgent` and `startTransfer` already did. Messages keep their own restore,
  `RemoveTurn`, which keeps a new thread's imported history, as before.
- **`promptSections` returns `Result`.** A section usually reads the middleware's own key, and `ThreadState.get` is
  a `Result`.
- **The issue title's "taskKey"** is C4's `EffectKey`. `ModelContext.run.position` already carries the
  recovery-stable `(threadId, superstep, taskId)`; C1 adds no key type.

## Runtime rules

1. **One batch, one snapshot.** Hooks run in single-task steps (input, model, finish); only tool wrappers run in a
   batch, and their rule is unchanged. The Block's prior-value record is written only by single-task steps: the
   model step records the batch's keys before it fans out, so no two tasks of a batch write `turn`.
2. **An update function that fails, fails the run.** No new key update function can fail: `priorValues` lives in
   `TurnState`, a replace key; `Restore` sets a value. Every refusal - an undeclared write, a duplicate section, an
   over-budget request - is decided while the hook's task runs, never when its update is applied.
3. **An update becomes visible from the next superstep.** `beforeAgent`'s update commits with the input task and is
   in the snapshot of the first model call; `wrapModelCall`'s with the model task, visible to the tools of its batch
   and later. `promptSections` reads the snapshot only; a section a hook needs in the current request is passed
   through the request by the wrapper that made it.
4. **Hooks run at least once.** `recover` re-runs the input, model and finish tasks with no committed write, so their
   hooks run again. Their state updates are data, regenerated by the re-run; effects outside state are C4's.
   `run.position` gives the stable `(threadId, superstep, taskId)`.
5. **A Block retracts messages only, today.** Widened: an output Block restores every key the turn wrote, keeping
   `usage`, and only while the key still holds the turn's write, so an `updateState` edit made while the turn
   waited is kept. An input Block commits only a new thread's seed, as before, and now its usage. Effects outside state
   (host files, a sandbox, a memory store) are not restored; the backend slices document it.
6. **Every checkpoint is a full snapshot.** `priorValues` holds one copy of the pre-turn value of each key the turn
   may write, and a 64-character fingerprint, for the length of the turn, and is cleared when it completes; prompt
   sections are never stored.
7. **Restore decodes state through each key's codec.** `TurnState.priorValues` is defaulted, so a stored `TurnState`
   without it decodes. `RunFailed.usage` is defaulted, and `RunEvent`'s codec reads a `RunCancelled` or `RunTimedOut`
   stored as the bare string they were before they carried usage, so stored events decode. No node, key or graph-version input
   is added, so the structural fingerprint and the agent's version are unchanged and existing threads restore.
8. **Tenant.** Nothing new is shared across threads. A hook that uses a shared resource reads the tenant from
   `context.run.config.tenantId`.
9. **Durable events carry no message content.** `ModelCallCompleted` and the terminal events' `usage` carry counts
   and cost.
10. **A failed task commits nothing.** Its usage goes through the committing terminal path - `RunFailed`, or
    `RunCancelled` / `RunTimedOut` for a task cut short; a Block's and a suspension's through their own updates.
11. **Every model call is accounted.** The loop's `next`, accounted clients, guardrail judges through the hook's
    context, and every attempt of a task that commits nothing. Only a run that loses its claim records nothing, by
    design (§4.16): it commits nothing at all.
12. **Bounded, measured on what is kept or sent.** Prompt sections: what they add to the rendered prompt, separators
    included, by `maxPromptSectionTokens`, and their number by `LoopAgent.MaxPromptSections`, both at the model step.
    `priorValues`: one entry per key the family declares, never two copies of a key, each the size of the key's own
    value - bounded by that key's owner, as rule 12 requires of every key. Hook updates and `BoundaryResult` text
    are what they write - a middleware's own key, the stored query or answer - and C1 keeps no other copy of them;
    their bounds are the key's and the message's.
13. **Every named type exists or is defined here.** `ModelContext`, `ModelResponse`, `BoundaryResult` and
    `PromptSection` (`org.llm4s.agent.graph.middleware`), `StateOperation.Restore` (`org.llm4s.agent.graph`,
    private), `PriorValue` and `TurnState.priorValues` (`toolloop`), `RunEvent.RunFailed.usage`,
    `RunEvent.RunCancelled(usage)`, `RunEvent.RunTimedOut(usage)`, `Guardrail.validate(value, context)`.

## Limits

- An `updateState` edit made while a batch waits for approval, to a key that batch's tools may write, is taken as
  the turn's when the batch's `collect` fingerprints the key: a later Block undoes it with the turn. The tools'
  writes and the edit land in the same key between two loop steps, and the loop cannot tell them apart.
- A guardrail of your own that calls a model counts its calls only if it overrides `validate(value, context)` to
  call through `context.accounted`.

## Implementation plan

1. Tests first: `MiddlewareStackSpec` (attribution, `addUpdate` order, discarded responses), `KernelHooksSpec` (state
   through each hook, undeclared writes, `beforeAgent` visible to the first call, section order, duplicates and
   budget, retry usage, accounted clients, a Block restoring a middleware key and a tool key - also one a handoff
   source wrote - while keeping `usage`, `RunFailed` usage, old `TurnState` and `RunFailed` JSON decoding),
   `AgentKernelHooksSpec` (traced usage of a failed run), `SqliteKernelHooksSpec` (updates and prior values through a
   SQLite checkpoint and `recover`).
2. Kernel: `StateOperation.Restore`, `RunContext`'s task usage, `RunEvent.RunFailed.usage`, the runtime collecting a
   failed task's usage.
3. Middleware API: `ModelContext`, `ModelResponse`, `BoundaryResult`, `PromptSection`; the new hook signatures and
   `MiddlewareStack` attribution.
4. Loop: hook updates and their checks, prompt sections, accounting in `next`, `TurnState.priorValues` and the
   Block restore, write sets.
5. Built-in middleware, `AgentBuilder.withMaxPromptSectionTokens`, `AgentTracing`, tests across modules, guides,
   CHANGELOG and the migration guide.
