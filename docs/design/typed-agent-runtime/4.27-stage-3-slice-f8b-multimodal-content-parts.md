# 4.27 Stage 3 slice F8b: multimodal content parts ([#1913](https://github.com/llm4s/llm4s/issues/1913))

Part of the [Typed Agent Runtime design](../typed-agent-runtime-design.md), §4. Section numbers (§N.N) refer to that document and its [slice records](../typed-agent-runtime-design.md#slice-records). The slice is specified in the [Phase 3 spec](../../superpowers/specs/2026-10-13-phase-3-harness-design.md), "F8b"; the rules cited as "rule N" are that spec's "Runtime rules every slice must satisfy".

Until this slice a core `Message` carried one `String`, and a tool's `ToolOutcome.Success` one `ujson.Value` that `ToolLoop` rendered to that string. Nothing typed could carry an image or a document to a model. This slice gives user and tool messages content parts, tool results the same parts, and every chat provider a mapping for the parts it can send and a typed error for the rest.

## Vocabulary (rule 13)

- **`org.llm4s.media.MediaSource`** (module `llm4s-media`): where a part's bytes are.
  - `Url(uri: java.net.URI)`: the provider fetches it.
  - `Inline(bytes: IArray[Byte])`: the bytes themselves. Equality and hash are by content, and `toString` prints the length, never the bytes.
  - `ProviderFile(provider: String, id: String)`: a file already uploaded to the provider whose id is `provider` (`openai`, `gemini`), by that provider's id.
  - Pure data. `llm4s-media` keeps its rule of no I/O, no sniffing and no dependency, and nothing in it validates, because validation returns a `Result`, which is core's type.
- **`org.llm4s.media.DocumentMediaType`**, a `MediaType` family beside `ImageMediaType` and `AudioMediaType`: `Pdf` (`application/pdf`, category `Application`), `PlainText` (`text/plain`, `txt`), `Markdown` (`text/markdown`, `md`, alias `markdown`, MIME alias `text/x-markdown`), `Html` (`text/html`, `html`, alias `htm`) and `Csv` (`text/csv`), all `Text` category but `Pdf`. They are in `MediaType.all`, so `fromExtension`, `fromPath` and `fromMimeType` resolve them. No caller of those functions outside `llm4s-media` exists today, so adding the text types changes no behaviour.
- **`org.llm4s.llmconnect.model.ContentPart`** (core), `@Stable`: `Text(text)`, `Image(source, mediaType: ImageMediaType)` and `Document(source, mediaType: DocumentMediaType)`.
  - **Divergence from the spec:** the spec put it in `org.llm4s.model`. That package holds the model registry and metadata. `Message` is in `org.llm4s.llmconnect.model`, so `ContentPart` goes beside it.
  - `Image` and `Document` have private constructors and are built by `ContentPart.image(source, mediaType)` and `ContentPart.document(source, mediaType)`, which return `Result` (the bound, below). `Text` is public, as a blank text is a message-level check.
  - Its upickle codec is in core, in `ContentPart`'s companion: `{"type": "text", "text": ...}`, `{"type": "image" | "document", "mediaType": "<mime>", "source": {"type": "url", "uri": ...} | {"type": "inline", "data": "<base64>"} | {"type": "providerFile", "provider": ..., "id": ...}}`. A MIME type that is not an image (for `image`) or a document (for `document`) fails to read.
  - `ContentPart.kind` names a part for errors and logs: `text`, `image (url, image/png)`, `document (inline, application/pdf)`, `image (provider file openai, image/png)`.
- **Core depends on `llm4s-media`.** It did not before; `llm4s-image` was the only consumer. `llm4s-media` has no dependency, so `frozenDependencyCheck` is unaffected. `media` is not in `stabilityTierModules` (it cannot see `org.llm4s.annotation`, which is core's); its types are part of core's public API from now on and are frozen with it at 0.5.0.

## Messages

- `UserMessage(parts: Vector[ContentPart])` and `ToolMessage(parts: Vector[ContentPart], toolCallId: String)`, as `final class`es with `withParts`, equality by value, and **no extractor**. A case class would have kept `case UserMessage(content) =>` compiling with `content` now the parts, which code that only interpolates the binder (`s"$content"`) would not notice: it would send `Vector(Text(...))` as text, or drop the media silently. An `unapply` that kept binding the text was considered and rejected: old provider code would keep compiling and silently drop every media part, the failure this slice exists to prevent. With no extractor every positional pattern is a compile error, and the fix (`case u: UserMessage => u.content` or `u.parts`) is a choice made at each site. `UserMessage(text)` and `ToolMessage(text, toolCallId)` stay as the one-part constructors, so the ~400 call sites that build text messages do not change. `SystemMessage` and `AssistantMessage` keep text: no provider takes media from either.
- `Message.content` stays, as the text view: a user or tool message's text parts joined by `"\n"`. It is what token counting, logging, guardrails, the semantic cache and the Java facade read. A pattern `case UserMessage(content)` no longer compiles (above), so every provider had to decide what to do with a part. That is the point of the break.
- `validate`: a user or tool message must have at least one part, and is refused when every part is a blank `Text` (as a blank string was before).
- `toString` shows non-text parts as their `kind`, never bytes.
- `Message.hasMedia(messages)` says whether any message carries an image or document. The semantic cache uses it to pass such a conversation straight to the model: it embeds text, so two requests differing only in an image would otherwise share an answer.

## Tool results

- `ToolOutcome.Success(content: ToolContent, update)`, with `enum ToolContent { case Json(value: ujson.Value); case Parts(parts: Vector[ContentPart]) }` in `org.llm4s.agent.graph.tool`. A breaking change with no shim; `AgentTool.fromToolFunction` returns `Json`.
- `ToolLoop` turns `Json(v)` into one `Text` part, rendered as before (a non-blank string as itself, anything else as JSON), and passes `Parts` through unchanged into the `ToolMessage`. The provider maps them.
- The loop's `tool-results` key, which holds each call's result until the batch's `ToolMessage`s are appended, now holds `ToolResult(assistantMessageId, toolCallId, parts, isError)`.
- A `Parts` result is checked **when the tool runs** (rule 2), and becomes the call's error result for the model, not a run failure, when it has no part with content, or carries more than `ContentPart.MaxInlineBytes` of inline bytes in total (below).
- The live `ToolCallResult` event keeps `content: String`, now the result's text view. Media is not put on the event bus.
- F4's offload will act on text parts only; core's `ToolOutputCompressor` and `DeterministicCompressor` already do so in this slice: they rewrite a message's text parts (as one part, where the first was) and keep its image and document parts in place, and a message with media never joins a block of examples that `DeterministicCompressor` consolidates into one.

## Provider mapping

Each chat client maps every part it can send and fails the request, before anything is sent, with **`UnsupportedContentPartError(provider, part, role)`** (`org.llm4s.error`, `@Stable`, non-recoverable) for any other. It names the provider, the part's `kind` and the role (`user`, `tool`). Nothing is dropped and nothing is turned into text. A `ProviderFile` is sent only to the provider it names; any other client refuses it.

| Provider (module) | User message | Tool result |
|---|---|---|
| OpenAI, Azure OpenAI, Requesty (`llm4s-openai`, Chat Completions) | text; image `Url`, `Inline` (`image_url`, a data URL for inline); PDF `Inline` (`file`, `file_data`) and `ProviderFile` (`file_id`) | text only (the API takes text parts in a tool message) |
| OpenAI-compatible: generic, Z.ai, OpenRouter, Mistral, Cohere (`llm4s-openai-compatible`) | text; image `Url`, `Inline` (`image_url`) | text only |
| ... OpenRouter, in addition | PDF `Url`, `Inline` (`file`, `file_data`) | |
| ... Mistral, in addition | PDF `Url` (`document_url`) | |
| ... DeepSeek | text only (its chat API takes no media) | text only |
| Anthropic (`llm4s-anthropic`) | text; image (`png`, `jpeg`, `gif`, `webp`) `Url`, `Inline`; PDF `Url`, `Inline`; plain text `Inline` (a `text` document source) | the same blocks inside `tool_result` |
| Gemini API (`llm4s-gemini`) | text; image and document `Inline` (`inlineData`); a web `Url` and the provider's own `ProviderFile` (`fileData.fileUri`; a file by its Files API `uri`, or by its name `files/abc`, resolved against the base URL) | text only (`functionResponse.response`) |
| Vertex AI (`llm4s-gemini`) | text; image and document `Inline`; a `gs://` `Url` (`fileData.fileUri`, a Cloud Storage object); no `ProviderFile` (no file store) | text only |
| Ollama (`llm4s-ollama`) | text; image `Inline` (`images`, base64) | text only |
| Bedrock (`llm4s-bedrock`, Converse) | text; image (`png`, `jpeg`, `gif`, `webp`) and document (all five types) `Inline` (bytes) or `Url` with an `s3://` URI (`s3Location`) | the same, inside `toolResult` |
| watsonx.ai (`llm4s-watsonx`) | text; image `Inline` (a data URL `image_url`; the service takes no remote URL) | text only |

Notes on the table, as built:

- "Own `ProviderFile`" is the client's own provider id: an Azure client takes `ProviderFile("azure", ...)`, a Requesty one `ProviderFile("requesty", ...)`, Vertex AI `ProviderFile("vertexai", ...)`.
- A message of several text parts and no media is sent as one string, the parts joined by `"\n"`, by the OpenAI-compatible dialects (not every endpoint documents array content) and by Ollama; OpenAI and Anthropic send each text part as its own block. A one-text message encodes exactly as before everywhere.
- Each client checks the conversation it will send with `PartEncoding` before building the request (after the request transform, before any token exchange), so a refused part costs no round trip.
- anthropic-java 2.65.0 has file sources, but only behind the beta Files API header, so Anthropic refuses `ProviderFile`.
- Bedrock names documents `document-1`, `document-2`, ... in conversation order, as Converse requires a name, and refuses (with a `ValidationError`, before sending) a message that carries a document but no text, which Converse rejects.
- A `Url` the provider fetches itself (OpenAI, the OpenAI-compatible dialects, Anthropic, the Gemini API) must be `http` or `https` (`PartEncoding.isWebUrl`); Bedrock takes `s3://` only and Vertex AI `gs://` only. Any other scheme is refused before sending, rather than accepted and rejected by the provider.
- `PartEncoding.check` asks each client's partial function only `isDefinedAt`, so inline media is encoded once per request, when the request is built.

Media types a wire format cannot name (Anthropic's and Bedrock's image formats are fixed enums) are refused by the same error. A media type the wire format can name but a given model rejects is the provider's error, as it is for text.

`ProviderModuleChecks.assertContentParts(providerId, response, path)(supported*)(client)` sends each case of `ContentPartContract.cases` (a user image by URL, inline and as a provider file; a PDF the same three ways; an inline plain-text document; an image and a PDF in a tool result; another provider's file) to a `LocalProviderTestServer`. A case the module declares supported must succeed and put its payload (the URL, the base64 bytes, the file id) in the request; any other must fail with `UnsupportedContentPartError` and send nothing. Text in several parts must always be sent. Every chat provider module's spec calls it.

## Stored threads (rule 7)

- **Core's `Message` codec writes a user or tool message whose parts are exactly one `Text` in the old shape**, `{"type": "user", "content": ...}`, and any other as `{"type": "user", "parts": [...]}`. Its reader accepts both. So:
  - every message written before this slice, in any store (an agent checkpoint, a memory store, a saved conversation), reads as a one-`Text` message;
  - a text-only conversation serialises byte for byte as before, which keeps every `ThinkingReplay` binding made before the upgrade valid. A binding is a digest of the earlier messages' JSON, so a changed shape would unseal every stored turn's signed thinking, and a thread suspended mid tool-loop with Anthropic thinking would then be sent without the thinking its continuation needs.
- **`Messages.key`'s state and update codecs move to version 2.** Version-1 JSON is valid version-2 JSON (the reader takes the old shape), so the step from 1 is the identity. The bump is what makes a version-2 value, which may hold `parts`, fail on an older runtime with "version 2 cannot be read by a codec at version 1" instead of a decode error deep in a message.
- **`tool-results` moves to version 2** for both codecs, with a real step: each `ToolResult`'s `content` string becomes one `Text` part. A pending write of a batch that failed before the upgrade (rule 10 keeps it) migrates on `recover`.
- **The agent's `input` node** (`AgentInput`, whose `history` holds messages) and the parked continuations that hold an `AgentInput` need no step: their messages are read by core's reader, which takes both shapes.
- Tested on `text-only-thread.db`, a SQLite file written by `main` (656aa537) before this slice, with a completed turn and a failed batch whose pending `tool-results@1` write is kept: it restores, `recover` runs only the failed tool, and the thread continues with a new turn. `CheckpointFormatSpec` covers the steps on JSON.

## Bounds (rules 6 and 12)

- **An `Inline` part is at most `ContentPart.MaxInlineBytes` (5 MiB)**, checked by `ContentPart.image` and `ContentPart.document`, which return `Left(ValidationError)` above it. An overload takes a lower or higher `maxInlineBytes` for a caller that knows its provider's limit. Every checkpoint is a full snapshot (rule 6), so each retained checkpoint copies each inline part, base64-encoded (a third larger), for as long as the message stays in the thread. Larger media must be a `Url` or a `ProviderFile`; the Scaladoc and the guide say why.
- A `Url` must be absolute, and must not be a `data:` URI, which is inline bytes by another name and would escape the bound.
- **A tool result carries at most `MaxInlineBytes` of inline bytes in total**, checked by the loop when the tool runs, so a tool cannot put more into one result than one part could hold. A user message is built by the caller, part by part, and is not given a total: what it costs is the caller's to decide, and the agent's input is text.
- **A thread's messages hold at most `Messages.MaxInlineBytes` (20 MiB) of inline media in total**, and so does a batch's `tool-results`. The per-part and per-result bounds are measured per item: a thread gains messages turn after turn, a caller's imported history can hold many parts, and the calls of one batch each fit on their own but run concurrently on one snapshot (rule 1), so no check made when a tool runs can bound them together. Both keys' updates are therefore total and evict: an update that takes the key over the bound is applied, and then the oldest inline parts are each replaced by a text part naming what was removed (`[image (inline, image/png) removed: the thread keeps at most N bytes of inline media]`) until it fits. No run fails for it. A checkpoint therefore holds at most 20 MiB of inline media in `messages` plus 20 MiB in `tool-results`, base64-encoded. A core `Conversation` a caller passes to `LLMClient` is not stored by llm4s and is the caller's to size.
- The reader does not check the bound again. A stored part was admitted when it was built, and a thread must restore.

## Runtime rules

1. **One batch, one snapshot.** Unaffected: a tool's parts are its own result, written to `tool-results` under its own call; no check is made against other calls' results.
2. **Update functions are total.** `tool-results` and `messages` apply exactly as before. The checks on a `Parts` result (empty, over the bound) are made when the tool runs and become the call's error result; nothing is checked when the update applies.
3. **Visibility.** Unaffected: the batch's `ToolMessage`s are appended by the join, as before.
4. **At least once.** A tool that returns parts is re-run by `recover` like any other. Building a part is pure; there is no external effect to guard.
5. **Block retracts messages.** Media parts live only in messages, which `RemoveTurn` retracts, so an output Block retracts them too.
6. **Full snapshots.** Inline media is copied into every retained checkpoint, which is why it is bounded and why larger media must be a reference (above).
7. **Codec migration.** As "Stored threads": version 2 for `messages` and `tool-results`, the old shape read by core's reader, tested on a file `main` wrote.
8. **Tenant.** Nothing shared across threads is added. A `ProviderFile` id is the provider account's, resolved by the client's own credentials.
9. **No content in durable events.** No durable event changes. The only event that carries a result, `ToolCallResult`, is live, and carries the text view only.
10. **A failed task commits nothing.** A provider's `UnsupportedContentPartError` fails the model call before any request is sent; the model task fails as for any provider error, with no request cost to account.
11. **Every model call is accounted.** No model call is added.
12. **Bounded.** As "Bounds": each inline part, and each tool result's inline bytes in total.
13. **Every type defined.** `MediaSource`, `DocumentMediaType`, `ContentPart`, `ToolContent`, `UnsupportedContentPartError`, `ContentPartContract` and `ContentPartCase` are defined above, with their modules and codecs.

## Not in this slice

- The agent's input stays a `String` (`agent.run(query)`); a user turn with media is put into a thread through `run(..., history)` or by a tool. A parts input is follow-up work for the agent API.
- `SystemMessage` and `AssistantMessage` stay text. Audio and video parts, and model output parts (generated images), are not added.
- Token counting (`ConversationTokenCounter`) counts text parts only; an image's token cost is provider- and size-specific.
- The Java facade's `JMessage` exposes the text view; it gains no parts.

## Implementation plan

1. `llm4s-media`: `MediaSource`, `DocumentMediaType`; specs at 100%.
2. Core: `core` depends on `media`; `ContentPart` and its codec; `UserMessage`/`ToolMessage` parts, `validate`, `toString`, the `Message` codec; `UnsupportedContentPartError`; `PartEncoding`, a `private[llm4s]` helper the clients share (a client describes the parts it sends as a partial function, and a part it does not cover is the error); the compressors and the semantic cache. Specs first.
3. `llm4s-provider-testkit`: `ContentPartContract`, `assertContentParts`.
4. Each provider module, one commit each: the mapping, mapping specs, and `assertContentParts` in its module spec.
5. `llm4s-agent`: `ToolContent`, `ToolLoop`, `ToolResult`, the version bumps and step; every `ToolOutcome.Success` call site. `llm4s-agent-checkpoint-sqlite`: the fixture restore spec.
6. Java API, Kotlin tests, samples, docs: CHANGELOG, migration guide, the agents guide.
