# 4.61 Stage 5 slice P2: exit test, guide and parity matrix ([#2140](https://github.com/llm4s/llm4s/issues/2140))

Part of the [Typed Agent Runtime design](../typed-agent-runtime-design.md), §4. Section numbers (§N.N) refer to that document and its [slice records](../typed-agent-runtime-design.md#slice-records). Stage 5 spec: `docs/superpowers/specs/2026-10-20-stage-5-production-design.md`, "Exit criteria", "P2" and "Rules every slice must satisfy".

Slice P2 of [#2129](https://github.com/llm4s/llm4s/issues/2129), the last, after every other slice (4.50-4.60). It
proves the stage's exit criteria against the example service of P1 ([4.60](4.60-stage-5-slice-p1-example-service-and-a-three-instance-deployment.md)),
documents the result for users, compares it with LangGraph Platform and Deep Agents, and closes §6 row 5.

## What it adds

- `MultiMachineExitSpec` (`modules/it`, `org.llm4s.deploy`, `@Docker`): three `DeployServiceMain` processes on one
  fresh Postgres schema, one test per exit criterion.
- `docs/guide/agents/multiple-machines.md`, "Running agents on several machines": the store, the queue and workers,
  cancel and the busy-thread policy, tracing, metrics, retention, the example deployment, upgrades and limits. The
  durable-checkpointers guide and the agents index link to it.
- `docs/reference/agent-platform-parity.md`: the parity matrix.
- `typed-agent-runtime-design.md` §6: row 5 rewritten to what Stage 5 delivered, with the spec's exit criteria, and
  marked done; row 6, agent evaluation (#410).

No library code changes: the exit test passed against the merged slices as they are. The example service's demo `pause`
tool gains one gauge, `llm4s_demo_tool_calls_active` (`ExampleAgent.ActiveCalls`), so a client can tell a call has started.

## Decisions

**"Instance A" is the instance that executes the run, chosen by the queue, not by the test.** The criteria say both
"a run started through instance A is executed by whichever worker takes it" and "instance A is killed mid-run". Three
workers poll one queue and take with `FOR UPDATE SKIP LOCKED`, so which one takes an entry is a race the test should
not rig: forcing it (one fast poller and two slow ones, or workers that run different agent ids) would test a
deployment nobody runs, and a slow poller would also be too slow to recover the killed run. So the test always
submits through instance A, reads the entry's first attempt from the queue - its lease holder is the worker's label,
which is the instance's name, plus a random suffix - and then kills, streams, cancels and replays through instances
chosen relative to the executing one: the stream through one of the other two, the replay through the third, the
cancel through one that is not executing. It reports the roles it drew (`info`); over the local runs the executing,
recovering and cancelled instances varied from run to run.

**The trace is checked on the checkpoints, not on exported spans.** The example service builds its agent without a
tracing backend (P1), and the three processes are separate JVMs, so an in-process span exporter in the test would see
nothing; adding OpenTelemetry and a collector to the exit test would test the exporter, which `llm4s-observability-otel`'s
own specs already do (`OpenTelemetrySpanTreeSpec`). What makes a run one trace across machines is that every attempt
continues the same `TraceContext`: the queue entry stores the submitter's (`Submission.traceContext`), each attempt
passes it as `RunConfig.traceContext`, and every checkpoint the attempt commits records it (`Checkpoint.trace`). A
tracing backend derives every span id from that trace id and the run's identity (4.58), so it cannot place the two
attempts' spans in different traces. The test sends a fresh `traceparent` with the submission and checks that the
killed attempt's checkpoints (committed on the first machine) and the recovering attempt's (on the second) all carry
its trace id, and that the two attempts' lease holders are different instances.

**Mid-run means inside the tool call, as the tool itself reports.** The demo model's one tool call per turn takes
`LLM4S_SERVICE_TOOL_DELAY` (2 seconds here). The store cannot say a tool call has started: it records the call only
once it finished, and a committed model call asking for a tool says only that the tool is next - the run may still stop
at the boundary before it (Codex review). So the demo `pause` tool reports its calls in progress as a gauge,
`llm4s_demo_tool_calls_active` on its instance's `/metrics`, set as a call starts and ends (`ExampleAgent.ActiveCalls`;
the only change to the example service). The test waits until the instance holding the entry's latest attempt shows a
call in progress and the store holds no result for the call the model asked for, and only then kills, interrupts or
cancels. Each test has one run executing at a time, so the call in progress is that run's. That is a condition, not a
sleep, and leaves nearly the whole tool delay as the window, which is what makes the `Interrupt` criterion
meaningful: the started tool call must finish (`outcome = Succeeded`, the tool message says `paused`), the first run
must make no further model call, and its entry closes `interrupted` by the second.

**Short ttls by system property, inside rule 2.** Claims and leases last 4 seconds (renewed every second), so recovery
after `kill -9` takes seconds; the store's call and connection timeouts are 1 second each, so its bound (2 seconds)
stays inside `ttl - renewEvery` (3 seconds), as rule 2 asks. The worker polls every 200 ms, sweeps every second with a
3-second tombstone age, and the service's event stream rereads its entry every 500 ms. All are `-D` settings on the
process; nothing in the service changed.

**"No gaps or duplicates" is checked against the log, and replay byte for byte.** The live follower (through a
surviving instance) must have received events before the kill and more after; its sequence numbers must equal the
thread's whole event log as the store holds it, be consecutive, and come from exactly the entry's two attempts'
`RunId`s. The replay through the third instance is checked from five positions - `0`, the second event, the middle
(by `Last-Event-ID`), the last but one and the last - each giving exactly the later events, with data identical to
what the live stream carried.

**The delete is the kernel's, called from the test.** The example service has no delete endpoint (4.60), and the
criterion is about the sweep and its readers, not about HTTP. The test calls `RunSubmitter.deleteThread` over its own
connection to the schema - the same call a service's delete makes - and then lets the instances' workers sweep: the
reclamation is done by the services' scheduled sweep, not by the test. It checks the tombstone row is gone and the
store's reclamation mark has passed the old log, and that a reader resuming the old run's stream through another
instance is answered `ThreadDeleted` (4.53's documented answer, an SSE `error` event) before reclamation, after it,
and after a new thread has reused the id; the new thread numbers past the old log.

**The test JVM reads the schema as an operator's tool.** Entries' attempts (which instance held each), the thread's
event log and checkpoints are read through a `PostgresCheckpointer` the test opens on the same schema, after the three
services have migrated it. Everything a user would observe - submission, streaming, replay, cancel, thread state, the
`ThreadDeleted` answer - goes through the services' HTTP endpoints.

**One failure does not fail the rest.** Each test first restarts any instance an earlier test left dead, so a failed
kill test does not turn into five connection errors. The kill test itself restarts the killed instance under the same
name at its end, as a replacement pod would, and later tests run on three instances again.

**Parity matrix: sources and "where it went".** The matrix is capability by capability, from the spec's goals,
non-goals and Decisions 11, with LangGraph Platform's and Deep Agents' current documentation cited per row. Every gap
names its destination: a later stage (evaluation, Stage 6, #410), an issue to be opened from Decisions 11's deferred
list, the separate HTTP server project (Decisions 2), or out of scope (another database, an external durability
engine).

## Results

Run locally against Postgres 16 in Docker: 16 runs (the last 5 with the tool-start gauge), 6 of 6 tests passing in each, about 32 seconds a run after the
three processes are ready.

## Not in this slice

- The HTTP server product, a delete endpoint in the example service, or a tracing backend wired into it: the service
  stays P1's example.
- The deferred items of Decisions 11: each becomes its own issue, as the parity matrix lists.
