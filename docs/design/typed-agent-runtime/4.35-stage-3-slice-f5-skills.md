# 4.35 Stage 3 slice F5: Agent Skills ([#1909](https://github.com/llm4s/llm4s/issues/1909))

Part of the [Typed Agent Runtime design](../typed-agent-runtime-design.md), §4. Section numbers (§N.N) refer to that document and its [slice records](../typed-agent-runtime-design.md#slice-records). Phase 3 spec: `docs/superpowers/specs/2026-10-13-phase-3-harness-design.md`, "F5".

Slice F5 of [#1901](https://github.com/llm4s/llm4s/issues/1901), a feature slice on C1 (§4.22: `ModelContext`,
`promptSections`) and C3 (§4.25: `FileBackend`, `FileContext`, `VPath`). It adopts the
[Agent Skills standard](https://agentskills.io/) (§9 "Skills and memory distinction"): a skill is a folder holding a
`SKILL.md` whose YAML frontmatter names and describes it. `SkillsMiddleware` finds the skills under a list of
source folders through a `FileBackend`, puts each one's name and description in one prompt section, and leaves
loading to the model: it reads a skill's `SKILL.md` and resources with F1's `read_file`, so no tool is added.
Everything is in `llm4s-agent`, package `org.llm4s.agent.harness`, `@Experimental`, opt-in.

F6 (instruction memory, §4.36) has the same shape - documents read through a backend once per run, bounded per
document and in total, cached by run, reported in a durable event, shown as one prompt section - so the mechanism
is built here once, as a small `private[harness]` piece (`RunDocuments.scala`), and F6 reuses it.

The specs are `SkillFrontmatterSpec` (the parser), `SkillsMiddlewareSpec` (through the tool loop: discovery,
section, bounds, events, caching, recovery) and `RunDocumentsSpec` (the shared piece).

## API

- `final case class Skill private (name, description, path: VPath, allowedTools: Vector[String], license:
  Option[String], metadata: Map[String, String])`, with `apply` and `with*` setters (growth-prone: the standard
  may add fields). `path` is the skill's `SKILL.md`. `allowedTools` is parsed - from the standard's
  space-separated string, or a flat list - and exposed, not enforced in Stage 3.
- `Skill.parse(path: VPath, content: String): Result[Skill]`: the frontmatter of one `SKILL.md`, or a
  `SkillFormatError`.
- `final case class SkillFormatError(path: VPath, line: Int, problem: String) extends LLMError`: the file and the
  1-based line, and a problem stated in the parser's own words (it never quotes the file).
- `final class SkillsMiddleware(sources: Vector[VPath], backend: FileBackend, maxSkills = 20,
  maxDescriptionChars = 256, maxSectionTokens = 2000, maxScanned = 100, maxCachedRuns = 64, id =
  MiddlewareId("skills"))`. Every limit must be at least 1 (`require`). `skills(context: ModelContext)` returns the
  skills the run lists, through the run's cache.
- `HarnessEvents.DocumentsReported` (`harness.documents_reported`, v1), durable:
  `DocumentsReported(middleware: String, issues: Vector[DocumentIssue], omitted: Int)`, with
  `DocumentIssue(path: VPath, kind: DocumentIssue.Kind, line: Option[Int], detail: String)` and
  `Kind = NotListed | Cut | Malformed | Unreadable | Shadowed | NotScanned`. Shared with F6.

## Decisions

- **Discovery.** On a run's first model call, for each source in order: `ls(source)`; each directory entry `d`
  is a candidate, `d/SKILL.md` read and parsed. A missing source and a directory without `SKILL.md` are skipped
  silently: a user-scope source need not exist. At most `maxScanned` entries are examined across all sources; a
  source with more is reported `NotScanned`. A later source's skill of the same name replaces an earlier one (the
  project overrides the user), which is reported `Shadowed`. The skills are listed in source order, then path order.
- **What is listed.** At most `maxSkills`, each `- name: description (path)`, the description with line breaks and
  control characters replaced by spaces and cut at `maxDescriptionChars` code points. The section - its guide
  line included - is at most `maxSectionTokens` estimated tokens (C1's estimate, one token per four characters,
  now shared as `PromptSection.estimatedTokens`), so it fits the agent's `maxPromptSectionTokens` on its own
  terms. A skill past either limit is reported `NotListed`; an entry is listed whole or not at all. The section's
  id is the middleware's id and it is `cacheable`: it is the same for every request of a run. With no skill, there
  is no section.
- **The frontmatter parser** is written for the job, with no YAML dependency. The file starts with a `---` line
  (a BOM is dropped) and the frontmatter ends at the next. It accepts `key: value` lines whose value is a plain
  scalar (a ` #` comment dropped), a double- or single-quoted string, or a flow list `[a, "b"]` of scalars; a key
  with no value followed by a block list (`- item`) or, for `metadata` only, by one level of indented
  `key: scalar` entries. Blank and `#` lines are skipped. Anything else - a block scalar (`|`, `>`), a flow map,
  an anchor, alias or tag, a tab indent, a nested list or map, a continuation line, a duplicate key, a key that
  is not `[A-Za-z0-9][A-Za-z0-9_.-]*` - is a `SkillFormatError` naming the file and line. Then the standard's
  rules: `name` and `description` are required, non-empty strings; `name` is at most 64 characters of
  `[a-z0-9-]`, without a leading, trailing or doubled hyphen, and equals its folder's name; `license` is a
  string, `allowed-tools` a string or a list of strings, `metadata` a map of strings. Other keys are parsed
  (so a malformed one is still an error) and ignored. Only the frontmatter is read: at most 16 KiB
  (`Skill.MaxFrontmatterChars`), and a file whose frontmatter does not close within it is malformed.
- **A malformed skill is skipped, not fatal.** It is reported `Malformed` with its line and problem; the run goes
  on. A backend refusal of one file or source (binary content, a source that is a file) is `Unreadable`, named by
  the refusal's kind only. Any other backend error - a store that failed - fails the model step, as a backend
  error fails a tool call (`BackendRefused.toolOutcome`): the task commits nothing and `recover` reads again.
- **Reading through the backend.** The middleware reads with `FileContext(run, state)`: a hook's context, the
  step's committed snapshot. A `StateFileBackend`'s skills come from the thread's files - the checkpoint, after a
  recovery; a store or resolved backend's from its store, chosen per run (rule 8). The middleware's `writes` are
  the backend's, so a state backend's key is registered with the graph even when no file tool is (the middleware
  itself never writes it). Pass the same backend, or the same composite, that the agent's file tools use, so the
  paths in the section are the paths `read_file` takes.

### The shared piece: `RunDocuments.scala`

`private[harness]`, used by `SkillsMiddleware` and by F6's `InstructionMemoryMiddleware`:

- **`RunCache[A](maxRuns)`**: a value computed once per run incarnation and kept in a bounded LRU of `maxRuns`
  entries. The key is `(threadId, runId, fencingToken)`: a `RunId` can be reused (`RunConfig.withRunId`, a recovery
  under the same id), so the id alone would let a recovered run reuse a stale read, or two threads given one id
  share one; the claim's fencing token is new for every run that claims the thread (as `RunScope` keys a run,
  #1918). So a run recovered or resumed - in this runtime or a fresh one - reads the backend again. The value
  is computed under a per-entry lock, so the concurrent model steps of one run read once. A failed read is not
  cached. The cache also owns the report (below).
- **`RunDocuments[A](id, maxRuns)(read)`**: a middleware's documents through `RunCache`: `read(ctx, report)` is
  given a hook's `FileContext` and a `Report`, and returns the value and the section's text; `sections(context)` is
  the section, cacheable, with the middleware's id, and the report goes out as `DocumentsReported`. Both middleware
  are this plus their own `read`.
- **Reporting.** A durable event commits with the task that emits it and is discarded if that task fails (rule
  10). The cache remembers which task produced the value and emits its report then, and again whenever that task
  runs the hook again - a node retry after a failed attempt, whose events were discarded. A later task of the same
  run emits nothing: it runs only after the reporting task committed. A failed run's recovery is a new
  incarnation, so it reads and reports again. The report is thus committed at least once per run that reached a
  model call, and at most once per committed task of it.
- **`DocumentText.read(backend, path, maxChars, ctx, stop)`**: a file's text, page by page (`read` with an offset),
  at most `maxChars` characters, cut on a code-point boundary and flagged when cut, stopping early at a line
  `stop` accepts; `None` when the file does not exist. The bound is checked as each line is added, so nothing over
  it is kept.
- **`SectionText(maxChars)`**: builds a section within `maxChars` characters, adding a part whole or not at all, or
  cut with a marker that is counted in the bound.
- **`Report`**: collects `DocumentIssue`s, keeping at most 32 and counting the rest in `omitted`, so the event is
  bounded whatever a source holds.

### Changes to C3 and F3

- **A missing file is typed.** `read`, `edit` and `delete` of a file that does not exist were refused as plain
  `Refused`, so only `ls` told a caller "absent" from any other refusal. They are now `BackendRefused.Kind.NotFound`
  in every C3 backend (`FileTree.fileOf`, `deletable`, `StoreFileBackend.delete`), and `FileBackendContract` checks the
  kind for `read`, `ls`, `edit` and `delete`, so a backend of one's own is held to it. A missing skill or instruction
  file is skipped by that kind.
- **One estimate, one cleaner.** C1's token estimate is `PromptSection.estimatedTokens` (used by the loop's budget and
  by this slice's bounds), and the control-character cleaning and code-point clipping F3 wrote for its plan section
  are `DocumentText.oneLine` and `clipMarked`, used by both.

## Where the spec was imprecise

- **`maxSectionTokens` and `maxScanned` are added.** The spec bounds the count and each description. A path is up
  to 1024 bytes, so `maxSkills × maxDescriptionChars` does not bound the section; `maxSectionTokens` does. Naming
  "the rest" needs a bound on how many are looked at, and each candidate costs a read: `maxScanned` bounds both.
- **Names in the event are paths.** "The rest are named": by the `SKILL.md` path, never the frontmatter's name or
  description, which are file content (rule 9).
- **"Cached by run id"** is cached by run incarnation, for the reason above.

## Runtime rules

1. **One batch, one snapshot.** Skills are read from the snapshot of the run's first model step, once; nothing is
   checked against it, and the middleware writes nothing. A skill edited during a run shows from the next run
   (tested: an edit through `updateState` mid-thread is seen by the next run, not the current one).
2. **Total updates.** No update function: the middleware writes no key.
3. **Visibility.** The section is built in the request it is for (`promptSections`), so the first model call sees
   the skills (tested).
4. **At least once.** Reading is idempotent and performs no external effect. The report is at least once per run
   (above); a retried task reports again, a later task does not (tested: a failing first attempt, then recover).
5. **Block.** Nothing to retract: no key is written. A state backend's files are restored by C1 as the file tools'
   writes, unchanged by this slice.
6. **Full snapshots.** Nothing is added to a checkpoint.
7. **Codecs and structure.** No key is added beyond the backend's own; adding the middleware changes the agent's
   version by its middleware id (§4.29), as any middleware does. `DocumentsReported` is a new event at v1 with
   derived codecs (tested round trip).
8. **Tenant.** The backend is the tenant boundary: a resolved backend is chosen per run by its tenant. The cache is
   keyed by run incarnation, which has one tenant, so no read of one tenant's run is served to another.
9. **No content in durable events.** `DocumentsReported` carries paths, kinds, line numbers and the parser's own
   problem text; never a name, description or line of a file (tested on the stored event).
10. **A failed task commits nothing.** A failed step's report is discarded with it, and the next attempt or the
    recovered run reports again (tested).
11. **Every model call accounted.** Not applicable: no model call.
12. **Bounded.** The section is at most `maxSectionTokens` (by construction, tested); at most `maxSkills` skills;
    each description at most `maxDescriptionChars`; at most `maxScanned` entries examined and as many frontmatter
    reads, each at most 16 KiB kept; the event at most 32 issues; the cache at most `maxCachedRuns` entries, each
    holding at most `maxSkills` skills (each from at most 16 KiB of frontmatter) and one section. Every bound is
    checked as the text is read or added, before anything over it is kept.
13. **Types.** `Skill`, `SkillFormatError`, `SkillsMiddleware`, `DocumentsReported`, `DocumentIssue` and its `Kind`
    are defined here, in `llm4s-agent`, with their codecs where they are stored or sent.

## Not in this slice

- Enforcing `allowed-tools` (Stage 3 exposes it).
- A host-directory backend (#1964): with one, a skill folder on disk may change between a run and its recovery;
  the recovered run sees the files as they are then. A state backend's skills come back with the checkpoint.
- A `read_file` tool: F1 (#1905).
